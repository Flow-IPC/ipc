# Now we test batch-receiving.  Unlike the above, which more comprehensively tests APIs on
# individual varieties of {Native_handle|Blob}_{sender|receiver} and then also
# bundling-channels (themselves implementing those concepts), in this case we avoid all that
# tedium by just using bundling-channels; first a POSIX MQ + socket-stream bundle; then
# repeat the exact same steps for a bipc MQ + socket-stream bundle.

# So: POSIX MQ is the MQ pipe; and socket-stream is the sockets pipe.  We typically
# test them in parallel (sometimes we might need to do it in series).  The socket-stream
# white-boxily (at least if available as in moderm Linux) uses native OS batch-receiving
# (SOCK_SEQPACKET + recvmmsg() in Linux), while the MQ stream emulates batch-receiving as
# a series of single-receives.  The black-box behavior is the same, as you'll see.
# The only exception to this is that an MQ has a small out-buffer (10 msgs) which limits how
# much stuff we can load onto "the wire" and have the opposing side batch-read all in one go.
# When this is relevant, we comment on it (as of this writing there's one spot).
# (Spoiler alert: Just keep in mind: 1 user message = 1 MQ raw message; but 1 PING (or graceful-close)
# = 2 MQ raw messages.  So, e.g., 5 PINGs in a row would fill the out-queue, and... etc.
# It's not some catastrophe; it just means a batch might be limited in size, and... etc...
# so we must have the proper expectations on the receiving side.)

# What's left?  We've covered realistic errors except OS-graceful-close (which isn't really *that*
# realistic (typically opposing side would issue Flow-IPC-graceful-close via end_sending()), but let's
# say that is still TODO).  Let's consider how a non-error RECV_...BATCH into N-batch can end-up
# (where N>1, as N=1 is a degenerate case that simplifies things; let's focus on non-simplified).
# Consider also that each raw in-message on "the wire" is either a PING or a MSG (user message).
# (In our context it cannot be an incomplete message: For the Native_socket_stream protocol there's no
# such thing, as message<=>dgram; for MQ protocol it is possible -- CONTROL message, then would-block --
# but triggering it without instrumenting the code is ~impossible; but perhaps a TODO to instrument it.)
# Also for this discussion consider a batch-receive to be "really" just a series of single-receives.
# (The MQ algorithm will do just that a/k/a batch-receive emulation.  The N_s_s algorithm will use an
# actual native batch-receive, if available (as in modern Linux), but ultimately that still conceptually
# performs single-receives albeit in the kernel.  So in our context we can/should still think of it that way
# and then leave it to Flow-IPC to properly wrangle the native-batch-receive calls; after all that's
# functional testing.)  So then here are the possible events in a single batch-receive Flow-IPC API call:
#   - MSG (got user message; but after recording it in batch, 1+ slots remain; must read again);
#   - MSG-FULL (got user message; but after recording it in batch, 0 slots remain; done);
#   - PING (got auto-ping; throw it out; must read again);
#   - BLK (got would-block; done).
#     (Native batch-receive can yield <N in-dgrams which also implies BLK... but again, we're ignoring
#     native batch-receiving and are discussing it as what it reduces to: single-receives the last of
#     which yields BLK.)
# Now, of these, the exactly one of exactly the following ends any given batch-receive:
# MSG-FULL, BLK.  Have we covered both of these?  Yes, we have, in some form.  However we should cover
# varieties of each.  We've covered for sure the following sequences (X+ means X 1 or more times; X* means
# X 0 or more times) -- not every form of each but good enough probably:
#   - [MSG*, BLK];
#   - [MSG+, MSG-FULL];
#   - [{MSG or PING}*, PING, MSG*, MSG-FULL];
#   - [{MSG or PING}*, PING, MSG+, BLK].
# Closer to English: the latter 2 = sequence involving PINGs but a PING is not immediately followed by BLK;
# the former 2 are vanilla PING-less sequences.
#
# So that leaves:
#   - [{MSG or PING}*, PING, BLK].
# which can be broken down into:
#   -1- [PING+, BLK];
#   -2- [{MSG or PING}+ with at least one MSG in there, PING, BLK].
# Indeed, white-boxily speaking:
#   - The native-batch-receive-using algorithm (the sockets pipe in our setup here) has tricky logic about
#     throwing out PINGs and then potentially trying again, since if the last nb-read filled the batch,
#     the thrown-out PINGs free-up space to try again.  We've tested it when PING is *not* the last thing
#     on "the wire," but not if it is; what if the tricky algorithm breaks?  Test it.
#   - The batch-receive emulation (the MQ pipe in our setup here) is not tricky in that sense, and likely
#     if PING-not-last sequences work, then so do PING-last ones... but why chance it?  Test it with the
#     same sequence(s) as for the preceding bullet point.
# Thus we will now try (for each pipe type as usual) varieties of -1- and -2-.
