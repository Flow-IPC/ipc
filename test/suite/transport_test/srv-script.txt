# Timeout notes:
#
# - There are very tight timeouts below -- in "microseconds" -- and the idea is to ensure
#   it doesn't block at all in situations, e.g., where we know there are N messages queued-up
#   locally at that point.  However the actual time depends on computer speed, and on slower machines
#   like default GitHub runners it can take longer than one experiences in a powerful lab machine.
#   We are not benchmarking here or perf-testing, so to avoid false failures we use a less tight
#   timeout that's still in the microseconds.  So 50usec is realistic usually, but we use 500usec.
# - Moreover... particularly in open-source automated CI/CD pipeline... we sometimes run these
#   tests (1) on slow machines *and* (2) while compiled with run-time sanitizers (ASAN, MSAN, etc.),
#   some of which slow-down the code by up to, like, 5x.
#   So bottom line is some of the below (e.g., 15ms) will look pretty generous even for slower machines;
#   but the *SANs are the reason it is like that.  TODO: Consider varying this depending on build type (via CMake
#   build).  That said, again, we are not benchmarking or perf-testing here; timeouts here are to ensure stuff
#   does not hang for seconds mainly.

# Send ping immediately, then time sends around subsequent auto-pings; cli should receive the actual
# messages (auto-ping occurs without user knowing).
#   PING/.5s/<665>/<664>/<663>/1s/PING/.5s/<662>/1s/PING/.5s/<661>
#   Total time = 3 * .5 + 2 * 1 = 3.5s.
#
# Subtlety: Originally we wanted to do a longer, more even thing like
#   PING/.5s/<665>/1s/PING/.5s/<664>/1s/PING/.5s/<663>/1s/PING/.5s/<662>/1s/PING/.5s/<661>
# and for the sockets pipe that's totally fine.  For the MQ pipe, though, it creates a race that -- while
# entirely reasonable for production use -- means which of the 2 situations will actually happen for us;
# so at least we can't know what to script in cli for this part (in fact: I (ygoldfel) observed that the
# race shook out one way when cli had TRACE+ logging but another with INFO; the timing made the difference).
# Specifically: In MQ protocol each user message = 1 raw msg; but each PING = 2 raw msgs (0-length CONTROL
# msg; then a particular small PING-indicating msg).  So the msgs in range [PING, <662>] above are intended
# to end up in a single receive-side 4-batch: 665/664/663/662 (with interleaved PINGs getting ignored).
# But an MQ has an out-buffer max-size of 10 raw msgs; however [PING, <662>] has 4 PINGs (8 raw msgs) and
# 4 user msgs (4 raw msgs); that's 12 which would cause send-side would-block (our side) with the msgs
# in excess of 10 getting queued within Flow-IPC user-land.  The race is then on: cli pops a raw msg;
# srv in background detects it (epoll() for POSIX, special thread + pipe + epoll() for POSIX) and
# dequeues the previously-enqueued-from-would-block item(s) and sends it or them; whether this is delivered
# before cli reaches receive-side would-block = the race.  So cli might see a 4-batch as intended; or
# a 3-batch.  (Please realize that the latter is not a functional bug; how close-together-in-time in-messages
# get subdivided into in-batches is always a matter of timing.  A proper receiver would simply get the
# 3-batch and kick-off a new async-receive -- which would simply wake up almost immediately and get the
# slightly-straggling 1-batch.  However in a test script we have to be precise; can't just give it both
# possibilities. ...So, to sum up, we cover pretty much the same stuff we intended either way, and in less
# time this way, and we need not have differing timings/payloads for the sockets pipe versus the MQ pipe.
