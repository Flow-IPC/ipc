44/**
45 * Wrapper around jemalloc. This is a thin wrapper around the jemalloc API: used by SHM-jemalloc for its internal
46 * impl purposes but available for direct end user calls as well.
47 *
48 * ### Purpose ###
49 * It is usable directly as a small jemalloc wrangler. That is, it can make easier some of the more advanced
50 * activities, like working with custom-made arenas, including the surprisingly tricky business of destroying
51 * one safely. The stats-dump helpers like stats_dump_to_string() and stats_dump_to_ostream() are potentially
52 * nice too. (However they're also available through Ipc_arena::info_dump().) Last but not least, using this
53 * wrangler instead of direct jemalloc-API calls can avoid certain jemalloc landmines not yet fixed as of
54 * jemalloc-5.4.0 (see below).
55 *
56 * It won't block access to the actual jemalloc API.
57 *
58 * That said, the main purpose of its existence is for the SHM-provider SHM-jemalloc (see ipc::shm for overall
59 * intro to Flow-IPC's SHM-providers) to implement its services. For example Ipc_arena::construct() and
60 * Ipc_arena::allocate() will use Memory_manager::allocate(), while Ipc_arena::create() will create_arena()
61 * while hooking up its SHM-wrangling extent hooks that would execute as part of allocate() at times.
62 *
63 * The public access to these goodies seemed worthwhile as well, so we made it user-facing.
64 *
65 * @see also Thread_cache which provides a related, and fairly sophisticated, wrangler of the jemalloc tcache
66 * system. How to properly use the jemalloc tcache feature is not necessarily obvious, especially so if
67 * custom arenas with arbitrarily overlapping finite lifetimes are involved. Things are prone to crash --
68 * and not necessarily right when one does the wrong thing but, in some scenarios, later.
69 *
70 * ### SHM-jemalloc versus direct use of jemalloc ###
71 * Using jemalloc directly ("directly" in this case includes calls through Memory_manager) is possible with or
72 * without using SHM-jemalloc (centered on Ipc_arena) in parallel. As far as conflicts of using jemalloc
73 * directly versus SHM-jemalloc in parallel:
74 * - SHM-jemalloc [de]allocates() only through jemalloc-arenas it creates/destroys/manages by itself; never
75 * through the default arenas (i.e., it would not do a regular jemalloc-`malloc()` but rather always specifies
76 * some arena ID it itself maintains). This holds whether or not jemalloc is also your default
77 * `malloc()`/`free()`/`new`/`delete` for regular heap purposes.
78 * - Certain *global* (as opposed to per-arena) jemalloc config options are required for SHM-jemalloc to work
79 * properly. In some cases this is something we enforce programmatically: by emitting an error
80 * if something is set wrong (best-effort). Otherwise we assume the default/common setup is what
81 * is in effect and proceed under that assumption (see below `todo`). As of this writing the checking/emission
82 * occurs in Ipc_arena::create().
83 *
84 * @todo While the current SHM-jemalloc impl is thought to play nicely with other parallel jemalloc use (such
85 * as for vanilla heap allocation) -- with all allocation segregated into separately maintained jemalloc-arenas and
86 * with only very few enforced global option-setting requirements -- we should methodically explore
87 * and document what exactly SHM-jemalloc requires of the jemalloc config (both compiled-in and dynamically
88 * settable options). Things are OK given a standard jemalloc build, within a fairly wide (calendar-wise)
89 * version range, and we check some (a small # of) global settings we know we require, but a methodical analysis
90 * in the guts of SHM-jemalloc might yield more and save users some pain.
91 *
92 * ### Stats-dump versus arena creation/destruction ###
93 * We offer a thin wrapper for jemalloc's stats-dump-to-string dump feature (`malloc_stats_print()`):
94 * stats_dump_to_ostream(), stats_dump_to_string(), log_stats_dump(). It turns out that `malloc_stats_print()`
95 * is likely to crash (abort with a message like `<jemalloc>: Failure in xmallctlbymib()` and variations), if
96 * concurrently an arena is being destroyed or (conservatively speaking) created.
97 * (This is not fixed, or counted as a bug, as of jemalloc-5.4.0 (9/2026).)
98 *
99 * SHM-jemalloc works around it (internally by using a process-wide mutex), so as long as one uses our APIs
100 * (Flow-IPC generally for SHM-jemalloc arena control as needed, naturally; Ipc_arena::info_dump() or
101 * `Memory_manager::*stats_dump*()` for stats-dumping), one is safe from this problem. Just be warned that using
102 * these jemalloc APIs directly (for whatever reason) can lead to trouble, as direct calls will not know to
103 * collaborate with Flow-IPC's use of the internal mutex; and Flow-IPC may itself create/destroy arenas and
104 * dump stats at various times.
105 */

111 /**
112 * Wrapper around extent hooks, which are callbacks that can be instituted in jemalloc per arena. The
113 * prescribed usage is to implement desired callbacks that execute the implementation within the creating
114 * object (arg `owner` to ctor). The `extent_hooks*` callback parameter can be cast to a pointer of this type
115 * to retrieve the owner of the callback for execution in that class object's context.
116 *
117 * So to jemalloc, which is provided `this` as cast to `extent_hooks_t*`: It sees a table of free/`static`
118 * functions of yours and calls the appropriate one depending on the event (e.g.: new extent needed). (Next to
119 * that is stored the value `owner` given to ctor, but jemalloc does not know or care.) Each
120 * of those functions is given the `extent_hooks_t*` plus the hook-specific args; so the function can then
121 * -# take `extent_hooks_t*` and cast it to `Extent_hooks_wrapper<T>*`;
122 * -# call `->get_owner()` on that which gets the aforementioned stored `T*`;
123 * -# on that, call the appropriate method (e.g., one that handles "new extent needed") of T, passing it
124 * the rest of the args following the `extent_hooks_t*` arg.
125 *
126 * @tparam T
127 * Any type; see get_owner().
128 */
129 template<typename T>
130 class Extent_hooks_wrapper :
131 public extent_hooks_t
132 {
133 public:
134 // Constructors/destructor.
135
136 /**
137 * Constructor.
138 *
139 * @param extent_hooks
140 * The set of callback functions.
141 * @param owner
142 * See get_owner().
143 */
144 Extent_hooks_wrapper(extent_hooks_t&& extent_hooks, T* owner);

149 * Returns the value `owner` as given to ctor earlier.
150 * @return See above.
151 */
152 T* get_owner() const;

172 /**
173 * Allocates uninitialized memory by using jemalloc's vanilla `malloc()` implementation.
174 *
175 * This may use an automatically determined thread cache, transparently.
176 *
177 * A jemalloc-arena is internally chosen from jemalloc's own arena set, also transparently.
178 *
179 * @note If used in an STL-compliant allocator, proper behavior on null return from this is to throw an exception
180 * (such as `std::bad_alloc`).
181 *
182 * @param size
183 * The allocation size which must be greater than zero.
184 * @return Upon success, a non-null pointer to the base address of the allocation; otherwise, null.
185 */
186 void* allocate(size_t size) const;

189 * Allocates uninitialized memory, in the specified jemalloc-arena, without the use of a thread cache.

195 * @param size
196 * The allocation size which must be greater than zero.

203 /**
204 * Allocates uninitialized memory, in the specified jemalloc-arena, with the (potential) use of the specified
205 * thread cache.
206 *
207 * @note If used in an STL-compliant allocator, proper behavior on null return from this is to throw an exception
208 * (such as `std::bad_alloc`).
209 * @see Thread_cache class doc header for a description of how jemalloc tcache works. Using this API form,
210 * without knowing that information or equivalent, may lead to confusing and undefined behavior.
211 *
212 * @param size
213 * The allocation size which must be greater than zero.
214 * @param arena_id
215 * The jemalloc-arena ID.
216 * @param thread_cache_id
217 * The thread cache ID with which to associate the allocation.
218 * jemalloc requires that a given tcache is not used by more than one thread concurrently; a stronger (not
219 * strictly required but, informally speaking, convenient) rule is that the mention of a given tcache be
220 * restricted to the thread in which it was created.
221 * All in all: suggest using class Thread_cache to manage these.
222 * @return Upon success, a non-null pointer to the base address of the allocation; otherwise, null.
223 */
224 void* allocate(size_t size, arena_id_t arena_id, tcache_id_t thread_cache_id) const;

308 /**
309 * Writes a broad, raw, process-wide jemalloc statistics dump (all arenas) to `os`. Thin wrapper around
310 * jemalloc `malloc_stats_print()`. For curated, typed, per-Flow-IPC-arena stats use
311 * jemalloc::Ipc_arena::memory_manager_stats() instead; this dump is the complementary "everything jemalloc
312 * knows" firehose of information.
313 *
314 * The output ends in a newline. No bracketing text is added by us: it all comes from jemalloc. (OK, fine,
315 * for Stat_format::S_JSON we add a newline at the end.)
316 *
317 * If the linked jemalloc was built without statistics support (a configure-time option, `--disable-stats`,
318 * reported at runtime by the read-only `config.stats` option), the output is still well-formed and non-empty.
319 * Roughly, it'll include at least things like jemalloc version + build config + settings but will
320 * omit per-arena runtime statistics (alloc counts/bytes, bins/large/extents/mutex).
321 *
322 * @note Relatedly: our curated stats-accessor, Ipc_arena::memory_manager_stats(), will also produce
323 * nominally non-empty output, if jemalloc not built with stats support, but essentially it'll be
324 * zeroes all-over.
325 *
326 * @param os
327 * Stream to which to write. Defaults to standard output.
328 * @param format
329 * Format of the output. Defaults to human-readable text.
330 * @param extra_opts
331 * If not empty: appended verbatim to jemalloc's `malloc_stats_print()` options string (its flag letters
332 * toggle output sections -- merged-vs-per-arena, bins/large/extents/mutex; see jemalloc docs).
333 */
334 void stats_dump_to_ostream(std::ostream& os = std::cout, Stat_format format = Stat_format::S_TEXT,
335 util::String_view extra_opts = {}) const;
