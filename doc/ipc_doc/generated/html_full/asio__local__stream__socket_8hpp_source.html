59/**
60 * Similarly to the transport::Msg_batch_in concept (as taken by API
61 * `{Blob|Native_handle}_receiver::async_receive_*_batch()` concept) implements persistent-across-reads
62 * batched-receipt of messages over an `asio_local_stream_socket::Peer_socket<Protocol_pkt_stream>`.
63 * There is a heavy focus on performance, including across multiple batched receives (nb_read()) on the same
64 * `*this` without linear-time prep work ahead of each such receive op.
65 *
66 * @see Native_handle_receiver concept doc header for an explanation of receive-batching (including what
67 * native batching is; how `Msg_resource_t` template-param relates to things); and how the general design
68 * enables high perf.
69 *
70 * ### Rationale ###
71 * Formally speaking this is a stand-alone class template, as opposed to an implementation of any particular
72 * concept. (See Native_socket_stream_msg_batch_in for the `Msg_batch_in` concept impl for
73 * Native_socket_stream. As noted below it in fact uses a `*this` most centrally in its impl.) Put simply,
74 * it (1) prepares the data structures needed for -2-; (2) wrangles `recvmmsg()` or equivalent; and (3) maintains
75 * the aforementioned data structures, so that repetitions of -2- can be done with almost zero additional
76 * work (and certainly not linear in batch-size). In order to do something fancier, such as actually being
77 * suitable as main arg `batch` to sync_io::Native_socket_stream::async_receive_blob_batch(), it would need to
78 * speak a more advanced protocol rather than what it does speak... which is simply "receive whatever arrives
79 * and save it for the user to access." So why is it a public API? Answer: For the same reason, e.g.,
80 * nb_read_some_with_native_handle() (and other public members of the ipc::transport::asio_local_stream_socket
81 * namespace) are public: It may well prove useful for low-level work directly on raw local sockets.
82 * (That said, informally, we expect most users to use the somewhat higher-level Native_socket_stream
83 * instead -- or something even higher-level such as struc::Channel.)
84 *
85 * Please note that we have intentionally made the receiver-engine-facing API, namely nb_read() and
86 * reuse_result_payloads(), publicly accessible, again due to the above reasoning. Again the idea
87 * is that conceivably the Flow-IPC user could make use of it,
88 * as it is fairly general. As of this writing, however, only other Flow-IPC internal code (namely
89 * sync_io::Native_socket_stream) uses this sub-API; but that need not be the case.
90 *
91 * ### Details ###
92 * As of this writing this is internally done, specifically, via Linux-specific `recvmmsg()` API operating on a
93 * `SOCK_SEQPACKET` connection (hence the aforementioned #Protocol_pkt_stream). When/if support for non-Linux is
94 * added, this class (or hypothetical similar one) could support any equivalent from other OS.
95 *
96 * This implementation is fairly general, down to allowing an arbitrary (albeit mandatorily consistent across a given
97 * `*this` lifetime) #Mutable_buffer_sequence type. (E.g., could provide a simple util::Blob_mutable
98 * or an `array<Blob_mutable>` or `vector` thereof, etc.) The main limitation is one shared with the rest
99 * of transport::asio_local_stream_socket API -- as informed by the needs of the rest of Flow-IPC -- in that
100 * in addition to arbitrary binary data blobs it supports the transmission of `Native_handle`s, namely either zero
101 * or one such items per in-message. As usual a given in-message may contain 0+ bytes of blob data and 0 or 1 handles;
102 * but never 0 bytes and 0 handles (this is treated as a fatal error).
103 *
104 * It features the following APIs as of this writing:
105 *
106 * - For user (including internal user struc::sync_io::Channel): `size_t max_msg_count`-taking ctor,
107 * initialized(), n_used(), full(), clear_used(), prepare_target_payload(), result_payload_blob(),
108 * result_payload_hndl() (for Native_handle_receiver only).
109 * - For higher-level receiver engine (such as sync_io::Native_socket_stream + Native_socket_stream_msg_batch_in
110 * working in concert): nb_read(), reuse_result_payloads().
111 * - The expected order of ops for each batched-read (after reaching initialized() originally) is:
112 * -# (Usually) Higher-level user invokes Blob_receiver::async_receive_blob_batch() or
113 * Native_handle_receiver::async_receive_native_handle_batch() which internally invokes:
114 * -# Core batch-receive: nb_read().
115 * -# Filter-out control messages without destroying them: reuse_result_payloads()
116 * (if applicable depending on your higher-level protocol if any).
117 * - Harvest any control-message info among the filtered-out in-messages.
118 * -# User consumes results: result_payload_blob() and possibly result_payload_hndl().
119 * -# User resets for next batch-read:
120 * -# Save N = n_used().
121 * -# clear_used().
122 * -# prepare_target_payload() (for each of the first N slots only).
123 *
124 * The algorithmic centerpieces of a `*this` are as follows. Note that, as usual in this context, this info is
125 * of interest not to the eventual user doing higher-level receiving via Blob_receiver and the like; but implementers
126 * of specific `Blob_receiver`s (et al). So we have:
127 *
128 * - nb_read() which internally performs `recvmmsg()` (or equivalent op in other OS).
129 * - prepare_target_payload() and result_payload_blob() et al interact with it to maintain high perf.
130 * - reuse_result_payloads() which helps (at least Native_socket_stream_msg_batch_in but conceivably others)
131 * support higher-level protocols with both user in-messages and control messages (e.g., auto-ping, graceful-close)
132 * while maintaining high perf.
133 *
134 * ### Regarding structure of each target-blob area(s) user supplies to prepare_target_payload() ###
135 * You can skip this section if you promise to, in every prepare_target_payload() call for a given `*this`,
136 * supply the same number of scatter/gather buffers of the same respective lengths. (E.g.: always a 2-buffer and
137 * a 4096-buffer.)
138 *
139 * In general you *can* provide a different structure (e.g. 1 2-byte buffer and 3 1-byte buffers; or just 1 7-byte
140 * buffer; or...) to each prepare_target_payload() versus the others. It is conceivable to make use of this for
141 * some real purpose. However:
142 *
143 * - Informally: one typically doesn't know (at this level) what's coming, so it is probably correct to provide, at
144 * least, the same total number of target bytes for each prepare_target_payload(). It is also likely more
145 * natural to have the same # and length-order of scatter/gather buffers across which to spread these bytes;
146 * though technically doing otherwise could be fine (just... why bother?).
147 * - This is even more-so if you plan to use reuse_result_payloads() which shall potentially swap slot order
148 * which would probably make keeping-up with what happened hard-to-impossible, unless each slot is structurally
149 * identical to all others.
150 *
151 * @internal
152 *
153 * ### Impl notes ###
154 * Generally the details here are informed by the somewhat higher-level needs of Native_socket_stream and
155 * Native_socket_stream_msg_batch_in which implement the protocol used by the former. As such that protocol is
156 * close to -- but not quite the same as -- simply supporting arbitrary in-datagrams (each with an optional
157 * native-handle), which is what a `*this` supplies.
158 *
159 * The devil is really in the details, while being driven by the basic receive-batching design described in
160 * Native_handle_receiver concept doc header. The basic point is, after invoking ctor and N prepare_target_payload(),
161 * subsequent per-batched-read (nb_read()) are not linear-time, so that:
162 *
163 * - each actually received-to slot will understandably need processing;
164 * - but all others require little to no reset or post-processing.
165 *
166 * Thus we get the benefits of receiving potentially many in-messages via 1 OS-call; while requiring ~no extra
167 * compute when compared with a conventional non-batched series of N single-message-receives-until-would-block.
168 *
169 * `recvmmsg()` makes this achievable, though far from trivial. To summarize:
170 *
171 * - `recvmmsg()` takes an array of `mmsghdr`, each of which contains an `msghdr` (identical to what `recvmsg()`
172 * takes one of) and `.msg_len`; and returns the number of `mmsghdr`s that were actually received-to;
173 * while each individual `.msg_len` holds the # of bytes received for that in-message (identical to what
174 * `recvmsg()` would have returned).
175 * - The `msghdr` has a pointer/length w/r/t a scatter/gather array of `iovec` structures in heap, each storing
176 * a location/size, being conceptually identical to our util::Blob_mutable.
177 * - It also has a pointer/length w/r/t a complex *ancillary data* structure in heap (we use it for 0-1 FDs).
178 * - If a given slot was not read-to by a `recvmmsg()`, then its `mmsghdr` array entry is untouched and can be
179 * reused as-is.
180 * - If a given slot *was* read-to, but via reuse_result_payloads() it is determined that it contained no
181 * user in-message but merely what the receiver-engine considers a control/metadata in-message -- not to be
182 * passed to the user as such -- then that `mmsghdr` (and related) array entry can also be reused as-is... almost.
183 * A couple of items do need to be set again; you'll see. In any case these should be very cheap and relatively
184 * rare anyway.
185 * - If it was read-to, and it was indeed a user in-message, then naturally prepare_target_payload() has to be
186 * re-invoked. However you'll see that even this requires only a certain subset of the work compared to
187 * the one-time initializing prepare_target_payload().
188 * - For our part we make use of this as follows:
189 * - We store the array of `mmsghdr`s, which is continually received-to, re-primed, received-to, re-primed, ....
190 * This is #m_mmsg_hdrs, a `vector`.
191 * - All other info, including the aforementioned `iovec`-array and ancillary-data
192 * `mmsghdr`-member-pointer-pointees, is stored in #m_mdts, a structurally identical `vector` (same
193 * size, capacity, and index order as `m_mmsg_hdrs`).
194 * - So slot indexed `idx` exactly consists of the two `struct`s `m_mmsg_hdrs[idx]` and `m_mdts[idx]`.
195 * - User's prepare_target_payload() calls sets them up until initialized() is true.
196 * - nb_read() and reuse_result_payloads() read into the first N slots, where N = # of pending messages capped
197 * at total # of slots we store.
198 * - User can consume any received-to slot `idx`'s data and then re-prepare that slot by supplying new target memory
199 * area(s). They do this by calling `prepare_target_payload(..., idx)`.
200 * - Any slots that were untouched by nb_read() or reuse_result_payloads() simply carry-over to the next nb_read().
201 * They need not be touched at all.
202 *
203 * @endinternal
204 *
205 * @tparam Msg_resource_t
206 * Same as for Generic_msg_batch_in. However, caution! Be very sure that whatever is stored here, if it
207 * provides the backing bytes for the #Mutable_buffer_sequence passed to the corresponding
208 * prepare_target_payload(), does *not* change location in memory if the `Msg_resource_t` is *moved*
209 * onto another `Msg_resource_t`. For example, this *does* hold for `flow::util::Blob` or `vector` or
210 * `unique_ptr<int>`; but *not* for `array` or `int`.
211 * @tparam Mutable_buffer_sequence_t
212 * See #Mutable_buffer_sequence.
213 */

339 /**
340 * Performs a high-perf non-blocking batched-receive into the batch area with indices
341 * [n_used(), `max_msg_count`). See ctor for the latter. Usually, but not necessarily, `this->n_used() == 0`,
342 * as usually one would clear_used() first, or `*this` was just initialized(). Returns `false` if
343 * the aforementioned range is empty -- that is full() is `true` and no-ops modulo logging; otherwise returns
344 * `true` and proceeds. Further documentation assumes the latter.
345 *
346 * Let `n_payloads` be the size of the aforementioned range (thus `n_payloads >= 1`). This receives
347 * at most `n_payloads` messages. If no error but no in-messages are pending, it is would-block
348 * (see specific code below). If no error, and messages were pending, the number is not explicitly returned
349 * but rather reflected in n_used() increasing by that # (at least 1, at most `n_payloads`). If error,
350 * and no messages were pending, emits that error and leaves n_used() unchanged.
351 *
352 * It is *not* a possible outcome that messages were emitted (n_used() changed) *and* an error is emitted.
353 * See section "Deferred errors" just below however.
354 *
355 * @note Be aware of the *implied would-block* condition. See full() doc header. Spoiler alert:
356 * if we yielded data/no error, then it wasn't would-block... but if `full() == false` post-op, then
357 * the in-pipe is nevertheless in would-block state. It would be wasteful to try another nb_read().
358 * Conversely, though, if `full()` then you can and should nb_read() again (assuming the goal is to
359 * drain the in-pipe such as in edge-triggered loops).
360 *
361 * ### Special graceful-close (a/k/a EOF) semantics ###
362 * nb_read_some_with_native_handle(), a-la Boost, emits `boost::asio::error::eof` on encountering graceful-close
363 * in the message stream -- never combined with emitting an in-message as well; so in a sense that "error" is
364 * an in-message itself (never followed by any more in-messages). This nb_read() never emits that code however.
365 *
366 * Instead: If and only if there is no error emitted (including would-block), and any pending in-messages (0 or more
367 * of them) are capped with graceful-close, then `*graceful_close` is set to `true`; else to `false`. The
368 * graceful-close "in-message" thus is treated semantically as an in-message and is always emitted if and only if it
369 * is pending. To recap the possible outcomes:
370 *
371 * - Socket-hosing error or `INVALID_ARGUMENT`: emitted via standard flow error semantics.
372 * - Subtle exception: error::Code::S_MESSAGE_SIZE_EXCEEDS_USER_STORAGE and
373 * error::Code::S_LOW_LVL_UNEXPECTED_STREAM_PAYLOAD_BEYOND_HNDL are not socket-hosing. Further I/O
374 * can be attempted. However:
375 * - In-direction: Informally, it is ill-advised to continue work in this direction. In-messages potentially
376 * following the overflowing one, in this batch, would have been dropped. In most protocols it would be
377 * difficult to continue from this point.
378 * - Out-direction: Work really can continue. Informally, though, it might be ill-advised to take advantage
379 * of this -- but less so than in the previous bullet point.
380 * - No in-message(s) and no graceful-close pending: emitted via those same semantics as
381 * `boost::asio::error::would_block`.
382 * - Otherwise, at least 1 of (in-message, graceful-close) is pending. So:
383 * 0+ in-message(s) are emitted into `*this` (n_used() increases if 1+), and `*graceful_close` is assigned
384 * to `true` if graceful-close capped those 0+ in-messages; to `false` otherwise.
385 * - So: It is not possible that there is no error, n_used() did not increase (0 in-messages), *and*
386 * `*graceful_close = false` is set.
387 *
388 * @note Graceful-close, if detected (and it will be if indeed pending), is never deferred to the next nb_read().
389 * This is potentially important, if you're running an edge-triggered-poll (e.g., `EPOLLET` with `epoll_*()`)
390 * event loop. If we were to defer reporting a pending graceful-close, you'd likely invoke `epoll_wait()` (or
391 * equivalent), and it will probably hang, as the *readability edge* has already been consumed.
392 * (We've empirically confirmed this in Linux.)
393 *
394 * ### Edge-triggered-poll friendliness ###
395 * A key guarantee, for those who run an edge-triggered-poll event loop (e.g., `EPOLLET` with `epoll_*()`), is that
396 * *all* pending in-messages (counting graceful-close as in-message) are flushed into `*this` (and `*graceful_close`),
397 * up to `full() == true`. Thus, if you nb_read() repeatedly until would-block is emitted, or `!full()`
398 * (implied would-block), or socket-hosing error, and then await (edge-triggered) readability again, all will work
399 * well.
400 *
401 * ### Deferred errors: Advanced discussion ###
402 * (Some of this references implementation details. In this advanced context we deem it appropriate.)
403 *
404 * We've noted that we will never emit a
405 * (socket-hosing / `MESSAGE_SIZE_EXCEEDS_USER_STORAGE` / `LOW_LVL_UNEXPECTED_STREAM_PAYLOAD_BEYOND_HNDL` /
406 * `INVALID_ARGUMENT`, non-would-block, non-graceful-close)
407 * error, if we do emit 1+ in-messages (let's count `*graceful_close = true` as an in-message for this discussion).
408 * What happens, though, if the socket has 1+ in-messages pending *and* an error following those in-messages? In
409 * Linux, as of this writing, at least in some mainstream versions, the `man recvmmsg` page says that in this case (it
410 * is even marked under "BUGS," probably out of caution more than anything) the error is not emitted; but any
411 * following `recv*()` call will emit the pending error. In short: we simply report (in this context) what the OS
412 * does, so if that happens, we'll simply emit the same stuff (in fact we have no good way of knowing it's happening,
413 * rather than the error simply happening a bit later).
414 *
415 * Not so fast, though: This opens the possibility of a subtle problem. To wit: if the OS knows an error is pending
416 * after 1+ in-messages, and `recvmmsg()` ignores it, but the next `recv*()` will report the error, then can't this
417 * break the edge-triggered-poll-event-loop-friendly semantics, wherein *all* in-data must be flushed before
418 * invoking another await-readability OS-call (`epoll_wait()` in Linux)? That is, an `epoll_wait()` for readability
419 * would hang in such a hypothetical scenario (if edge-triggered, `EPOLLET`; level-triggered is always safe).
420 *
421 * In short: As of this writing, in the case of Linux, it is not a problem in practice. So don't worry about it...
422 * but read on if you want to understand why/what is happening.
423 *
424 * Essentially it is not a problem simply because, in our case of dgram-based local IPC over Unix-domain sockets,
425 * specifically when reading, there simply *is* no error condition that can be "queued" after in-messages.
426 * Graceful-close is possible -- but we handle that, and it's not (internally in Linux) an error. `ECONNRESET`
427 * is not a thing in this context; `EPIPE` is for writing (not reading); others catastrophic problems such as
428 * `EBADF` are not "queued." With TCP, `ECONNRESET` would indicate an RST, but it's not a thing for us. With UDP,
429 * some sort of ICMP wackiness could maybe pop up -- but we aren't networking, and it's not UDP.
430 *
431 * That said, it is important to keep an eye on this (as Linux develops and/or we add other OS support); semantics
432 * could differ there. Even in Linux, we *did* empirically confirm that in general the situation wherein a
433 * socket is in queued-error state, and `recv*()` would yield an error (namely `ECONNRESET` due to queued RST
434 * intentionally sent by opposing side), then an `epoll_wait()` for readability, with `EPOLLET`, will hang and not
435 * re-report readability despite the error-state of the socket. Again, though, we could only force this in TCP, so
436 * it's not immediately relevant -- but it is conceivable it could become relevant. E.g., this code could be
437 * extended to newer Linux that act differently and/or other OS that act differently and/or support networked
438 * sockets (perhaps UDP).

448 * @param err_code

450 * error::Code::S_INVALID_ARGUMENT (`!this->initialized()` at entry);

469 /**
470 * Scans every in-message slot in range [`start_idx`, `this->n_used()`); performantly rearranges this range
471 * so that all in-messages for which `is_unused_func(M) == false` (if any + without mutual order changing) are
472 * at the start of the range, followed by the other ones (if any; no ordering guarantees); and adjusts
473 * (no-op or decreases) n_used() by the # of the `is_unused_func(M) == true` slots detected.
474 *
475 * @see Msg_batch_in class doc header for rationale/background/discussion. In short, though, the idea is
476 * `is_unused_func(M) == false` indicates a "user in-message" (worthy of remaining within the
477 * 0-to-`n_used()` range), while the converse indicates a control/metadatum message (which should
478 * be moved past the "used" range).
479 *
480 * Conceptually this is similar to `std::remove_if()`, except swaps -- instead of mere moves -- are used, thus
481 * ensuring the slots potentially change relative order, but the set of slots by value is unchanged; and
482 * n_used() changes instead of a returned iterator are the mechanism of communicating how many items are
483 * "filtered out."
484 *
485 * ### What to do with the filtered-out slots? ###
486 * One option is to do nothing. You can nb_read() again; these slots will be readable-into; no problem.
487 * So then you'd just consume the ones up to `this->n_used()` as normal, and that's that... ready to nb_read()
488 * again.
489 *
490 * Otherwise -- namely if the filtered-out messages potentially carry useful information, or something --
491 * you can do the first or possibly both of the following.
492 *
493 * - Scan them (even though they're past the first `n_used()` slots) via `result_payload_*()`.
494 * - Consume and re-prepare (prepare_target_payload()) them.
495 *
496 * Bottom line is, you can (but need not) do stuff to them just as you can do to the not-unused ones. Have care.
497 *
498 * @param start_idx
499 * Index (0-based) of first message to scan (see above). Typically this would be what n_used() returned
500 * before the preceding nb_read(). (Fittingly the last message to scan is indicated by
501 * current/post-`nb_read()` value of also n_used().)
502 * @param is_unused_func
503 * See above. We suggest this is written to be as performant as humanly possible. E.g. try to find
504 * the cheapest-and-likeliest conditions first and thus early-return whenever possible.
505 */
506 template<typename Is_unused_func>
507 void reuse_result_payloads(size_t start_idx, const Is_unused_func& is_unused_func);

805template<typename Mutable_buffer_sequence_t, typename Msg_resource_t>
806void Msg_batch_in<Mutable_buffer_sequence_t, Msg_resource_t>::prepare_target_payload
807 (const Mutable_buffer_sequence& target_blob, Msg_resource&& msg_resource, size_t idx)
808{
809 using Buf_seq_adapter = decltype(Mdt_per_payload::m_buf_seq_adapter);
810
811 if (idx == size_t(-1)) // Set up new slot.
812 {
813 // Ensure .emplace_back() wouldn't increase .capacity().
814 assert((!initialized())
815 && "At this time the fully-initialized batch size shall be permanently set via ctor; cannot grow.");
816
817 m_mdts.emplace_back(target_blob, std::move(msg_resource));
818 auto& mdt = m_mdts.back();
819
820 /* This part is identical to what we do in nb_read_some_with_native_handle() when making msghdr, so omitting cmnts.
821 * (@todo Code reuse here is arguably possible but would probably (1) be more lines overall and (2) might
822 * be challenging due to this one doing .emplace_back(), the other simply declaring on stack. Revisit.) */
823 m_mmsg_hdrs.emplace_back(); // @todo Is there some way to .emplace_back({ ... })?
824 auto& mmsg_hdr = m_mmsg_hdrs.back();
825 auto& msg_hdr = mmsg_hdr.msg_hdr;
826
827 // Identical to msghdr setup in nb_read_some_with_native_handle(); omitting those comments.
828 msg_hdr.msg_name = nullptr; // (Unused.)
829 msg_hdr.msg_namelen = 0; // (Unused.)
830 // (Ptr does not change, not even via prepare_target_payload(); see below.)
831 msg_hdr.msg_iov = mdt.m_buf_seq_adapter.buffers();
832 // (Does not change except via prepare_target_payload() or reuse_result_payloads(); see below.)
833 msg_hdr.msg_iovlen = mdt.m_buf_seq_adapter.count();
834 msg_hdr.msg_control = mdt.m_msg_control_as_union.m_buf.data(); // (Ptr does not change.)
835 // (Compile-time constant as in-arg *and* is modified by recv[m]msg() as out-arg; but nb_read() shall correct it.)
836 msg_hdr.msg_controllen = sizeof(Msg_control_as_union::m_buf);
837 // (Compile-time constant as in-arg *and* is modified by recv[m]msg() as out-arg; but nb_read() shall correct it.)
838 msg_hdr.msg_flags = S_PER_MSG_FLAGS;
839 // mmsg_hdr.msg_len: Out-arg (queried in, e.g., result_payload_blob()). Can leave uninit.
840
841 // Caution! Any changes or reasoning about the above <=> check reuse_result_payloads()'s swap logic too!
842 }
843 else if (idx < m_mdts.size()) // Re-prepare slot to describe new target memory area.
844 {
845 auto& mdt = m_mdts[idx];
846
847 /* Buf_seq_adapter{target_blob} is self-evidently correct; then move-assign (really copy-assign) the temporary
848 * into mdt.m_buf_seq_adapter. Perf: as of this writing (and likely ~forever) it copies a size_t total-size;
849 * and the iovec array by value. (As of this writing -- when used by Native_socket_stream_msg_batch_in --
850 * that is array<2>; so a couple void* and a couple size_t; but in general it could be a heavier op.) */
851 mdt.m_buf_seq_adapter = Buf_seq_adapter{target_blob};
852
853 mdt.m_resource = std::move(msg_resource); // Same as when initializing.
854
855 // The other `mdt` members are out-args; can be left alone. (Up to user to query responsibly.)
856
857 /* Now as for m_mmsg_hdrs[idx]: For unchanging/unused members it is uncontroversial to do nothing.
858 * That leaves msg_iov and msg_iovlen; let's discuss those. (It probably seems highly questionable to not
859 * simply reassign them again; the safest thing would be to just do that; but in for a penny, in for a pound
860 * perf-wise.)
861 * - msg_iov: Oh boy... to avoid excessive verbiage we point you to reuse_result_payloads() which discusses it,
862 * namely how it never changes.
863 * - msg_iovlen: For a general Mutable_buffer_sequence there's no choice but to reassign this simple integer.
864 * Again please read comment in reuse_result_payloads().
865 * @todo It is conceivable to skip it depending on Mutable_buffer_sequence; the logic could be specialized
866 * (much like buffer_sequence_adapter does). For example, if we are used by Native_socket_stream_msg_batch_in,
867 * then as of this writing Mutable_buffer_sequence is array<2>, so `mdt.m_buf_seq_adapter.count() == 2`, period.
868 * Considering this is a mere integer assignment, the to-do is hardly the highest-priority thing. */
869 auto& msg_hdr = m_mmsg_hdrs[idx].msg_hdr;
870 msg_hdr.msg_iovlen = mdt.m_buf_seq_adapter.count();
871
872 assert((msg_hdr.msg_controllen == sizeof(mdt.m_msg_control_as_union))
873 && "It is initialized to this constant value, and while recv*() shall modify it, nb_read() should have "
874 "immediately reset it again.");
875 }
876 else // if (idx >= m_mdts.size()) && not -1
877 {
878 assert(false && "prepare_target_payload(x) must either replace an existing slot x or add slot via `x = -1`.");
879 }
880} // Msg_batch_in::prepare_target_payload()

931void Msg_batch_in<Mutable_buffer_sequence_t, Msg_resource_t>::Mdt_per_payload::swap(Mdt_per_payload* that)
932{
933 using std::swap; // This is the proper ADL-friendly style (do *not* inline std::swap() instead).
934
935 /* Rationale for caring about swapping of guys like *this: (at least) Msg_batch_in::reuse_result_payloads().
936 * It might be best to look at that thing for context too when grokking this.
937 *
938 * Why the custom swap()? Answer:
939 * - At least one thing need not actually be swapped; see below.
940 * - If there's a custom, faster swap(Msg_resource_t&, Msg_resource_t&), then the below will invoke it
941 * (as opposed to the default which would do 3 move-assigns).
942 * - There *is* a custom, faster Native_handle swap, so we invoke it (similar reasoning). */
943
944 /* This ultimately swaps the `iovec` arrays (and perhaps some other stuff such as the computed total size) stored
945 * inside boost::asio::detail::buffer_sequence_adapter. (Depending on the Mutable_buffer_sequence specialization
946 * they might not be arrays but, e.g., just single `iovec`s... but memory-wise equivalent to arrays of some constant
947 * length.) So most likely it can be thought of as 3 memcpy()s. Actually as of this writing Mutable_buffer_sequence,
948 * when we are used by Native_socket_stream_msg_batch_in, is array<2> (b/c its prepare_target_payload() takes just
949 * a single Mutable_buffer, and we pre-pend m_msg_type's location/size); so in that case it's more like:
950 * 3-op swap of 2 void*, 3-op swap of 2 size_t. That is to say it's pretty quick. In general though depending
951 * on Mutable_buffer_sequence it could be slower; but that's life.
952 *
953 * Perf aside the point is: this is a by-value swap. */
954 swap(m_buf_seq_adapter, that->m_buf_seq_adapter);
955
956 /* m_msg_control_as_union is out-arg, and nb_read() saves any contents to m_result_hndl; so this is garbage.
957 * No need to swap via `swap(m_msg_control_as_union, that->m_msg_control_as_union)`. */
958
959 swap(m_resource, that->m_resource); // Either std::swap() or custom-swap the `Msg_resource_t`s (ADL).
960
961 /* This is an important out-arg, so of course we should swap it. It is just an int really.
962 * Though since we're expounding on every little thing already... std::swap()
963 * of Mdt_per_payload would cause 3 Native_handle move-assigns, and as of this writing actually that'd
964 * waste cycles on unnecessarily nullifying source ->m_result_hndl, 3 times; so it's nice to do this. */
965 swap(m_result_hndl, that->m_result_hndl);
966} // Mdt_per_payload::swap()

968template<typename Mutable_buffer_sequence_t, typename Msg_resource_t>
969template<typename Is_unused_func>
970void
971 Msg_batch_in<Mutable_buffer_sequence_t, Msg_resource_t>::reuse_result_payloads(size_t start_idx,
972 const Is_unused_func& is_unused_func)
973{
974 using std::swap; // This is the proper ADL-friendly style (do *not* inline std::swap() instead).
975
976 /* This is adapted from a GNU STL remove_if() impl; but swap()s instead of merely move()ing.
977 * (To illustrate, remove_if("abc def ghi ", " ") would result in "abcdefghihi "; as the defghi chars
978 * in the back would get moved-to the front area, hence the move-from would just duplicate them; for other element
979 * types it would nullify them. Our algorithm would instead yield "abcdefghi ", the earlier-on spaces being
980 * swap-moved to the back.) Also we deal in indices and is_unused(idx) calls as opposed to iterators/F(*it); but
981 * logically same thing. */
982
983 auto& first = start_idx; // (Mere alias so as to match the GNU STL impl more closely.)
984
985 for (; (first != m_n_used) && (!is_unused_func(first)); ++first) {}
986
987 if (first == m_n_used)
988 {
989 return; // Unchanged -- all elements are used.
990 }
991 // else
992
993 auto result = first++;
994 for (; first != m_n_used; ++first)
995 {
996 if (!is_unused_func(first))
997 {
998 // Must swap slots [result] and [first]. Slot = m_mmsg_hdrs[idx] + m_mdts[idx].
999
1000 m_mdts[result].swap(&m_mdts[first]); // See inside this for key comments.
1001 // ^-- @todo swap(..., ...) would be better, but it's a private inner struct, so we haven't bothered....
1002
1003 /* There is no custom swap(mmsghdr&, mmsghdr&), so the default would happen if we simply did
1004 * swap(m_mmsg_hdrs[result], m_mmsg_hdrs[first]);
1005 * Namely the scalars therein would be swapped using the usual 3-step thing. They are all integers or pointers,
1006 * so the perf is fine... but (1) in for a penny, in for a pound: We decided to be precious about perf and swap
1007 * only what is necessary; and (2) more importantly in our case some of the values point to m_mdts[idx] -- so
1008 * the proper "swap" is to do nothing in that case! So it wouldn't just be "slow" but also wrong.
1009 *
1010 * Let's justify what we actually do do. To wit:
1011 *
1012 * - Firstly we can ignore (for perf) the various unused and constant-valued fields:
1013 * msg_hdr.{msg_name, msg_namelen, msg_flags, msg_controllen}.
1014 * - msg_hdr.msg_controllen is a subtle beast. As an in-arg, it is always set to a constant value in our case
1015 * (sizeof(a thing)). Then, however, recv*() modifies it! It is unclear to *what* exactly it is modified;
1016 * presumably something like the size of received ancillary data; but docs do not say how to use it and
1017 * moreover say CMSG*() macros are to be used to traverse ancillary data (and we do just that in nb_read(),
1018 * where we grab the native handles if any and save in m_mdts[...].m_result_hndl). That does not, however,
1019 * mean msg_controllen (as out-arg) is not used; maybe CMSG*() grabs it/uses it somehow. That said: by the
1020 * time we are executed, nb_read() has already set m_result_hndl (and the m_mdts[].swap() dealt with it
1021 * above), and reset msg_controllen to the constant value it must equal as in-arg in the next nb_read().
1022 * Therefore: bottom line: It is always set to a constant value, except for a short time inside nb_read()
1023 * just after recv*(). Therefore, here, we can ignore it as a constant-valued field.
1024 * - The out-arg mmsghdr::msg_len (# of bytes received) is clearly correct to swap in normal fashion; it
1025 * is accessed via public accessor(s).
1026 * - msg_control points to where ::recvmmsg() is to place received FDs.
1027 * Its value is: mdt[...].m_msg_control_as_union.m_buf.data(): ptr to element 0 of array, namely the
1028 * ancillary-data (FD) storage area of a certain constant (no matter the slot) size. Even if the
1029 * values inside said array mattered (they don't as of this writing; nb_read() copies FD(s) into m_mdts[]),
1030 * pointing to the same-index-th mdts[].m_msg_control_as_union would have been correct; meaning
1031 * the contents would've been swapped above, so the pointers should remain unchanged. (This is a bit tricky
1032 * IMO (ygoldfel) to realize and might require some pencil-and-paper to prove to oneself.)
1033 * - msg_iov and msg_iovlen: Okay, so IMHO (ygoldfel) this is shockingly difficult to grok, if one is not
1034 * very careful in one's reasoning. It also very much relies on how
1035 * boost::asio::detail::buffer_sequence_adapter is implemented; it's in detail:: in the first place and
1036 * in any case internally could change; but we've already decided to take that risk elsewhere. So let's
1037 * just go with the facts of its current state (Boost-1.87). buffer_sequence_adapter, for the purposes of
1038 * this discussion, should be thought of as being isomorphic to array<iovec, N>, where N is a constant
1039 * (yes, it could even just be simply equal to `iovec`, depending on Mutable_buffer_sequence, but that still
1040 * fits). Then, msg_iov is a pointer &...[0] of that array; and `msg_iovlen <= N` is how much of that
1041 * array to use. (This all would be different if .buffers() returned some malloc()ed heap address instead
1042 * of a pointer right into m_mdts[] memory area itself.) So given that info:
1043 * - Up above, we did in fact swap the *contents* of the two array<iovec, N>s. Therefore
1044 * the *pointers* msg_iov should *not* be swapped: they are pointing at the proper iovec-arrays already.
1045 * - However the active *lengths* do need to be swapped! E.g., picture [1 2 x]<=>[3 4 5]; this becomes
1046 * [3 4 5]...[1 2 x]. msg_iov (unchanged) were pointing at 1 and 3; now to 3 and 1; that's right.
1047 * But if the lengths were 2<=>3, their becoming 3...2 is correct; whereas remaining 2...3 would be
1048 * blatantly wrong; the msg_iovlen=2 would ignore the element `5`, and msg_iovlen=3 would refer to
1049 * the element `x` among others.
1050 * So yes, as odd it may seem, the correct thing is to not touch msg_iov; but to swap msg_iovlen.
1051 * @todo See also to-do in prepare_target_payload() regarding conceivable specialized logic that could
1052 * at times skip this swap as well.
1053 * - Just to confuse you even more: if we're being real, any user of reuse_result_payloads() is highly
1054 * likely to simply keep msg_iovlen always at the same value, and same for the individual buffers'
1055 * lengths (inside each iovec), when comparing between any two slots. If it's possible their algorithm
1056 * allows for swapping slots like this, then they pretty much have to have identical structure. Granted,
1057 * perhaps one could have, like, 3 1-buffers and 1 3-buffer (totaling the same capacity, 3) in 2 respective
1058 * slots; but come on, why do such a thing? So the swapping is likely a no-op anyway... but hey, if
1059 * we want to be correct, we should be correct. */
1060
1061 auto& mmsg_hdr1 = m_mmsg_hdrs[result];
1062 auto& mmsg_hdr2 = m_mmsg_hdrs[first];
1063 auto& msg_hdr1 = mmsg_hdr1.msg_hdr;
1064 auto& msg_hdr2 = mmsg_hdr2.msg_hdr;
1065
1066 swap(mmsg_hdr1.msg_len, mmsg_hdr2.msg_len);
1067 swap(msg_hdr1.msg_iovlen, msg_hdr2.msg_iovlen);
1068
1069#if 0 // This is pretty well tested by now -- cut it out for perf when assert()s enabled.
1070 // Paranoia strikes deep... opportunistically check this invariant... perhaps again.
1071 assert((msg_hdr1.msg_controllen == sizeof(Msg_control_as_union::m_buf))
1072 &&
1073 (msg_hdr2.msg_controllen == sizeof(Msg_control_as_union::m_buf))
1074 && "It is initialized to this constant value, and while recv*() shall modify it, nb_read() should have "
1075 "immediately reset it again.");
1076#endif
1077 // End of swap code.
1078
1079 ++result;
1080 } // if (!is_unused_func(first))
1081 } // for (; first != m_n_used; ++first)
1082
1083 m_n_used = result;
1084
1085 /* @todo Conceptually, our approach to swapping the m_mdts[] and m_mmsg_hdrs[] pairs is arranged as follows:
1086 * Skip anything constant/unused; swap m_mdts[] first; swap non-m_mdts[]-referencing parts of m_mmsg_hdrs[]
1087 * (i.e., msg_len); and lastly update/swap the relevant m_mdts[]-referencing parts (i.e., msg_hdr.msg_iovlen).
1088 * The part of that that's at all tricky is this subset: swap m_mdts[] by value, so no pointer into m_mdts[]
1089 * needs updating. This *is* correct (hence all the verbiage above), but perf-wise: there's the
1090 * m_buf_seq_adapter swap (linear in sizeof(Mutable_buffer_sequence) -- could be quite quick, could be less so);
1091 * and m_resource swap. The potential to-do would be to switch the paradigm: m_mdts becomes a mere store
1092 * (wouldn't even need to be a vector<>; could be anything like set<>; but vector<> is faster for our purposes;
1093 * point is, the index into it no longer has meaning); and the swapping would only swap various pointers
1094 * in m_mmsg_hdrs[]. So m_mdts[] are *not* swapped by value, only various referents into it are.
1095 * This would avoid those *sort of* expensive m_buf_seq_adapter and m_resource swaps. Some of the reasoning
1096 * above wouldn't need to be so annoying (arguable). Probably would need to use the trick where msg_name would store
1097 * a pointer into m_mdts, for our own purposes, at least to be able to find the proper m_mdts[].m_result_hndl.
1098 *
1099 * Should we do it? In terms of simplifying stuff, it might be a wash. In terms of perf, it depends on how
1100 * we're used. As of this writing the swap-stuff/reuse_result_payloads() algorithm exists because of
1101 * how Native_socket_stream_msg_batch_in uses us, so let's consider that use case; see
1102 * Native_socket_stream_msg_batch_in::nb_read(), namely how it uses reuse_result_payloads() as of this writing.
1103 * To wit: illegal in-dgrams are non-existent; and there's at most one graceful-close per connection; so the
1104 * only reason to actually swap would be auto-ping in-dgrams. Those might seem like they could be quite prevalent;
1105 * but consider that if the system is so loaded to where *this* level of optimization at all matters, then
1106 * such a connection would hardly ever even need to send auto-pings (which occur in an idle channel, not otherwise).
1107 * So... I (ygoldfel) would at this point say, keep an eye on profiling results, and if reuse_result_payloads() looks
1108 * like a hot-spot, then look into it. Otherwise, leave it alone. */
1109} // Msg_batch_in::reuse_result_payloads()

1112bool
1113 Msg_batch_in<Mutable_buffer_sequence_t, Msg_resource_t>::nb_read(flow::log::Logger* logger_ptr,
1114 Peer_socket<Protocol_pkt_stream>* peer_socket_ptr,
1115 bool* graceful_close, Error_code* err_code,
1116 int message_flags,
1117 size_t* total_rcvd_bytes_or_null)
1118{
1119 using flow::log::Sev;
1120 using boost::system::system_category;
1121 using boost::io::ios_all_saver;
1122 namespace sys_err_codes = boost::system::errc;
1123 using std::swap;
1124 using std::memcpy;
1125 using ::recvmmsg;
1126 using ::recvmsg;
1127 using ::mmsghdr;
1128 using ::cmsghdr;
1129 // using ::SOL_SOCKET; // It's a macro apparently.
1130 using ::SCM_RIGHTS;
1131 using ::MSG_DONTWAIT;
1132 using ::MSG_TRUNC;
1133 using ::MSG_CTRUNC;
1134 // using ::errno; // It's a macro apparently.
1135
1136 FLOW_ERROR_EXEC_AND_THROW_ON_ERROR(bool, nb_read, logger_ptr, peer_socket_ptr, graceful_close, _1, message_flags,
1137 total_rcvd_bytes_or_null);
1138 // ^-- Call ourselves and return if err_code is null. If got to present line, err_code is not null.
1139
1140 FLOW_LOG_SET_CONTEXT(logger_ptr, Log_component::S_TRANSPORT);
1141
1142 assert((m_mmsg_hdrs.size() == m_mdts.size()) && "Gotta be a bug somewhere in Msg_batch_in.");
1143 if (!initialized()) // As advertised:
1144 {
1145 FLOW_LOG_WARNING("Local_stream_batch [" << *this << "]: "
1146 "Attempt to batch-read without adding all [" << m_mdts.capacity() << "] slots; so far "
1147 "only [" << m_mdts.size() << "] slots have been added via prepare_target_payload(). "
1148 "This is the API user's error, though since this API is used internally in the library "
1149 "too, it might be a bug in the library. We can't tell from here. Emitting invalid-argument "
1150 "error.");
1151 *err_code = error::Code::S_INVALID_ARGUMENT;
1152 return true;
1153 }
1154 // else
1155
1156 const size_t n_payloads = m_mdts.size() - m_n_used;
1157
1158 if (n_payloads == 0)
1159 {
1160 return false;
1161 }
1162 // else if (n_payloads >= 1):
1163
1164 /* To reader/maintainer: The rest is similar to nb_read_some_with_native_handle() in various places ("just"
1165 * applied to 2+ potential in-dgrams), so we will skip some comments.
1166 *
1167 * The difference is basically that for each of the following, there are now roughly speaking n_payloads
1168 * of that thing:
1169 * - msghdr to the OS-call:
1170 * - Instead there's an array of them, one per potential in-dgram, arranged into mmsghdr [sic] structs.
1171 * - And therefore buf_seq_adapter (iovec array with target in-bufs in msghdr):
1172 * - Instead there's (essentially) a sequence of them (yes, seq of seqs), m_mdts[*].m_buf_seq_adapter.
1173 * - Also therefore msg_control_as_union (which sits ready to receive an FD, or none, upon recvmsg()):
1174 * - Instead there's one of these per msghdr, m_mdts[*].m_msg_control_as_union.
1175 * - n_rcvd_or_error (bytes received into buf_seq, returned by recvmsg(), or -1 for error):
1176 * - Instead recvmmsg() returns -1 for error, else the # of leading `msghdr`s that did receive data, and
1177 * for each of those the `n_rcvd` part, so to speak, is populated in that mmsghdr, m_mmsg_hdrs[*].msg_len.
1178 *
1179 * Due to the design of *this class, we've been painstakingly maintaining all of those things, so we can
1180 * pretty much execute ::recvmmsg() right away with no linear-time prep. Reminder: We don't target the
1181 * *entire* m_mmsg_hdrs+m_mdts vectors; but rather the trailing n_payloads of them, starting with
1182 * m_...[m_n_used]. */
1183
1184 assert(peer_socket_ptr);
1185 auto& peer_socket = *peer_socket_ptr;
1186 const Native_handle peer_hndl{peer_socket.native_handle()};
1187
1188 /* Since this method and class are to be heavily optimized: Use this optimization that caches
1189 * whether TRACE messages should be logged instead of computing it per-message. The negatives are:
1190 * - The code is a bit more involved (not too bad, when perf is truly at stake).
1191 * - If the verbosity is changed under us *during* the method's execution, this will not respond to it
1192 * immediately. It's fine: the lag is only a split-second; and a slight unevenness in taking verbosity
1193 * config changes is an expected/accepted phenomenon generally. */
1194 const bool do_log_trace = logger_ptr && logger_ptr->should_log(Sev::S_TRACE, get_log_component());
1195
1196 auto recvmmsg_hdr_ptr = &(m_mmsg_hdrs[m_n_used]);
1197 int n_rcvd_msgs_or_error;
1198
1199 /* Massage message_flags for our required purposes.
1200 * Same comments as when calling ::recvmsg() in nb_read_some_with_native_handle(). */
1201 message_flags = (message_flags | (MSG_DONTWAIT | MSG_TRUNC));
1202
1203 if (n_payloads == 1)
1204 {
1205 // There is only one target dgram; try to optimize somewhat by reverting to single-msg native API.
1206 const auto n_rcvd
1207 = recvmsg(peer_hndl.m_native_handle, &recvmmsg_hdr_ptr->msg_hdr, message_flags);
1208 if (do_log_trace)
1209 {
1210 FLOW_LOG_TRACE_WITHOUT_CHECKING
1211 ("Local_stream_batch [" << *this << "]: Connected local peer socket [" << peer_hndl << "] "
1212 "tried to batch-read up-to 1 in-message, "
1213 "potentially into a scattered-blob plus possibly a native handle; "
1214 "for efficiency used recvmsg() instead of recvmmsg(); it yielded return value "
1215 "[" << n_rcvd << "]; we shall now continue as-if this was done using recvmmsg().");
1216 }
1217
1218 if (n_rcvd == -1)
1219 {
1220 n_rcvd_msgs_or_error = -1;
1221 }
1222 else
1223 {
1224 n_rcvd_msgs_or_error = 1;
1225 recvmmsg_hdr_ptr->msg_len = static_cast<unsigned int>(n_rcvd);
1226 // Note: n_rcvd might be 0, indicating EOF (graceful-close). recvmmsg() *would* also result in `->msg_len == 0`.
1227 }
1228 }
1229 else
1230 {
1231 n_rcvd_msgs_or_error
1232 = recvmmsg(peer_hndl.m_native_handle, recvmmsg_hdr_ptr, n_payloads, message_flags,
1233 nullptr); // Don't mess with timeouts.
1234 }
1235
1236 /* Carefully check all the outputs. Return value first.
1237 * (Code reuse with nb_read_some_with_native_handle() is possible, but there are enough little differences, such
1238 * as logging, to where it feels more unwieldy than it is worth. @todo Maybe revisit.) */
1239
1240 if (n_rcvd_msgs_or_error == -1)
1241 {
1242 /* Not even 1 byte of a blob was read; and hence nor was any FD. (Omitting various comments from
1243 * nb_read_some_with_native_handle() that apply equally here.) */
1244
1245 const Error_code sys_err_code{errno, system_category()};
1246 if ((sys_err_code == sys_err_codes::operation_would_block) || // EWOULDBLOCK
1247 (sys_err_code == sys_err_codes::resource_unavailable_try_again)) // EAGAIN (same meaning)
1248 {
1249 if (do_log_trace)
1250 {
1251 FLOW_LOG_TRACE_WITHOUT_CHECKING
1252 ("Local_stream_batch [" << *this << "]: Connected local peer socket [" << peer_hndl << "] "
1253 "tried to batch-read up-to [" << n_payloads << "] in-messages, each "
1254 "potentially into a scattered-blob plus possibly a native handle per each; but read attempt "
1255 "indicated would-block; not an error condition. No in-messages received.");
1256 }
1257 *err_code = boost::asio::error::would_block;
1258 return true; // m_n_used unchanged.
1259 }
1260 // else
1261
1262 assert(sys_err_code);
1263
1264 FLOW_ERROR_SYS_ERROR_LOG_WARNING(); // Log based on sys_err_code.
1265 FLOW_LOG_WARNING("Local_stream_batch [" << *this << "]: "
1266 "Connected local peer socket [" << peer_hndl << "] "
1267 "tried to batch-read up-to [" << n_payloads << "] in-messages, each "
1268 "potentially into a scattered-blob plus possibly a native handle per each; "
1269 "but an unrecoverable error occurred. No in-messages received.");
1270 *err_code = sys_err_code;
1271 return true; // m_n_used unchanged.
1272 } // if (n_rcvd_msgs_or_error == -1)
1273 // else if (n_rcvd_msgs_or_error != -1)
1274
1275 if (n_rcvd_msgs_or_error == 0)
1276 {
1277 assert((n_payloads > 1) && "We should have returned false on 0; and used recvmsg() on 1, resulting in "
1278 "n_rcvd_msgs_or_error being -1 or 1, not zero.");
1279 // The assert() states that recvmmsg() was used. So given that:
1280
1281 FLOW_LOG_FATAL
1282 ("Local_stream_batch [" << *this << "]: Connected local peer socket [" << peer_hndl << "] "
1283 "tried to batch-read up-to [" << n_payloads << "] in-messages, each "
1284 "potentially into a scattered-blob plus possibly a native handle per each; "
1285 "but recvmmsg() returned 0; this is an unexpected semantic; EOF (graceful-close) should result in "
1286 "an in-message with msg_len=0 instead. Aborting; please look into this situation; it could be a bug.");
1287 assert(false
1288 && "Tried to batch-read up-to 2+ in-messages, each "
1289 "potentially into a scattered-blob plus possibly a native handle per each; "
1290 "but recvmmsg() returned 0; this is an unexpected semantic; EOF (graceful-close) should result in "
1291 "an in-message with msg_len=0 instead. Aborting; please look into this situation; it could be a bug.");
1292 std::abort();
1293 }
1294 // else if (n_rcvd_msgs_or_error > 0):
1295
1296 /* In-message(s) received. Here in-message means either an actual in-message or a graceful-close "in-message."
1297 * (A fairly-important, albeit undocumented and obscure fact: graceful-close is emitted as an in-message record
1298 * with msg_len=0 (no data)... followed by identical such records up to n_payloads total records.)
1299 *
1300 * Check each one for corner case errors and finalize each one's out-args. Again:
1301 * Omitting various comments that apply equally in nb_read_some_with_native_handle(). */
1302
1303 const auto recvmmsg_hdr_end = recvmmsg_hdr_ptr + n_rcvd_msgs_or_error;
1304 auto mdt_ptr = &(m_mdts[m_n_used]);
1305
1306 /* Used inside the loop on any error; essentially -- seeing as how we are emitting failure <=> no emitted msgs --
1307 * it (1) cleans-up *this (m_mmsg_hdrs, m_mdts) that may have been set to non-unused-state before the
1308 * current (recvmmsg_hdr_ptr, mdt_ptr) one that triggered the error; and (2) ensures no native-handles
1309 * that may have been received in the batch get leaked (since we emit no msgs) -- it returns these to OS.
1310 * (Subtlety: Un-emitted slots (i.e., ones starting with [m_n_used]) aren't required to have .m_result_hndl
1311 * in any particular state, .null() or otherwise. So this helper doesn't "formally" promise anything about that;
1312 * only that any in-batch-contained raw handles get closed.)
1313 *
1314 * (1) might be unnecessary paranoia -- generally user should not and possibly cannot use the socket
1315 * after an error anyway -- but we've spent significant effort on ensuring msg_{controllen|flags} is in its in-arg
1316 * form as much as possible; this will make quite sure in the (relatively) rare error case.
1317 *
1318 * (2) accounts for an edge (given a sane opposing guy) scenario; but in general why not?
1319 *
1320 * Note this is only necessary for the slots recv*() actually touched. So in particular no need to do this
1321 * at all unless `n_rcvd_msgs_or_error > 0`. */
1322 const auto clean_remaining_func = [&]() -> bool
1323 {
1324 assert((recvmmsg_hdr_ptr != recvmmsg_hdr_end) && "Internal pre-condition violated.");
1325
1326 /* (1), in short, is just resetting msg_{controllen|flags} to their init-values. For pre-error slots it's
1327 * already done; so we do it for the post-error (inclusive) slots. This loop is over those.
1328 *
1329 * (2) needs to un-leak any handle-copies in the entire in-batch: the pre-error slots if any; and the
1330 * post-error slots (inclusive; so at least 1). In this loop therefore we do the latter half. */
1331 do
1332 {

1344 * (In practice, as of this writing, this is equivalent behavior to never having received the
1345 * post-error slots; clearly sensible. As of this writing that applies to the error-slot in particular too,
1346 * as calling code below only touches .m_result_hndl last, after eliminating all error possibilities.) */

1378 * area was used. Though, as in nb_read_some_with_native_handle(), it may also indicate overflow
1379 * (N-byte in-dgram but <N bytes in target buffer). Refer to that function; keeping comments light except ones
1380 * relevant here only. */

1384 if (msg_len > target_payload_blob_sz)
1385 {
1386 FLOW_LOG_WARNING("Local_stream_batch [" << *this << "]: "
1387 "Connected local peer socket [" << peer_hndl << "] "
1388 "tried to batch-read up-to [" << n_payloads << "] in-messages, "
1389 "each potentially into a scattered-blob plus possibly a native handle per each; "
1390 "and it returned it read [" << n_rcvd_msgs_or_error << "] in-messages; and for message "
1391 "index [" << (n_rcvd_msgs_or_error - (recvmmsg_hdr_end - recvmmsg_hdr_ptr)) << "] (0-based) "

1393 "the blob's capacity [" << target_payload_blob_sz << "]. "
1394 "Acting as if nothing received + error.");

1396 && "In-dgram size overflows user-supplied buffer <=> MSG_TRUNC out-flag supposed to be set.");
1397
1398 /* Note/caution: Suppose this is iteration 2+. We emit the error anyway and don't report any received
1399 * data -- those in-dgrams are "eaten." This doesn't violate the contract (wherein we promise to not
1400 * emit data *and* an error). However it doesn't do the conceivable thing (that recvmmsg() itself does), where
1401 * we report the in-dgrams now and defer the error to the next receive-op later. Why not? Answer: Firstly
1402 * it would be hard-ish to implement; we'd have to actively store the error in a new m_, and so on. Secondly
1403 * we feel it is not worth it, as this error is truly exceptional -- the other side is misbehaving.

1439 {
1440 ios_all_saver saver{*(logger_ptr->this_thread_ostream())}; // Revert std::hex/etc. soon.

1442 ("Local_stream_batch [" << *this << "]: Connected local peer socket [" << peer_hndl << "] "
1443 "tried to batch-read up-to [" << n_payloads << "] in-messages, "

1448 "out-flags value [0x" << std::hex << out_flags << "] which includes MSG_CTRUNC. "
1449 "That flag indicates more stuff was sent as ancillary data; but we expect at most 1 native "
1450 "handle. Other side sent something strange. Acting as if nothing received + error.");
1451 }
1452

1454
1455 *err_code = error::Code::S_LOW_LVL_UNEXPECTED_STREAM_PAYLOAD_BEYOND_HNDL;
1456 return clean_remaining_func(); // m_n_used unchanged.
1457 }
1458 // else: Fall-through.
1459 } // if (out_flags != 0)

1462 * This is a new point though: We don't necessarily have to save the FD anywhere; the accessor
1463 * result_payload_hndl() could just do the below itself and return the result from there directly. However then:
1464 * the error handling has to move there which is annoying API-wise; and it's slower, as we have to do the
1465 * CMSG_FIRSTHDR() and the checking and... let's just take care of it and save the FD in a nice Native_handle for

1470 {

1472 (recvmsg_hdr_cmsg_ptr->cmsg_type == SCM_RIGHTS))

1506 * reuse_result_payloads() comment discussing it. That justifies the following (as well as clean_remaining_func())
1507 * in more detail -- but basically we have the invariant that recvmsg_hdr.msg_controllen is always this constant
1508 * value as in-arg, and recv*() happens to set it to something else as out-arg. So we always undo it either here
1509 * (up to detecting an error) or via clean_remaining_func() (upon detecting error). */
1510 recvmsg_hdr.msg_controllen = sizeof(Msg_control_as_union::m_buf);
1511
1512 /* Almost done except for the following fairly-important, albeit ~undocumented and obscure fact:
1513 * recvmmsg() will *not* simply return 0 on EOF (nor defer doing so until the next recv*(), if 1+ in-messages
1514 * preceded it in the present recvmmsg()). Instead, it will yield endless 0-length data-free "messages,"
1515 * apparently mimicking what would happen if we were to instead trigger repeated recvmsg() calls (each would
1516 * return 0, hence the corresponding mmsg_hdr.msg_len is set to 0 also). Therefore: */
1517 const bool eof_marker = (msg_len == 0) && mdt.m_result_hndl.null();
1518 if (eof_marker)
1519 {
1520 /* K (see below) <= n_rcvd_msgs_or_error - 1.
1521 * If current n_rcvd_msgs_actual = its original value, then K < n_rcvd_msgs_actual, so n_rcvd_msgs_actual
1522 * shall now become the new smaller value, marking the *first* empty "in-dgram" (really, EOF marker).
1523 * If current n_rcvd_msgs_actual has been set by a previously set EOF marker in an earlier iteration,
1524 * then K > n_rcvd_msgs_actual; hence n_rcvd_msgs_actual remains unchanged and continues to mark the first
1525 * EOF marker "in-dgram." So this is a nice compact/fast way to express setting it only once at most.
1526 *
1527 * However:
1528 * - This assumes there won't be non-data-free datagrams following an EOF-marker one. Indeed that is
1529 * impossible, unless sender sends an entirely data-free datagram; we disallow this formally and also
1530 * even if that weren't followed, then by either updating m_n_used accordingly, or emitting `eof` error (see
1531 * after loop), we'll essentially ignore anything following the first EOF-marker -- no matter what that is.
1532 * That's fine.
1533 * - This doesn't care if, after EOF-marker 1, all available slots are filled with EOF-markers
1534 * (n_rcvd_msgs_or_error == n_payloads), or if some were left untouched (n_rcvd_msgs_or_error < n_payloads).
1535 * Any touched ones shall be reset; any untouched ones don't need any reset; and n_rcvd_msgs_actual (and
1536 * therefore m_n_used or *err_code) shall be set based on EOF-marker 1. That said as of this writing
1537 * in reality Linux at least will fill all subsequent slots with EOF-marker "datagrams"
1538 * (n_rcvd_msgs_or_error == n_payloads). Our code is agnostic of this and does not verify this.
1539 * - We could also (on seeing EOF-marker 1) stop the loop, etc. etc. However that actually seemed more complex
1540 * to code; particularly given our desire to reset the in-arg/out-args .msg_flags and .msg_controllen for
1541 * potential reuse/whatever. So we go the pithier way. */
1542 n_rcvd_msgs_actual = std::min(n_rcvd_msgs_actual,
1543 // Let the following arg's value be K in the above comment.
1544 size_t(size_t(n_rcvd_msgs_or_error)
1545 - size_t(recvmmsg_hdr_end - recvmmsg_hdr_ptr))); // This is always >= 1.
1546 } // if (eof_marker)
1547
1548 if (do_log_trace)
1549 {
1550 FLOW_LOG_TRACE_WITHOUT_CHECKING
1551 ("Local_stream_batch [" << *this << "]: "
1552 "recvmmsg[" << peer_hndl << "] reports for message index "
1553 "[" << (n_rcvd_msgs_or_error - (recvmmsg_hdr_end - recvmmsg_hdr_ptr)) << "] (0-based) receipt of possible "
1554 "native handle [" << mdt.m_result_hndl << "]; as well as "
1555 "[" << msg_len << "] bytes of the blob's capacity [" << target_payload_blob_sz << "]; "
1556 "EOF-marker? = [" << eof_marker << "]. "
1557 "Total in-message records received: [" << n_rcvd_msgs_or_error << "] out of max [" << n_payloads << "]. "
1558 "Potentially corrected (due to 1st EOF-marker record) in-message count: [" << n_rcvd_msgs_actual << "].");
1559 }
1560
1561 total_rcvd_bytes += msg_len; // EOF markers contribute 0; no extra cost.
1562
1563 // All done (for this in-message)!
1564 }
1565 while ((++mdt_ptr, ++recvmmsg_hdr_ptr) != recvmmsg_hdr_end);
1566
1567 assert(graceful_close);
1568 if (n_rcvd_msgs_actual == size_t(n_rcvd_msgs_or_error))
1569 {
1570 // Mainstream case. Note that `n_rcvd_msgs_or_error > 0`; hence 'n_rcvd_msgs_actual > 0'.
1571 *graceful_close = false;
1572 }
1573 else
1574 {
1575 // Occurs at most once per connection.
1576
1577 assert((n_rcvd_msgs_or_error > 0) && "n=0 and n=-1 should have been dealt with earlier + return.");
1578 *graceful_close = true;
1579
1580 if (do_log_trace)
1581 {
1582 FLOW_LOG_TRACE_WITHOUT_CHECKING
1583 ("Local_stream_batch [" << *this << "]: Connected local peer socket [" << peer_hndl << "] "
1584 "tried to batch-read up-to [" << n_payloads << "] in-messages, each "
1585 "potentially into a scattered-blob plus possibly a native handle per each; "
1586 "and got ostensibly [" << n_rcvd_msgs_or_error << "] of those; but only [" << n_rcvd_msgs_actual << "] were "
1587 "actual in-messages (0 = allowed), while the rest were EOF-markers; therefore emitting "
1588 "graceful-close=1 flag.");
1589 }
1590 }
1591
1592 err_code->clear();
1593
1594 if (total_rcvd_bytes_or_null)
1595 {
1596 *total_rcvd_bytes_or_null = total_rcvd_bytes;
1597 }
1598
1599 m_n_used += n_rcvd_msgs_actual; // m_n_used increases here; except it might be unchanged, if *graceful_close.
1600 return true; // OMG. Amazing.

1693 msg_control_as_union.m_buf.data(), // Still need to load it with stuff after this (uninit for now).

1712 * since we're working with a boost.asio-managed socket; that's actually fine -- there's a portable
1713 * API native_non_blocking() in boost.asio for setting this -- but feels like the less interaction between
1714 * portable boost.asio code we use and this native stuff, the better -- so just keep it local here. */

1719 {
1720 /* Not even 1 byte of the blob was sent; and hence nor was payload_hndl. (Docs don't explicitly say that 2nd
1721 * part after the semicolon, but it's essentially impossible that it be otherwise, as then it'd be unknowable.
1722 * Update: Confirmed in kernel source and supported by this delightfully reassuring (in several ways) link:
1723 * [ https://gist.github.com/kentonv/bc7592af98c68ba2738f4436920868dc ] (Googled "SCM_RIGHTS gist").) */

1725 const Error_code sys_err_code{errno, system_category()};

1732 * 1, that is what boost.asio's own spiritually similar Peer_socket::write_some() would do in non_blocking() mode.
1733 * 2, then we can promise a specific code instead of making them check for the above 2 errno values.
1734 *
1735 * Subtlety: net_flow::Peer_socket::sync_receive() uses somewhat different semantics; it indicates would-block by
1736 * returning 0 *but* a falsy *err_code. Why are we inconsistent with that? Answer: Because net_flow is not
1737 * trying to be a boost.asio extension; we are. In net_flow's context (as of this writing) no one is surprised
1738 * when semantics are somewhat different from boost.asio; but in our context they might be quite surprised
1739 * indeed. */
1740 *err_code = boost::asio::error::would_block;
1741 return 0;
1742 }
1743 // else
1744
1745 assert(sys_err_code);
1746
1747 // All other errors are fatal.
1748 FLOW_ERROR_SYS_ERROR_LOG_WARNING(); // Log based on sys_err_code.
1749 FLOW_LOG_WARNING("Connected local peer socket tried to write scattered-blob "
1750 "([" << buf_seq_adapter.count() << "] sub-blobs, total size [" << payload_blob_sz << "], "
1751 "first sub-blob at @[" << buf_seq_adapter.buffers()->iov_base << "]) "
1752 "plus native handle [" << payload_hndl << "]; "
1753 "but an unrecoverable error occurred. Nothing sent.");
1754 *err_code = sys_err_code;
1755 return 0;
1756 } // if (n_sent_or_error == -1)
1757 // else if (n_sent_or_error != -1)
1758
1759 if constexpr(is_same_v<Protocol, Protocol_pkt_stream>)
1760 {
1761 assert((static_cast<size_t>(n_sent_or_error) == payload_blob_sz)
1762 && "sendmsg() returned neither -1 nor full-dgram-sent length; unexpected behavior for SEQPACKET! "
1763 "Dgram too large? Misunderstood/misdocumented OS API?");
1764
1765 FLOW_LOG_TRACE("sendmsg() reports the native handle [" << payload_hndl << "] was successfully sent; as "
1766 "were all of the dgram blob's [" << payload_blob_sz << "] bytes.");
1767 }
1768 else
1769 {
1770 assert((n_sent_or_error > 0)
1771 && "sendmsg() should return either -1 or a positive number (indicates success).");
1772
1773 FLOW_LOG_TRACE("sendmsg() reports the native handle [" << payload_hndl << "] was successfully sent; as "
1774 "were [" << n_sent_or_error << "] of the blob's [" << payload_blob_sz << "] bytes.");
1775 }
1776
1777 err_code->clear();
1778 return static_cast<size_t>(n_sent_or_error);
1779} // nb_write_some_with_native_handle()

1804 using ::MSG_CTRUNC;

1807 FLOW_ERROR_EXEC_AND_THROW_ON_ERROR(size_t, (nb_read_some_with_native_handle<Protocol, Mutable_buffer_sequence>),
1808 logger_ptr, peer_socket_ptr, target_payload_hndl_ptr,
1809 target_payload_blob, _1, message_flags);
1810 // ^-- Call ourselves and return if err_code is null. If got to present line, err_code is not null.
1811
1812 /* To reader/maintainer: The below isn't that difficult, but if you need exact understanding and definitely if you
1813 * plan to make changes -- even just clarifications or changes in the doc header -- then read the entire doc header
1814 * of nb_read_some_with_native_handle() first. */

1816 assert(peer_socket_ptr);
1817 assert(target_payload_hndl_ptr);
1818
1819 buffer_sequence_adapter<util::Blob_mutable, Mutable_buffer_sequence> buf_seq{target_payload_blob};
1820
1821 auto& peer_socket = *peer_socket_ptr;
1822 auto& target_payload_hndl = *target_payload_hndl_ptr;
1823
1824 FLOW_LOG_SET_CONTEXT(logger_ptr, Log_component::S_TRANSPORT);
1825 target_payload_hndl = {}; // We promised to set to this if no native-handle received (including on error).
1826
1827 /* Let us receive as much as possible into buf_seq area up to its size; and a native socket (if any) into
1828 * target_payload_hndl (if none, then it'll remain null()).
1829 * As explicitly documented in boost.asio docs: it does not provide an API for the latter (fairly hairy
1830 * and Linux-specific) feature, but it is doable by using recvmsg() natively via peer_socket.native_handle()
1831 * which gets the native handle (a/k/a FD).
1832 *
1833 * Recommending first looking at nb_write_some_with_native_handle(), as we operate symmetrically/similarly. */
1834
1835 const size_t target_payload_blob_sz = buf_seq.total_size();
1836
1837 /* Set up .msg_control*. This, and then interpreting the output after the call, is based on the out-equivalent in
1838 * nb_write_some_with_native_handle() as well as cross-referencing with some Internet sources.
1839 *
1840 * Before the call, we must reserve space for the ancillary out-data, if any; set msg_control to point to that;
1841 * and msg_controllen to the size of that thing. */
1842
1843 Msg_control_as_union msg_control_as_union;
1844 /* Caution! `man cmsg` in Linux says:
1845 * "When initializing a buffer that will contain a series of cmsghdr structures (e.g., to be sent with sendmsg(2)),
1846 * that buffer should first be zero-initialized to ensure the correct operation of CMSG_NXTHDR()."
1847 * (We are recv*(), not send*(), but seems it would apply too... unless kernel would do it in that case.)
1848 * We don't use CMSG_NXTHDR() though, so skip `msg_control_as_union.m_buf.fill(0)` here for perf.
1849 * Careful! May need to add this later, if adding more types of ancillary data (but not if merely increasing
1850 * N_PAYLOAD_FDS). */
1851
1852 msghdr recvmsg_hdr =
1853 {
1854 nullptr, // msg_name - Address; not used; we are connected.
1855 0, // msg_namelen - Ditto.
1856 /* msg_iov - Scatter/gather array. See similarly-themed notes at similar
1857 * spot in nb_write_some_with_native_handle(); they apply here too, more or less. */
1858 buf_seq.buffers(),
1859 // msg_iovlen - # elements in msg_iov. This is an *input* arg only; output is total length read: the ret value.
1860 buf_seq.count(),
1861 /* The following fields:
1862 * msg_control - In-arg; points to complex ancillary data area (which can only be properly navigated using
1863 * CMSG* macros) which is an out-arg of sorts. This value itself is an in-arg however.
1864 * msg_controllen - In-arg *and* out-arg. As in-arg, it's the length of area pointed by msg_control.
1865 * As out-arg, it describes the size of resulting ancillary data; however it is not to be itself checked
1866 * or used apparently; CMSG* macros shall be used to traverse ancillary data. Nevertheless msg_controllen
1867 * can/will be set by recv[m]msg() (not important for us here but can be important if reusing inputs in
1868 * a subsequent calls; see class Msg_batch_in).
1869 * msg_flags - This is an out-arg containing special feature flags. These may be checked below after call. */
1870 msg_control_as_union.m_buf.data(),
1871 sizeof(Msg_control_as_union::m_buf),
1872 0 // May or may not need to be initialized, but the language won't let me avoid it, and anyway it seems prudent.
1873 };
1874
1875 // Massage message_flags for our required purposes. Re. message_flags please read notes in our doc header.
1876
1877 /* If socket is un-readable then don't block; EAGAIN/EWOULDBLOCK instead. ...Further comment omitted;
1878 * see sendmsg() elsewhere in this header. Same thing here. */
1879 if constexpr(is_same_v<Protocol, Protocol_pkt_stream>)
1880 {
1881 // For dgram-based protocol: Also use MSG_TRUNC, so we can (at least) log some info on overflow.
1882 message_flags = (message_flags | (MSG_DONTWAIT | MSG_TRUNC));
1883 }
1884 else
1885 {
1886 message_flags = (message_flags | MSG_DONTWAIT);
1887 }
1888
1889 const auto n_rcvd_or_error
1890 = recvmsg(peer_socket.native_handle(), &recvmsg_hdr, message_flags);
1891
1892 // Carefully check all the outputs. Return value first.
1893
1894 if (n_rcvd_or_error == -1)
1895 {
1896 /* Not even 1 byte of a blob was read; and hence nor was any target_payload_hndl. (See comment in similar
1897 * spot in nb_write_some_with_native_handle(); applies here equally.) */
1898
1899 const Error_code sys_err_code{errno, system_category()};
1900 if ((sys_err_code == sys_err_codes::operation_would_block) || // EWOULDBLOCK
1901 (sys_err_code == sys_err_codes::resource_unavailable_try_again)) // EAGAIN (same meaning)
1902 /* Reader: "But, ygoldfel, why didn't you just check errno itself against those 2 actual Evalues?"
1903 * ygoldfel: "Because it makes me feel better about portable-ish style. Shut up, that's why. Get off my lawn." */
1904 {
1905 FLOW_LOG_TRACE("Connected local peer socket tried to read into scattered-blob "
1906 "([" << buf_seq.count() << "] sub-blobs, "
1907 "up to total size [" << target_payload_blob_sz << "], "
1908 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
1909 "plus possibly a native handle; and read attempt indicated would-block; "
1910 "not an error condition. Nothing received.");
1911 // Subtlety x 2: ...omitted. See similar spot in nb_write_some_with_native_handle(). Same here.
1912 *err_code = boost::asio::error::would_block;
1913 return 0; // target_payload_hndl already set.
1914 }
1915 // else
1916
1917 assert(sys_err_code);
1918
1919 // All other errors are fatal.
1920 FLOW_ERROR_SYS_ERROR_LOG_WARNING(); // Log based on sys_err_code.
1921 FLOW_LOG_WARNING("Connected local peer socket tried to read into scattered-blob "
1922 "([" << buf_seq.count() << "] sub-blobs, "
1923 "up to total size [" << target_payload_blob_sz << "], "
1924 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
1925 "plus possibly a native handle; but an unrecoverable error occurred. Nothing received.");
1926 *err_code = sys_err_code;
1927 return 0; // target_payload_hndl already set.
1928 } // if (n_rcvd_or_error == -1)
1929 // else if (n_rcvd_or_error != -1)
1930
1931 if (n_rcvd_or_error == 0)
1932 {
1933 /* WARNING doesn't feel right: it's a graceful connection end.
1934 * INFO could be good, but it might be too verbose depending on the application.
1935 * Use TRACE to be safe; caller can always log differently if desired. */
1936 FLOW_LOG_TRACE("Connected local peer socket tried to read into scattered-blob "
1937 "([" << buf_seq.count() << "] sub-blobs, "
1938 "up to total size [" << target_payload_blob_sz << "], "
1939 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
1940 "plus possibly a native handle; "
1941 "but it returned EOF meaning orderly connection shutdown by peer. Nothing received.");
1942 *err_code = boost::asio::error::eof;
1943 return 0; // target_payload_hndl already set.
1944 }
1945 // else if (n_rcvd_or_error > 0):
1946
1947 err_code->clear(); // Used by some checks below to mean "no error condition found yet."
1948
1949 // Check for in-dgram overflow (if applicable).
1950 if constexpr(is_same_v<Protocol, Protocol_pkt_stream>)
1951 {
1952 if (size_t(n_rcvd_or_error) > target_payload_blob_sz) // This is detectable due to *input* flag MSG_TRUNC.
1953 {
1954 /* As advertised log a WARNING and treat it as an error. Officially we said the in-dgram is eaten, and it is;
1955 * but in reality also a truncated in-dgram is now in the target buffer(s), though we didn't mention that. */
1956 FLOW_LOG_WARNING("Connected local peer socket tried to read into scattered-blob "
1957 "([" << buf_seq.count() << "] sub-blobs, "
1958 "up to total size [" << target_payload_blob_sz << "], "
1959 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
1960 "plus possibly a native handle; "
1961 "and it returned it read [" << n_rcvd_or_error << "] bytes successfully, but this overflows "
1962 "the aforementioned total-size; emitting error accordingly. Socket remains operational, but "
1963 "the overflowing in-dgram is lost.");
1964
1965 // Sanity-check that the *output* flag MSG_TRUNC is active (<=> ret value shows overflow, per docs + tests).
1966 assert((recvmsg_hdr.msg_flags & MSG_TRUNC)
1967 && "In-dgram size overflows user-supplied buffer <=> MSG_TRUNC out-flag supposed to be set.");
1968
1969 *err_code = error::Code::S_MESSAGE_SIZE_EXCEEDS_USER_STORAGE;
1970 /* target_payload_hndl already set.
1971 * Would `return 0` here but want to avoid leaking received handles, so defer until below. */
1972 }
1973 // else { No overflow. }
1974 }
1975 // else { No overflow possible in stream mode. }
1976
1977 /* Assuming no error found yet:
1978 *
1979 * Next, buf_seq-pointed area... which is already written to (its first n_rcvd_or_error bytes). Nothing to do.
1980 *
1981 * Next, recvmsg_hdr.msg_flags. Basically only the following is relevant: */
1982 if ((!*err_code) && (recvmsg_hdr.msg_flags != 0))
1983 {
1984 if (logger_ptr && logger_ptr->should_log(Sev::S_INFO, get_log_component()))
1985 {
1986 ios_all_saver saver{*(logger_ptr->this_thread_ostream())}; // Revert std::hex/etc. soon.
1987 FLOW_LOG_INFO_WITHOUT_CHECKING
1988 ("Connected local peer socket tried to read into scattered-blob "
1989 "([" << buf_seq.count() << "] sub-blobs, "
1990 "up to total size [" << target_payload_blob_sz << "], "
1991 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
1992 "plus possibly a native handle; "
1993 "and it returned it read [" << n_rcvd_or_error << "] bytes successfully but also returned raw "
1994 "out-flags value [0x" << std::hex << recvmsg_hdr.msg_flags << "]. "
1995 "Will check for relevant flags but otherwise "
1996 "ignoring if nothing bad. Logging at elevated level because it's interesting; please investigate.");
1997 }
1998
1999 if ((recvmsg_hdr.msg_flags & MSG_CTRUNC) != 0)
2000 {
2001 if (logger_ptr && logger_ptr->should_log(Sev::S_WARNING, get_log_component()))
2002 {
2003 ios_all_saver saver{*(logger_ptr->this_thread_ostream())}; // Revert std::hex/etc. soon.
2004 FLOW_LOG_WARNING_WITHOUT_CHECKING
2005 ("Connected local peer socket tried to read into scattered-blob "
2006 "([" << buf_seq.count() << "] sub-blobs, "
2007 "up to total size [" << target_payload_blob_sz << "], "
2008 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
2009 "plus possibly a native handle; "
2010 "and it returned it read [" << n_rcvd_or_error << "] bytes successfully but also returned raw "

2012 "That flag indicates more stuff was sent as ancillary data; but we expect at most 1 native "
2013 "handle. Other side sent something strange. Acting as if nothing received + error.");
2014 }
2015 *err_code = error::Code::S_LOW_LVL_UNEXPECTED_STREAM_PAYLOAD_BEYOND_HNDL;
2016 /* target_payload_hndl already set.
2017 * Would `return 0` here but want to avoid leaking received handles, so defer until below. */
2018 }
2019 // else { No truncation occurred. }
2020 } // if ((!*err_code) && (recvmsg_hdr.msg_flags != 0)) (but *err_code may have become truthy inside)
2021
2022 /* Lastly examine ancillary data (which might have also been truncated: MSG_CTRUNC above).
2023 * Use, basically, the method from `man cmsg` in Linux.
2024 *
2025 * We are interested whether *err_code (un-leak any received hndl) or !*err_code (emit any received hndl). */
2026 cmsghdr* const recvmsg_hdr_cmsg_ptr = CMSG_FIRSTHDR(&recvmsg_hdr);
2027 if (recvmsg_hdr_cmsg_ptr)
2028 {
2029 // There is some ancillary data. It can only (validly according to our expected protocol) be one thing.
2030 if ((recvmsg_hdr_cmsg_ptr->cmsg_level == SOL_SOCKET) &&
2031 (recvmsg_hdr_cmsg_ptr->cmsg_type == SCM_RIGHTS))
2032 {
2033 static_assert(N_PAYLOAD_FDS == 1,
2034 "Should be only dealing with one native handle with recvmsg() as of this writing.");
2035 memcpy(&target_payload_hndl.m_native_handle, CMSG_DATA(recvmsg_hdr_cmsg_ptr),
2036 sizeof(target_payload_hndl.m_native_handle));
2037
2038 if (*err_code)
2039 {
2040 target_payload_hndl.close(); // Avoid the native-handle (which is a received copy) leak.
2041 }
2042 // else { Cool: Native-handle received and emitted. }
2043 }
2044 else if (!*err_code) // && (unknown ancillary data type)
2045 {
2046 FLOW_LOG_WARNING("Connected local peer socket tried to read into scattered-blob "
2047 "([" << buf_seq.count() << "] sub-blobs, "
2048 "up to total size [" << target_payload_blob_sz << "], "
2049 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
2050 "plus possibly a native handle; "
2051 "and it returned it read [" << n_rcvd_or_error << "] bytes successfully but also "
2052 "unexpected ancillary data of cmsg_level|cmsg_type "
2053 "[" << recvmsg_hdr_cmsg_ptr->cmsg_level << '|' << recvmsg_hdr_cmsg_ptr->cmsg_type << "]. "
2054 "Acting as if nothing received + error.");
2055 *err_code = error::Code::S_LOW_LVL_UNEXPECTED_STREAM_PAYLOAD_BEYOND_HNDL;
2056 // target_payload_hndl already set. We shall return below.
2057 }
2058 // else if (*err_code && (unknown ancillary data type)) { Detected error before; stick with that one. }
2059
2060 /* Used to check here that CMSG_NXTHDR() would yield null (meaning no more ancillary data) and issued
2061 * LOW_LVL_UNEXPECTED_STREAM_PAYLOAD_BEYOND_HNDL if not. However it was a perf giveaway that was likely pointless,
2062 * even with a misbehaving opposing peer; we've only provided space for 1 FD, and MSG_CTRUNC (checked above) would
2063 * have pointed out if that were insufficient. So just move on. */
2064 }
2065 // else { No ancillary data, meaning no native handle; that's quite normal. }
2066
2067 if (*err_code)
2068 {
2069 return 0; // Any potential handle-leak avoided; can get out.
2070 }
2071 // else:
2072
2073 if constexpr(is_same_v<Protocol, Protocol_pkt_stream>)
2074 {
2075 FLOW_LOG_TRACE("Connected local peer socket tried to read into scattered-blob "
2076 "([" << buf_seq.count() << "] sub-blobs, "
2077 "up to total size [" << target_payload_blob_sz << "], "
2078 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
2079 "plus possibly a native handle; recvmsg() reports receipt of possible "
2080 "native handle [" << target_payload_hndl << "]; as well as "
2081 "an in-dgram taking [" << n_rcvd_or_error << "] of the "
2082 "blob's [" << target_payload_blob_sz << "]-byte capacity.");
2083 }
2084 else
2085 {
2086 FLOW_LOG_TRACE("Connected local peer socket tried to read into scattered-blob "
2087 "([" << buf_seq.count() << "] sub-blobs, "
2088 "up to total size [" << target_payload_blob_sz << "], "
2089 "first sub-blob at @[" << buf_seq.buffers()->iov_base << "]) "
2090 "plus possibly a native handle; recvmsg() reports receipt of possible "
2091 "native handle [" << target_payload_hndl << "]; as well as "
2092 "[" << n_rcvd_or_error << "] of the blob's [" << target_payload_blob_sz << "]-byte capacity.");
2093 }
2094
2095 return static_cast<size_t>(n_rcvd_or_error);
