51/**
52 * Internal, non-movable pImpl-lite implementation of sync_io::Native_socket_stream class.
53 * In and of itself it would have been directly and publicly usable; however Native_socket_stream adds move semantics
54 * which are essential to cooperation with sync_io::Native_socket_stream_acceptor and overall consistency with the rest
55 * of ipc::transport API and, arguably, boost.asio API design.
56 *
57 * @see All discussion of the public API is in sync_io::Native_socket_stream doc header; that class forwards to this
58 * one. All discussion of pImpl-related notions is also there. See that doc header first please.
59 * Then come back here.
60 *
61 * Impl design
62 * -----------
63 * ### Intro / history ###
64 * In the past transport::Native_socket_stream was one monolithic thing and therefore was not exactly easy
65 * to understand as a unit. It has since been split into this `sync_io`-pattern core (which, to be clear, is
66 * useful in and of itself) and transport::Native_socket_stream built around it. Due to this split,
67 * the complexity is split too, and each part is really quite manageable.
68 *
69 * To understand `*this`, the only real obstacle is grokking the `sync_io` pattern (see util::sync_io doc header).
70 * We will not recap it here in any depth. The essential idea, though, is that when `*this` internally needs to
71 * - async-read or async-write over `m_peer_socket` (the low-level transport); or
72 * - schedule a timer to fire in T time
73 *
74 * we must express either operation in terms of an async-wait (outsourced to the `*this` user).
75 * Namely:
76 * - async-read/write = async-wait on FD for readable/writable (outsourced) + on active event, we nb-read/write.
77 * - scheduling timer = with the help of util::sync_io::Timer_event_emitter, make it so that when it does fire,
78 * a certain FD is made readable; async-wait on FD for readable (outsourced) + on active event, we read
79 * to the firing.
80 *
81 * Those are the building blocks. Other than that, it's a matter of designating our 2 pipes and how each one's
82 * algorithm works. Both are async algorithms but expressed in terms of the above building blocks (in the
83 * `sync_io` pattern).
84 *
85 * Reminder: we do not deal with threads. To summarize our thread safety guarantees:
86 * - there are none, on a given `*this`; except
87 * - once in PEER state, send-ops (including `(*on_active_ev_func)()` from `start_send_*_ops()`) are allowed to
88 * be invoked concurrently to receive-ops (including `(*on_active_ev_func)()` from `start_receive_*_ops()`).
89 *
90 * To allow for the latter, the design is carefully split into 2 op-types; and the only data they ever touch
91 * in common comprise `m_*peer_socket`. This makes makes perfect sense: a Unix domain socket connection
92 * is full-duplex but done over a single FD. See #m_peer_socket doc header regarding how we ensure
93 * safe concurrency without sacrificing perf. (Spoiler alert: a tiny and simple critical section w/r/t
94 * `m_*peer_socket` only.)
95 *
96 * There is, also, NULL state, wherein one can sync_connect() et al. This is separate from the other 2, in this case
97 * preceding them entirely. We will soon discuss each algorithm: connect-ops, send-ops, receive-ops (though
98 * connect-ops is treated more as an afterthought at the end). Before we can speak of send-ops and receive-ops
99 * algorithms, we have to establish the substrate over which they operate: the protocol they speak. Don't worry;
100 * it is a simple protocol.
101 *
102 * Before even speaking of *that* more generally, there was this specific question to settle:
103 *
104 * ### Shutting down individual-direction pipes ###
105 * As required by the concepts, the out-pipe can be (arbitrarily preceding dtor call) ended via APIs
106 * `*end_sending()`. How is this internally implemented? I (ygoldfel) faced a dilemma in
107 * answering this question. Initially I was tempted to use the `shutdown()` native/boost.asio `Peer_socket` call
108 * which takes an argument `int how`, specifying which-direction pipe to shut down. Eventually I decided against it,
109 * because the exact semantics of `shutdown()` for stream UDS are rather unclear; vaguely speaking how they act is
110 * documented mostly w/r/t to TCP sockets, not local (UDS) ones, and even assuming UDS act the same isn't great, since
111 * TCP involves an unreliable medium with FIN/ACK/etc., while stream UDS internally just reliably shuffles around bytes
112 * in kernel memory. It's possible to get straight answers by reading kernel code, but how portable/maintainable is
113 * that? Lastly, when using `shutdown()`, the signaling-other-side semantics are particularly unclear; e.g., if I
114 * `shutdown(how=WRITE)`, will opposing peer get an "EOF" (connection gracefully closed)? Possibly but does that imply
115 * the other side was also closed? `EPIPE` is also involved (if closing reader -- N/A for us but...)... it's just
116 * low-level-obscure and hairy. (Color commentary: POSIX and Linux documented behavior doesn't have the formal
117 * completeness that Boost docs do; and if it did it'd still IMO (ygoldfel) be arguably less formally
118 * considered in its design.)
119 *
120 * Therefore I (ygoldfel) decided instead to take full control of it by *not* using `shutdown()` and instead using
121 * the following semantics/impl. The semantics = inspired both by common sense and `man` page references to similar
122 * behavior when using actual `shutdown()` on native stream UDS; but really the latter is a sanity-check on the former;
123 * and the former is king.
124 * - Two local flags, #m_snd_finished and a conceptual rcv_finished, which start `false` and can only be set to `true`
125 * (1x). (rcv_finished is really just for exposition; it is represented by the general condition wherein
126 * #m_rcv_pending_err_code stores a truthy `Error_code`.)
127 * - If side A user does `*end_sending()`, this sets #m_snd_finished and sends a special very-short
128 * "graceful half-duplex close" message -- albeit in order after any actual user messages from
129 * preceding `send_*()` calls; side B receives this and sets its rcv_finished (assigns a particular
130 * receives-finished `Error_code` to #m_rcv_pending_err_code).
131 * - #m_snd_finished means: Send-through any pending-to-be-sent user messages from `send_*()`; then
132 * the graceful-close message; and any `send_*()` calls after `*end_sending()` are
133 * an immediate error::Code::S_SENDS_FINISHED_CANNOT_SEND at best (though could be another error, if something
134 * else is detected... but to the user error=error and is probably to be treated the same).
135 * - If rcv_finished became true (due to the other side sending a graceful-close):
136 * - There will be no subsequent low-level data after that, by definition of how the protocol is designed, meaning
137 * the other peer shouldn't send any more (as said a few bullet points ago). On our side, though, we don't
138 * rely on that and simply stop reading, as on socket error.
139 * - This condition will be emitted via the `async_receive_*()` completion handler like any other
140 * connection-ending error (in this case, via error::Code::S_RECEIVES_FINISHED_CANNOT_RECEIVE; but for example
141 * `boost::asio::error::eof` is a graceful-UDS-close "error" and is conceptually very similar).
142 *
143 * The required internal code does require some care; but the resulting semantic certainty and control are
144 * IMO (ygoldfel) worth it. Using `shutdown()` instead might seem easy, but I strongly suspect the pain of semantic
145 * uncertainty would make up for that many times over.
146 *
147 * OK; we've decided how to deal with pipe ending -- basically, graceful-close is a message we explicitly need to
148 * encode when sending and understand when receiving -- so now we can get into the topic of the protocol.
149 *
150 * @note Historically, we then applied this idea of an explicit graceful-close quasi-message to the general
151 * concepts Blob_sender, Blob_receiver, etc. Therefore their other impls, such as Blob_stream_mq_sender
152 * and Blob_stream_mq_receiver, do the same.
153 *
154 * ### Internal protocol design ###
155 * This is most natural to discuss from the sending perspective; the receiving perspective will flow naturally from
156 * that. (We'll talk about send_native_handle() and async_receive_native_handle(); the `*_blob()` variants
157 * are mere degenerate versions of those. We'll also talk of end_sending() as opposed to async_end_sending(),
158 * as the latter involves the same protocol -- only adding a way of signaling the local user about completion
159 * which is irrelevant here.)
160 *
161 * To summarize, overall, send_native_handle() takes a non-`null()` #Native_handle, a non-empty util::Blob_const
162 * (buffer), or both; call the two together (one of which may be null/empty) a *user message*. The other side is to
163 * receive the entire *user message* unchanged and without re-ordering w/r/t other user messages from preceding or
164 * succeeding calls. In addition, if user invokes end_sending(), the effect on the other side should be as if a special
165 * (safely distinguished from normal user messages) user message was received indicating sending-direction pipe
166 * closing by the user (via a particular #Error_code emitted to async_receive_native_handle() completion handler).
167 *
168 * Lastly auto_ping() mandates some kind of internal ping message which is to be ignored by the receiver other
169 * than resetting any idle time engaged via idle_timer_run().
170 *
171 * That describes the top layer on either side. At the bottom layer (the low-level transport mechanism) is a local
172 * (Unix domain) peer socket through which we can send things. Briefly summarizing, it is capable of all of
173 * the above essentially directly with the following important exceptions or caveats:
174 * -# Stream UDS don't usually# implement message boundary preservation -- hence messages must be
175 * encoded somehow in such a way as to indicate message boundaries (and decoded on the other side).
176 * This is further complicated by the case when a native handle must also be sent together with the
177 * boundary-preserved blob.
178 * - (#) `SOCK_STREAM` does not preserve message boundaries. `SOCK_SEQPACKET` is very similar, apparently, but
179 * *does*. I (ygoldfel) decided against it due to a subjective feeling of "baggage": it's Linux-only-ish
180 * (not POSIX), rarely used, and apparently spiritually associated with the obscure SCTP protocol. None of this
181 * is fatal (that I know of) but does not seem worth it given that, ultimately, a couple of bytes to encode
182 * a length over `SOCK_STREAM` = both easy and of low perf cost. (`SOCK_DGRAM` is not that suitable, because we
183 * require a connection-based model; or perhaps more accurately would require us to build a small layer
184 * simulating such.)
185 * -# There is no# equivalent to the end_sending() (close-one-direction-but-not-the-other) feature
186 * natively -- hence it must be encoded somehow yet without accidentally clashing with a normal user message
187 * (some kind "escaping" or equivalent is needed).
188 * - (#) We avoid `shutdown(int how)` for the reasons detailed above.
189 * -# There is no built-in ping message either.
190 *
191 * Important update: Leaving the text above intact for historical reference. However: after about a year we decided to
192 * in fact use `SOCK_SEQPACKET` when it is available. Rationale: We found that performance can be significantly
193 * affected under load by how many syscalls are made; by maintaining message boundaries this mode allows to cut-down
194 * the syscall count by 2x on both sides (when/if we support batching via Linux-only `*mmsg()` functions, we could
195 * do even more). That's in addition to the convenience and simplicity of it. (The latter consideration is
196 * partially mooted by needing to support both, in case `SOCK_SEQPACKET` is not available. However we keep the code
197 * paths essentially separate, so each one is reasonably clean.) So, this impl does support both modes
198 * (determined at compile-time, universally); in code you'll find `if const()` and similar constructions to that
199 * effect.
200 *
201 * @see potentially perf-relevant notes in doc header for Native_socket_stream_cfg::S_USE_OS_DGRAM_SUPPORT.
202 * Spoiler alert: `SOCK_SEQPACKET`, in Linux, will apply an additional potentially-would-block-yielding
203 * limit on unread kernel-held messages (plus the kernel send-buffer total size limit either way).
204 *
205 * Important update: We now support batch-receipt via Linux's `recvmmsg()`. This is referenced in the preceding
206 * paragraph as an informal to-do; well, now that to-do is done on the receive side. (That leaves the send side,
207 * but the arguments for adding that are significantly less convincing. Discussion omitted here though.)
208 * Unlike mere `SOCK_SEQPACKET` support -- which is entirely doable internally to this impl class -- batch-receiving
209 * requires the user to actually request it, namely by invoking async_receive_native_handle_batch() or
210 * async_receive_blob_batch(). If the OS supports *both* `SOCK_SEQPACKET` *and* `recvmmsg()` thereof
211 * (Native_socket_stream_cfg::S_USE_OS_DGRAM_SUPPORT and Native_socket_stream_cfg::S_USE_OS_DGRAM_BATCH_SUPPORT),
212 * then such a blob-receive request is implemented natively using those techniques. Otherwise, again
213 * via compile-time `if constexpr()` we emulate it (at little to no perf loss -- but certainly no perf gain versus
214 * non-batched receipt).
215 *
216 * For the emulation we can (and do) use the async_receive_batch_emulation() tool, giving it a functor built on
217 * top of our own standard-single-message-receive op (basically, the core of async_receive_native_handle()).
218 * (Blob_stream_mq_receiver does the same; as can any other Blob_receiver / Native_handle_receiver impl.)
219 *
220 * For the non-emulation code-path (for batch-receiving) -- obviously preferred for performance if available --
221 * we cooperate with (essentially outsource to) our buddy Native_socket_stream_msg_batch_in, which
222 * - implements the required Msg_batch_in concept (pointer to an impl of which the user shall pass to
223 * `async_receive_*_batch()`);
224 * - is therefore the target of our #Native_handle_batch_in and #Blob_batch_in aliases;
225 * - speaks the protocol described below.
226 *
227 * Using batch-receiving does not change the per-message protocol; and one can mix-and-match single-message
228 * receiving and batch-receiving calls if desired.
229 *
230 * @see Native_handle_receiver concept class doc header section "Batch-receiving." It provides key
231 * background/discussion about this tricky thing, in a general way.
232 *
233 * ### Protocol with `Protocol_byte_stream` (OS does not maintain message boundaries) ###
234 * Here's the protocol to handle these.
235 * - Each user message (send_native_handle()) is represented, in the same order, by 1+ bytes and optionally
236 * a handle: all sent over stream UDS. Suppose (at least for exposition) we support blobs of size up to 64KiB.
237 * The user message is then encoded as 1-2 *payloads* in this order:
238 * - Payload 1 (required): The *meta-length*, encoded as a native-endianness 2-byte number, indicating size
239 * of the meta-blob provided by the user; 0x0000 indicates no meta-blob. Plus, byte 1 may be paired with
240 * a native handle; or no such handle if user provided no handle. Note that meta-length=0 means there
241 * *must* be a handle; otherwise the user's sending nothing (not allowed by API).
242 * - Payload 2 (present unless meta-length=0x0000): The user-provided meta-blob, with given meta-length, verbatim.
243 * - Graceful-close message (from end_sending()) is encoded as 1 *payload*:
244 * - Payload 1 (required): 2-byte number 0x0000; no native handle. Note this doesn't conflict with the
245 * above, since there 0x0000 implies there is a handle too.
246 * - Auto-ping message (from auto_ping()) is encoded as 1 *payload*:
247 * - Payload 1 (required): 2-byte number 0xFFFF; no native handle. Note this doesn't conflict with the
248 * above, since the length 0xFFFF is not allowed (due to Native_socket_stream_cfg::S_MAX_META_BLOB_LENGTH
249 * excluding it).
250 *
251 * Naturally if user doesn't end_sending() before the whole thing is destroyed, then there is no
252 * graceful-close message either.
253 *
254 * ### Protocol with `Protocol_pkt_stream` (OS maintains message boundaries) ###
255 * Here's the protocol to handle these.
256 * - Each user message (send_native_handle()) is represented, in the same order, by 1+ bytes and optionally
257 * a handle: all sent over dgram-stream UDS. Suppose (at least for exposition) we support blobs of size up to
258 * 64KiB. The user message is then encoded as *one datagram* (<=> OS-write call) consisting of 1-2 *payloads*
259 * in this order:
260 * - Payload 1 (required): The *meta-header*, encoded as the 2-byte number 0x0000,
261 * indicating: "this datagram encodes a single user message; or graceful-close" (but read on).
262 * - Payload 2 (present unless user provided no meta-blob): The user-provided meta-blob of length equal to
263 * the size of the datagram minus length of payload 1 (that is, 2 bytes).
264 * - Thus if the length of the datagram *is* 2, then there is no payload 2, hence no user-provided meta-blob.
265 * - Plus, datagram may be paired with a native handle; or no such handle if user provided no handle.
266 * - If there is no payload 2, then the datagram *must* be paired with a native handle. Otherwise the user's
267 * sending nothing (not allowed by API).
268 * - Graceful-close message (from end_sending()) is also *one datagram* (<=> OS-write call) encoded as 1
269 * *payload*:
270 * - Payload 1 (required): 2-byte number 0x0000; no native handle. Note this doesn't conflict with the
271 * above, since there 0x0000 + no payload 2 => there is a handle too.
272 * - Auto-ping message (from auto_ping()) is also *one datagram* (<=> OS-write call) encoded as 1
273 * *payload*:
274 * - Payload 1 (required): 2-byte number 0xFFFF; no native handle.
275 *
276 * Naturally if user doesn't end_sending() before the whole thing is destroyed, then there is no
277 * graceful-close message either.
278 *
279 * To handle an in-datagram following this algorithm without copying of user-data one shall use scatter/gather
280 * semantics of an OS-read op: Provide an array of at least 2 target-buffers; buffer 1 exactly 2-bytes long;
281 * and buffer 2 (or buffers 2, 3, ...) of total length not below receive_meta_blob_max_size(); plus a target
282 * `Native_handle` to fill if relevant. Now, the message type can be determined from the following bits of info:
283 * - Is the 2-byte buffer 1 equal to 0x0000 -- or 0xFFFF?
284 * - Is the in-datagram's length, minus 2, equal to zero -- or a positive number?
285 * - Was a native-handle received -- or not?
286 *
287 * Subtlety: If target buffer 2 (or 2, 3, ... in total) is not large enough to receive an entire given in-message,
288 * then the OS-read may need to truncate an in-datagram on receipt. We use the OS feature which detects this
289 * and issue error::Code::S_MESSAGE_SIZE_EXCEEDS_USER_STORAGE in that case. (Spoiler alert:
290 * ultimately it is asio_local_stream_socket::Msg_batch_in::nb_read() that does this; and
291 * #Native_handle_batch_in / #Blob_batch_in a/k/a Native_socket_stream_msg_batch_in is a thin wrapper around
292 * asio_local_stream_socket::Msg_batch_in.)
293 *
294 * ### Outgoing-direction impl design ###
295 * At construction, or entry to PEER state, we get a connected #m_peer_socket; and then it's off to the races.
296 * Every message, whether from `send_*()`, the periodic auto_ping() timer firing, or `*end_sending()`, translates
297 * into a series of 1+ *low-level payloads*: each low-level payload containing: 0-1 `Native_handle`s associated with
298 * the 1st byte of the following; and ("the following") a contiguous location in memory (pointer + length) to send.
299 * At steady state, we can simply attempt to nb-send each payload, in sequence. Unless would-block is encountered --
300 * which should not occur often assuming good opposing-side behavior -- this will simply work.
301 *
302 * If it does not -- would-block does occur -- then:
303 * - Any unsent payload(s), headed potentially by a fragment of one of them (if one was partially sent), have
304 * to be *copied* and *enqueued* on a pending-payloads queue. This is #m_snd_pending_payloads_q.
305 * - The partial-send situation is possible with `Protocol_byte_stream` but not with `Protocol_pkt_stream`.
306 * - We initiate an async-wait on #m_peer_socket becoming writable, executed via `sync_io` pattern.
307 *
308 * While this queue is not empty, any additional payloads (from the aforementioned sources -- `send_*()`, etc.)
309 * that might be built go to the back of `m_snd_pending_payloads_q`. In the case of `Protocol_pkt_stream` it is
310 * required that a given Snd_low_lvl_payload corresponds 1-1 to an attempted-but-would-blocked OS-write. In the
311 * case of `Protocol_byte_stream` this would not be strictly necessary but, partial success aside, is the most
312 * convenient thing to do in any case in avoiding further copying.
313 *
314 * While in this would-block state (where that queue is not empty), we await the async-wait's completion.
315 * Once it does come in we just try to send off the payloads again, this time off the queue. The sent stuff
316 * gets dequeued, if anything is left another async-wait is in order; etc.
317 *
318 * ### Incoming-direction impl design -- `Protocol_byte_stream` ###
319 * It is dealing with the in-pipe, which is independent of the out-pipe, with the exception of sharing the same
320 * handle (FD), `m_peer_socket`. (We've spoke of this already. Just see `m_peer_socket` doc header.)
321 * To deal with it, operate based on what we know of our own out-pipe:
322 *
323 * The outgoing-direction algorithm is written to be agnostic as to what each low-level payload means:
324 * user messages (including graceful-close and auto-ping) are simply translated into "1+" payloads each, and then
325 * `m_snd_pending_payloads_q` just treats them as a sequence of payloads (it no longer matters how they came to be).
326 * However the incoming-direction algorithm does need to decode them back into the user messages that they
327 * originally meant. To see how, just go back to the "Internal protocol design" above. Each message starts with
328 * "payload 1," which is also the only one that might contain a #Native_handle. The payload 1 blob, always of length 2,
329 * is the "meta-length" field. In exactly 1 scenario -- where it's neither 0 nor 0xFFFF -- is there payload 2 to
330 * read; and that one's length is the meta-length, and it is simply the entire meta-blob the sender sent. In
331 * all other scenarios, there is no payload 2 -- the message is finalized; and it's off to the next one again.
332 *
333 * So it's a state machine; not too exotic. Read payload 1; if that's the whole message back to the start;
334 * otherwise read payload 2; back to the start; if error (including idle-timeout or graceful-close)
335 * then stop algorithm.
336 *
337 * As in the Native_handle_receiver/Blob_receiver concepts at most 1 `async_receive_*()` is outstanding at a time,
338 * that's all there is to the algorithm. That said the code can get somewhat hairy, due to the difficulty of
339 * expressing things that would've been pretty simple with boost.asio, such as `boost::asio::async_read()`
340 * free function (which will read exactly N bytes, no less, unless error occurs). We cannot do that stuff, as
341 * we have to issue async-waits to the user via `sync_io` pattern. #Native_handle complicates it a bit more too.
342 * That said all that stuff is tactical really. Just see the code.
343 *
344 * ### Incoming-direction impl design -- `Protocol_pkt_stream` ###
345 * Essentially all of the above applies except for the one key (for perf among other things) difference, albeit
346 * tactical. To wit: Even if we wanted to, we couldn't do an OS-read of payload 1 and then a separate OS-read of
347 * payload 2. Fortunately (actually in some ways it is *the* reason to use `SEQPACKET`/`Protocol_pkt_stream`) we
348 * can read both, using scatter/gather, in delightful fashion in exactly 1 OS-read. Please see above
349 * in section "Protocol with `Protocol_pkt_stream` (OS maintains message boundaries)." (There's no need to encode
350 * any length, as the OS will maintain message boundaries for us.)
351 *
352 * So, for a regular (non-batch) receive (`async_receive_{native_handle|blob}()`), we implement this protocol as
353 * a single in-dgram read, or repeat this on would-block, upon asking user to async-wait for socket readability.
354 *
355 * There is a compile-time dichotomy as to which code-path shall implement this same per-message protocol, but only
356 * for batch-receiving (`async_receive_*_batch()`). In that case:
357 * - If Native_socket_stream_cfg::S_USE_OS_DGRAM_BATCH_SUPPORT is `true`:
358 * Our partner Native_socket_stream_msg_batch_in::nb_read(), for performance, shuffles things
359 * around as needed to filter out auto-pings (while noting their presence, to head off idle timeout) and
360 * graceful-close (while noting its presence and communicating it via out-arg to `*this`), resulting in only
361 * regular messages being accessible to the user (via Msg_batch_in concept accessors). Hence
362 * `*this` essentially wraps a single
363 * `Native_socket_stream_msg_batch_in::nb_read()` (unless it yields would-block -- then it has the usual
364 * logic to ask user to async-wait for readability, indicating which triggers another `nb_read()` attempt).
365 * - If Native_socket_stream_cfg::S_USE_OS_DGRAM_BATCH_SUPPORT is `false`:
366 * As noted earlier, in this case we use the tool async_receive_batch_emulation() to implement the batch-receive
367 * as a series of, basically, single-message `async_receive_{native_handle|blob}()` calls.
368 * So in this case it is a series of stuff, where "stuff" is the short paragraph above that starts with
369 * "So, for a regular (non-batch) receive...."
370 *
371 * This dichotomy is not really lacking in code reuse per se -- there's nothing copy/pasted -- but some simple logical
372 * elements (e.g., how an auto-ping or graceful-close or regular in-message is represented) are indeed present in both
373 * places. We think it's reasonable, especially given how tight and quick
374 * `Native_socket_stream_msg_batch_in::nb_read()` is as a result.
375 *
376 * ### Connect-ops impl design ###
377 * The algorithm itself is easy enough to just follow in the code. What is subtle however, we think, is why it is
378 * structured the way it is. As per the public API of sync_io::Native_socket_stream (and the async-I/O-pattern
379 * counterpart transport::Native_socket_stream for that matter), there is only the one public API, sync_connect():
380 * it is non-blocking and synchronous, meaning it totally succeeds or fails immediately. async_connect() and
381 * start_connect_ops() are `private`; replace_event_wait_handles() does not affect connect-ops. Yet sync_connect()
382 * is written around those `private` facilities. One, how is this even possible -- if there's (even internally)
383 * an async step, how can sync_connect() be synchronous yet non-blocking? And two, supposing that is fine, then
384 * why write it this way -- as if following the `sync_io` pattern but entirely within the internal code of a `*this`?
385 *
386 * For the 1st question: First we quote the transport::Native_socket_stream public doc header which explains
387 * why there is only `sync_connect()` but no `async_connect()`:
388 * "Without networking, the other side (Native_stream_socket_acceptor) either exists/is listening; or no.
389 * Connecting is a synchronous, non-blocking operation; so an `async_connect()` API in this context only makes
390 * life harder for the user. (However, there are some serious plans to add a networking-capable counterpart
391 * (probably via TCP at least) to Native_socket_stream; that one will almost certainly have an `async_connect()`,
392 * while its `sync_connect()` will probably become potentially blocking.)" So that is why it works: internally
393 * with a Unix domain stream socket async-connect either immediately succeeds or fails in
394 * all situations, at least in Linux (as of this writing all that's supported). (There are some further details
395 * inline in `async_connect()` impl.) So internally it's simple to do a non-blocking sync-connect; return
396 * success/failure if not would-block; or async-wait for writability in the rare would-block situation; this too
397 * is resolved quickly, and we can internally use a future-promise pair to briefly-await that resolution inside
398 * sync_connect().
399 *
400 * That doesn't answer the 2nd question: Why is it written like this? It would seem the code could be more compact
401 * if it were not written in the `sync_io`-pattern fashion, wherein we have a (`private`) start_connect_ops() and
402 * call it as-if we're an outside connect-ops user of sorts. Answer: Truthfully, historically, I (ygoldfel)
403 * originally wrote it that way not really contemplating closely whether a local-socket connect-op can really
404 * take a blocking amount of time; and async_connect() *was* public. Once I looked into it however, it became
405 * clear that it's always quick, which allowed various APIs -- all the way up to ipc::session::Session connect API --
406 * quite a bit more convenient to use. At that point making only a public `sync_connect()` became a no-brainer.
407 * However, while I did contemplate then cutting down that code to get rid of the `sync_io`-pattern structuring,
408 * I realized that over time this would only hurt us. Why? Answer: As we said publicly in the quote above,
409 * there probably *will* be a networked public `async_connect()`, and a huge % of the code in the
410 * networked-socket-stream class containing it will be reused from Native_socket_stream. At that point
411 * the `sync_io`-pattern-based structuring will come in quite handy. It's a subjective decision, undoubtedly, but
412 * I feel pretty good about it. Also, it's really not all that much complex; after all the `sync_io` pattern
413 * is used all over the place including our own `*this` send-ops and receive-ops.
414 *
415 * ### Error handling ###
416 * See #m_snd_pending_err_code and #m_rcv_pending_err_code doc headers. It's pretty simple:
417 * once that pipe is hosed, the appropriate one is set to truthy. Now any user sending or receiving (whichever
418 * is applicable to the pipe) immediately yields that error.
419 *
420 * @todo Internal Native_socket_stream and Native_socket_stream_acceptor queue
421 * algorithms and data structures should be checked for RAM use; perhaps
422 * something should be periodically shrunk if applicable. Look for `vector`s, `deque`s (including inside `queue`s).
423 *
424 * ### Protocol negotiation ###
425 * This adds a bit of stuff onto the above protocol. It is very simple; please see Protocol_negotiator doc header;
426 * we use that convention. Moreover, since this is the init version (version 1) of the protocol, we need not worry
427 * about speaking more than one version. On the send side: All we do is send the version ahead of the first
428 * payload that would otherwise be sent for any reason (user message from `send_*()`, end-sending token from
429 * `*end_sending()`, or ping from auto_ping(), as of this writing), as a special message that is identical to
430 * a normal payload 1 (see above) whose contents are (instead of the usual meaning) the protocol version,
431 * namely the value `1`, meaning version 1. Conversely on the receive side: we expect the first message received to be
432 * a native-handle-free payload 1 with contents encoding a version number; then we let Protocol_negotiator
433 * do its thing in determining the protocol version spoken.
434 *
435 * (The preceding paragraph was written before Flow-IPC supported `Protocol_pkt_stream` if available; it supported
436 * only `Protocol_byte_stream` at the time.)
437 *
438 * @note It is very tempting to do that initial send in lazy fashion: meaning, about to send the first "real" payload?
439 * OK, then pre-pend the negotiation message. However this can create trouble in the future, if
440 * a future protocol wants to be backwards-compatible (support more than 2 protocol versions): we'll need
441 * to have received the opposing guy's preferred version, and thus determined which version to speak,
442 * before sending further (non-negotiation) messages. Bottom line... the initial send shall occur as soon
443 * as we are operational (start_send_blob_ops()).
444 *
445 * After that, we just speak what we speak... which is the protocol's initial version -- as there is no other
446 * version for us. (The opposing-side peer is responsible for closing the stream, if it is unable to speak version 1.)
447 * Update: We now have `Protocol_pkt_stream` support with its own (very slightly different from the one used for
448 * `Protocol_byte_stream`) protocol on top. The `Protocol_byte_stream` protocol is not changed. However, the
449 * support for an entirely new socket type is a difference; but it's not like whether to use it can be negotiated
450 * in any sane way. So we've decided to handle it like this, out of an abundance of caution:
451 * - The fact that on the same machine both ends must use the code that supports `pkt` protocol is just a fact...
452 * and it cannot really be negotiated or detected... so users will (this time only) just have to ensure both
453 * ends use the same (or compatible, in the future) software.
454 * - We still bump up the protocol version to 2 however, just to be clear about it. For simplicity, at this early
455 * juncture, we won't take advantage of Protocol_negotiator ability to support back-versions; meaning we'll just
456 * say we support version 2 and *only* version 2.
457 *
458 * As for the Protocol_negotiator mechanics themselves: If `pkt` protocol is in effect (as opposed to `byte`),
459 * then the above mechanic still holds with the following addition/clarification: The protocol-version-bearing
460 * payload shall *be* the first in-datagram received and out-datagram sent. Subtle detail:
461 * if the first async-receive op issued by the user is a batch-receive, then our batch-handling bro
462 * Native_socket_stream_msg_batch_in::nb_read() handles the protocol negotiation inside it as needed; we just
463 * give it a ptr to #m_protocol_negotiator, and it takes care of business. This means some slight duplication of
464 * logic between batched-receive protocol negotiation versus normal-receive protocol negotiation.
465 *
466 * If we do add more protocol versions in the future, then things *might* become somewhat more complex (but even
467 * then not necessarily so). This is discussed in the `Protocol_negotiator m_protocol_negotiator` member doc header.
468 *
469 * @note We suggest that if more version(s) is/are added, then the above notes be kept more or less intact; then
470 * add updates to show changes. This will provide a good overview of how the protocol evolved; and our
471 * backwards-compatibility story (even if we decide to have no backwards-compatibility).
472 */

948 /**
949 * The resulting native handle (possibly null) intended to be assigned to `*m_target_hndl_ptr` -- the user's
950 * specified location -- if and only if the receive op ultimately succeeds. If it fails, then any handle
951 * stored here shall be closed (preventing a leak) and forgotten (preventing double-close and similar
952 * nefariousness).
953 *
954 * ### Sorry, what? Rationale ###
955 * It's easiest to explain by starting in a world where there is no `m_own_hndl`, only #m_target_hndl_ptr.
956 * Reading a particular in-message involves a state machine, and this state machine can be simple or complex,
957 * depending especially on Native_socket_stream_cfg::S_USE_OS_DGRAM_SUPPORT. (It is simplest if dgrams are
958 * available, so we use them; otherwise we don't have msg boundaries natively, so we have to do it ourselves
959 * w/r/t a byte stream.) `m_own_hndl` is helpful either way, but in the complex case it's easiest to explain.
960 * So: With a byte stream, I might read (say) 1 byte and a non-null handle; but that's not enough -- I now
961 * need the rest of payload 1 which might encode the length of the meta-blob that came with the handle, or 0
962 * (and other possibilities). Then I may have to read that meta-blob (or not). Then I can report the
963 * handle -- with the other stuff -- to user. No problem: algorithmically it'd be fine to save the handle
964 * straight into the user-specified place: `*m_target_hndl_ptr`. Later we'll get the rest of the message,
965 * report the length received: cool. Or, if we hit some error before getting the in-message, we'll report
966 * the error; by contract `*m_target_hndl_ptr` is meaningless/to be ignored (we touched it; fine): still cool.
967 *
968 * What's not cool in that latter (error) case, though, is that the handle (descriptor) we actually did receive
969 * (and it is a copy of the one the opposing side sent to us) now leaks. So what we really want is, in that
970 * case, to "un-leak" `*m_target_hndl_ptr`. That's doable, certainly, but in our case we have that complex
971 * code path with the state machine; which means it's not all that easy. Or maybe it's easy enough, but
972 * maintainers that would change this code path would have a hard time keeping it working -- and a leak here
973 * is very quiet.
974 *
975 * util::Own_native_handle, which is `unique_resource<Native_handle>` (with `{}` as the default/"unallocated"
976 * sentinel), which (if you're not familiar) is kind-of like `unique_ptr<Native_handle>` sans heap-allocs:
977 * it is made for this. The idea is: the moment we have a `Native_handle` from a lower layer, subsume it
978 * into an auto-closing `Own_native_handle`. Then, once ready to actually *emit it to the user*, finally
979 * assign it to `*m_target_hndl_ptr`; and `m_own_hndl.release()` (to prevent double-close and other bad things).
980 * (Those last two things combined = util::disowned_native_handle().) Now it's up to the user to worry about
981 * leaking or otherwise. The emission-to-user spots are exactly these:
982 *
983 * - In async_receive_core(), when about to *synchronously* report a successfully read in-message.
984 * - In `rcv_on_ev_peer_socket_..._stream_readable_or_error()`, when about to *asynchronously* (through
985 * #m_on_done_func) report a successfully read in-message.
986 *
987 * Any other eventuality causes `m_own_hndl.get()` -- if it ever became non-null in the first place -- to be
988 * nicely auto-closed when this Rcv_user_request is destroyed (which happens at the end of
989 * the `_core()` op, synchronously or otherwise), at the latest.
990 *
991 * Is it necessary to store it as state? No: It could also be passed-around as args and captures. Either way
992 * is fine; but the same applies to the other members here; this one is not special.
993 *
994 * Is it necessary to store it as state *here*, as opposed to directly in `_impl`? No: We could store it
995 * separately. It is quite convenient, however, as this way it starts off null at the start of the op. That's
996 * indispensable, so otherwise we'd have to do it by hand: Why bother, when we've got this
997 * `optional<Rcv_user_request>` rig already just for that?
998 */
999 util::Own_native_handle m_own_hndl;
1000 }; // struct Rcv_user_request

1220 * pop of the kernel buffer will get *some* message, even if it's not the auto-ping we wanted to send;

1887 * INFO-logs current stats. See below regarding when it's best to invoke this.
1888 *
1889 * ### Rationale (applies to snd_log_stats() and rcv_log_stats() too) ###
1890 * `*log_stats()` just INFO-logs the stats (if in PEER state; otherwise not much to log); but how/why should they be
1891 * called as of this writing? Answer: In dtor is an obvious place, near the already-present INFO-log there. However
1892 * a `*this` often sits around for a while, even though really it's for practical purposes useless, in one or
1893 * both directions, because (although forever in PEER state) it is hosed (#m_snd_pending_err_code or
1894 * #m_rcv_pending_err_code has become truthy). So the other type of situation we'd want to call this is when
1895 * that occurs. We use the following approach (out of at least a couple possible ones) to detect this in
1896 * a hopefully-not-spaghetti-ish way:
1897 *
1898 * A `*this` is essentially a straightforward state machine in PEER state; APIs are called in series by user,
1899 * and during the course of each API's impl `m_*_pending_err_code` might change from falsy to truthy.
1900 * Each impl, first, checks whether it is truthy already; if so it returns. Once such things are out of the
1901 * way, the true impl executes. At the end of this impl check whether the thing is truthy -- if so call us.
1902 *
1903 * Reminder: there are the actual APIs, and then there's the thing where (in `sync_io` pattern we follow)
1904 * our state machine cannot proceed until a handle (socket/et al) is readable or writable (hosed = readable/writable
1905 * too), so we inform the user, and the user does detect it later and invokes a certain functor to inform us.
1906 * The reminder: this is also an API in various contexts including this one. The user is calling into `*this`.
1907 * (In particular, we might try to -- say -- read #m_peer_socket and detect its hosing which would
1908 * truthify #m_rcv_pending_err_code. Hence you get the point.)
1909 *
1910 * Another approach would've been to call us whenever `m_*_pending_err_code` becomes truthy, right as it becomes

1912 * arguably more straightforward. As written, though, it's not quite so simple; there are various patterns
1913 * (very tactically speaking) as to how we touch those data members, so (yes, it is subjective) the resulting
1914 * logic would be more spaghetti-like.
1915 *
1916 * ### Subtlety 1: Versus user handler ###
1917 * In cases where the impl invokes a user handler before returning (e.g., `sync_io`-pattern event handlers
1918 * calling on_done_func()), do the truthy-`m_*_pending_err_code` check + possible `*log_stats()` call *before*

1923 * ### Subtlety 2: Which halves? ###

1925 * receive-op may execute concurrently; and each stats-half is touched only by its own ops. Hence this
1926 * both-halves dump is only for fully-exclusive contexts (dtor); from a send-op or receive-op context use

2018 /**
2019 * The peer Unix domain socket; or null pointer if we've detected the connection has become hosed
2020 * and hence have ceased all all work on the boost.asio `Peer_socket` short of its destruction.
2021 *
2022 * The Unix domain socket can be of either native protocol `Protocol_byte_stream` (`SOCK_STREAM` natively)
2023 * or `Protocol_pkt_stream` (`SOCK_SEQPACKET` natively). As discussed in "Impl" section of our class doc header:
2024 * we prefer the latter if available, otherwise the former. Native_socket_stream_cfg::Protocol alias
2025 * determines this, as you can see.
2026 *
2027 * Note that (1) it starts non-null (see also related #m_peer_socket_hosed), and is in
2028 * "open" (FD-bearing) state from the start -- even if the NULL-state ctor was used; and (2) can only
2029 * become null (irreversibly so) when in PEER state, only on error.
2030 * - In State::S_NULL #m_state, this is an "open" (FD-bearing) but unconnected socket.
2031 * - In State::S_CONNECTING #m_state, this is the same socket, in the process of connecting.
2032 * (If connect fails, the FD persists but goes back to just a steady-state "open" unconnected state.)
2033 * - In State::S_PEER #m_state, this is either the same socket, now connected; or, upon a detected error in
2034 * either direction, a null pointer.
2035 *
2036 * Moreover the FD cannot be replaced with another FD: if PEER-state ctor is used, then that FD is connected
2037 * from the start; if NULL-state ctor is used, then that FD is unconnected but may become connected (if/when)
2038 * State::S_PEER is reached (via async_connect()).
2039 *
2040 * `*m_peer_socket` is used *exclusively* for non-blocking calls; *never* `.async_*()`. That conforms to
2041 * the `sync_io` pattern. See #m_nb_task_engine doc header.
2042 *
2043 * ### Rationale ###
2044 * The above facts are important -- namely that from the very start (up to an error) the FD is loaded and never
2045 * changes -- because the watcher FD-wrappers used in the `sync_io` pattern can be simply and correctly
2046 * initialized at any time and not change thereafter (in terms of what FD they wrap).
2047 *
2048 * As for the null-pointer state, it exists for 2 reasons which are somewhat in synergy:
2049 * - It is a way of giving back the FD-resource to the kernel as early as possible.
2050 * (Destroying `Peer_socket` closes the contained FD/socket.)
2051 * - Update: Unfortunately another, more important consideration has obsoleted this reason. It no longer applies.
2052 * See #m_peer_socket_hosed for more (but it's not that interesting here).
2053 * - It is a way for the incoming-direction processing logic to inform the outgoing-direction counterpart logic
2054 * that it has detected the socket is entirely hosed, in both directions (and hence no need to even try further
2055 * operations on it); and vice versa.
2056 *
2057 * As to that 2nd reason: a couple of other approaches would work:
2058 * - We could simply let the 2nd-to-detect-failure processing direction discover the hosedness by naively
2059 * trying an operation and getting the inevitable error from the kernel (probably the same one).
2060 * - This is actually a pretty good alternative approach; it might even be better:
2061 * As written direction 2 will get a catch-all `S_LOW_LVL_TRANSPORT_HOSED_CANNOT_SEND` or
2062 * `S_LOW_LVL_TRANSPORT_HOSED_CANNOT_RECEIVE` error; while with the alternative approach we could
2063 * get the "real" error in both directions. There are benefits to each approach; the alternative one
2064 * provides more info when looking at just one direction, while the existing one is quicker and
2065 * less entropy-laden (arguably), returns the FD/socket resource sooner, and still makes the true error
2066 * available. See to-do at the end of this doc header, as the alternative approach may carry another
2067 * benefit.
2068 * - We could have incoming-direction logic check #m_snd_pending_err_code/outgoing-direction check
2069 * #m_rcv_pending_err_code ahead of accessing #m_peer_socket.
2070 * - This idea sucks. It breaks the intentional and important (for perf) guarantee under
2071 * "Thread safety" in the sync_io::Native_socket_stream doc header, wherein
2072 * receive-ops logic and send-ops logic may execute concurrently (as now the latter accesses some of
2073 * the former's data and vice versa).
2074 *
2075 * ### Concurrency, synchronization ###
2076 * That brings us to the key discussion of concurrency protection: #m_peer_socket is the
2077 * *only* non-`const`-accessed datum in `*this` that may be accessed concurrently by receive-ops methods
2078 * and send-ops methods. Namely: send-ops are started by `start_send_*_ops()`; receive-ops are started by
2079 * `start_receive_*_ops()`; in PEER state all logic to do with sending can occur entirely concurrently with all
2080 * logic to do with receiving. Except, however, they both use #m_peer_socket -- for *non-blocking calls only!* --
2081 * as #m_peer_socket is bidirectional. In particular, for example, `m_peer_socket->read_some()` might execute
2082 * concurrently to `m_peer_socket->write_some()`. In addition, #m_peer_socket pointer might be nullified (due to
2083 * error) by one direction's logic, while the other is trying to dereference it and execute a method.
2084 *
2085 * This is resolved by our locking #m_peer_socket_mutex, albeit in a very tight critical section that always
2086 * looks like:
2087 * -# Lock mutex.
2088 * -# Check if it's null; if so unlock/exit algorithm. Else:
2089 * -# Attempt synchronous, non-blocking operation on dereferenced pointer.
2090 * -# If it exposed socket error, nullify pointer.
2091 * -# Unlock mutex.
2092 *
2093 * It's tight, so lock contention should be minimal. Also no other mutex is locked inside such a critical
2094 * section, so deadlock chance is nil. However see the following to-do for an alternative approach.
2095 *
2096 * @todo `Peer_socket m_peer_socket` synchronous-read ops (`read_some()`) are actually
2097 * documented in `boost::asio` to be thread-safe against concurrently invoked synchronous-write ops
2098 * (`write_some()`), as are OS calls `"::recvmsg()"`, `"::sendmsg()"`; therefore for possible perf bump
2099 * consider never nullifying Native_socket_stream_impl::m_peer_socket; eliminating `m_peer_socket_mutex`; and
2100 * letting each direction's logic discover any socket-error independently. (But, at the moment,
2101 * `m_peer_socket_mutex` also covers mirror-guy `m_ev_wait_hndl_peer_socket`, so that must be worked out.)
2102 *
2103 * To be clear, the text above
2104 * w/r/t concurrency/synchronization says `->write_some()` and `->read_some()` might execute concurrently --
2105 * but boost.asio docs (`basic_stream_socket` page) indicate that is actually okay; and implies
2106 * the same about underlying OS calls (which includes `readmsg()` and `writemsg()` which we use when
2107 * `Native_handle` transmission is needed). Now, the nullification versus dereferencing of the `unique_ptr`
2108 * wrapping `m_peer_socket`: that is indeed not thread-safe, which is why we'd need to also get rid of that method
2109 * of communicating socket-hosed state from one direction to the other. However, as we wrote above, the
2110 * alternate approach, where each direction discovers the socket error independently, would be compatible
2111 * with `m_peer_socket` not needing to be a `unique_ptr` at all. That said the socket would not be given
2112 * back to the system as early (potentially) -- note that boost.asio `close()` is noted to not be
2113 * safe against concurrent reads/writes -- and in general the approach "feels" more entropy-laden.
2114 * I (ygoldfel) must say, though; it does sound entirely viable nevertheless; and it would be a limited change
2115 * that would also eliminate error::Code::S_LOW_LVL_TRANSPORT_HOSED_CANNOT_SEND
2116 * and error::Code::S_LOW_LVL_TRANSPORT_HOSED_CANNOT_RECEIVE. One could even argue it is elegant, in that
2117 * it decouples the 2 directions as much as humanly possible, to the point of even using the kernel's support
2118 * for it. (Last note: the boost.asio docs single out `connect()`, `shutdown()`, `send()`, `receive()`
2119 * as okay to invoke concurrently; not `read_some()` and `write_some()`; but I very strongly suspect
2120 * this is only an omission, perhaps due to `*_some()` appearing for uniformity in a boost.asio overhaul
2121 * after those docs were written; in the source it is clear they invoke the same exact stuff. Googling shows,
2122 * generally, the underlying OS calls including `*msg()` are thread-safe to use in this manner also.)

2126 /**
2127 * Null to start, this takes on the value from #m_peer_socket when and only when #m_peer_socket is nullified
2128 * (which occurs when and only when an error is detected on it). Protected (along with #m_peer_socket) by
2129 * #m_peer_socket_mutex.
2130 *
2131 * So, at steady state, either #m_peer_socket is null, or #m_peer_socket_hosed is null, but never both null
2132 * or both non-null.
2133 * - `m_peer_socket` begins as non-null, `m_peer_socket_hosed` null.
2134 * - `m_peer_socket_hosed = std::move(m_peer_socket)` may execute (or never execute), swapping them.
2135 * - In destructor, the non-null one gets destroyed; which internally closes the contained native-socket (FD).
2136 *
2137 * ### Rationale ###
2138 * Why do this? Why not simply nullify `m_peer_socket`, both to mark it (as explained in its doc header) for
2139 * algorithmic purposes and to return the FD resource to the OS? The answer is subtle but very real:
2140 * Suppose an error is detected on the socket, and we simply destroy it -- thus closing the native socket.
2141 * In most cases this is okay; the user code will be informed of the error and not do further work on the socket.
2142 * What work does it do with it anyway? Answer: it is allowed to, at most, "watch" it: await readability
2143 * and/or writability, so as to report it to `*this` as part of the `sync_io` pattern. Once `*this` is hosed,
2144 * there's no need to watch it, right? Right... so consider they might be using a native mechanism, most notably
2145 * Linux's `epoll_ctl()` and `epoll_wait()`, to do so. With such a stateful mechanism the right thing to do
2146 * would be to unregister the now-worthless native-socket-handle on which they might currently be registered
2147 * to detect active events (as asked by us via `sync_io` pattern). So with `epoll` they'd do perhaps
2148 * `epoll_ctl(EPOLL_CTL_DEL)` to remove the FD from an epoll-set FD... but we just closed (`"::close()"`) it!
2149 * That's bad. (In reality -- subtleties/details omitted -- we might be able to get away without catastrophic
2150 * events... but at absolute best, this is entropy-laden and ugly and really just merely fortunate.)
2151 *
2152 * In short, we should not invalidate a native-handle that we may have asked the `*this` user to be watching
2153 * for activity, until we are sure they are no longer doing that. We can only be sure of that -- particularly
2154 * in light of the potential desire to unregister it from watch-set(s) -- once our dtor begins execution, at which
2155 * point they're contractually obligated to not touch the native-handle any longer.
2156 *
2157 * Okay... in that case... why not simply *not* nullify #m_peer_socket but use some other marker (a separate flag,
2158 * `bool m_peer_socket_hosed` maybe)? Answer: Sure, we could. It's not necessarily better or worse. In truth
2159 * it's arguably a historic artifact of how the code was written before considering the aforementioned problematic
