62/**
63 * In SHM-jemalloc, a context between this process and a single (typically other) opposing process w/r/t
64 * lending (sharing) in-SHM objects from our `Ipc_arena`s to them, and their doing the same conversely.
65 *
66 * @note In the wider Flow-IPC world, centered around ipc::session::Session, a session is -- quite similarly --
67 * a context for process A IPCing with process B (again A is usually not the same as B but can be, such as
68 * in testing/debugging). We are too, really; just it's not general IPCing but rather sharing of in-SHM items
69 * via the lend-borrow paradigm.
70 *
71 * @note These notes (in Shm_session doc header) are written from the standpoint of presenting it (and the rest of
72 * SHM-jemalloc) as a standalone system. In most situations a general Flow-IPC user can think of
73 * SHM-providers, whether SHM-jemalloc or another one (such as SHM-classic in shm::classic), interchangeably.
74 *
75 * @see ipc::shm namespace doc header for high-level description of the lend-borrow SHM-arena paradigm.
76 *
77 * @see Ipc_arena: to put things into one's own SHM arena. Then to share such a thing with another process --
78 * possibly more than one -- establish a Shm_session and use Shm_session::lend_object(); on the other
79 * side Shm_session::borrow_object() (peer Shm_session object). Ipc_arena doc header explains this setup --
80 * from a SHM-jemalloc-as-standalone-module PoV -- in more detail than the present recap.
81 *
82 * The aforementioned Ipc_arena doc header hopefully explains most things of interest including where a `*this`
83 * fits into things. If you read/grok that first, then Shm_session should make sense. We cover anything
84 * left-over in that vein next:
85 *
86 * ### Shm_session lifetime versus Ipc_arena ###
87 * Like Ipc_arena, one accesses `Shm_session`s exclusively via `shared_ptr` handles, including using
88 * the create() factory instead of any direct ctor. As noted regarding Ipc_arena, if one does
89 * `session->lend_arena(arena)` (with `shared_ptr<Ipc_arena> arena`), then `*arena` shall outlive `*session`.
90 * Thus, after you've lent an arena through a session, you must end the conversation with the opposing process
91 * before the arena (most notably its in-SHM resources) is allowed to be destroyed. (As of this writing
92 * there is no undo-`lend_arena()` API, but it could be added. That would modify the preceding statements in
93 * a self-explanatory way.)
94 *
95 * ### Shm_session lifetime versus object-handles returned via borrow_object() ###
96 * In short: When `this->borrow_object<T>()` returns a handle -- `shared_ptr<T>` -- to an in-SHM object constructed
97 * in an opposing arena -- the resulting `shared_ptr` group silently retains a `shared_ptr<Session>` to
98 * `*this`, dropped only when that smart-pointer group reaches ref-count zero. (As with Ipc_arena: that's not
99 * the same as the actual in-SHM object being destroyed; that requires the owner and all other borrowers to
100 * also drop their handles. Here it's about just the returned, process-local `shared_ptr<T>`.) Hence a
101 * Shm_session outlives all objects borrowed through it.
102 *
103 * ### When/why and how to destroy your Shm_session ###
104 * Firstly, how: Step 1, let all the `borrow_object()`ed handles reach ref-count zero. (Ipc_arena equivalent of
105 * this, w/r/t letting Ipc_arena go away, is to let `construct()`ed handles do the same.) Step 2, nullify your
106 * handle(s) to `*this`.
107 *
108 * Secondly, why/when: This mirrors the identical question about the more general Flow-IPC sessions. The answer is
109 * two-fold (the two triggers being mutually exclusive):
110 * - Local trigger: That is, you don't want to talk to them anymore. So you destroy your Shm_session to them.
111 * - Opposing trigger: That is, they don't want to talk to you anymore. This requires your finding out that
112 * fact somehow. Formally any technique will do. Informally/in practice:
113 * - If you're using a `*this` as supplied to your by wider Flow-IPC ipc::session mechanism: It is handled
114 * for you. This isn't in our purview but for the sake of providing context: A `Session` issues the
115 * registed on-error callback; hence you shall destroy that `Session` -- the connection is no more.
116 * That SHM-enabled `Session` will therefore destroy its internally stored Shm_session
117 * (the thing you access via Session::shm_session() if desired).
118 * - If you're using SHM-jemalloc in standalone fashion: Detect error via the `shm_channel_error_handler`
119 * you gave us via Shm_session::create(). Once that fires, destroy the Shm_session.
120 *
121 * ### The SHM-channel ###
122 * To create/start a `*this`, you must provide to create() a freshly established #Shm_channel
123 * (`sync_io`-pattern core, basically a socket ready to transmit).
124 *
125 * Why is it needed? Answer: Internally an arena-lending SHM-provider, SHM-jemalloc in this case, must sometimes
126 * send messages for internal purposes to synchronize certain key state. (High-level example for context:
127 * a lend-arena message with some info about A is internally sent when one does `session->lend_arena(A)`;
128 * now the opposing Shm_session will be able to borrow_object() items that are `A->construct()`ed across process
129 * boundary.)
130 *
131 * If you're using a `*this` via an ipc::session general `Session`, then it worries about all that, so you don't
132 * need to; you won't even be calling create() in the first place. If however you are using it standalone
133 * (example: you **are** the code in ipc::session general `Session` eating our own dog food!):
134 *
135 * Establish a #Shm_channel yourself (various techniques are documented elswhere) and provide it to
136 * Shm_session::create(); from that point on the resulting `*this` takes over that object.
137 *
138 * ### Thread safety ###
139 * lend_object() and borrow_object() are safe to call concurrently with each other and with any other method,
140 * on the same `*this` or otherwise. (In practice these are the frequently-called ones, often from various threads.)
141 * The rest have the usual default level of thread safety -- e.g., lend_arena() is not safe to call concurrently
142 * with another lend_arena() on the same `*this` -- unless a method's doc header says otherwise (e.g., the stats
143 * accessors are safe to call anytime).
144 *
145 * @internal
146 *
147 * @todo shm::arena_lend::jemalloc::Shm_session could probably become `shm::arena_lend::Shm_session`, handling
148 * sessions dealing with arena-lending SHM-arenas backed by any memory-manager-backed #Arena type (which could
149 * become a template parameter). Historically that had likely been a tall order, but looking at `Shm_session`
150 * insides now, it is actually (1) fairly contained in its duties, and (2) seems to make no jemalloc-specific
151 * mentions other #Arena itself (which, again, would become a template parameter). (Regarding "fairly contained
152 * in its duties": E.g., borrowed-pool and borrowed-object handling is now in `Thread_lcl_obj_db_*` and
153 * Borrower_shm_pool_collection_repository singletons -- both already `Shm_arena`-parameterized and -segregated.
154 * Owner_shm_pool_repository handles owner-side pools and objects. Shm_session forwards things to them when
155 * needed is all.)
156 */

259 /**
260 * Creates an instance of this class; the resulting Shm_arena object is immediately ready to receive incoming
261 * opposing lend_arena() calls, and you can call lend_arena(), lend_object(), and borrow_object().
262 *
263 * See class doc header for motivation for using the ref-counting handle paradigm.
264 *
265 * @warning `*logger` -- unless `logger` is null -- must exist at least past (1) all
266 * `borrow_object()`-returned pointers' groups and (2) of course the returned pointer group.
267 *
268 * @warning It is important that `shm_channel.remote_peer_process_credentials()` is properly set
269 * (we need the opposing PID for internal purposes). If the `Native_socket_stream` was set-up
270 * from a socket handle transmitted via IPC (and originally `connect_pair()`ed or equivalent),
271 * then it may be necessary for the caller to perform an extra step.
272 * See transport::Native_socket_stream::remote_peer_process_credentials() doc header for this info.
273 *
274 * ### About `shm_channel_error_handler` (and `shm_channel`) and error reporting ###
275 * Firstly:
276 *
277 * @see class doc header discussion of error handling -- or more specifically, the whys and hows of
278 * detecting that the IPC connection to the other side has gone down (usually gracefully) on account of
279 * the other side ending it (as opposed to the end user here deciding to end it).
280 * `shm_channel_error_handler` is a part of that picture but, as you'll note, not *necessarily* a
281 * mandatory one to use.
282 *
283 * `shm_channel` is a low-level (unstructured) channel -- transport::Channel -- of the specific type #Shm_channel,
284 * such that a similar peer object is passed to the opposing Shm_session to which we're connecting,
285 * typically (though not mandatorily; e.g. for testing, debugging) across a process boundary.
286 * It is a `sync_io`-pattern variant (formally with `transport::Channel::S_IS_SYNC_IO_OBJ == true`).
287 * (Arguably in plainer English: it's essentially a synchronously-used core, not dissimilar to
288 * a Unix domain socket FD (with Flow-IPC's internal protocol and API niceties of course).) It must be
289 * a freshly established channel: no calls to `Blob_{sender|receiver}`-concept APIs. `*this` shall subsume
290 * it via move semantics and own it. It'll be used internally for important communications such as pool-
291 * and arena-lending notifications and acks, but to a `*this` user it is black box stuff. Hold that thought.
292 *
293 * With one important exception (which we tackle just below) a `*this` cannot fail. Things like Linux `mmap()`
294 * failing or "we cannot open a named SHM object that the opposing Ipc_arena says it created a split second ago"
295 * are not reasonably recoverable; we log and abort or otherwise catastrophically fail. Don't worry about these.
296 *
297 * @note A Shm_session, by the arena-lending design, never allocates in the user's SHM arena(s);
298 * #Arena (`Ipc_arena`) does that. Shm_session exists entirely to enable lend_object() (prep
299 * an `Arena::construct<T>()`ed `T` to be borrowed by opposing side) and borrow_object() (accept that,
300 * yielding a handle-to-`T` on this side, so that it is accessible + participates in GC together with
301 * the opposing `construct()`ed handle and any other-process-similarly-borrowed handles-to-`T`).
302 * The point: at least #Arena can fail due to failure to allocate (out of RAM according to special SHM
303 * limits configured in OS: not atypical). Shm_session doesn't do that, so it can't. So:
304 *
305 * The exception is simply this: the session (a/k/a conversation with the other arena-lending-and-borrowing
306 * thing like us) may have ended, due to the other side deciding to do so (or crash or whatever). This
307 * is called "channel is hosed." `shm_channel` being hosed has the following effect:
308 *
309 * `*this` detects it, typically, as soon as it occurs. It is also technically possible that it first
310 * detects it when trying to *send* an internal message. Regardless: it is detected *at most once*
311 * and therefore is then reported to you immediately and *at most once*. To wit: `*this` shall
312 * execute *from thread W*: `shm_channel_error_handler(E)` (`E` being the reason for the channel-hosing).
313 * This mechanism is identical to async error reporting via the various async-I/O-pattern IPC primitives
314 * in ipc::transport (e.g.: transport::Blob_receiver::async_receive_blob()). It is just used for this one
315 * limited thing.
316 * - If you *do* need to use `*this`'s detecting the channel-hosing as *the* method of detecting
317 * other-side-caused ("opposing trigger") session-hosing, then in `shm_channel_error_handler()` --
318 * which runs from thread W -- we recommend you signal one of your user threads to end all use
319 * of `Shm_session`-borrowed objects, nullifying them; and destroy Shm_session. E.g., if you use
320 * boost.asio or `flow::async`, then it'd be typical to `post()` those steps onto your main thread.
321 * - Regardless: do not block inside `shm_channel_error_handler()`. Thread W also replies to the opposing
322 * Shm_session's internal requests; the opposing side waits for those replies, sometimes while inside an
323 * allocation in its arena; so blocking thread W can stall even the other process.
324 * - If you *do not* need to do that -- ipc::session is wrangling create() and `*this` for you, or
325 * you detect session-hosing via the hosing of some other channel or socket -- then in
326 * `shm_channel_error_handler` you could just log; or do nothing.
327 *
328 * @warning Do not destroy `*this` (e.g., by dropping the last `shared_ptr` to it) from within
329 * `shm_channel_error_handler()`: undefined behavior (likely `std::terminate()` due to thread W trying to
330 * self-join).
331 *
332 * Nevertheless, after this event (after channel's hosing is detected) but before Shm_session destruction
333 * (which you would allow, by dropping all borrowed handles and the `create()`-returned `Shm_session`-handle),
334 * APIs shall act as follows.
335 * - lend_arena() will return `false`. (Object-lending wouldn't work properly anyway so why lie to you?)
336 * - lend_object() will return an empty blob (so there's nothing for the opposing to borrow_object()).
337 * (We could return a functional/`borrow_object()`able blob here; but channel-hosed means there's a
338 * high chance the opposing (borrowing) process will have *no* information about the latest SHM-pools
339 * from our `lend_arena()`d `Ipc_arena`s, so passing a thing into borrow_object() is an invitation for
340 * crashing and other chaos. Plus in any case: if the session is down, then it's likely you wouldn't be
341 * able to transmit the blob anyway let alone then `borrow_object()` it.
342 * - borrow_object() (on `*this`) however will work normally. If you've managed to receive the blob
343 * to pass to that method, then both general IPC and opposing lend_arena() and lend_object() worked fine
344 * for in-SHM objects including that one; there's no reason to create more failure modes by having this
345 * artifically fail.
346 *
347 * Because Shm_session is not itself a communication channel, we're belaboring these points. That said this is
348 * no different from other async-I/O-pattern objects in Flow-IPC. Simply:
349 * - Be ready for lend_arena() and lend_object() to fail, indicating: this Shm_session is already hosed,
350 * and shm_channel_error_handler() shall fire imminently or already has. Typically one would stop
351 * normal processing but otherwise no-op. And orthogonally:
352 * - Handle `shm_channel_error_handler(E)` -- or your other method of session-hosing detection -- swiftly.
353 * As noted before: nullify all `this->borrow_object()`-returned handles; and destroy `*this` by dropping
354 * any handles from create().
355 * - You could also preempt the preceding bullet point *if* you happen to detect failed lend_arena() or
356 * lend_object() first. If you don't care about logging/reporting the `Error_code` associated with
357 * the channel-hosing, then you could end the Shm_session immediately. However you should still be ready
358 * to handle `shm_channel_error_handler(E)`, if it happens first. After all lend_object() and
359 * definitely lend_arena() are not done continuously, and it is proper to react to session-hosing ASAP.
360 *
361 * ### Details ##
362 * The following information is for context only, if you want to understand more precisely how/why we detect
363 * and report channel-hosing. It should not affect how you handle all this, and it is somewhat white-boxy info.
364 * Nevertheless: Here are the paths as of this writing to triggering `shm_channel_error_handler()` (and thus
365 * setting the internal flag that'll cause lend_arena() and lend_object() to fail subsequently as well).
366 * - lend_arena() itself tries to send internal `LendArena` message over `shm_channel`; the send fails
367 * synchronously. Thread: end user thread.
368 * - Result: post `shm_channel_error_handler(E)` onto thread W to execute ASAP. lend_arena() returns false.
369 * - `Arena::allocate()`, for an #Arena that has been successfully `lend_arena()`ed earlier, is told
370 * synchronously (by memory manager jemalloc) that a new SHM-pool is required, so it created it and informed
371 * every `Shm_session` (including `*this`) through which it has been let that this occurred, and that it
372 * must inform the opposing process(es), receive ack(s), and only then let `Arena::allocate()` return.
373 * However the send of the info fails synchronously. Thread: end user thread.
374 * - Result: post `shm_channel_error_handler(E)` onto thread W to execute ASAP. Arena `allocate()` proceeds
375 * normally after that. (Nota bene: Shm_session failure does not cause Ipc_arena allocation failure.)
376 * - The internal channel itself detects hosing while awaiting (like always) in-messages for internal use.
377 * Thread: that channel's own background thread.
378 * - Result: post `shm_channel_error_handler(E)` onto thread W to execute ASAP.
379 * - This includes the opposing side becoming stuck (not dead): Each side will issue, inside create(),
380 * Blob_sender::auto_ping() and Blob_receiver::idle_timer_run() on `shm_channel`. If it's unresponsive
381 * at any point, for a few seconds, you'll see E = transport::error::Code::S_RECEIVER_IDLE_TIMEOUT.
382 * - In thread W, we receive a message (`LendArena`, `LendPool`) and reply with ack response.
383 * However the send of the ack fails synchronously. Thread: W.
384 * - Result: execute `shm_channel_error_handler(E)` (already in thread W).
385 *
386 * @todo It'd be nice for Shm_session::create() to become a template with parameterized functor type
387 * instead of `flow::async::Task_asio_err` for `shm_channel_error_handler`. There is zero functional
388 * difference, as internally it is stored as a `Task_asio_err` (which a `Function<>`) anyway; but
389 * for consistency and maintainability it'd be nice.
390 *
391 * @param logger
392 * Used for logging purposes.
393 * @param shm_channel
394 * The channel used for transmitting internal messages. See above for requirements (which are simple).

427 /**
428 * Registers an in-SHM object for lending to the borrower on the other end of the session; and returns a small blob
429 * to pass to borrow_object() in the opposing Shm_session to obtain access to the same in-SHM object.
430 * borrow_object() returns a handle much like `object` -- and participating in the same GC (garbage collection)
431 * of `*object` (thus making it effectively a cross-process `shared_ptr` group).
432 *
433 * An object that is `lend_object()`ed but not yet (or ever) subsequently `borrow_object()`ed against the
434 * opposing Shm_session is extant: it will not be destroyed until either (1) `*this` is destroyed or (2) the
435 * `borrow_object()` et al does occur. So if you fail to ever `borrow_object()` the returned blob, it is a leak
436 * until the lending `Shm_session` is destroyed, at the earliest. In more detail:
437 * - Think of it as a cross-process ref-count (*use-count*) of processes (owner, lenders). Ipc_arena::construct()
438 * sets it to 1. Local lend_object() increments it by 1. `construct()`ed `shared_ptr` group reaches local
439 * ref-count zero (owner-side disposer runs) => decrement by 1. Opposing-process `borrow_object()`ed
440 * `shared_ptr` group reaches local ref-count zero (borrower-side disposer runs) => decrement by 1. Note
441 * that opposing-process borrow_object() itself does not affect this use-count; this lend_object() already did
442 * so.
443 * - Until one does opposing-process borrow_object(), object is therefore (under continuing normal operation,
444 * nothing shutting down) safe from in-SHM garbage-collection (freeing), as use-count remains at least 1
445 * due to this lend_object(). By the same token, though, if one *never* calls it, then it remains "safe" from
446 * freeing for the same reason...
447 * - ...except that the destruction of the Ipc_arena itself will in fact free all owned memory including this
448 * object, whether or not its use-count had reached zero. However, Ipc_arena itself cannot be
449 * destroyed (even if you drop your `shared_ptr<Ipc_arena>` handle from Ipc_arena::create() and all
450 * `construct()`ed handles, including possibly `object` itself), until all
451 * `Shm_session`s through which it was `lend_arena()`d have been destroyed. That includes `*this`; so `*this`
452 * Shm_session going away is a necessary (not sufficient though) condition for `object` getting GCed --
453 * in that scenario.
454 *
455 * @note The serialization returned includes information on how to deserialize the object and not the contents
456 * of the object itself. It is small.
457 *
458 * @note It is up to the caller/user to transmit the returned blob via any IPC technique whatsoever. (Flow-IPC
459 * does provide a bunch of them; and ipc::transport::structured::Channel does it for you in a couple of
460 * senses that make sense for its mission.) `shm_channel` -- passed to `*this` via create() for "internal
461 * use" -- is *not* to be used by anyone for this purpose.
462 *
463 * @warning Be ready for this method returning empty blob. See below regarding return value.
464 *
465 * ### Thread safety ###
466 * Safe to call anytime. See class doc header.
467 *
468 * @tparam T
469 * The object type being lent. As of this writing it actually does not need to match the `T` used
470 * for Ipc_arena::construct() to obtain `object`; e.g., `T = void` might be useful in some cases.
471 * (borrow_object() is a different story. See its doc header.)
472 * @param object
473 * The handle to object to be lent; it *must* have come from Ipc_arena::construct().
474 * If not the method throws a `flow::error::Runtime_error` (itself an `std::runtime_error`).
475 * Moreover that Ipc_arena must have been successfully `lend_arena()`ed via `*this`; otherwise behavior
476 * is undefined.
477 * @return Non-empty blob on success; empty on failure. Failure indicates `shm_channel`'s hosing had been
478 * detected earlier. If so `shm_channel_error_handler(E)` has fired
479 * in a background thread, and `*this` is hosed. See create() doc header.
480 */
481 template<typename T>
482 Blob lend_object(const Handle<T>& object);

539 /**
540 * Returns the process-wide borrower-side stat-set Borrower_pool_stats -- the
541 * running totals across all `Shm_session`s in this process -- and (optionally) output a copy of similar information
542 * broken down by arena, each identified and in ascending order by stat::Uniq_arena_id
543 * Borrower_pool_stats::m_uniq_arena_id. See stat::Borrower_pool_stats doc header for background on interpreting
544 * the data; some related notes are below.
545 *
546 * @note The returned-by-ref Borrower_pool_stats has its Borrower_pool_stats::m_uniq_arena_id all-zeroes, as it
547 * is aggregated info, not per-arena.
548 * @note (Assume `per_arena_stats_sz_limit_or_0 = 0`, and no eviction of historical per-arena data has occurred.)
549 * The returned totals could almost be computed by summing the per-arena `Borrower_pool_stats` (via
550 * `flow::util::stat::stats_sum()`) -- except the `HI_WMARK`s, which are accurate only on the returned
551 * totals (continuously updated there); that historical info is lost when split by arena across time.
552 * @note In each stat-set in `*per_arena_stats` Borrower_pool_stats::m_n_borrowed_arenas cannot exceed 1.
553 *
554 * ### Concurrency semantics ###
555 * The returned (totals) reference is to live `atomic<>`s which can change at any moment concurrently;
556 * hence even values grabbed in immediate succession can be slightly mutually incoherent. Consume via
557 * `flow::util::stat::load()` / `stats_assign()` / `print()` (et al); see `flow::util::stat` doc header.
558 *
559 * Each element in out-arg `*per_arena_stats`, by contrast, is a snapshot copy as of this call; it will
560 * not change on return.
561 *
562 * ### Limits on result size `per_arena_stats->size()` ###
563 * There are two limits, one user-controlled and one (usually much larger) not.
564 *
565 * The limit you can control is the in-arg `per_arena_stats_sz_limit_or_0`, if set to non-zero. Supposing
566 * we internally have history of N, greater than `per_arena_stats_sz_limit_or_0`, per-arena stat-sets:
567 * We shall output only `per_arena_stats_sz_limit_or_0` of them. This is useful for practical purposes
568 * when, say, logging all the results; it might be not too useful to print hundreds of stat-sets.
569 *
570 * @note `*n_arenas_omitted` is set to the number of stat-sets thus dropped past `per_arena_stats_sz_limit_or_0`.
571 *
572 * There is also an internal limit, which is a constant; as of this writing 1,000. To avoid unbounded growth
573 * of overall per-arena stats here, we irreversibly forget an old stat-set, if we are about to go past this limit.
574 * Therefore (even with `per_arena_stats_sz_limit_or_0 = 0` a/k/a infinity) `per_arena_stats->size()` shall
575 * not exceed this large internal limit.
576 *
577 * If arena-stat-sets are omitted due to the limit in-arg, and/or arena-stat-sets are forgotten due to the
578 * internal growth limit, the *oldest* (according to the same age criterion) arenas are omitted/forgotten.
579 * This *age* is determined by the following criterion: time passed since the last time a stat-modifying event
580 * has occurred for that arena. Namely:
581 * - the arena is borrowed through a session (opposing Shm_session::lend_arena());
582 * - the arena is unborrowed through a session (as of this writing: local Shm_session borrowing it is destroyed);
583 * - a pool through the arena was unborrowed (ditto);
584 * - a pool through the arena was borrowed (opposing process allocated in arena, and that allocation
585 * necessitated the creation -- and therefore automatic lending -- of a new SHM-pool in the arena).
586 *
587 * ### Thread safety ###
588 * Safe to call concurrently with anything on any `Shm_session` (or none).
589 *
590 * @param per_arena_stats
591 * If null, ignored; else cleared, then loaded with per-arena stat copies (the `unique_ptr` wrapper is
592 * for your convenience -- cheap moves; and the stat-sets are not natively copyable due to their `atomic`
593 * members). Sorted ascending by Uniq_arena_id::m_id1 (owner-PID), then `m_id2` (per-process ordinal).
594 * @param per_arena_stats_sz_limit_or_0
595 * (Ignored if `per_arena_stats` is null.) If not zero, result `per_arena_stats->size()` is limited to
596 * at most this many elements, with most-recently updated stat-sets given precedence.
597 * @param n_arenas_omitted
598 * (Ignored if `per_arena_stats` is null; or if `n_arenas_omitted` is itself null.)
599 * `*n_arenas_omitted` shall be set to the number of stat-sets
600 * internally available but omitted from `*per_arena_stats` due to `per_arena_stats_sz_limit_or_0`.
601 * (If `per_arena_stats_sz_limit_or_0 == 0`, `*n_arenas_omitted` shall be zero.)
602 * @return See above (the across-all-`Shm_session`s totals).
603 */

1060 {

1062 return {};
1063 }

1065

1067 * switch impls (e.g., to boost::shared_ptr), use that impl's get_deleter() equivalent. */

1072 * throws Runtime_error, albeit with a nice Error_code, if one doesn't supply non-null Error_code* err_code).

1075 * error reporting for consistency (internally and versus Flow-IPC in general) and robustness. For now, guidance:
1076 * 1, assert() would not be crazy; it's not that different from passing null when non-null is expected.
1077 * 2, on the other hand, if one is not used to the project they might pass some random shared_ptr<T> in here,
1078 * and a nice error might be a more civilized way of informing them. If so: probably this should just be
1079 * one of many Flow-IPC APIs with Flow error-emission semantics (take Error_code*, on error throw if null,
1080 * set out-arg otherwise; on success don't throw/set to falsy Error_code respectively). -ygoldfel */
1081 throw Runtime_error{"lend_object() was given handle (shared_ptr) without disposer of the expected type; "
1082 "did you get it from Ipc_arena::construct() as required?"};
1083 }
1084 // else
1085
1086 const auto object_ptr = object.get();
1087
1088 Blob blob{sizeof(Shm_object_handle)};
1089 const auto& shm_arena = *disposer->m_shm_arena;
1090 const auto collection_id = shm_arena.get_id();
1091 const auto use_ct_idx = disposer->m_use_ct_idx;
1092 const auto lend_tracker_pool_id = disposer->m_lend_tracker_pool_id;
1093

1097 * of breaking aliasing rules. */

1100 object_handle->m_collection_id = collection_id;
1101 object_handle->m_lend_tracker_pool_id = lend_tracker_pool_id;
1102 object_handle->m_use_ct_idx = use_ct_idx;
1103 Owner_shm_pool_repository::from_address(object_ptr, // <-- from that | compute these --v
1104 object_handle->m_pool_id, object_handle->m_pool_offset);
1105

1109 * to the thread-local obj-DB *admin* directly. We know it exists in this thread, so might as well;

1111 * data in the same thread unnecessarily. */

1114 }

1117 Thread_lcl_obj_db_client

1125Shm_session::Handle<T> Shm_session::borrow_object(const Blob& blob) const
1126{
1127 using ipc::shm::arena_lend::detail::Thread_lcl_obj_db_admin;
1128 using ipc::shm::arena_lend::detail::construct_with_borrower_obj_disposer;
1129 using Borrower_shm_pool_collection_repository
1130 = ipc::session::shm::arena_lend::detail::Borrower_shm_pool_collection_repository<Arena>;
1131 using std::memcpy;
1132
1133 Thread_lcl_obj_db_admin<Arena>::this_thread_piggy_scan(); // Opportunistic!
1134
1135 const size_t blob_size = blob.size();
1136 if (blob_size != sizeof(Shm_object_handle))
1137 {
1138 FLOW_LOG_WARNING("Blob size [" << blob_size << "] does not match expected "
1139 "size [" << sizeof(Shm_object_handle) << "]. This indicates a bug on someone's part; "
1140 "either the blob was somehow improperly formed owner-side, or the user has supplied something "
1141 "unequal to what was formed there. borrow_object() returning null as advertised.");
1142 return {};
1143 }
1144 // else
1145
1146 /* memcpy() it out of there: the source address may not be aligned. (In many APIs such things are assumed as a
1147 * matter of course, but as `blob` may be IPCed-over to us via any technique, we're being extra defensive.) */
1148 Shm_object_handle object_handle;
1149 memcpy(&object_handle, blob.const_data(), sizeof(object_handle));
1150
1151 const auto obj_addr
1152 = Borrower_shm_pool_collection_repository::to_address_safe(object_handle.m_pool_id,
1153 object_handle.m_pool_offset);
1154 if (!obj_addr)
1155 {
1156 /* We used to_address_safe() (rather than the marginally quicker and subsequently-used to resolve various
1157 * pointers such as inside STL-compliant containers (off borrowed handles like this one... but valid)
1158 * to_address()) as a safety measure against bogus/buggy `blob`s. This follows the philosophy in
1159 * classic::Pool_arena::borrow_object() to be defensive at this particular point, where we process an
1160 * ostensibly IPCed-over datum. That said: this is a best-effort thing: In particular m_pool_offset as of
1161 * this writing can point outside the pool (to_address_safe() will not detect it); never mind any check for
1162 * whether sizeof(T) would lie beyond the pool's bounds. classic's equivalent as of this writing can and
1163 * does perform those checks.
1164 *
1165 * Inside Borrower_shm_pool_collection_repository::to_address_safe() there are some notes on what it would take to
1166 * extend this -- but, again, it is a best-effort safety measure. */
1167
1168 FLOW_LOG_WARNING("Borrowed blob encodes pool ID [" << object_handle.m_pool_id << "], but this pool ID "
1169 "is no longer borrowed or has never been borrowed; treating the blob as invalid. "
1170 "borrow_object() returning null as advertised for invalid SHM-handle blobs.");
1171 return {};
1172 }
1173 // else
1174
1175 /* See doc header for Shm_object_handle for recap of which pieces of info below are used when/why.
1176 * See doc header for construct_with_borrower_obj_disposer() for a recap of the properties of the disposer
1177 * we are attacking to the shared_ptr returned here. */
1178 return construct_with_borrower_obj_disposer<T, Shm_session>
1179 (static_cast<T*>(obj_addr),
1180 object_handle.m_lend_tracker_pool_id, // Datum 1/1 used in the fast path.
1181 object_handle.m_use_ct_idx, // Datum 2/2 used in the fast path.
1182 m_remote_process_id, // A/k/a owner_id of type owner_id_t. Used in slow path.
1183 object_handle.m_collection_id, // Used in slow path.
1184 /* As of this writing this value (shared_ptr<const Shm_session> pointing to *this) isn't used per se;
1185 * but it prevents death of *this Shm_session while shared_ptr<T> handles that came from its
1186 * .borrow_object() still live. For better or worse those are the semantics we want to guarantee with the
1187 * factory+private ctor pattern. See Shm_session doc header. */
1188 shared_from_this());
1189
1190 /* Interesting fact; could be useful at some point: *this is actually only a little necessary for borrow_object()'s
1191 * impl. Suppose it were not necessary: borrow_object() could be static; that change could be propagated to
1192 * ipc::session::Session (though then it would become more asymmetrical to arena-sharing providers including
1193 * SHM-classic) and possibly somewhat beyond. At any rate in and of itself relationships would become simpler,
1194 * all else being equal (which it's not, but read on). As for how *this is required as of this writing:
1195 * - m_remote_process_id: Convenient, but could be obtained some other way such as directly from the
1196 * m_shm_channel API or encoded in object_handle.
1197 * - shared_from_this() a/k/a `this` itself: Passed to construct_with_borrower_obj_disposer(), but as noted
1198 * it is only stored to ++ its group ref-count, preventing *this death before all the borrowed SHM-handles
1199 * it generates (in this method) are dropped. That is actually an ontensibly important guarantee, and
1200 * other things document it. Though, as I (ygoldfel) understand it, it is apparently a stand-alone feature;
1201 * don't think anything specifically relies on it, outside of potentially user code to have been written
1202 * by now (removing it would be a breaking change). It's a nice guarantee; at least it is quasi-symmetrical
1203 * with owner-side Ipc_arena similarly not dying until all it-construct()ed SHM-handles are dropped.
1204 * Not suggesting removing this dependency; as written or implied just above it makes some sense. Good to keep
1205 * in mind though. */
1206} // Shm_session::borrow_object()
