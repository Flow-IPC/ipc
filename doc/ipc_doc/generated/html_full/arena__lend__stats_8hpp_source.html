84/**
85 * Cousin of arena_lend::stat::Owner_obj_stats, this tracks the *zombie-reaper scan* algorithm whose task
86 * is to find all first-class objects `arena.construct()`ed by this thread (or by the now-joined thread whose
87 * exit caused this specialized drain-thread to be spawned) that are *zombie objects*; and to destroy them.
88 * A zombie object is one such that no user thread, cross-process, holds a reference to it any longer.
89 *
90 * ### Context: How it works ###
91 * Despite the scary name, a zombie object is a completely normal phenomenon -- it just means
92 * the last guy to let go of its ref to the object happened to not be the original `.construct()`ing
93 * thread-and-process. Only that original thread may destroy such an object, and since we do not
94 * control user threads, we can only do so opportunistically (a/k/a *piggy-backed*). If that (user) thread happens to
95 * exit (join its parent) while an object is still live, then a *specialized drain-thread* is launched at that point
96 * by SHM-jemalloc and will periodically execute the zombie-reaping algorithm in the same way as
97 * the piggy-backed scan.
98 *
99 * There are therefore two of Zombie_obj_reaper_stats per arena: one counting the piggy-backed scans' stats;
100 * the other counting the dragin-threads' scans' stats.
101 *
102 * @internal
103 * The piggy-backed code path is detail::Thread_lcl_obj_db_admin::this_thread_piggy_scan().
104 * (Additionally, up to once per `.construct()`ing thread, detail::Thread_lcl_obj_db_admin::~Thread_lcl_obj_db_admin()
105 * dtor launches a scan. It is counted together with the piggy-backed scans.)
106 *
107 * The drain-thread code path is detail::Thread_lcl_obj_db_admin::degraded_admin_thread_body().
108 */

226 * through the obj-DB. However, there is a limited number of possible hints (as of this writing 16; but

302/**
303 * A bundle of several individually-documented stat-sets -- object construct/dispose/live and
304 * zombie-reaper stats -- grouped into this one `Stat_set` because they are all collected together (for
305 * performance, via thread-local sharding) and therefore consumed together but separately from non-sharded
306 * items. The grouping itself is based on these impl constraints; to the stat-consuming user that is not
307 * too interesting. What is interesting is what each member tracks; see that member's own type's doc header.
308 *
309 * @see Pool_stats: A peer grouping of per-arena stats; it must be separate due to not being TL-sharded when
310 * internally collected; therefore the method of return is different from a `*this`.
311 * @see Memory_manager_stats: A peer grouping of per-arena stats; it is separate due to coming from an
312 * external data source (memory manager: e.g., jemalloc) as opposed to from internal algorithms/data.
313 * (They could still be bundled together. Nevertheless the subject matter/data source are, we feel,
314 * so sharply different that Memory_manager_stats simply should remain separate from all others.)
315 *
316 * ### Semantics ###
317 * Generally, they're just `struct`s as usual. In a publicly returned `*this` (returned by, e.g.,
318 * jemalloc::Ipc_arena::sharded_stats()), the value in a given leaf stat-member is what it is: the measurement
319 * of that thing, since the last reset (or init). However:
320 *
321 * As a TL-sharded `Stat_set` (see `flow::util::stat` doc header for full discussion), there are some caveats
322 * or interesting notes to keep in mind about it. To recap these:
323 * - Stat-members named `..._hi_wmark` (by convention having `Stat_type::S_HI_WMARK`: high-water-mark) do not
324 * (cannot, due to limitations of sharding) represent, simply, the highest value (since reset if any) that
325 * the gauged-stat has ever achieved. Instead each `_hi_wmark` represents the highest value (since reset if
326 * any) that the gauged-stat has achieved *sampled at stat-consumption (or last reset, or init) times*.
327 * Hence the more regular stat-consumption is, the more accurate/interesting `_hi_wmark`s are.
328 * - A diagnostic member named `m_n_shards` -- in this case shm::stat::Owner_obj_stats::m_n_shards -- is
329 * interesting in that it shows how many shard-`*this`es were used to generate (generally via summing, at
330 * last stat-consume time) the resulting `*this` being inspected. That's how many threads overall participated
331 * in reporting data, each reporting at least one stat-member's worth.
332 *
333 * @internal
334 *
335 * Stat sub-`struct`s grouped in this one `struct`, so that Thread_lcl_obj_db_admin and
336 * Thread_lcl_obj_db_client TL-registries can, at stat consumption time, aggregate per-thread shards corresponding to
337 * each of those sub-`struct`s. Since a `*this` is a single (composed) `Stat_set` (in the `flow::util::stat`
338 * sense), it is possible to aggregate N threads' shards into an overall result `Stat_set` with a single
339 * `flow::util::stat::stats_aggregate_shards()` call. After that, the stat-consumption API can copy-out or
340 * otherwise rearrange/present individual sub-`struct`s to the user, re-organizing them as it sees fit. Or
341 * it can just present them all in this same grouping, which is what we chose to do ultimately; hence why this
342 * grouping `struct` is public.
343 *
344 * Impl nitty-gritty notes
345 * -----------------------
346 * If none of the below makes any sense, have a look at the stat-consumption API's impl as well as a few places
347 * where these stat-members are updated. In any case, also, a familiarity with `flow::util::stat` namespace doc
348 * header is assumed.
349 *
350 * @see detail::stat::sharded_stats() (stat-consume), detail::stat::sharded_stats_reset() (stat-reset).
351 * @see detail::Thread_lcl_obj_db_admin, detail::Thread_lcl_obj_db_client, and
352 * detail::stat::Finalized_shards: These three hold shard `*this`es; the former two regularly update
353 * theirs. Then the free function `sharded_stats()` aggregates them into a target `*this`;
354 * `sharded_stats_reset()` resets that target `*this`.
355 *
356 * The following is arguably really about Thread_lcl_obj_db_admin + Thread_lcl_obj_db_admin impl details,
357 * and could be best discussed in one of those doc headers, but we're all friends (but not `friend`s) here,
358 * and if you're interested in stats-related impl design, then this is a pretty good place to talk about it.
359 * In any case Sharded_stats impl (the way it chooses to group sub-`struct`s basically) and
360 * Thread_lcl_obj_db_admin + Thread_lcl_obj_db_client impls are all designed to work together.
361 *
362 * ### Who updates the stat-member values between stat-consumptions? ###
363 * For each given stat-member, it may be updated only by Thread_lcl_obj_db_admin, or only by
364 * Thread_lcl_obj_db_client, or by both (across potentially many threads). If it's not *both* but only one --
365 * let's say `_admin` for exposition purposes -- then no per-thread `_client`
366 * will ever touch that stat-member, so its value shall remain zero in all per-`_client` shard `*this`es.
367 * During aggregation any given `_client` simply won't contribute (to the aggregated total for this stat-member)
368 * and is harmless.
369 *
370 * There is an alternative approach: Have 3 `struct`s, conceptually the non-overlapping union of which
371 * equals the 1 `struct` you're reading now; one with the `_admin`-only stats, one with the `_client`-only stats,
372 * and one with those that both touch. One could claim this is cleaner; it does save some processor cycles
373 * and RAM -- but the saved cycles are at stat consumption time (rare), and the RAM difference is small.
374 * The increase in boiler-plate is considerable however; there are 3 types instead of 1; each has to be
375 * `stats_aggregate_shards()`ed separately. So, we're doing it the other way (previous paragraph).
376 *
377 * There is another slightly different category of stat-member in here too; as of this writing comprising
378 * only `m_live_obj.m_live_object_zombies`. (So the preceding 2 paragraphs describe all but that stat-member.)
379 * For this category:
380 * - The stat-members are still sharded/aggregated as described.
381 * - They are, however, not updated during the regular operation of `Thread_lcl_obj_db_*` -- that is, between
382 * stat-consumption points. Instead, at stat-consumption -- before the actual `stats_aggregate_shards()`
383 * call but under central lock that allows an undisturbed aggregation-walk over the extant per-thread
384 * `Thread_lcl_obj_db_*` objects -- we grab the required values (as of this writing, all are fittingly
385 * GAUGEs) and stuff them into the per-thread `*this`. Then they get aggregated with everything else.
386 *
387 * @see stats_update_pre_consumption() impl which explains why we do this.
388 *
389 * ### Stat consumption / Stat resetting ###
390 * We've already discussed stat-consumption above. Just to be explicit about it though: User wants stats so:
391 * We follow the suggested pattern for TL-sharded stat-consumption from `flow::util::stat` doc header.
392 * (For simplicity of exposition let's ignore Thread_lcl_obj_db_client and pretend only Thread_lcl_obj_db_admin
393 * is involved. Call it `Admin` + some other made-up short identifiers for brevity.) So there is a
394 * `static Thread_local_state_registry<Admin> s_reg`. At stat-consumption we do `s_reg.while_locked(F)`,
395 * where `F()` is where we do the aggregation. To wit in `F()` we use `state_per_thread` which
396 * is essentially a set-container of per-thread `Admin`s. While the state *within* each `Admin` can
397 * absolutely concurrently change (in our case the state of interest is specifically the `*this` stat-set
398 * inside `Admin`), no new `Admin`s can be created (new thread joins the fray) or removed (thread exits) --
399 * within `F(){}` body. Now we can use some iterator magic to feed an iterator-range of `*this`es to
400 * `flow::util::stat::stats_aggregate_shards()`, corresponding to the set-container of `Admin`s.
401 *
402 * Resetting is similar (and again it follows the `flow::util::stat` doc header's suggestions).
403 * User wants the ongoing stat-collection to be reset (in short: leave GAUGEs alone, reset ACCUMULATORs to zero,
404 * and reset HI_WMARKs to match the GAUGEs' current values). So we do the above, except that in `F()` upon
405 * acquiring the set-container of extant `Admin`s, we don't feed their respective `*this`es into a single
406 * `stats_aggregate_shards()` but rather into `stats_reset_shard_aggregate()`.
407 *
408 * This also has the nice property of synchronizing (a/k/a making serial) stat-consumptions and stat-resets.
409 * The `X.while_locked()` is both cases is on the same `X`, thus internally the same central mutex is being
410 * locked.
411 *
412 * Adding Thread_lcl_obj_db_client into this does not essentially change the picture. The code itself will
413 * clarify those details.
414 */

437/**
438 * Stats about the RAM use of the arena-lending SHM-provider's auxiliary (non-user-data) SHM-pools which are
439 * used internally to store and performantly communicate (cross-process) the current use-counts per
440 * first-class (`arena.construct<T>()`ed) object.
441 *
442 * ### Background et al ###
443 * Internally, an arena-lending SHM-provider (including SHM-jemalloc) maintains a *first-class object*
444 * (a/k/a `arena.construct()`ed object) database in memory. A given such object's *use-count* is defined as 1
445 * upon `.construct()` (and thus insertion into this obj-DB). Each `shm_session.lend_object()` -- typically
446 * so as to share it to another process which obtains its first-class object handle via
447 * `shm_session.borrow_object()` -- increments use-count by 1. Conversely, when the `.construct()`ed `shared_ptr`
448 * group reaches ref-count 0, use-count decrements by 1; and similarly for the `.borrow_object()`ed `shared_ptr`
449 * group. Once the use-count reaches zero, it is garbage-collected (GCed).
450 *
451 * The use-count is a *cross-process* quantity: process A constructs/lends/drops
452 * handle (`= 1`, `++`, `--` respectively), but process B borrows/drops (`--` for the latter), usually.
453 * Process A is the one with the original *arena*, so it must be aware of then the use-count drops to zero,
454 * including if process B was the one to have executed the last `--`. To avoid sending actual IPC messages for
455 * this situation, we maintain an internal-use only SHM-pool (per arena *per `arena.construct()`ing thread*),
456 * called *aux pool*; it is created the first time per `arena` that a given *thread* does `arena.construct<T>()`.
457 * Other thread(s), in this (owner) and borrowing process(es), each opens a SHM-handle to this same pool as
458 * needed, when a use-count must be affected (namely on `shm_session.lend_object()`, dispose in owner process;
459 * dispose in borrower process). When the aux-pool is no longer necessary (arena shutdown; or user-thread exit +
460 * no live objects from it left), it is destroyed.
461 *
462 * The point for stats is this: These aux pools take non-trivial RAM. This `Stat_set` tracks various facts
463 * about that topic and similar (e.g., not just about RAM per se but also counts of things that are causing the
464 * RAM use, or vaddr space use for that matter).

691/**
692 * Similar mission to shm::stat::Owner_obj_stats (which is relevant regardless of SHM-provider type) and
693 * Owner_obj_stats but applied specifically to the mechanism of arena-lending SHM-providers wherein each SHM-arena
694 * is divided into multiple, potentially many, SHM-pools.
695 *
696 * ### Background ###
697 * From the perspective of the arena (hence `Owner_` prefix) in which first-class objects are constructed
698 * (and GCed) and/therefore raw buffers are [de]allocated: a memory manager (such as jemalloc) carves allocations
699 * out of contiguous *vaddr areas* (a/k/a *extents*), which it obtains by having memory *memory-mapped*. Mapped
700 * space is not RAM in use: a page becomes *resident* (taken from general OS use) only once accessed. In an
701 * arena-lend SHM-provider (such as SHM-jemalloc) each such mapping is of a named *SHM-pool* (a/k/a segment,
702 * SHM-object; in Flow-IPC we use "[SHM-]pool"). (A SHM-pool can be accessed by other process(es); however that is
703 * not of direct interest from the owner's PoV, and therefore in the context of this discussion.)
704 *
705 * So, here we concern ourselves with SHM-pools, which compose the arena. Events of interest are, e.g.,
706 * memory-manager requested an extent (for us, pool), so we opened a SHM-pool and mapped M total bytes in that pool;
707 * perhaps the reverse (pool no longer needed, close it). These are straightforward, really, but a few
708 * things to keep in mind:
709 * - Pools are generally created when a user, directly or indirectly (usually indirectly in Flow-IPC),
710 * executes something like `alloc(N)`, and then *the memory manager, lazily requests pool creation* upon
711 * having run out of already-mapped pool space.
712 * - A pool can never change size, and it either exists (is mapped) or does not (is not mapped, name removed
713 * from file-system), in the arena-lending SHM-provider's owner context (i.e., arena context).
714 * - A given memory manager may want to work on finer units than entire pools, or possibly the reverse:
715 * it could split a pool into 2+ extents; or possibly merge 2+ pools into an extent -- if they are
716 * adjacent in vaddr-space. In short, we do not concern ourselves with that here. It is not super interesting
717 * to us from the SHM-provider perspective; and in any case see preceding bullet.
718 *
719 * @internal
720 * There are some counts that would be available to count, in SHM-jemalloc extent-hooks in particular at least --
721 * unclear if they would have equivalents for other/all arena-lend SHM-providers -- which we did not include.
722 * They are at least (again, for SHM-jemalloc) as follows.
723 * - Split-extent and merge-extents requests: Potentially interesting albeit inside-baseball. Not included
724 * chiefly because for all we currently know, they could be frequent enough to where the non-sharded
725 * counting otherwise used for Owner_pool_stats become sufficiently costly to have to introduce sharding or
726 * at least have a compile-time gate for whether to track these. Information is likely also available in
727 * native-jemalloc stats, which are available without us, *and* we facilitate grabbing them more conveniently
728 * elsewhere as well.
729 * - Commits/decommits: Too hairy/inside-baseball; not really an area of SHM-provider interest; not sure if perf
730 * risk. Probably available in native-jemalloc stats (ditto prev bullet). Might also be more of a thing or
731 * less of a thing depending on OS which speaks to its inside-baseballhood.
732 * - Lazy-purge, forced-purge: Probably not a perf risk. Again it seems too hairy/inside-baseball; and again
733 * probably available in native-jemalloc stats. As in prev bullet might be OS-dependent.
734 */

944/**
945 * Loosely similar subject matter to Owner_pool_stats but regarding the *borrower-side* view of SHM-pools,
946 * as opposed to an owner/arena-side view thereof.
947 *
948 * ### Background et al ###
949 * The most basic fact here is that, essentially, an owner-process has an arena which in a sense *produces*
950 * SHM-pools (as required by the memory manager, such as jemalloc, during allocations), and it also *deletes*
951 * them. Cf. the borrower side which *consumes* them via a procedure called pool-lending/borrowing.
952 * (This occurs in the background without user participation.) The setup is:
953 * - owner process A with arena X;
954 * - borrower process B;
955 * - a session SAB (`Shm_session` object SA in A, peer object SB in B) = communication context between them;
956 * - user explicitly *lends* arena: `SA.lend_arena(X)`. Now:
957 * - whenever arena X creates pool P1, it auto-lends P1 to B via SAB by-virtue of the fact that X has been lent
958 * through SAB. (There can of course be more pools over time.)
959 *
960 * None of this is limited to, like, one thing. A can have session SAC to process C; it can even have a
961 * separate session SAB2 -- but only via a separate `Shm_session` SA2 (and SB2 in B) -- again to B. (If X
962 * is lent through all of these sessions -- SAB, SAC, SAB2 in this example -- then a pool like P1 is auto-lent
963 * through all of them: twice to B, once to C.)
964 *
965 * @note What is "borrowing a pool"? It is: open a SHM-pool handle according to the pool's name (same one with
966 * which owner-process-arena create-opened it) -- as of this writing for read-only access, enforced by
967 * the kernel -- and memory-map it to a process-local vaddr.
968 *
969 * Due to this setup, the accounting is a bit tricky. Consider, now, a given process; B for example. It maintains,
970 * internally, a **global** *borrower repository* (*BR* for short), whose basic purpose is to maintain
971 * *every* pool currently being borrowed. We've shown above, though, that a given arena X can be (from a BR's
972 * PoV) be borrowed 2x+; and therefore a given pool P1 in X can be borrowed 2x+ also. BR shall nevertheless
973 * only maintain *one* SHM-pool handle (and *one* record of containing arena), while maintaining a *use-count*
974 * for each.
975 * - When an arena, and in-arena pool's, use-count goes from 0 to 1: record arena; *open pool*.
976 * - When an arena, and in-arena pool's, use-count goes from not-0 to not-0 (borrowed again/unborrowed, but use-count
977 * remains 1+): just inc or dec the use-counts; neither open nor close pool; just let it be.
978 * - When an arena, and in-arena pool's, use-count goes from 1 to 0 (unborrowed, as from session closing):
979 * *close pool* (un-memory-map; close pool-handle; delete record of arena).
980 *
981 * Therefore, from BR's (global) PoV, you've got: arena/pool registering (a/k/a borrowing), where use-count goes up;
982 * the opposite (goes down); opening (use-count reaches 1); and closing (use-count reaches 0). Plus, since each
983 * pool has a permanent (can never change) size, each actual-pool-handle + sums thereof <=> mapped-size + sums
984 * thereof. All these things, including use-counts, are counted in Borrower_pool_stats; and the global BR thus owns
985 * a global Borrower_pool_stats.
986 *
987 * The complexity continues: the above talks of the BR's PoV; but there is also:
988 * - BR's PoV, but broken down by *ever-borrowed arena*. (An arena, in this context, is identified by a
989 * machine-wide-unique, between boots, ID: owner/PID + in-process-ordinal-ID.) (Subject to culling of old
990 * per-arena stats; see session::shm::arena_lend::jemalloc::Shm_session::borrower_pool_stats_process_wide().)
991 * - A given arena X can be borrowed via session SAB, then unborrowed when SAB closes; then borrowed again
992 * via fully-subsequent session SAB2. Accumulators like pool-open-count for pool P1 will carry-over
993 * throughout and shall persist during any gap when X isn't borrowed by anything. Nothing is degenerate;
994 * though #m_n_borrowed_arenas cannot exceed 1 (an arena is either currently being borrowed, or it isn't).
995 * - A given `Shm_session`'s point-of-view. To wit: a given arena can only be borrowed via SB once
996 * (borrowing same via SB2 is not the same thing; the processes are the same in our example, but the
997 * session -- while similar in configuration -- is a different session). So all of the same things apply;
998 * but the use-count of a given arena, and pool therein, can only ever be 1. The values of some stat-members,
999 * when applied to a `Shm_session`, will thus carry certain degenerate values which are correct but of low
1000 * interest. They are still recorded, however, so we can reuse the same `struct` -- the amount of boiler-plate
1001 * otherwise would be obnoxious.
1002 * - Remember though: from this PoV, last-deregistering a pool does *not* necessarily mean closing its handle
1003 * and unmapping it. Same with first-registering versus opening+mapping. (It only does mean that from the
1004 * global BR's overall PoV, or as broken-down by arena.)
1005 *
1006 * Well... don't worry about it too much right now. Things will make more sense once you look at the actual
1007 * stat-consumption API... or, indeed, each of the 3:
1008 * - BR's global `Borrower_pool_stats` object. (No degenerate-valued members.)
1009 * - BR's global by-arena map: arena-ID => `Borrower_pool_stats`. (No degenerate-valued members.)
1010 * - A `Shm_session`'s non-global `Borrower_pool_stats` object. (Some degenerate-valued arena/pool-oriented members.)
1011 */

1199/**
1200 * The memory-manager-level statistics for a single native allocator-arena (for SHM-jemalloc: one jemalloc
1201 * arena) backing an arena-lend `Shm_arena` (e.g. jemalloc::Ipc_arena).
1202 *
1203 * @see Pool_stats: A peer grouping of per-arena stats; it must be separate due to not being TL-sharded or
1204 * coming from an external data source when internally collected; therefore the method of return is different
1205 * from a `*this`.
1206 * @see Sharded_stats: A peer grouping of per-arena stats; we are separate from it due to coming from an
1207 * external data source (memory manager: e.g., jemalloc) as opposed to from internal algorithms/data.
1208 * (They could still be bundled together. Nevertheless the subject matter/data source are, we feel,
1209 * so sharply different that Memory_manager_stats simply should remain separate from all others.)
1210 *
1211 * To summarize: An arena-lending SHM-provider (at least: SHM-jemalloc) manages SHM pools and sessions, as well as
1212 * cross-process garbage-collectable *first-class objects* (as `.construct<T>()`ed and `.borrow_object<T>()`ed);
1213 * but when it is required to actually allocate (or later deallocate) a buffer in SHM, the SHM-provider uses
1214 * a *memory manager* (for SHM-jemalloc, that's jemalloc). (In the middle of an allocation, sometimes
1215 * the memory manager needs a new vaddr area, which it requests of SHM-jemalloc via customization hook, so we
1216 * create a SHM-pool and... so it goes; the memory manager and the leveraging SHM-provider thus cooperate.)
1217 *
1218 * So, Memory_manager_stats tracks stats that happen to have these general properties:
1219 * - They are about the memory manager.
1220 * - They are usually collected by the memory manager itself; so Flow-IPC queries its stats subsystem
1221 * (e.g., jemalloc's robust stats/profiling module) and organizes it in useful shapes here. (All of the
1222 * information -- and surely more -- is available directly if desired. Use, e.g.,
1223 * jemalloc::Ipc_arena::get_jemalloc_arena_id() to grab the equivalent of #m_native_arena_id; then
1224 * query the memory manager itself. We aim to give the most relevant stuff here, though, for convenience.)
1225 * - They include (but aren't limited to) stats such that accurately accounting them means some kind of
1226 * tracking inside every `allocate()` and `deallocate()` ([de]allocate buffer) call. We stay away from
1227 * doing this in Flow-IPC proper, due to the performance risk at least, but memory managers know how to do
1228 * it well.
1229 * - `_hi_wmark` (e.g.: Vaddr::m_mapped_sz_hi_wmark) fields are not reported by memory manager directly (if they
1230 * were, we'd take them!), so their semantics have the same limitation as within TL-sharded `struct`s (e.g.: see
1231 * Sharded_stats doc header).
1232 *
1233 * This `struct` is SHM-provider-agnostic by design; a given SHM-provider impl fills what it can and leaves the
1234 * rest at default (usually zero).
1235 *
1236 * The first (as of this writing only) arena-lend SHM-provider is SHM-jemalloc, which fills these from jemalloc's
1237 * `mallctl()` statistics surface.
1238 *
1239 * ### How it is consumed ###
1240 * Unlike the continuously-sampled (and often TL-sharded) stat-sets, these are *raw readings* obtained from the
1241 * provider at stat-consumption time -- a single consistent snapshot per consume (for SHM-jemalloc: one
1242 * `mallctl("epoch")` refresh, then a batch of reads, repeated if someone else refreshed meanwhile). (Internally
1243 * this uses `flow::util::stat::stats_since_reset_state()`/`stats_mark_reset_state()`.)
1244 *
1245 * Per-arena context: a `Shm_arena` exposes one Memory_manager_stats per native arena it maintains, each
1246 * self-identified by #m_uniq_arena_id (<=> `Shm_arena`) and #m_native_arena_id (<=> native arena), both emitted
1247 * as GAUGEs.
1248 *
1249 * For SHM-jemalloc, as of this writing:

1358 /**
1359 * Sub-group: raw allocation activity -- cumulative counts of memory-manager allocate/deallocate operations
1360 * (e.g. each `Arena::construct<T>()` plus each nested container allocation), and the currently-live count/bytes
1361 * derived from them.
1362 *
1363 * These count *raw* (low-level) allocations, *not* first-class `construct()`ed objects (those are tracked
1364 * elsewhere, e.g. shm::stat::Owner_obj_stats): one `construct<T>()` of a container-bearing `T` may trigger many raw
1365 * allocations.
1366 *
1367 * The cumulative counts are ACCUMULATORs (reported relative to the last reset; see Memory_manager_stats "How it
1368 * is consumed"); the live count/bytes are GAUGEs (absolute), each with a high-water mark.
1369 *
1370 * Regarding HI_WMARKs: See note for Vaddr::m_mapped_sz_hi_wmark.
1371 *
1372 * SHM-jemalloc: How these stats are accounted
1373 * -------------------------------------------
1374 * ### Why discuss SHM-jemalloc specifically, here? ###
1375 * Formally speaking SHM-jemalloc is "merely" one SHM-provider of the arena-lend type. It is however the first
1376 * such SHM-provider; and as of this writing it is the only one. Therefore, out of pragmatism, we include
1377 * these notes here, even though this is the shm::arena_lend namespace as opposed to shm::arena_lend::jemalloc.
1378 * If or when more arena-lend SHM-providers are added, we may choose to reorganize this documentation; but
1379 * until then this discussion should be here for posterity.
1380 *
1381 * Now to the actual topic at hand: *How does (SHM-)jemalloc (de)allocation work + how is it accounted in `*this`*?
1382 *
1383 * ### Significant mechanism: jemalloc tcache ###
1384 * jemalloc -- and plausibly future arena-lend providers -- adds a *thread cache* (*tcache*) between the
1385 * "user" and the arena proper: a store of allocations kept on hand for quick reuse without arena-level locking.
1386 * SHM-jemalloc passes a tcache (one per thread, per-jemalloc-arena #m_native_arena_id) to every allocation;
1387 * jemalloc uses it for sizes up to its tcache maximum (32Ki bytes by default), while larger allocations bypass
1388 * it. (Build flag `IPC_SHM_ARENA_LEND_JEMALLOC_NO_TCACHE` skips tcache use entirely. Let us assume it is not
1389 * skipped, as tcache is a valuable perf mechanism.)
1390 *
1391 * Crucially, an allocation sitting in a tcache counts, from the arena's accounting standpoint, as *allocated* --
1392 * though no user holds it.
1393 *
1394 * @see Thread_cache doc header for a deeper look at how jemalloc tcache works.
1395 *
1396 * The upshot for the stats here is that jemalloc's counters (whether the `_sz` byte-counts or the `_count`s)
1397 * count allocations moving between the arena proper and the caches (or the user, when a cache is bypassed), not
1398 * individual user calls. A given `allocate()` or `deallocate()` serviced by the tcache does not update them.
1399 * Over time, though, the counters will be updated -- but in a lumpier/batchier way.
1400 *
1401 * Thus with the tcache in play:
1402 * - Cumulative #m_alloc_count / #m_alloc_sz (and the dealloc counterparts) measure allocations moving between
1403 * the arena and caches, not the count/bytes of user calls. They differ from the user-call counts in *either*
1404 * direction: a low-traffic size shows more than the calls (a cache refill fetches a batch, caching the
1405 * surplus), while a hot, recycled size can show fewer (allocations ping-pong between user and cache without
1406 * touching the arena). The size of the gap depends on the tcache churn pattern.
1407 * - The live #m_live_count / #m_live_sz similarly reflect what is currently taken from the arena, which
1408 * includes allocations in tcaches (therefore *not* used by actual user allocated-buffers). So `m_live_*`
1409 * members overstate what the user actually holds, by the current cache contents.
1410 * - Cf. Vaddr::m_active_sz: pages holding cached allocations stay "active" -- same effect, same cause.
1411 *
1412 * If the tcache use (by SHM-jemalloc) is compiled-out (see above), then all of this collapses: each counter
1413 * tracks user `allocate()`/`deallocate()` directly, and the live values are what the user holds. That's nice
1414 * for understanding the stats in real-time fashion, but in terms of perf it means more mutex-locking inside
1415 * jemalloc.
1416 *
1417 * @note jemalloc also counts per-call allocation requests (`nrequests`), but with no deallocation counterpart, so
1418 * it cannot feed the live values; hence all members here (including #m_histo_alloc_count_by_sz) use the
1419 * `nmalloc`/`ndalloc` view, with the above caveats. Nor do we offer an `nrequests`-based stat: with
1420 * explicit tcaches, jemalloc files part of those tallies under a different (automatic) arena, so
1421 * per-*our*-arena request counts would be an undercount of unknowable size.
1422 *
1423 * @internal
1424 * On `nrequests` (verified against jemalloc 5.3.0 and 5.4.0 source): tallies recorded at a tcache refill go to
1425 * the filling arena (ours); those recorded at a tcache flush or destruction go to the tcache's *associated* arena,
1426 * chosen internally at tcache creation; no public API can point it at our arena.
1427 */

1429 {
1430 // Data.
1431
1432 /// Cumulative count of allocate ops (for SHM-jemalloc: jemalloc small + large `nmalloc`).
1433 uint64_t m_alloc_count = 0;
1434
1435 /// Cumulative count of deallocate ops (for SHM-jemalloc: jemalloc small + large `ndalloc`).
1436 uint64_t m_dealloc_count = 0;
1437
1438 /**
1439 * Cumulative bytes allocated (for SHM-jemalloc: sum over size-classes of `nmalloc` x size-class-byte-size).
1440 *
1441 * @note Post size-class quantization (see #m_live_sz): bytes the heap handed out, not user-requested sizes.
1442 */
1443 uint64_t m_alloc_sz = 0;
1444
1445 /// Cumulative bytes deallocated (for SHM-jemalloc: sum over size-classes of `ndalloc` x size-class-byte-size).
1446 uint64_t m_dealloc_sz = 0;
1447
1448 /// (Gauge) Currently-live allocation count (= #m_alloc_count minus #m_dealloc_count).
1449 uint64_t m_live_count = 0;
1450
1451 /// Max of #m_live_count observed so far.
1452 uint64_t m_live_count_hi_wmark = 0;
1453
1454 /**
1455 * (Gauge) Currently-live allocated bytes (for SHM-jemalloc: jemalloc small + large `allocated`).
1456 *
1457 * @note This is post size-class quantization -- i.e. "what the heap holds," not the sum of user-requested sizes.
1458 */
1459 size_t m_live_sz = 0;
1460
1461 /// Max of #m_live_sz observed so far.
1462 size_t m_live_sz_hi_wmark = 0;
1463
1464 /**
1465 * Cumulative allocation count broken down by allocation size-class, as a histogram: each bucket counts the
1466 * cumulative allocations of a certain size-class; so a user-request for allocation of N bytes results in
1467 * a `++` for the bucket whose `Histogram_counter` bounds are [N or lower, N or higher].
1468 *
1469 * A caveat here:
1470 *
1471 * @note The previous description ignores the tcache mechanism. See Alloc doc header which explains
1472 * how tcache can affect these semantics.
1473 *
1474 * For SHM-jemalloc this is jemalloc's small `bins` followed by its large `lextents`, concatenated into one

1480 * unknown at compile-time, so we use some placeholder values (`{2, 1}`) in the default-init near this
1481 * doc-comment; but this structure is never used. The placeholder bounds in the default-initializer
1482 * are overwritten when actually emitting stats into a `*this`, most notably at stat-consume (via public
1483 * `Shm_arena` API invoked by the user) time.
