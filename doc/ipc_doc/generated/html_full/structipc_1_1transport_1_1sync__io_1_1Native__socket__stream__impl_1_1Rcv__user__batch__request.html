Detailed Description

Similar in spirit to Rcv_user_request but stores a batch-receive request as opposed to a single-message-receive request.

Todo:
For a fairly-minor (especially since this is inside the impl, not the API) bit of consistency with the vaguely comparable sync_io::Async_adapter_receiver, we should arguably rename Rcv_user_request => Rcv_user_request_one, Rcv_user_batch_request => Rcv_user_request_batch. The former was kept as-is basically because pre-batch-feature that is what it was called.

Why *_batch_in m_batch itself not in here?

I.e., the central object is the *batch arg to async_receive_*_batch(), so why isn't it here? Answer: the type is parameterized: ..._batch_in<Msg_resource>, where Msg_resource is a function template parameter and can well be different between different calls to the API (a method template). Using type erasure here does not make sense (trust us).

So where is it?

It is passed around as a lambda capture + template-parameterized arg to all the hairy internal functions in the batch-receive code-path. (E.g. note rcv_read_batch_from_pkt_stream() is a template that takes batch as an arg.) This is not particularly exotic at this point; when using lambda captures classic state-as-data-members can go away. Whether that makes code clearer or less-clear is subjective... but in this case there's no choice anyway (in my (ygoldfel) opinion it is no less clear anyway). To summarize, then: we store what we can in here, and we pass-around batch via captures + args (because we can't store it in here).

This might raise the question, though: why even store any such state as the data members m_rcv_user_request and m_rcv_user_batch_request? We could e.g. make Rcv_user_batch_request a struct template parameterized on Batch; and exclusively pass it and Rcv_user_request around via lambda capture + template-parameterized arg. Answer: Honestly this might just be a don't-rock-the-boat situation; as m_rcv_user_request was in-use pre-batching-feature, so we made Rcv_user_batch_request consistently with that (but batch cannot be stored that way, so it is passed-around differently). The resulting code seems fine... but, arguably, the following to-do is worth considering.

Todo:
Consider making Native_socket_stream_impl::Rcv_user_batch_request a template on typename Batch; removing Native_socket_stream_impl::m_rcv_user_request and m_rcv_user_batch_request; and passing them around Native_socket_stream_impl insides via lambda captures and template-parameterized args. The motivation is consistency and, arguably, simplicity; see discussion in the preceding paragraph relative to this to-do in the code. Note that (1) this would be essentially a stylistic change (perf impact negligible) and (2) we'd still need to mark whether a user-request is in progress, to continue guarding against user attempts to launch simultaneous receive requests. For (2) we'd probably replace the struct members m_rcv_user_request and m_rcv_user_batch_request with a single bool m_rcv_user_request_active.
