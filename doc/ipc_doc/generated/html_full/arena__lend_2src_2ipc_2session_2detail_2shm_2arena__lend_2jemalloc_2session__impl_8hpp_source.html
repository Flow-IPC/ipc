48/**
49 * Common data and logic for shm::arena_lend::jemalloc::Server_session_impl and
50 * shm::arena_lend::jemalloc::Client_session_impl. Arena-lending SHM-providers are almost exactly the same,
51 * once everything is open; the only difference is session-server provides an extra `Arena` shared among
52 * all sessions with the same opposing Client_app (created the first time such a session-client establishes
53 * a session); jemalloc::Session_server tracks these `Arena`s and coordinates with jemalloc::Server_session.
54 * So all the in-common stuff is here in this internally-used super-class of the 2 `*_impl`. The setup
55 * procedure is asymmetrical, and the two sides of that asymmetry are in those 2 `*_impl`s -- including
56 * the differing APIs (e.g., Client_session_impl::sync_connect()).
57 *
58 * @tparam Session_impl_t
59 * Our base that our sub-class wants to build on-top-of. E.g., `Server_session_impl<...>`.
60 */

203 /**
204 * To be invoked at most once, synchronously sets up nearly-all aspects of this arena-lending-SHM-capable `Session`;
205 * the prerequisite from sub-class `_impl` being that the possibly-asynchronous steps leading up to this have been
206 * completed successfully. Namely the arg `local_hndl` is the local half of the connected socket-pair created
207 * by the server as needed to create the internal-use IPC channel for the SHM-provider; and
208 * - Client_session_impl: it has async-received this item, after opposing Server_session_impl generated it;
209 * - Server_session_impl: it has generated it and successfully sent the other (of 2) handle to opposing
210 * Client_session_impl.
211 *
212 * That says "nearly-all aspects." That is because Server_session_impl must do one extra thing; namely also create
213 * the `.app_shm()`-returned #Arena and pass that to us as `app_shm_or_null`.
214 *
215 * @param local_hndl
216 * See above. Must not be `.null()`; else behavior undefined (assertion may trip).
217 * `local_hndl` becomes `.null()` at exit. Regardless of init_shm() success or failure, it shall ensure
218 * return of the contained native handle to the OS at the proper time (the caller can rest easy).
219 * @param pool_name_fragment_or_empty
220 * Fragment to add, unless empty, into the SHM-pool name when pool(s) is/are created by SHM-provider.
221 * In particular the final absolute pool name, for each pool, shall be `/P/X/R`, where P and R will
222 * be determined by `*this` internally; while X -- which shall exclude the leading and trailing
223 * util::Shared_name::S_SEPARATOR (represented as forward-slash in this explanation) -- is
224 * supplied in `pool_name_fragment_or_empty`. If the arg is `.empty()`, then the `/X/` part shall be
225 * omitted. Rationale: for cleanup purposes Client_session_impl needs to encode certain info
226 * (spoiler alert: session-client process ID) that can be later parsed-out upon performing a
227 * `for_each_persistent()` (spoiler alert: directory-listing of `/dev/shm` in Linux at least).
228 * More generally perhaps other info could be encoded there so as to be acquired from an existing
229 * pool-name later. So this here provides the opportunity for our sub-classes to do that.
230 * @param app_shm_or_null
231 * See above. It'll be registered with shm_session() unless null.
232 * @return Whether it was successful (creation of, at least, the #Arena may fail); falsy if so,
233 * the reason describing failure if not. In the former case, post-conditions:
234 * session_shm() and shm_session() are not null.
235 */
236 Error_code init_shm(util::Native_handle&& local_hndl,
237 const Shared_name& pool_name_fragment_or_empty,
238 const std::shared_ptr<Arena>& app_shm_or_null = {});

250 /**
251 * With the pre-condition that this session is in PEER or (in `Server_session` case) at least almost-PEER state,
252 * and we are currently in thread W (`Base::async_worker()`), and `Base::hose()` has not been called,
253 * performs `session_shm()->sample_hi_wmarks()` and schedules for this to occur again in some regular period
254 * of time. Stops ticklings once PEER state is reached and `hosed() == true`; or `session_shm()` is null.
255 * (Not saying the latter is even possible... but if it were possible and happened, then the stat-tickling and
256 * further scheduling thereof stops.)
257 *
258 * ### Rationale / Background ###
259 * Consider having *just* reached PEER or almost-PEER state (the latter = session is open, but user must still call
260 * `Server_session::init_handlers()` to reach PEER state; we do not care about that either way here). So then:
261 *
262 * Done! Success! At this moment: In (almost-)PEER state, in thread W:
263 * We shall now add some value. This requires a little background though. SHM-jemalloc's jemalloc::Ipc_arena
264 * and `Shm_session` (aliased for genericness in our `Session`-land as `Arena` and `Shm_session`
265 * respectively), and a whole complicated host of thread-local and global-singleton modules that aid them,
266 * maintain various stats a-la `flow::util::stat`. That's all basically self-contained and not special.
267 * Also, formally speaking, not special: For some of its many stats, it has to use particular stat-collection
268 * techniques (spoiler alert: (1) TL-sharding; (2) querying memory manager -- jemalloc -- as data source)
269 * that have the implication on how `_hi_wmark` stat-members are computed/what they mean. See
270 * `Sharded_stats` and `Memory_manager_stats` doc headers for details, but in short: a given `m_X_hi_wmark`
271 * is only across samples taken at stat-consumption time, because the value of `m_X` cannot be
272 * continuously watched in-between. So, in order for those particular members -- the HWMs
273 * (high-water-marks) -- to be at least somewhat useful, stats have to be sampled regularly.
274 *
275 * A direct user of `Ipc_arena`/`Shm_session`/SHM-jemalloc would -- if they even care about this corner which
276 * is certainly not a given -- have to be responsible for the regular stat-consuming (even when not
277 * interested in the actual stats at those times). We, however, have a nice, low-activity worker thread
278 * and event loop (thread W!), so we can easily do this for them.
279 *
280 * The mechanics: `Shm_session`-oriented stats are not involved in this; the HWMs if any are accurate sans
281 * intervention. So it's just `Ipc_arena`. One just calls: `arena.sample_hi_wmarks()`.
282 *
283 * A question is, what's `arena` for us? Answer:
284 * - There is `*(session_shm())`. That's one. We just set it up earlier using init_shm().
285 * - There is `*(app_shm())`. That's the other one. That has a lifetime unrelated to a particular
286 * single session (`*this` included), though, and is therefore maintained by jemalloc::Session_server.
287 * So `Session_server` is responsible for handling the `app_shm()` guys in this respect.
288 *
289 * So that's that. Let us set-up the periodic `session_shm()`-tickling. Specifically: Tickle it "now,"
290 * upon having reached (almost-)PEER state, and schedule the next one.
291 */
292 void session_shm_stats_tickle_and_schedule();

315TEMPLATE_JEM_SESSION_IMPL
316Error_code CLASS_JEM_SESSION_IMPL::init_shm
317 (util::Native_handle&& local_hndl,
318 const Shared_name& pool_name_fragment_or_empty,
319 const std::shared_ptr<Arena>& app_shm_or_null)
320{
321 using ipc::shm::arena_lend::jemalloc::Memory_manager;
322 using flow::util::ostream_op_string;
323 using std::make_shared;
324 using std::string;
325 using std::to_string;
326
327 // We are in thread W (of vanilla Server/Client_session_impl).
328
329 assert(!local_hndl.null());
330
331 assert(!m_session_shm);
332 assert(!m_shm_session);
333
334 // First m_session_shm (per-session-scope Arena). This can fail.
335
336 /* Arena needs a pool name prefix it will use each time the memory manager decides it wants a new mmap()ped vaddr
337 * space (in the SHM context, <-> SHM-pool). We use our standard semantics for per-session items; but
338 * possibly add pool_name_fragment_or_empty for reasons explained in our method doc header. */
339 auto shm_pool_name_prefix = build_conventional_shared_name(Shared_name::S_RESOURCE_TYPE_ID_SHM,
340 Shared_name::ct(Base::Base::m_srv_app_ref.m_name),
341 Base::Base::srv_namespace(),
342 Shared_name::ct(Base::Base::cli_app_ptr()->m_name),
343 Base::Base::cli_namespace());
344 shm_pool_name_prefix /= SHM_SUBTYPE_PREFIX;
345 if (!pool_name_fragment_or_empty.empty())
346 {
347 shm_pool_name_prefix /= pool_name_fragment_or_empty;
348 }
349
350 /* Arena::create() throws on failure (it does not return null). We must catch it: we are in a flow::async thread,
351 * where an uncaught exception would exit() the entire process; whereas this merely means this session cannot
352 * open. (Realistic causes are environmental limits: e.g., the per-process FD limit, as each SHM-pool takes an FD.)
353 * Emit the exception's own Error_code, if it has one; else a general one of our own. */
354 Error_code create_err_code;
355 try
356 {
357 m_session_shm
358 = Arena::create(get_logger(),
359 /* @todo At the moment this is fine: it is even data-free in practice.
360 * TBD whether "formally" this is correct, or we should be storing a singleton or let user
361 * pass-in a thing, or what; particularly if this goes beyond jemalloc specifically.
362 * At the moment it really is fine; even though it derives from a generic-looking
363 * Memory_manager, echan confirms that's at the moment a basically-abandoned idea. Nor is there
364 * a practical plan to really un-abandon it. */
365 make_shared<Memory_manager>(),
366 std::move(shm_pool_name_prefix),
367 /* This is clearly correct if *this super-classes Server_session_impl; but what about
368 * Client_session_impl, given that the setting comes from Server_app m_srv_app_ref?
369 * Answer: Yes, still; see discussion in Server_app::m_permissions_level_for_client_apps doc
370 * header. */
371 util::shared_resource_permissions
372 (Base::Base::m_srv_app_ref.m_permissions_level_for_client_apps));
373 }
374 catch (const boost::system::system_error& exc) // Including flow::error::Runtime_error.
375 {
376 create_err_code = exc.code() ? exc.code() : Error_code{error::Code::S_SHM_ARENA_CREATION_FAILED};
377 FLOW_LOG_WARNING("Session [" << *this << "]: Failed to create session-scope Arena; exception "
378 "[" << exc.what() << "]; emitting [" << create_err_code << "] "
379 "[" << create_err_code.message() << "]. Session will not open.");
380 }
381 catch (const std::exception& exc)
382 {
383 create_err_code = error::Code::S_SHM_ARENA_CREATION_FAILED;
384 FLOW_LOG_WARNING("Session [" << *this << "]: Failed to create session-scope Arena; exception "
385 "[" << exc.what() << "]; emitting [" << create_err_code << "] "
386 "[" << create_err_code.message() << "]. Session will not open.");
387 }
388
389 if (create_err_code)
390 {
391 assert(!m_session_shm);
392
393 /* We promised to dispose of this at the proper time. Since we won't create the Channel that would do it,
394 * let's do it directly. */
395 local_hndl.close();
396
397 return create_err_code;
398 }
399 // else
400 assert(m_session_shm && "Arena::create() throws on failure, else returns non-null.");
401
402 /* Next m_shm_session (the lender from any locally-managed arena(s), including m_session_shm; the borrower
403 * from opposing-process-managed arena(s)).
404 *
405 * It needs this channel for internal communications, notably about lending arenas (as we will below)
406 * and subsequently pools within those (automatically). */
407
408 const auto nickname = ostream_op_string("jem-", *this);
409 /* Sure, Shm_session gave us this nice alias; but really it's a specific type, and we must feed it specific things;
410 * namely (substantively speaking) the local_hndl we painstakingly obtained during our session setup. */
411 Shm_session::Shm_channel raw_shm_channel{get_logger(), nickname,
412 transport::sync_io::Native_socket_stream
413 {get_logger(), nickname, std::move(local_hndl)}};
414
415 /* Please see Native_socket_stream::remote_peer_process_credentials() doc header for explanation of this.
416 * (Technically this is only necessary server-side; client-side the values will already be correct, because
417 * the connect_pair() call occurred on the opposing-to-us side; and hence will overwrite X with X -- a no-op.
418 * Nevertheless doing it this way is (1) simpler code; (2) perf-wise of negligible impact; and (3) more
419 * maintainable. In any case master_channel_const().owned_channel()->remote_peer_process_credentials() has
420 * correct values, so shoving them into raw_shm_channel is not-wrong.) */
421 {
422 Error_code err_code;
423 const auto& creds = Base::master_channel_const().owned_channel()->remote_peer_process_credentials(&err_code);
424 if (err_code)
425 {
426 /* The *session master channel's* socket stream got hosed (by an error, e.g., the opposing process died)
427 * before we got here; so it no longer hands out the opposing-process creds. Session opening is doomed;
428 * that master-channel error is logged and handled elsewhere. We could wait for it; but (as in a similar
429 * corner case in jemalloc::Server_session_impl, which emits the sibling catch-all Code
430 * S_SERVER_MASTER_SHM_UNEXPECTED_TRANSPORT_ERROR) let's just fail synchronously. Cleanup: m_session_shm,
431 * created above (be somewhat aggressive, though they'd go away in destructor anyway); while raw_shm_channel
432 * (owning the handle formerly in local_hndl, as we promised to dispose of it) goes away on return. */
433 FLOW_LOG_WARNING("Session [" << *this << "]: Could not obtain opposing-process creds from session master "
434 "channel, whose transport must have just been hosed: "
435 "[" << err_code << "] [" << err_code.message() << "]. Session will not open; the "
436 "triggering error is (or will be) logged separately.");
437 m_session_shm.reset();
438 return error::Code::S_MASTER_SHM_UNEXPECTED_TRANSPORT_ERROR;
439 }
440 // else
441 raw_shm_channel.blob_snd()->remote_peer_process_credentials(creds);
442 }
443
444 /* Shm_session requires a non-nil session token (its internal channel is keyed to our logged-in session); but
445 * the session master channel's session_token() returns nil, if that channel has been hosed by now. Same corner
446 * case, and same treatment, as just above. */
447 const auto& session_token = Base::master_channel_const().session_token();
448 if (session_token.is_nil())
449 {
450 FLOW_LOG_WARNING("Session [" << *this << "]: Session master channel reports nil session token; it must have "
451 "just been hosed. Session will not open; the triggering error is (or will be) logged "
452 "separately.");
453 m_session_shm.reset();
454 return error::Code::S_MASTER_SHM_UNEXPECTED_TRANSPORT_ERROR;
455 }
456 // else
457
458 auto setup_done = make_shared<bool>(false);
459
460 // Recommend reading create() doc header; it explains how error reporting works w/r/t raw_shm_channel.
461 m_shm_session = Shm_session::create(get_logger(),
462 std::move(raw_shm_channel), // m_shm_session owns it fully now.
463 session_token,
464
465 /* During its operation (not the init we're doing right now!) a synchronous
466 * Shm_channel op (send(), sync_request()) may yield a channel-hosing error --
467 * at most once -- and then this will be called: */
468 [this, setup_done]
469 (const Error_code& err_code) mutable
470 {
471 /* We are in m_shm_session's background thread. It calls it thread W, but that's not our
472 * thread W (of vanilla Server/Client_session_impl).
473 *
474 * Shm_session got an incoming-direction channel-hosing error, or an outgoing-direction error trying to do
475 * send() or equivalent; either way per contract it reports such a thing up to *once* from the aforementioned
476 * thread. As discussed in Shm_session::create() our choices here are:
477 * - Eat it (log and that's it), because we have our own way(s) of responsively detecting session-hosing
478 * and then <handle session hosing> (discussed a bit down).
479 * - Don't eat it: It indicates Shm_session permanently lost contact with its peer, hence we must now
480 * <handle session hosing>.
481 *
482 * We are going with "eat it." It is just simpler.
483 * - If this added socket-stream-based channel dies, so would m_master_channel (also socket-stream-based).
484 * We have to, and do, handle that.
485 * - So it would hose the session anyway, maybe even sooner if it's due to zombification
486 * (it has keep-alive/idle-timer in both directions, unlike at this time this new channel).
487 *
488 * What is <handle session hosing>? There are 3 phases involved, and finding out about session-hosing
489 * could happen in any of them.
490 * -# Before *setup_done becomes true, a few lines below. Namely we will make 1-2 m_shm_session->lend_arena()
491 * calls.
492 * -# After *setup_done becomes true but before PEER state; also quite soon. The actual steps taken
493 * depend on whether this is Server_session or Client_session.
494 * -# Upon reaching PEER state.
495 *
496 * In phase 3, which is the long one, as of this writing do basically:
497 * `if (!Base::hosed()) { Base::hose(err_code); }` which invokes the session on-error handler that must have been
498 * provided by user to enter PEER state.
499 *
500 * In phase 2: details omitted, but at a high level both Client_session and Server_session paths properly
501 * deal with whatever might go wrong (on_master_channel_error() on server, and what-not).
502 *
503 * In phase 1: it is not per se special; in this context it is the same as phase 2. That said, each of the 1-2
504 * m_shm_session->lend_arena() calls can return false. By contract the meaning is: "couldn't do it, because
505 * the attempt to inform peer Shm_session via raw_shm_channel.send()/equivalent synchronously failed, and we will
506 * fire the callback you gave us [what you are reading now] from a background thread with more info, 1x."
507 * Hence we could literally ignore lend_arena()'s return value. Our own session-hosing sensing will handle it,
508 * and the fact that the other side isn't aware of 1 or both of the relevant of our arenas won't matter:
509 * we're going to fail to open the session, or worst case detect it immediately in phase 3 and fire the
510 * session on-error handler.
511 *
512 * Nevertheless we don't ignore lend_arena()'s return value(s). If 1 fails, we emit an error to that effect
513 * and fail immediately in phase 1. (Note that all this is quite unlikely in the first place. Nevertheless
514 * we should do the right thing.) Why? It isn't cut-and-dried. The drawback is that we won't know the
515 * exact way the link was severed, in the form of an Error_code: our session-hosing sensors produce this
516 * (basically: m_master_channel's socket stream disconnected with errno so-and-so => Error_code), but we will
517 * shortcircuit the (very) short wait for that and just synchronously emit a generic Error_code here.
518 * The benefit is simply a reduction of entropy by acting synchronously with information that's synchronously
519 * available. (At least logs will include the "real" Error_code; but programmatically it's not available to
520 * the user which is a bit of a downgrade. It's not a massive loss given the context.)
521 *
522 * So that's the grand plan. And as part of that plan, here we will only log. */
523 Base::async_worker()->post([this, setup_done = std::move(setup_done), err_code]()
524 {
525 // We are in thread W (of vanilla Server/Client_session_impl).
526 if (*setup_done)
527 {
528 FLOW_LOG_WARNING("Session [" << *this << "]: Internal-use (for SHM) channel reported "
529 "error [" << err_code << "] [" << err_code.message() << "]. This occurred after SHM-setup; "
530 "almost certainly the session master channel and/or attempts to lend/borrow "
531 "will catch a problem or have caught it; "
532 "session will be hosed, or session opening will fail, depending on the situation.");
533 // That last part is an oblique reference to the above so-called phases 2 and 3.
534 }
535 else
536 { // So-called phase 1 above.
537 FLOW_LOG_WARNING("Session [" << *this << "]: Internal-use (for SHM) channel reported "
538 "error [" << err_code << "] [" << err_code.message() << "]. This occurred during SHM-setup, "
539 "so we will catch it or have caught it and will fail to open session.");
540 }
541 });
542 }); // m_shm_session = Shm_session::create()
543
544 assert(m_shm_session && "It's not supposed to fail according to contract.");
545
546 // Next register shm_session() with session_shm(), so stuff constructed in session_shm() can be lend_object()ed.
547
548 if (!shm_session()->lend_arena(session_shm_ptr()))
549 {
550 /* This message recaps the trade-off between failing out here versus letting session-hosing-sensing occur
551 * that we discussed in the comment inside the functor given to create() above. */
552 FLOW_LOG_WARNING("Session [" << *this << "]: Registering session-scope local Arena with borrow/lend engine: "
553 "failed (details likely above). Assuming we are bug-free in using the SHM-provider API "
554 "this would occur only on internal SHM-provider IPC channel error; but due to certain internal "
555 "reasons the triggering Error_code has not reached this thread yet; reporting a more general "
556 "Error_code. That detail aside: Session will not open.");
557
558 m_shm_session.reset(); // Be somewhat aggressive, though they'd go away in destructor anyway.
559 m_session_shm.reset();
560 return error::Code::S_SHM_ARENA_LEND_FAILED;
561 } // if (!shm_session()->lend_arena(session_shm()))
562 // else
563
564 // Lastly register per-app-scope one if so asked (if Server_session_impl is the sub-class invoking us).
565
566 if (app_shm_or_null && (!shm_session()->lend_arena(app_shm_or_null)))
567 {
568 FLOW_LOG_WARNING("Session [" << *this << "]: Registering app-scope local Arena with borrow/lend engine: "
569 "failed (details likely above). Assuming we are bug-free in using the SHM-provider API "
570 "this would occur only on internal SHM-provider IPC channel error; but due to certain internal "
571 "reasons the triggering Error_code has not reached this thread yet; reporting a more general "
572 "Error_code. That detail aside: Session will not open.");
573
574 m_shm_session.reset();
575 m_session_shm.reset();
576 return error::Code::S_SHM_ARENA_LEND_FAILED;
577 }
578 // else
579
580 *setup_done = true;
581
582 FLOW_LOG_INFO("Session [" << *this << "]: Successfully created session-scope Arena; and "
583 "borrow/lend engine Shm_session; registered the former to the latter; "
584 "registered app-scope arena too? = [" << bool(app_shm_or_null) << "].");
585
586 return {};
587} // Session_impl::init_shm()

589TEMPLATE_JEM_SESSION_IMPL
590void CLASS_JEM_SESSION_IMPL::session_shm_stats_tickle_and_schedule()
591{
592 using boost::chrono::seconds;
593
594 /* Firstly see our doc header; then come back here.
595 *
596 * Secondly let's discuss the appropriate (default at least) period for this tickling. In actual fact this
597 * will ultimately invoke, at most, Ipc_arena::sharded_stats() and Ipc_arena::memory_manager_stats().
598 * The tickling won't log anything INFO-or-higher, so it isn't about that. Computationally it's not exactly cheap --
599 * have to aggregate a bunch of thread-local stat-shards and query jemalloc-stats respectively. It is probably
600 * okay every second though. We're going on the safe side and doing it 10x less frequently than that.
601 * The tension is of course with trying to increase the resolution of the handful of HWM values involved.
602 * 10 seconds "feels" decent. */
603 constexpr util::Fine_duration TICKLE_PERIOD = seconds{10}; // @todo Provide a knob including ability to turn off?
604
605 // We are in thread W.
606
607 assert(((!Base::Base::on_err_func_set()) || (!Base::Base::hosed()))
608 && "Bug: internal contract is to call this only pre-hose().");
609
610 const auto arena = session_shm();
611 if (!arena)
612 {
613 /* Don't even care why or how (maybe it's even impossible; does not matter). No arena anymore for some reason?
614 * Then nothing to tickle. Move on. It's deliberately defensive/self-contained logic. */
615 return;
616 }
617 // else
618
619 arena->sample_hi_wmarks(); // Thread safety: It is safe from any thread by its contract.
620
621 Base::async_worker()->schedule_from_now(TICKLE_PERIOD, [this](auto&&) mutable
622 {
623 // We are in thread W.
624 if ((!Base::Base::on_err_func_set()) || (!Base::Base::hosed()))
625 {
626 session_shm_stats_tickle_and_schedule();
627 }
628 // else { Same as above: Whatever; we're done with the ticklings then. GTFO. }
629 });
630} // Session_impl::session_shm_stats_tickle_and_schedule()
