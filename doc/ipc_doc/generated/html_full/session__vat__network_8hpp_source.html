113/**
114 * The core class of Flow-IPC's zero-copyification-of-capnp-RPC module, `Session_vat_network` implements
115 * `capnp::VatNetwork` and can be accurately described as `capnp::TwoPartyVatNetwork` but with zero-copy
116 * performance. That is: it behaves ~identically to that stalwart of vanilla capnp-RPC (`TwoPartyVatNetwork`),
117 * but every capnp-RPC message (including ones containing user's capnp-encoded data flying back and forth)
118 * is (under the hood) allocated in SHM and is *never* copied. Hence message size ceases to be a perf
119 * consideration: a large message costs about the same as a small one. (For small messages, which are cheap to copy
120 * anyway, expect perf similar to `TwoPartyVatNetwork`.) The one hard limitation: Session_vat_network cannot work
121 * over a network link (for obvious reasons). However, API-wise, the two alternatives are used identically after
122 * construction! So to the extent that user code can be written independently of whether networking is involved,
123 * one can write generic code that will work with either `capnp::TwoPartyVatNetwork` (required for networking) or
124 * Session_vat_network (zero-copy-enabled, for local IPC). It can even be a template parameter.
125 *
126 * @see ipc::transport::struc::shm::rpc namespace doc header for an overview of Flow-IPC capnp-RPC support, including
127 * how the present class relates to the others there.
128 *
129 * @note It is also possible to have our Session_vat_network act identically to the vanilla `TwoPartyVatNetwork`,
130 * such as for easy fallback, benchmarking, and so forth. See the "Bonus!" section below for the recipe.
131 *
132 * ### How to use this to do capnp-RPC? ###
133 * If you know capnp-RPC, then you probably already know about `VatNetwork` and `TwoPartyVatNetwork` and therefore
134 * already can basically answer that question.
135 *
136 * If you do not, or are rusty, we recommend reading the introduction pages
137 * in Cap'n Proto documentation (https://capnproto.org/rpc.html, https://capnproto.org/cxxrpc.html);
138 * perusing the Calculator sample; and once a bit comfortable coming back here. We do give a
139 * short recap here, but it is no substitute for the real thing (w/r/t giving one a capnp-RPC introduction).
140 *
141 * In short:
142 * - Wherever you were using `TwoPartyVatNetwork` -- as long as it does not involve crossing a machine boundary
143 * (networking) -- simply use Session_vat_network instead (and/or parameterize on which one you want in a given
144 * scenario at compile-time). The entire API is identical:
145 * - It implements `capnp::VatNetwork` and as such will slot-in to the standard capnp-RPC setup:
146 * `VatNetwork` + `capnp::RpcSystem` + `Client` + `Capability::Client`.
147 * - The rest of the API (stuff that is not `VatNetwork` virtual impls) is very small; essentially you
148 * can get a disconnect-promise via a particular method, same as with `TwoPartyVatNetwork`.
149 * - The only difference: (next paragraph)
150 * - Constructing a Session_vat_network has a somewhat different API. It makes use of ipc::session, and we
151 * provide a KJ-promise-based-event-loop-friendly interface for creating `ipc::session::Sessions`s, so that
152 * it is natural to use in the capnp-RPC-ish style of programming.
153 * - We provide higher-layer APIs to make your life easier.
154 * (In all cases the core of things is still Session_vat_network.)
155 * - Client_context and Context_server will ease creation of the necessary `Session_vat_network`s by
156 * starting ipc::session session/server and auto-completing the procedure yielding the `VatNetwork` for
157 * each capnp-RPC conversation. However you shall then still create the #Rpc_system yourself and start and
158 * design your event loop.
159 * - Ez_rpc_client and Ez_rpc_server are higher-layer still and are exactly analogous to
160 * `capnp::EzRpcClient` and `capnp::EzRpcServer` (but zero-copy-enabled). These will start and
161 * run the entire event loop as needed as well.
162 *
163 * The `-> stream` feature (https://capnproto.org/news/#multi-stream-flow-control) has a potential impact on
164 * shared RAM (SHM) use, and possibly on performance. The way the related *flow control window* is determined
165 * differs from vanilla (non-zero-copy) capnp-RPC's impl (as described in that link).
166 * - You may control and/or observe the relevant window knob via streaming_flow_window_ki() methods
167 * (accessor, mutator).
168 *
169 * ### Bonus! You can turn this into a plain, non-zero-copy `TwoPartyVatNetwork` ###
170 * This might not blow your mind completely, but it might be nice to make use of Flow-IPC's ipc::session
171 * mechanism for the initial connection with a `TwoPartyVatNetwork` itself. It might be useful for fallback,
172 * benchmarking, debugging, profiling too.
173 *
174 * To achieve this:
175 * - Still choose some SHM-provider (perhaps the one you'd use when benchmarking *with* zero-copy; otherwise
176 * any one of them) and therefore template parameters. Easier yet use an alias like:
177 * - `"ipc::session::shm::classic::Client_session::Vat_network"` / `"Server_session::Vat_network"`;
178 * - `"ipc::session::shm::arena_lend::jemalloc::Client_session::Vat_network"` / `"Server_session::Vat_network"`.
179 * - Pass-in `shm_enabled_session = nullptr` (or, if applicable, `shm_lnd_brw = shm_arena = nullptr`) constructor
180 * arg(s). Or:
181 * - The aforementioned higher-layer APIs (Client_context + Context_server; Ez_rpc_client + Ez_rpc_server)
182 * all provide access to this mode as well. See their docs.
183 *
184 * @todo rpc::Session_vat_network and probably some of the layers built on top of it should make
185 * `capnp::ReaderOptions` configurable -- analogously to the vanilla `capnp::TwoPartyVatNetwork`. (Be sure to
186 * apply this judiciously to the correct layer of serialization; and document thoughtfully, as the practical
187 * perf implications here are different from the vanilla/non-zero-copy use case.)
188 *
189 * Object lifetimes: A caveat
190 * --------------------------
191 * This section applies if you use `*this` directly; or if you use Client_context and Context_server which
192 * is easier. The `Ez_rpc_*` APIs generally relieve you of having to worry about it.
193 *
194 * A potentially surprising fact, especially to those new to KJ and/or capnp-RPC, is that while a `VatNetwork`
195 * (a `*this` in our context) is indeed a central player in implementing a capnp-RPC system -- and indeed its
196 * lifetime (construction, destruction) is explicitly controlled by its user -- its
197 * destruction does *not* quite mean the RPCing initiated through it is all the way finished. It
198 * produces objects -- #Rpc_msg_out and #Rpc_msg_in -- per outgoing/incoming capnp-encoded
199 * message which are owned by the KJ loop (`*kj_io` to our ctor), not by `*this`. These objects
200 * need some of the key resources that a `*this VatNetwork` also needs. In other words those objects must
201 * stay alive potentially *longer* than `*this` Session_vat_network that originally accepts them via ctor.
202 * Particularly when an RPC system is shutting down, there is typically a danger zone, wherein `VatNetwork`
203 * is gone, but the messages it has produced are still briefly around. To be more exact:
204 *
205 * ### The objects of concern ###
206 * The objects whose lifetime we must carefully control, so it does not end before all outstanding message-objects
207 * are gone:
208 * - (If using `shm_enabled_session` ctor form)
209 * - The SHM-enabled session object, from ipc::session: `*shm_enabled_session`.
210 * - Objects that `*shm_enabled_session` relies on:
211 * - (if not null) `Logger*` pointee;
212 * - the IPC-universe-describing session::App `struct`s.
213 * - (If using generic ctor form)
214 * - The SHM-session object `*shm_lnd_brw`: thing with `.lend_object()` and `.borrow_object()`.
215 * - The SHM-arena object `*shm_arena`: thing with `.construct()`.
216 * - Objects that those 2 objects rely on. It depends.
217 *
218 * ### What to do ###
219 * We take either `shm_enabled_session`, or `shm_lnd_brw` + `shm_arena`, by `shared_ptr` handle in ctor.
220 * Therefore you are required to wrap the input object(s) in `shared_ptr` handle(s). `*this` and `*this`-created
221 * message-objects will hold refs to the object(s) no longer than necessary; once all message-objects and `*this`
222 * are finished, the session/SHM-session/arena can also be destroyed (from our PoV).
223 *
224 * So that covers the ctor-taken objects themselves. It does not however, necessarily, cover the
225 * "objects that ... relies/rely on" (from the bullet list above). It is your responsibility to ensure those
226 * objects stay alive past `*this` (naturally) but also the message-objects. Luckily this should be fairly
227 * easy.
228 *
229 * *Guaranteed/easy way*:
230 * Ensure the relied-upon objects (`Logger`, `App`, ...) shall outlive loop `*kj_io` given to `*this` ctor.
231 *
232 * @note that the `Logger*` mentioned here is not (necessarily) the `Logger*` given to `*this` ctor. Here
233 * we mean the `Logger*` given to `*shm_enabled_session`/`*shm_lnd_brw`/`*shm_arena`.
234 *
235 * *Tighter/more involved way*:
236 * The above is easy, but conceivably one might use `*kj_io` for something else after being done with this
237 * round of capnp-RPC; perhaps you'd prefer to not keep the logger/whatever alive at that point. In that
238 * case:
239 *
240 * Let the event loop run until it has nothing left to do, for instance by using `WaitScope::poll()`, which runs
241 * whatever is ready without blocking; once that returns, and none of your implementation methods is still
242 * executing, nothing of Flow-IPC's remains that uses your `Logger`, `App`s, etc.
243 *
244 * ### This is annoying.... ###
245 * We know. We didn't want to write the above either. Unfortunately it's an inescapable consequence of
246 * the way objects in capnp-RPC-over-KJ-loop land interact. It is not a problem for vanilla capnp-RPC simply
247 * because:
248 * - it only needs heap memory which is always available (we need SHM and SHM-sessions);
249 * - it does not do pluggable logging.
250 *
251 * Fortunately, it's easy enough to deal with, if one knows about it.
252 * - Session stuff is kept alive by `shared_ptr`: so you need not worry about that.
253 * - `session::App`s are by their nature unchanging, so they're typically always around (at low cost).
254 * - `Logger*` can be left null (parity with vanilla-capnp-RPC) if desired. Or keep it around throughout as
255 * shown above.

259 * Impl notes
260 * ----------
261 * ### General approach ###
262 * The goal here is to make a `capnp::VatNetwork` interface impl with the following characteristics.
263 * - It will keep any `rpc::Message`s -- including those carrying user-generated (over the course of their capnp-RPC
264 * work) capnp-payloads -- that the subsequent #Rpc_system needs to send -- in SHM instead of stuffing
265 * them into and out of an IPC byte-stream. That is: add zero-copy to capnp-RPC over a local IPC byte-stream pipe.
266 * - It will manage timely deallocation (and allocation) of such in-SHM areas.
267 * - It will be reasonably easy to integrate with Flow-IPC facilities in the following areas:
268 * - The byte-stream (which ultimately is typically just a pre-connected Unix-domain-socket stream) can be obtained
269 * from Flow-IPC, whether using ipc::transport::Native_socket_stream, ipc::transport::Channel, or
270 * ipc::session::Session.
271 * - The SHM support can be obtained from Flow-IPC, either when direct-using SHM arenas/lenders/borrowers or
272 * support for these in ipc::session::Session variants.
273 *
274 * Additionally, a caveat: `TwoPartyVatNetwork` has a method `onDisconnect()` which is not part of any formal interface
275 * (`VatNetwork`) to implement but, it appears to us, is effectively a requirement. So we provide that too.
276 *
277 * To understand how we do this (impl-wise), we feel it is generally sufficient to (1) be familiar with capnp-RPC,
278 * (2) be familiar with Flow-IPC at a reasonably in-depth level, and lastly (but not leastly) (3) grok
279 * `capnp::TwoPartyVatNetwork` implementation at a pretty deep level (but definitely not every detail; because
280 * as of this writing we have happily been able to reuse it as a black-box data member and graft-on the necessary
281 * zero-copy aspects without having to write our own variation of `TwoPartyVatNetwork` all the way through). Oh
282 * and, naturally, read the code.
283 *
284 * Here we will summarize the key points.
285 *
286 * There is some code -- very little by volume -- that is essentially lifted-ish from `TwoPartyVatNetwork`. This
287 * includes the on_disconnect() business; the decision for a `*this` to also *be* an #Rpc_conn
288 * (a/k/a `VatNetwork::Connection`), even though in general `VatNetwork`s one could produce multiple such
289 * `Connection`s in parallel in theory; some details following from this, such as accept() yielding either
290 * an immediately-fulfilled promise or a never-fulfilled one. These details are not very interesting. It isn't
291 * broken -- we do not fix it. These parts were not reusable either but not long, so this all feels okay.
292 *
293 * The interesting aspects begin in *how* we implement #Rpc_conn. The methods of most interest are
294 * newOutgoingMessage(), receiveIncomingMessage(), and newStream(); and `Rpc_conn` aside, the set of ctors we
295 * provide.
296 *
297 * However before getting into that consider the general strategy we adopt. The basic thing is that
298 * `TwoPartyVatNetwork` is in a sense almost enough by itself. The only "small" problem is:
299 * - When RPC-system tells it there's a newOutgoingMessage() it returns an object `X` that allocates
300 * a blank capnp-message in regular heap (`MallocMessageBuilder`); and when later it calls `X.send()`,
301 * that impl essentially copies that message into an IPC byte-stream.
302 * - Accordingly, on receipt, receiveIncomingMessage() and subsequent code will deal with that --
303 * again allocate in heap; copy that serialization into that location.
304 *
305 * Obviously we need, instead, for the allocation to happen in SHM; and then to read same in SHM on receipt.
306 * Flow-IPC provides the required `capnp::MessageBuilder` and `capnp::MessageReader` impls:
307 * shm::Capnp_message_builder, shm::Capnp_message_reader. The way one would use that in classic Flow-IPC style is:
308 * allocate in SHM; serialize in SHM; read in SHM; etc.; but when *transmitting* the message:
309 * - Use Capnp_message_builder::lend() to obtain a *very small* SHM-handle;
310 * - transmit *that SHM-handle instead of the actual message* over a byte-stream;
311 * - on the other side use Capnp_message_reader::borrow(), passing it the SHM-handle's contents;
312 * - now it can access the in-SHM actual-message serialization!
313 *
314 * The key point: There is still a byte-stream involved, and we are still IPC-transmitting things over it.
315 * Just, we are transmitting very small things instead of the actual messages. So while examining TwoPartyVatNetwork
316 * we asked ourselves: Can we rig it to do that part for us, while we add the required pre-processing and
317 * post-processing to properly generate these little payloads and understand them, respectively?
318 * The answer: Yes, totally. So that's what we are doing.
319 *
320 * Now when you read the code it should make sense; the details are tactical in nature.
321 *
322 * ### The constructors ###
323 * There was some question as what set of APIs to provide there. A related topic is how to template-parameterize
324 * the class. There are various ways one can hook-up to the rest of Flow-IPC. For example one can tailor those
325 * decisions to the idea that (A) one must use ipc::session end-to-end; or (b) not require that at all and instead
326 * supply each individual moving part (SHM-arena; SHM-lender/borrower; native socket handle for the byte-stream)
327 * individually; or something in-between.
328 *
329 * In short: We chose actually (B) as the baseline; while supplying one more ctor to make (A)
330 * also equally possible; and the template parameterization supports all of that. Arguably this flexibility makes
331 * things a bit confusing due to the degrees of freedom. However: By also supplying higher-level
332 * APIs Client_context and Context_server, as well as a range of aliases and documentation, we've reached a good
333 * balance. (Ez_rpc_client and Ez_rpc_server are higher-level still.)
334 *
335 * ### Future work ###
336 * I (ygoldfel) am reasonably confident that there is not a simpler version of this that somehow reuses existing
337 * capnp-RPC features in black-boxy fashion to an even greater extent. We've really kept everything
338 * `TwoPartyVatNetwork` did when transmitting capnp-encoded bytes -- just replacing the nature and size
339 * (smaller!) of what is being encoded, and of course setting up the in-SHM serialization of the actual big payloads
340 * (from `RpcSystem` and the user's schema/code).
341 *
342 * There is however, surely, an impl that has better performance by reimplementing more of what a two-party
343 * `VatNetwork` must implement. Perhaps in-SHM messages can be batched for fewer allocations; the byte-stream
344 * perf could be tuned for the smaller payloads; it is hard to say without some serious profiling and benchmarking.
345 * We could stop relying on KJ `AsyncIoStream`s and co.; and somehow make use of our own Native_socket_stream.
346 * (Note: "Could" does not mean "should" necessarily.) The `VatNetwork` interface is flexible enough for all
347 * of that and more. The most promising approach might be the following to-do:
348 *
349 * @todo In the ipc::transport::struc::Struct_builder-centered capnp-serialization module, a very perf-critical
350 * feature would be a serializer combining struc::Heap_fixed_builder and struc::shm::Builder, in that it
351 * would inline (in the for-IPC-transmission byte stream) smaller segment(s?) while SHM-storing larger ones
352 * (as shm::Builder does for all segments currently); integrate this work with both struc::Channel and
353 * capnp-RPC (rpc::Session_vat_network et al) structured-transport systems. shm::Builder and its
354 * `MessageBuilder`-implementing core shm::Capnp_message_builder would perhaps be extended to support this new --
355 * faster! -- mode, with the ability to fallback to its current SHM-always behavior (and perhaps
356 * to `Heap_fixed_builder`'s heap-always behavior if so desired). In designing this, there are two major questions
357 * to resolve first: 1, what is the fastest-behaving solution (where is the cut-over where SHM starts winning? etc.);
358 * 2, what is the best integration point between rpc::Session_vat_network and the new serializer. (Integration
359 * with struc::Channel is already through the Struct_builder + Struct_reader concepts, here implemented as
360 * shm::Builder and shm::Reader respectively. `Session_vat_network`'s possible integration methods are more
361 * of an open question. The ticket (https://github.com/Flow-IPC/ipc/issues/160) may contain detailed ideas.)
362 *
363 * A reminder: This capnp-RPC integration is an alternative to using struc::Channel which on the one hand is far
364 * less flexible semantically (it has request/response and message-type-demuxing... but that's it) but on the other
365 * hand much more predictable in terms of payload size and contents and timing. We digress; point is, one should
366 * keep in mind the alternative mechanism when profiling/learning/changing perf characteristics of this one; and
367 * vice versa. We could learn lessons that might apply to either.
368 */

562 /**
563 * The `-> stream` flow control window limit, in kebibytes, used by capnp-RPC w/r/t the sum of in-SHM
564 * `stream`ing traffic by all objects operating through `*this` at any point in time.
565 *
566 * This value is meaningful if and only if operating in zero-copy (SHM-using) mode. Thus if you used the
567 * "special mode" (in ctor, nullify args `shm_lnd_brw` or `shm_enabled_session`), it has no effect.
568 * We will then act identically to a vanilla `TwoPartyVatNetwork` with its normal flow control window computation.
569 *
570 * @see https://capnproto.org/news/#multi-stream-flow-control for an introduction to the `-> stream` feature.
571 * In our case, however, flow control applies to the RAM use of streaming objects; that RAM use
572 * = our use of shared memory (SHM) for streaming-involved bulk messages. Regarding the part of the text
573 * in that link describing how the kernel send buffer is used to compute a decent value for the window:
574 * that computation does not apply, in our case; the value returned here (at any given point in time,
575 * dynamically) will be used instead.
576 *
577 * @see the mutator overload, which can be used to change this value.
578 *
579 * A reasonable default value is used if one does not call the mutator:
580 * Session_vat_network_base::S_STREAMING_FLOW_WINDOW_KI.
581 *
582 * ### When to use the mutator ###
583 * This limit controls how much RAM at a time can be held by `*this` RPC engine in-flight -- meaning provided by
584 * sender-side user code, not yet consumed by receiver-side user code -- for `stream` payloads. In our
585 * case there is no networking involved, with very high bandwidth and very low latency; the effect of most sane
586 * values on (streaming) throughput should be low. A too-large value could have effect on RAM use; and in the
587 * presence of *possibly* limited SHM capacity it could even lead to out-of-arena-memory situation. When/if this
588 * is a factor (meaning memory is at a premium), typical uses of SHM are directly under the user's control:
589 * you know when and how much you're allocating (usually). In this case, though, capnp-RPC is deciding --
590 * only (*for this particular `stream` feature!*) -- how much it will allocate for you, at a time.
591 * Thus: If in the field you see RAM-use trouble as a result, or perhaps want to benchmark the window's effect on
592 * perf under load, the mutator overload streaming_flow_window_ki() may be useful.
593 *
594 * The default Session_vat_network_base::S_STREAMING_FLOW_WINDOW_KI is orders of magnitude smaller
595 * than *typical* SHM capacity available, hence *typically* you will not run out of SHM from `-> stream`ing.
596 * As of this writing the following SHM-providers come with Flow-IPC:
597 * - SHM-jemalloc: There is no per-arena limit; so it becomes a matter of general out-of-memory or hitting
598 * a SHM-use kernel limit if any.
599 * - SHM-classic: There is a per-arena limit. In `ipc::session`-created arenas a default is used which can
600 * be overridden with session::shm::classic::Session_server::pool_size_limit_mi() mutator. (If creating
601 * a shm::classic::Pool_arena directly, the size must be supplied via the create-mode ctor.) The default
602 * as of this writing is 2Gi, while `S_STREAMING_FLOW_WINDOW_KI` is 1/2 Mi (several orders' of magnitude
603 * difference).
604 *
605 * Ultimately, though, your mileage may vary, as environments and use-cases differ.
606 *
607 * @return See above.
608 */
609 size_t streaming_flow_window_ki() const;

861 /**
862 * This is #m_network essentially cast as an #Rpc_conn impl: see as_connection() body.
863 *
864 * ### Rationale ###
865 * Consider #Rpc_conn a/k/a `capnp::VatNetwork<...>::Connection`. Since we return via connect() + accept()
866 * (as_connection()) `*this`, we must implement #Rpc_conn abstract methods: chiefly
867 * newOutgoingMessage(), receiveIncomingMessage(), and a few other less central ones.
868 * Our particular impl is largely to forward this to #m_network (the `TwoPartyVatNetwork`).
869 * Since we happen to know `TwoPartyVatNetwork::connect()` and `accept()` also essentially return
870 * their `*this`, it is natural -- to achieve this forwarding -- to just call, e.g.,
871 * `m_network->newOutgoingMessage()`. Actually, though, that will not compile:
872 * `TwoPartyVatNetwork` inherits from `VatNetwork<...>`, in order to in fact implement abstract
873 * methods including `newOutgoingMessage()`... but it inherits them *privately*.
874 *
875 * This is, some would contend, a bit strange and counter-indicated by stylists: you are *allowed*
876 * to `private`ly subclass a `public`-method-bearing abstract interface, but it is arguably dodgy.
877 * I (ygoldfel) do somewhat get it, I think:
878 * - `TwoPartyVatNetwork` appears to return "new" connections but really *is* one connection object
879 * itself.
880 * - The latter fact is an internal implementation detail, formally.
881 * - So using that fact explicitly from the outside -- by trying to call one of the #Rpc_conn methods
882 * like newOutgoingMessage(), and/or by up-casting `TwoPartyVatNetwork*` to `Rpc_conn*` -- sort-of
883 * amounts to using an impl detail as an outside user. Private inheritance and private `virtual` method
884 * impls prevent that.
885 *
886 * In any case, we do need an #Rpc_conn for #m_network, so that we can do the aforementioned forwarding
887 * to its methods. Hence we use `TwoPartyVatNetwork::connect()` and/or `TwoPartyVatNetwork::accept()`
888 * to get at it (in ctor, ASAP).
889 *
890 * ### Corollary ###
891 * We happen to *not* follow `TwoPartyVatNetwork`'s lead: *our* #Rpc_conn impls such as
892 * newOutgoingMessage() *are* `public`, and we inherit from #Rpc_conn `public`ly. It really doesn't matter,

910 /**
911 * See on_disconnect(): the promise returned there, whose fulfillment indicates that for each successful call
912 * to connect() and accept(), each of which yielded an `Own<Rpc_conn>` (pointing to `*this`), that returned
913 * `Own<Rpc_conn>` has reached end of life.
914 *
915 * ### What? This `Fulfiller_disposer` and disconnect-promise business ###
916 * This "hack" (<= quoting the `TwoPartyVatNetwork` comment) can use some explaining. The explanation in
917 * `TwoPartyVatNetwork` is pithy and (for me, ygoldfel) eventually grokkable, but it took a bit of effort.
918 * In hopes of explaining it more explicitly to save time here goes:
919 *
920 * Same as inside `TwoPartyVatNetwork`: by definition in a two-party "universe" there can only be one connection
921 * at a time, so our `*this` is both a `VatNetwork` impl *and* an #Rpc_conn impl. But connect() and accept()
922 * by the `VatNetwork` interface must return `Own<Rpc_conn>` (similar to `unique_ptr<VatNetwork>`).
923 * At the same time it can't be a vanilla `Own<>` that, upon losing (not transferring) ownership (such as in its
924 * dtor), will `delete` the object. In our case that is nonsensical; we might even be on the stack and anyway
925 * we are also a Session_vat_network. Basically connect() and accept() does not create a new object in heap,
926 * so deleting it is nonsensical.
927 *
928 * So just for that reason, the disposer (like a deleter in STL smart-pointers) for that `Own` must simply not
929 * `delete`; Session_vat_network = #Rpc_conn and has its own proper lifetime.
930 *
931 * In addition, though, there is on_disconnect() which as noted earlier is supposed to return a `Promise` that
932 * fires once "all" previous issues connections have (usually by the `RpcSystem`) lost (not transferred)
933 * their `Rpc_conn` objects, indicating overall a "disconnect." So the aforementioned disposer (deleter) should
934 * firstly *not* `delete` anything; and secondly should decrement a refcount keeping track of how many times
935 * connect() or accept() successfully returned an `Own<Rpc_conn>` (to `*this`) minus which of those handles
936 * has dropped their object. Once the refcount is back to zero, they've all been dropped, hence promise shall
937 * be fulfilled.
938 *
939 * @see #m_disconnect_fulfiller which is where that logic takes place.
940 *
941 * @todo Maybe we can do the internal Session_vat_network::Fulfiller_disposer stuff with `shared_ptr` and/or
942 * `weak_ptr` or something? E.g., we did so in the case of Ez_rpc_kj_io (internal to `Ez_rpc_*` stuff).
943 * Just stylistically we prefer that sort of thing to `kj::Own` craziness. This would be pretty easy,
944 * and pithy at that, if we could return `shared_ptr<Rpc_conn>`, but the interface requires `Own<Rpc_conn>`.
945 * So maybe just leave it.
946 */
947 kj::ForkedPromise<void> m_disconnect_promise;

950 * Disposer for all `Own<Rpc_conn>`s returned by connect() and accept().
951 * See #m_disconnect_promise doc header for explanation of all this.

1193template<typename Shm_lender_borrower_t, typename Shm_arena_t>
1194void Session_vat_network<Shm_lender_borrower_t, Shm_arena_t>::Rpc_msg_out_impl::send()
1195{
1196 using ::capnp::AnyPointer;
1197 namespace rpc = ::capnp::rpc;
1198
1199 /* This is straightforward, once one understands how the pieces fit together. TwoPartyVatNetwork here
1200 * would send off the true payload rpc::Message by basically calling MessageBuilder::getSegmentsForOutput()
1201 * and writing out the backing capnp-segments in series (1 or more of them depending on message size, etc.).
1202 * It also does fancier stuff internally -- trying to reduce # of syscalls by some buffering; things of that
1203 * nature. All of that is great for us, or at least shouldn't hurt; it's just that the payload should be
1204 * little SHM-handles (in this send(), *one* little SHM-handle) to those rpc::Message-backing capnp-segments --
1205 * which we have placed (via our work in our ctor and getBody()) in SHM. So now that message contents
1206 * are finalized, we can load the SHM-handle (as capnp payload), and off we go. (Actually this could've been
1207 * done in the ctor; then here we'd just forward to m_msg->send(). Either way seems fine perf-wise,
1208 * so I'd rather keep it all in one place in the code.)
1209 *
1210 * The only other aspect of this is the isShortLivedMsg field. We explain this near the top of
1211 * Session_vat_network delegated-to ctor. Thus:
1212 * Rpc_msg_in::isShortLivedRpcMessage(), as of this writing computing it as control msgs <=> not CALL/RETURN <=>
1213 * short-lived=yes, is how vanilla TwoPartyVatNetwork determines whether an incoming rpc::Message is short-lived --
1214 * directly inside the in-buffer. So we use the same computation but *before* the send; then on receipt check the
1215 * bool result. */
1216
1217 auto capnp_msg_in_heap_root
1218 = m_msg->getBody().initAs<schema::detail::CapnpRpcMsgTopSerialization>();
1219
1220 const auto capnp_msg_in_shm_root_rdr = getBody().asReader();
1221 if (!Rpc_msg_in::isShortLivedRpcMessage(capnp_msg_in_shm_root_rdr))
1222 {
1223 capnp_msg_in_heap_root.setIsShortLivedMsg(false);
1224 }
1225
1226 const bool ok = m_capnp_msg_in_shm.lend(&capnp_msg_in_heap_root, m_shm_lnd_brw.get());
1227 /* Now the message in SHM is safe from deallocation until both m_capnp_msg_in_shm is destroyed with *this,
1228 * *and* the receiver MessageReader (see Rpc_msg_in_impl) has had .borrow() called on it, and that MessageReader
1229 * is destroyed with its containing Rpc_msg_in_impl. (Corollary: if the SHM-handle never reaches the receiver --
1230 * the connection died with the little message still queued in m_msg's write queue -- then the in-SHM message
1231 * stays allocated until the session is torn down. Bounded by session lifetime; acceptable.) */
1232
1233 KJ_REQUIRE(ok,
1234 "Was asked to send a capnp-message by the RPC-system, but Capnp_message_builder::lend() "
1235 "yielded failure which means the Flow-IPC session just went down (on account of opposing "
1236 "process ending session, e.g., so it can exit), and this has been or will soon be "
1237 "reported via the Flow-IPC session on-error callback. Basically SHM cannot be used, so "
1238 "we cannot transmit a message with zero-copy over it. Stuff is going down. This is not "
1239 "usually some catastrophe; just the IPC conversation has finished.");
1240
1241 /* The byte-streamed message is ready (as is the real in-SHM message but never mind), so
1242 * we can update this. Note that it is essentially impossible we're using more than one segment; so
1243 * this m_msg->sizeInWords() call should be a fast-path access inside capnp arena code. */
1244 const auto msg_out_sz_words = m_msg->sizeInWords();
1245 assert(msg_out_sz_words != 0);
1246 if (msg_out_sz_words > m_daddy->m_msg_out_max_sz_words) // (Initially it is zero, so this will be true.)
1247 {
1248 /* This is rare (interesting; but not interesting enough for INFO). TRACE-log about it.
1249 * Normally we'd derive from Log_context and just FLOW_LOG_TRACE(),
1250 * but since this is so frequent, and TRACE/DATA logging is typically
1251 * disabled, we'd rather not spend the cycles on keeping a typically unused Logger* + Component; and instead
1252 * pay a little more in cycles when TRACE logging *is* enabled (if this `if` evaluates to `true`). Also
1253 * the code is a bit longer, and this comment is somewhat annoying to write and read... but c'est la vie. */
1254 if (const auto logger_ptr = m_daddy->get_logger())
1255 {
1256 const auto log_component = m_daddy->get_log_component();
1257 if (logger_ptr->should_log(flow::log::Sev::S_TRACE, log_component))
1258 {
1259 FLOW_LOG_SET_CONTEXT(logger_ptr, log_component);
1260 FLOW_LOG_TRACE_WITHOUT_CHECKING("Session_vat_network [" << *m_daddy << "]: Outgoing message send: "
1261 "next byte-streamed (little) message size updated: "
1262 "[" << m_daddy->m_msg_out_max_sz_words << "] words => "
1263 "[" << msg_out_sz_words << "] words.");
1264 }
1265 } // if (logger_ptr)
1266
1267 m_daddy->m_msg_out_max_sz_words = msg_out_sz_words;
1268 } // if (msg_out_sz_words > m_daddy->m_msg_out_max_sz_words)
1269
1270 // Same comment as just above w/r/t logging perf... it is not pretty but worth it.
1271 if (const auto logger_ptr = m_daddy->get_logger())
1272 {
1273 const auto log_component = m_daddy->get_log_component();
1274 if (logger_ptr->should_log(flow::log::Sev::S_TRACE, log_component))
1275 {
1276 const auto root_as_rpc_msg = capnp_msg_in_shm_root_rdr.template getAs<rpc::Message>();
1277 FLOW_LOG_SET_CONTEXT(logger_ptr, log_component);
1278 FLOW_LOG_TRACE_WITHOUT_CHECKING("Session_vat_network [" << *m_daddy << "]: Outgoing message send: "
1279 "message (possibly truncated) "
1280 "[" << ostreamable_capnp_brief(root_as_rpc_msg) << "]; "
1281 "size = [" << m_capnp_msg_in_shm.sizeInWords() << "] words x "
1282 "[" << sizeof(::capnp::word) << "] bytes/word; outer serialization (of "
1283 "little SHM-handle+ in heap/to copy into transport) = "
1284 "[" << msg_out_sz_words << "] words.");
1285 FLOW_LOG_DATA("Here is the complete message:"
1286 "\n" << ostreamable_capnp_full(root_as_rpc_msg));
1287 }
1288 } // if (logger_ptr)
1289
1290 m_msg->send(); // Now let it be smart about buffering m_msg a bit, or whatever it wants to do.
1291} // Session_vat_network::Rpc_msg_out_impl::send()

1293template<typename Shm_lender_borrower_t, typename Shm_arena_t>
1294size_t Session_vat_network<Shm_lender_borrower_t, Shm_arena_t>::Rpc_msg_out_impl::sizeInWords()
1295{
1296 /* What to return here is not necessarily obvious (of course that is subjective). The API contract is
1297 * "Get the total size of the message, for flow control purposes." The question then is what "flow control"
1298 * in this particular context is. Naively one could assume it has to do with controlling back-pressure
1299 * w/r/t simply bytes traveling over the transport (whether -- in vanilla TwoPartyVatNetwork -- over the network
1300 * or IPC; just the latter for us). Without thinking about it too hard one would then simply
1301 * return m_msg->sizeInWords(); // This would return the size of our little SHM handle-containing message.
1302 * All cool -- that's what we're still transmitting; done! But no. To explain:
1303 *
1304 * (Firstly let's eliminate the over-the-network case from consideration. We are not doing that, so it'll be
1305 * easier and fully appropriate to ignore in the discussion. So: just local IPC.)
1306 *
1307 * This sizeInWords() does *not* apply to general traffic going through this connection, in the first place.
1308 * It applies only to a specific capnp-RPC user-facing feature: *streaming*. (This is completely independent of
1309 * AsyncIoStream or AsyncCapabilityStream... which is in fact the IPC-transport byte/FD-stream one could naively
1310 * guess per the paragraph above. Not that!) This is where in the schema an interface-method return type
1311 * is `-> stream`. As of this writing this isn't covered in the main docs at the capnp web site, but it is
1312 * introduced nicely in https://capnproto.org/news/#multi-stream-flow-control. Read that
1313 * as background, optionally, but the bottom line is: It allows one to set up, say, bulk uploads -- which will stream
1314 * at a controlled rate. This feature consists of two parts; part 1 is the syntactic niceness of expressing this
1315 * without having to set up the logic in one's own code; and part 2 -- which concerns us here -- is that by
1316 * expressing it in that syntax, it causes capnp-RPC's guts to engage *multi-stream flow control*, wherein it
1317 * takes a good stab at automatically controlling the rate at which it'll allow the `stream` payload to
1318 * proceed. So that's the flow control in question:
1319 * - A window-size (controlled by newStream(); see that guy).
1320 * - An accounting of how much of the window is currently in use. <- The relevant part here in sizeInWords().
1321 *
1322 * (Reminder: We're ignoring any networking aspect of this.) Without networking -- with a tiny latency and
1323 * very high bandwidth -- what's left to control is how much RAM is taken by (collective) streams.
1324 * (Incidentally: There is at most one ongoing stream per capability a/k/a interface-implementing object, and
1325 * 2+ objects don't share streams.) So, e.g., if I generate random bytes in chunks, stream them over capnp-RPC, and
1326 * the receiver then (say) writes them to tape as fast as it can, then I wouldn't want to keep generating
1327 * more random bytes until receiver-side has indicated it has written a bunch and can accept more bytes now.
1328 * Without back-pressure the accumulated-too-fast (and more and more so) bytes would exceed the available RAM.
1329 * So that's, ultimately, all it is.
1330 *
1331 * What we're returning here, then, is how much we'd contribute to that window. Both the window (see
1332 * newStream()) and the window-used (here) are about RAM use. For a vanilla TwoPartyVatNetwork the RAM use
1333 * is just the stuff traveling through the IPC-transport: first inside a MallocMessageBuilder around here (m_msg),
1334 * then in the kernel buffer(s), then in/near the MessageReader in the IncomingRpcMessage (a/k/a Rpc_msg_in).
1335 * So in that case `m_msg->sizeInWords()` is right. In our case, we avoid (almost) all that: the use of
1336 * the transport is (basically) negligible (~only SHM-handles go through it); instead we just plop user
1337 * (streamed) data in SHM. SHM is RAM; our area in it just doesn't get copied from one area to another to another
1338 * (zero-copy!). Thus: */
1339 return m_capnp_msg_in_shm.sizeInWords();
1340} // Session_vat_network::Rpc_msg_out_impl::sizeInWords()

1502 /* TwoPartyVatNetwork m_network uses an optimization in its next-lower layer, namely BufferedMessageStream
1503 * which streams capnp-encoded messages (we prepare this guy: m_capnp_msg_stream), wherein if it considers
1504 * an in-message "short-lived" (guaranteed to be handled fully before the next in-message), then it can
1505 * somewhat-later capnp-read the message directly inside some incoming-data buffer space. Otherwise it must
1506 * be copied elsewhere first, so it can be read in peace without being overwritten by subsequent in-messages.
1507 * So vanilla TPVN will look inside the message, correctly assume it is an rpc::Message (which is the case for
1508 * all vanilla TPVNs), check its top-level union-which enum value (message type), and assume yes-short-lived
1509 * for most types except two: CALL/RETURN. Incidentally these types <=> it is a user-mutated message, meaning
1510 * it is their code setting fields through the usual capnp-generated API. Hence *not* these types <=> it is
1511 * a *control* message generated for internal purposes by capnp-RPC.
1512 *
1513 * This vanilla behavior won't work for us, as we leverage TPVN m_network
1514 * to transmit a byte stream of our little SHM-handles (to the real rpc::Message messages, which are
1515 * now in SHM in our case); so that default check of as-if-rpc::Message will result in garbage results and ultimately
1516 * in our experience an assert-fail regarding short-livedness (at best). Fortunately TPVN lets us provide
1517 * our own BufferedMessageStream (which, again, we do), where we can easily provide a different
1518 * is-short-lived callback (which is what follows here). We figure we have two reasonable choices:
1519 * -# Say no messages are short-lived (just return false). Copying our little SHM-handle-bearing messages
1520 * probably isn't too expensive*, and the alternative technique in the next bullet point does involve
1521 * making those messages a bit bigger and doing a little extra computation for each.
1522 * - `*` But that's on a per-message basis. In aggregate there could be non-trivial amounts of data in
1523 * them. Moreover: yes, our IPC-transmitted msgs are small... but so are their *control* `rpc::Message`s --
1524 * likely bigger but still small -- and indeed the messages they classify as short-lived *are* the control
1525 * messages, not the (potentially large) user (CALL/RETURN) `rpc::Message`s. So actually the situations
1526 * (vanilla TPVN versus our SHM-handle-transmitting alternative) are pretty similar in this sense. I.e.:
1527 * our "wire" representation of the would-be short-lived (<=> control) messages is somewhat smaller
1528 * than vanilla TPVN's, but the latter are still small already, and yet the capnp code considers it
1529 * worthwhile to optimize away potential copying thereof. Hence:
1530 * -# Simply mark, in the byte-streamed message itself (whose contents and interpretation we control
1531 * in *this), whether it is short-lived. Then the callback can just check that. As a result we'll
1532 * get the available optimization (don't copy-out control messages) for a low encoding/decoding cost.
1533 *
1534 * Going with 2: the added data and computation are not significant, and perhaps
1535 * the optimization is worth keeping even if it's for much smaller messages than in a vanilla TPVN.
1536 * @todo Look into it: benchmark perf. How much does it help for us, versus how much
1537 * does it help vanilla TPVN? Questions like that: could be interesting. */

1540 if (m_shm_lnd_brw)
1541 {
1542 is_short_lived_msg_func = [](Capnp_msg_reader_interface& msg_in) -> bool
1543 {
1544 /* In Rpc_msg_out_impl we mark this bool appropriately, so just interpret it.
1545 * This code here is inspired by the impl of capnp::IncomingRpcMessage::getShortLivedCallback(). */
1546 return msg_in.getRoot<AnyPointer>().template getAs<schema::detail::CapnpRpcMsgTopSerialization>()
1547 .getIsShortLivedMsg();
1548 };
1549 }
1550 else // if (special mode where we do nothing useful)
1551 {
1552 is_short_lived_msg_func = Rpc_msg_in::getShortLivedCallback(); // Just do what TwoPartyVatNetwork would do.
1553 }
1554
1555 ReaderOptions network_reader_opts; // Default values.
1556 if (!m_shm_lnd_brw)
1557 {
1558 /* This is arguably a hack... and it would probably go away, if we handle the ReaderOptions-related to-do
1559 * in our class doc header. For now though: If not in "special mode" (where we would skip zero-copy)
1560 * we override the traversal-limit option for the in-SHM messages (see shm::Capnp_message_reader impl) to
1561 * make it essentially infinity. Well, in this "special mode" we want to have the same capabilities, just
1562 * without zero-copy. So make the same change at this higher layer in this case. */
1563 network_reader_opts.traversalLimitInWords = std::numeric_limits<uint64_t>::max() / sizeof(::capnp::word);
1564 }
1565
1566 if (hndl_transport_limit_or_0 == 0)
1567 {
1568 // Create non-FD-passing vanilla AsyncIoStream and use the TwoPartyVatNetwork ctor that takes such accordingly.
1569 m_kj_stream_of_blobs // (Per the TAKE_OWNERSHIP flag KJ owns the handle from this call on; so release ours here.)
1570 = m_kj_io->lowLevelProvider->wrapSocketFd(disowned_native_handle(std::move(bidir_transport_hndl)).m_native_handle,
1571 kj::LowLevelAsyncIoProvider::TAKE_OWNERSHIP);
1572 m_capnp_msg_stream = make_unique<BufferedMessageStream>(*m_kj_stream_of_blobs,
1573 std::move(is_short_lived_msg_func));
1574 m_network.emplace(*m_capnp_msg_stream,
1575 m_srv_else_cli ? ::capnp::rpc::twoparty::Side::SERVER
1576 : ::capnp::rpc::twoparty::Side::CLIENT,

1578 }
1579 else

1582 * accordingly. */
1583 m_kj_stream_of_blobs_hndls // (Release ours here, as above.)
1584 = m_kj_io->lowLevelProvider->wrapUnixSocketFd(disowned_native_handle(std::move(bidir_transport_hndl))
1585 .m_native_handle,
1586 kj::LowLevelAsyncIoProvider::TAKE_OWNERSHIP);
1587 m_capnp_msg_stream = make_unique<BufferedMessageStream>(*m_kj_stream_of_blobs_hndls,
1588 std::move(is_short_lived_msg_func));
1589 m_network.emplace(*m_capnp_msg_stream, hndl_transport_limit_or_0,

1596 * TwoPartyVatNetwork facilities (then we will pre/post-process some of the work for our purposes). Really
1597 * m_network *is* the Rpc_conn, but it `private`ly inherits from it, so... <please see full explanation

1692kj::Promise<kj::Maybe<kj::Own<Rpc_msg_in>>>

1694{
1695 /* The normal TwoPartyVatNetwork::receiveIncomingMessage() returns a promise to async-read bits off wire
1696 * if possible/appropriate; essentially yielding on success a heap-stored capnp::MessageReader + 0+ native-handles;
1697 * and if so basically bundling them in its impl of Rpc_msg_in, which provides accessors via its `virtual` impl
1698 * methods like getBody(). That's all just fine for our purposes! Just that MessageReader will contain
1699 * merely an encoding of a handle-into-SHM, where the actual message is stored; so we ourselves implement
1700 * Rpc_msg_in; store the aforementioned vanilla Rpc_msg_in (with the handle) inside; and have our getBody() access
1701 * the in-SHM serialization (according to that SHM-handle) instead... mission accomplished. */
1702 auto vanilla_result = m_conn->receiveIncomingMessage();
1703 if (!m_shm_lnd_brw)
1704 {
1705 return vanilla_result; // Special mode! Just do the vanilla thing.
1706 }
1707 // else: Actually do something useful.
1708
1709 return vanilla_result.then([this](kj::Maybe<kj::Own<Rpc_msg_in>>&& msg_uptr_maybe)
1710 -> kj::Maybe<kj::Own<Rpc_msg_in>>
1711 {
1712 KJ_IF_MAYBE(msg_uptr_ptr, msg_uptr_maybe)
1713 {
1714 // Post-process by dropping in our own Rpc_msg_in impl.
1715 return kj::heap<Rpc_msg_in_impl>(kj::mv(*msg_uptr_ptr), this);
1716 }
1717 // else

1726 * only work on SERVER; while connect() will work on either side (as long as the target `ref` is properly specified
1727 * to be the opposing peer's). One might expect connect() would work only on client side, yet this supports
1728 * both (e.g., both sides can connect()). This might just be an inconsistency (a bit of dead code of sorts),

1747template<typename Shm_lender_borrower_t, typename Shm_arena_t>
1748kj::Promise<kj::Own<Rpc_conn>> Session_vat_network<Shm_lender_borrower_t, Shm_arena_t>::accept()
1749{
1750 /* This is, like connect(), essentially copy/pasted from TwoPartyVatNetwork. How it is used (capnp-1.0.2):
1751 * every RpcSystem -- client-side (makeRpcClient()) or server-side -- starts an accept loop in its ctor:
1752 * `network.accept().then([](conn) { <register conn>; <loop again>; })`. It is strictly sequential: the next
1753 * accept() is issued only once the previous one's promise resolves. Hence:
1754 * - Server node: 1st accept() yields our one and only connection; the 2nd accept() yields a promise that never
1755 * resolves; hence a 3rd is never issued. The loop simply waits forever, as intended in a two-party world.
1756 * - Client node: the 1st accept() already yields the never-resolving promise; same eternal wait. (So a client-side
1757 * accept() call is not a misuse but the normal course of events.)
1758 * The never-resolving promise is thus the two-party idiom for "there will be no more connections; do not error out
1759 * the accept loop either." */
1760
1761 if (m_srv_else_cli && (!m_accepted))
1762 {
1763 FLOW_LOG_INFO("Session_vat_network [" << *this << "]: "
1764 "Session_vat_network::accept() invoked (perhaps by a capnp RPC-system) "
1765 "1st time for node with ID = [srv_else_cli=1]: success.");
1766 m_accepted = true;
1767 return as_connection(); // Pre-fulfilled Promise.
1768 }
1769 // else
1770
1771 if (m_srv_else_cli) // && m_accepted
1772 {
1773 FLOW_LOG_INFO("Session_vat_network [" << *this << "]: "
1774 "Session_vat_network::accept() invoked (perhaps by a capnp RPC-system) "
1775 "in node with ID = [srv_else_cli=1] after earlier having done so already; "
1776 "returning eternal promise. This appears, empirically, to be normal "
1777 "behavior by RpcSystem-et-al, hence this message is not a WARNING.");
1778 }
1779 else // if (cli)
1780 {
1781 FLOW_LOG_INFO("Session_vat_network [" << *this << "]: "
1782 "Session_vat_network::accept() invoked (perhaps by a capnp RPC-system) "
1783 "in node with ID = [srv_else_cli=0]: returning eternal promise.");
1784 }
1785
1786 /* Create a promise that will never be fulfilled. We must keep the fulfiller alive: destroying it would *reject*
1787 * the promise (broken-promise exception), which would land in the RpcSystem accept loop's error handler.
1788 * Per the above this branch executes at most once per *this (the loop awaits this promise forever), so the
1789 * assignment below never overwrites a live fulfiller. (Were it to somehow happen anyway, the effect would be that
1790 * rejection -- logged by RpcSystem as an error -- not undefined behavior.) */
1791 auto paf = kj::newPromiseAndFulfiller<kj::Own<Rpc_conn>>();
1792 m_accept_fulfiller = std::move(paf.fulfiller);
1793 return std::move(paf.promise);
1794} // Session_vat_network::accept()
