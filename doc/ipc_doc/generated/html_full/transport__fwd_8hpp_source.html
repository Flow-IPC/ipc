26/**
27 * Flow-IPC module providing transmission of structured messages and/or low-level blobs (and more)
28 * between pairs of processes. See namespace ::ipc doc header for an overview of Flow-IPC modules including
29 * how ipc::transport relates to the others. Then return here. A synopsis follows:
30 *
31 * @see The guided Manual chapters @ref chan_open (obtaining channels), @ref chan_struct and @ref chan_struct_advanced
32 * (structured transport), and @ref transport_core (unstructured transport) cover these topics.
33 *
34 * The main transport features of ipc::transport are: class template struc::Channel (for structured message and
35 * native handle transport) and various lower-level utilities (Channel; blob/handle streams; message queue
36 * (MQ) streams). Structured transmission facilities (struc::Channel being the main guy) are segregated in
37 * sub-namespace transport::struc.
38 *
39 * Generally speaking, to communicate (via struc::Channel and others), the two processes A and B that intend to
40 * talk must have established a broad conversation called a *session* within which all communication occurs.
41 * In fact, a transport::struc::Channel wraps a transport::Channel, and the latter can be established, in factory-ish
42 * fashion and otherwise, from an ipc::session::Session. Hence, see namespace ipc::session doc header to learn about
43 * establishing/terminating sessions. Once you have a session::Session, you can actually use main ipc::transport
44 * facilities.
45 *
46 * That said: ipc::transport does *not* require ipc::session to be used: One can instantiate all the various IPC
47 * mechanisms therein directly. ipc::session provides the lifecycle and organization to make this as simple as
48 * possible (but no simpler). In that sense ipc::transport has the essential building blocks; ipc::session provides
49 * access to those building blocks in one possible fashion -- for example by establishing a naming convention
50 * for the various required `Shared_name`s taken by the various ipc::transport constructors. Formally speaking
51 * there can certainly be other fashions of organizing ipc::transport resources. Therefore the API design of
52 * ipc::transport is not rigid.
53 */

517/**
518 * Implements `{Native_handle|Blob}_receiver::async_receive_*_batch()` by emulating batch-receiving as a
519 * series of single-message receive-ops.
520 *
521 * ### How to use ###
522 * Just call us; we'll do it. The main requirement is to provide a proper `async_rcv_impl_func()` which shall
523 * perform a regular one-message receive.
524 *
525 * The formal requirements for `async_rcv_impl_func()` are as follows. It shall be called in a `void` context
526 * and have the following arguments, in order:
527 * - (If and only if `NO_HNDLS == false`) `Native_handle*`: Target handle object.
528 * - `bool`: If `true`, your function may assume the pipe is in would-block state already
529 * which may help it be more efficient in doing its task; otherwise it must make no such assumption.
530 * (This will *not* simply always equal the eponymous argument to async_receive_batch_emulation()!)
531 * - util::Blob_mutable: Target memory area for the async-read.
532 * - `Error_code*`: The error-code object for the op. This shall *not* be null (you do *not* need to throw
533 * an exception to emit an error).
534 * - `size_t*`: Set the pointee to the received in-blob's size, unless an error is emitted.
535 * - Function-object of the specific type `flow::async::Task_asio_err_sz`, a/k/a
536 * `Function<void (const Error_code& err_code, size_t n_rcvd)>`.
537 * Attention! This may, or may not, be `.empty()`. See below.
538 *
539 * It shall act as-if `{Native_handle|Blob}_receiver::async_receive_{native_handle|blob}()` was called, except:
540 * - Which one it is: it must act consistently with `NO_HNDLS`.
541 * - It shall take the extra leading `Native_handle*` arg (see above) if `NO_HNDLS == false`.
542 * - It may assume the following checks have all passed: in PEER state, `start_*_ops()` has been called, no
543 * pipe-hosing error recorded yet from prior ops, no `async_receive_*()` already outstanding,
544 * `batch->initialized() && (!batch->full())`.
545 * - May act differently (probably for perf savings) depending on the `bool` arg (assume-would-block; see above).
546 * - If it emits non-success, non-would-block (in-pipe-hosing) error `E`, *and* the desired outcome *if* 1+
547 * in-messages have already been received successfully into `*batch` is *delayed error* (emit no error for this
548 * batch-receive, but next async-receive on that in-pipe shall instantly yield `E`), then `E` *must* be one of the
549 * following:
550 * - error::Code::S_RECEIVES_FINISHED_CANNOT_RECEIVE,
551 * - `boost::asio::error::eof`.
552 * - Any other `E` in that situation will cause the batch-receive to emit `E` (and therefore leave
553 * `batch->n_used()` unchanged); 1+ in-messages shall be eaten. (Promise: any `Native_handle`s received
554 * with the eaten in-messages shall be closed -- returned to the OS -- not leaked.)
555 * - The on-done handler may be non-empty (as required for normal user-triggered calls) or `.empty()`.
556 * If it's non-empty, act normally. If it's empty, and no would-block is encountered, act normally; which is
557 * to say synchronously emit the result, and that's that (on-done handler ignored). If it's empty, and
558 * would-block *is* encountered then there are 2 possibilities.
559 * - If would-block is encountered immediately (no partial message is read/non-steady state reached):
560 * Emit would-block as normal; but *end the async-receive op*. Do not issue an async-wait for readability;
561 * do not save on-done handler (which is empty anyway).
562 * - If would-block is encountered after receiving part of an in-message/a non-steady state is reached:
563 * Do the same; plus:
564 * - Memorize the partial-message payload/non-steady state, so that if another
565 * async-receive is issued by something/someone later, your state machine starts from the point as-if
566 * the partial-message payload/state had already been received/reached. (After all: it *had* already been
567 * received/reached -- it just ended up irrelevant to the previous async-receive; namely us.)
568 *
569 * Unfortunately that last bullet point can be tricky to implement (or even understand what it means),
570 * so we must discuss. Firstly the (potential) good news: If your protocol
571 * combined with the underlying transport is such that reading a partial in-message
572 * is impossible, and (non-hosed) pipe state is the same regardless of where a would-block occurs,
573 * then the bullet point cannot apply, and things (your code) remain simple.
574 *
575 * Example: Native_socket_stream, when operating (and this is determined at compile-time, not run-time) in
576 * datagram mode (asio_local_stream_socket::Protocol_pkt_stream, not `Protocol_byte_stream`; a/k/a
577 * in Linux `SOCK_SEQPACKET`, not `SOCK_STREAM`) can (and in our impl as of this writing does) map each in-message
578 * to one in-datagram, and the pipe is always in the same state (barring being hosed) upon receiving any in-dgram.
579 *
580 * However if it possible to read a payload which encodes (potentially) part of an in-message/non-steady state,
581 * then the bullet point may apply, and you must code for it.
582 *
583 * Example: Blob_stream_mq_receiver is essentially dgram-based too, so each in-message maps to one lower-level
584 * dgram (MQ message), *but* as of this writing our internal protocol is (for certain boring logical/technical reasons)
585 * such that some (non-user-in-message) messages are represented by 2 dgrams (MQ messages), not 1: a CONTROL
586 * message like an auto-ping is represented by an empty in-message (enters CONTROL state) and then a particular
587 * enumeration-value-encoding message (indicates auto-ping; goes back to normal state). So, the start of
588 * async-receive cannot assume normal state; it might be in CONTROL state because of the above. Of course this
589 * is pretty easy to handle; just keep a CONTROL-or-not state flag; and resume the state machine based on its value.
590 * There's no need to store any user payload copy.
591 *
592 * Example: Native_socket_stream, when operating in stream mode (asio_local_stream_socket::Protocol_byte_stream
593 * a/k/a `SOCK_STREAM` unlike the earlier example) might hit would-block after any given byte whatsoever; right down
594 * to the "worst case" of, say, reading all of a 60K-long payload except for the very last expected byte. Then you'd
595 * have to copy it from the would-be user buffer; and feed that part to the next async-receive's user buffer (another
596 * copy). Fortunately this eventuality should not be frequent enough to affect overall perf.
597 *
598 * In that case you'll need to do somehow save any partial-read results and apply them to the next async-read
599 * *of any type* at the start of that async-read, before reading any further potential low-level data. Usually
600 * this isn't a matter of performance, as at worst it's part of only 1 in-message, but you'll need some extra code,
601 * and the support for emulated batch-receiving will impact code not-itself-necessarily-related to batch-receiving.
602 *
603 * @warning It is important that `async_rcv_impl_func()` cache any new pipe-hosing error it encounters
604 * (and therefore emits via `Error_code*` -- but note it may emit non-pipe-hosing error(s) too, most notably
605 * would-block; that is different); so that if an async-receive is attempted subsequently, it knows to
606 * immediately emit it. We mention this, because async_receive_batch_emulation() will -- in the case of
607 * encountering 1+ in-messages followed by error (e.g., graceful close
608 * error::Code::S_RECEIVES_FINISHED_CANNOT_RECEIVE) -- *only* emit the 1+ messages and not any error; it will
609 * stop but ignore the error itself. `{Native_handle|Blob}_receiver::async_receive_*()`
610 * contract is to emit the error next time in that
611 * case -- and async_receive_batch_emulation() shall take no steps of its own to make that happen.
612 * Your `async_rcv_impl_func()` must take care of that.
613 *
614 * ### Rationale / use-cases ###
615 * @see Native_handle_receiver concept doc header "Batch-receiving" section for background.
616 *
617 * As of this writing Native_socket_stream and Blob_stream_mq_receiver use it internally. The latter does so, since
618 * (as of now anyway) there is no built-in batch-receiving OS support for POSIX MQs (nor bipc MQs). The former does
619 * so if and only if Native_socket_stream_cfg::S_USE_OS_DGRAM_BATCH_SUPPORT is `false`. In English -- in both
620 * cases there's no low-level batch-receiving, so to provide that higher-level interface it has to be emulated
621 * based on normal receiving.
622 *
623 * The same task would be faced by any potential Blob_receiver or Native_handle_receiver concept implementer,
624 * including when a Flow-IPC user wants to do so; an advanced type of work but entirely supported. Therefore it would
625 * be relatively rare that a user would call this... but definitely possible. Hence it is public.
626 *
627 * @tparam NO_HNDLS
628 * `true` if implementing Blob_receiver::async_receive_blob_batch().
629 * `false` if Native_handle_receiver::async_receive_native_handle_batch().
630 * @tparam Batch
631 * Blob_receiver::Blob_batch_in or Native_handle_receiver::Native_handle_batch_in (see `NO_HNDLS`).
632 * In addition, it must have the APIs with identical names/semantics to
633 * `Generic_msg_batch_in::clear_used(size_t)`, Generic_msg_batch_in::emulate_result(),
634 * Generic_msg_batch_in::next_target_blob(), and -- if `NO_HNDLS == false` --
635 * Generic_msg_batch_in::next_target_hndl(). (Rationale: We could have instead simply required that
636 * `Batch` be an instance of `Generic_msg_batch_in<Msg_resource, NO_HNDLS>`. Decided to formally allow
637 * any type, as long as it has the required behavior -- for freedom in custom scenarios.)
638 * @tparam Task_err
639 * As for `{Native_handle|Blob}_receiver::async_receive_*_batch()`.
640 * @tparam Async_rcv_impl_func
641 * See above.
642 * @param logger_ptr
643 * Logger to use for logging in this op, including its async-continuation if applicable.
644 * @param batch
645 * As for `{Native_handle|Blob}_receiver::async_receive_*_batch()`.
646 * @param assume_would_block
647 * As for `{Native_handle|Blob}_receiver::async_receive_*_batch()`.
648 * @param sync_err_code
649 * As for `{Native_handle|Blob}_receiver::async_receive_*_batch()`.
650 * @param on_done_func
651 * As for `{Native_handle|Blob}_receiver::async_receive_*_batch()`.
652 * @param async_rcv_impl_func
653 * Your `*_receiver`'s single-message receive op. See above.
654 */
655template<bool NO_HNDLS, typename Batch, typename Task_err, typename Async_rcv_impl_func>
656void async_receive_batch_emulation(flow::log::Logger* logger_ptr,
657 Batch* batch, bool assume_would_block,
658 Error_code* sync_err_code, Task_err&& on_done_func,
659 Async_rcv_impl_func&& async_rcv_impl_func);
