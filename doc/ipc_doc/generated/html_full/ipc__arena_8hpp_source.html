60/**
61 * Represents/manages a segregated collection of in-SHM (shared memory) objects and buffers allocated using
62 * the memory manager *jemalloc*, acting according to the SHM-arena-lend design. It is arguably the central
63 * class of SHM-jemalloc, a type SHM-arena-lending SHM-provider in Flow-IPC. SHM-jemalloc's key objects
64 * (Ipc_arena and ipc::session::shm::arena_lend::jemalloc::Shm_session, principally) can be plugged into a
65 * general Flow-IPC session, as established via ipc::session machinery; or they can be used on a standalone basis.
66 * It is generally significantly easier to do the former: a successfully established `Session` will get you
67 * an Ipc_arena (2, even, one of session-scope, another of app-scope) and `Shm_session` for free (~no additional
68 * coding effort is required). You may access `jemalloc::Session::session_shm()` (`Ipc_arena*`),
69 * `jemalloc::Server_session::app_shm()` (ditto), and `jemalloc::Session::shm_session()` (`Shm_session*`).
70 *
71 * @note These notes (in Ipc_arena doc header) are written from the standpoint of presenting it (and the rest of
72 * SHM-jemalloc) as a standalone system. In most situations a general Flow-IPC user can think of
73 * SHM-providers, whether SHM-jemalloc or another one (such as SHM-classic in shm::classic), interchangeably.
74 * That said each SHM-provider has certain properties specific to it. We mention them below under
75 * "Properties of SHM-jemalloc."
76 *
77 * @see ipc::session::shm::arena_lend::jemalloc::Shm_session, an important class required for sharing objects
78 * constructed via Ipc_arena with other process(es).
79 *
80 * The key relevant ops are as follows. Let `*arena` be an Ipc_arena. Let `*session` be a
81 * session::shm::arena_lend::jemalloc::Shm_session connected to an entity (process, usually not the process holding
82 * `*arena`) P. Both are `shared_ptr`s but never mind for now. Let `*session2` be the peer object of `*session`,
83 * in process P.
84 * - `shared_ptr<T> p = arena->construct<T>(...)`: Constructs a `T{...}` in SHM as *owned* by `*this` arena; jemalloc
85 * is used for allocation of actual buffers.
86 * - `session->lend_arena(arena)`: Makes it possible to share -- *lend* -- `p` (and others) to P.
87 * - `auto blob = session->lend_object(p)`: Registers that `*p` is planned to be *borrowed* by P.
88 * - IPC-transmit the short `blob` to P (call the received copy `blob2`).
89 * - (In opposing process P) `shared_ptr<T> p2 = session2->borrow_object(blob2)`.
90 * - Now: `*p` is garbage-collected *across processes* (ours and P in this scenario; but it is possible to
91 * lend to other processes via other `Shm_session`s, 1 of the latter for each). Only once the `p` and `p2`
92 * ref-counted-pointer groups each reaches ref-count zero does `*p` get destroyed (`~T()` runs, then
93 * `sizeof(T)` memory is jemalloc-deallocated).
94 *
95 * ### Interrelated lifetimes of Ipc_arena, its `construct()`ed objects, and lent-through `Shm_session`s ###
96 * `Ipc_arena`s are publicly accessed exclusively via `shared_ptr` handles (use create() factory method instead of
97 * any direct ctor). This semantic is used to ensure it will outlive each of the following.
98 * - 1, each (garbage-collectable) object `arena->construct<T>()`ed (in SHM), even while no process has borrowed
99 * it. Therefore you may picture that after `shared_ptr<T> p = arena->construct<T>(...)`, the `shared_ptr` group
100 * of `p` maintains an invisible `shared_ptr` copy of `arena`, live while the group is live.
101 * - 2, each (also `shared_ptr`-accessed) `Shm_session` object for which one has called `session->lend_arena(arena)`.
102 * Thus picture that the latter call saves a copy of `shared_ptr<Ipc_arena> arena` inside `*session`, live
103 * while `*session` is live. (The user should let go of `session` if and only if the connection to the opposing
104 * process is lost, and/or we want to imminently end that connection.)
105 *
106 * Hence, assuming no crashes/etc.:
107 * - A `*this` is required for constructing future objects to be shared via each given `Shm_session`. Therefore
108 * it outlives all `Shm_session`s through which it has been `lend_arena()`d.
109 * - A `*this` is required for destroying objects it has constructed, and which may or may not have been
110 * lent via 1+ `Shm_session`s. Therefore it outlives (...see prev bullet...); and it outlives all
111 * `shared_ptr` group(s) returned by `this->construct()`.
112 *
113 * @todo ipc::shm::arena_lend::jemalloc::Ipc_arena has public methods for end users but also an API, including
114 * (e.g.) add_shm_pool_listener(), used by Flow-IPC internals to make things work properly; these should
115 * be made non-`public` (accessible by said internals via a facade/attorney/etc. pattern of choice). A careful
116 * effort is required to clean up the API and then classify what's left as either public-facing or otherwise.
117 * Suggest also converting currently-used `protected`-for-unit-tests pattern to the facade/attorney/etc.
118 * pattern of choice (if necessary a separate facade/whatever could be used for internal-code consumers versus
119 * test-code consumers). E.g., start() is such a test-accessed `protected`-only-for-that-reason
120 * item. / Lastly: the public super-class Owner_shm_pool_collection, and its super-class(es), likely expose
121 * some public things that too should be gated-off from end-users.
122 *
123 * ### Cleanup (of in-SHM resources) ###
124 * As explained above, a borrowing/lending scheme + GC semantics ensure proper cleanup of `Ipc_arena`-constructed
125 * objects. What about the SHM-pools (a/k/a SHM objects, SHM segments, in-SHM extents) that are obtained from the
126 * OS? (Even if all buffers held in a given SHM-pool have been deallocated, at a lower level RAM may still be
127 * earmarked for SHM use on `*this` behalf. Plus there are vaddr areas that are mapped that may need to be
128 * unnmapped.) Answer:
129 *
130 * Assuming no crashes occur throughout, here or in borrowing process(es) if any: A `*this` shall only be destroyed
131 * when safe (via aforementioned `shared_ptr` techniques). When this occurs, the Ipc_arena destructor, synchronously
132 * or otherwise, shall return/free all resources, including SHM-pool handles (in Linux et al, FDs really) and/or mapped
133 * (in Linux et al, `mmap()`ed) vaddr areas, and SHM-pool names in the file-system. Similarly a borrowing
134 * `Shm_session` (also destroyed when safe via `shared_ptr` goodness) shall handle its end of such things
135 * (read-only SHM-pool handles, mapped areas). Once all (well, a subset) of this occurs, the relevant SHM-used
136 * RAM is returned to the system for general use.
137 *
138 * If a crash occurs, the dtor may not run (or its asynchronous aspects may not finish). The crash itself will
139 * return any SHM-pool handles and mapped extents; but a given SHM-pool's name would remain in the file-system;
140 * thus the RAM is not returned. Handling this eventuality is the responsibility of the Ipc_arena (et al) user.
141 * In particular by arranging a certain pool-naming scheme -- see `pool_name_base` arg to Ipc_arena::create() --
142 * one can opportunistically remove (unlink) dead process-created SHM-pools form the file-system.
143 *
144 * Happily ipc::session (available in Flow-IPC but optional to use with SHM-jemalloc) has implemented such
145 * post-crash opportunistic cleanup (and, relatedly, determines the pool-naming scheme). It calls
146 * Ipc_arena::create() in particular (among other things) for you. If you don't use ipc::session to establish
147 * your `Ipc_arena`(s), though, you would need to handle it yourself (or risk memory leaks).
148 *
149 * @warning Due to certain implementation details, the `create()`-returned `shared_ptr` group (that points to
150 * `*this`) reaching ref-count-zero concurrently to a *relevant thread* exiting can lead to undefined behavior.
151 * A *relevant thread* is defined as one in this process that has touched a `this->construct<T>()`ed
152 * handle group through any of the following operations: Ipc_arena::construct() itself,
153 * `Shm_session::lend_object()`, and the *disposer*. The *disposer* executes when the handle
154 * (#Handle a/k/a `shared_ptr<T>`) group reaches ref-count-zero. Loosely speaking this means either
155 * join the threads that work with SHM-objects `construct()`ed by `*this` before ending `*this` arena;
156 * or end this arena before joining such threads.
157 *
158 * ### Properties of SHM-jemalloc (and likely other SHM-arena-lending SHM-providers, if/when they exist) ###
159 * Please see the doc header for namespace ipc::shm. It contrasts the `Ipc_arena`-centered SHM-jemalloc, which
160 * is an *arena-lending* provider, to the `Pool_arena`-centered SHM-classic (an *arena-sharing* provider).
161 *
162 * Spoiler alert: e.g., in our case borrower-side access of a SHM-stored object is read-only.
163 *
164 * @internal
165 *
166 * The warning just above, in mentioning "certain implementation details," is actually referring to the limitations
167 * on when detail::Thread_lcl_obj_db_admin::forgetting_shm_arena() (ditto `Thread_lcl_obj_db_client`) can be safely
168 * called. This is documented in the doc headers for those two `static` methods. The danger zone begins when
169 * a relevant thread begins shutdown -- `Thread_local_state_registry` removes an `_admin` and/or `_client`
170 * (that has worked with `*this` arena's objects) from its extant-TL-states list -- and ends basically when
171 * the `_admin` and/or `_client`'s destructor has finished. This is a brief period called The Gap in some internal
172 * documentation in thread_lcl_obj_db.hpp-land.
173 */

287 /**
288 * `allocate()`s `sizeof(T)` bytes (in SHM), invokes `T{...}` ctor with the given args, and returns a
289 * ref-counted handle, so that the resulting object shall be garbage-collected w/r/t this process as well
290 * as any subsequent *borrower* process(es). That is to say, `~T()` dtor shall be called, followed by deallocate(),
291 * in this process -- but only after (1) the returned handle's `shared_ptr` group reaches ref-count zero,
292 * *and* (2) the same happens to any similar `Handle<T>` returned by `Shm_session::borrow_object()`.
293 *
294 * Does not return null. Throws on any error (details below).
295 *
296 * @see Class doc header for an overview of related ops including lend/borrow. That'll explain how the
297 * aforementioned `borrow_object()` call -- probably in another process! -- is connected to the
298 * handle returned here.
299 * (Spoiler alert: `p = a->construct()` => `blob = session->lend_object(p)`
300 * => `p2 = their_session->borrow_object(copy_of_blob_ipced_over_to_us)`.)
301 *
302 * [De]allocation propagation via STL-allocator
303 * --------------------------------------------
304 * What if `T` is not a plain old data type? Let's say specifically (as recommended for Flow-IPC users dealing
305 * with non-PoDs in SHM) that `T` is (or contains... but let's keep it simple) an STL-compliant container such as
306 * `vector<char>` or `flow::util::Basic_blob`. `sizeof(T)` then likely won't be holding the actual data;
307 * it'll need to allocate a buffer of size N. Let's say you used the T ctor that would immediately allocate
308 * N bytes. Then, for this to work properly (as opposed to allocating N bytes in regular heap: unhelpful),
309 * `T` must be configured with a SHM-aware allocator that will call `allocate(N)` via this `Ipc_arena` when
310 * needed. #Allocator provides this. So construct() itself will `allocate(sizeof(T))`,
311 * invoke `T{...}`; that will propagate any allocating to the allocator; that will in turn `allocate(N)`.
312 * Conversely, when SHM-jemalloc decides to garbage-collect (see above), it will invoke `~T()`; that will
313 * propagate deallocation of the N-buffer to the allocator; allocator in turn will `deallocate(...)` via
314 * `*this`; and lastly SHM-jemalloc shall `deallocate(p)`, where `p` is the raw pointer in the
315 * handle originally returned by `construct()` here.
316 *
317 * It is also possible, when working with a container such as the hypothetical `T`, to require more allocations
318 * and/or deallocations after ctor `T{...}` here and dtor `~T()` at GC-time. The same principles apply:
319 * `T` (e.g. `vector`) code tells allocator to [de]allocate; allocator forwards to `this->[de]allocate()`.
320 * However! The allocator must know which `Ipc_arena` to in fact use. If you are using `Stateless_allocator`
321 * (#Allocator) (as we recommend) then you will need to use shm::stl::Arena_activator (#Activator) to
322 * thread-locally set the "current" arena to `this`, in-scope of any potentially-[de]allocating ops (e.g.:
323 * `vector::resize()`).
324 *
325 * Integration with shm::stl::Stateless_allocator (#Allocator)
326 * -----------------------------------------------------------
327 * This method, bracketing the invocation of the `T` ctor, sets the thread-local #Activator context to `this`.
328 * Therefore the caller need not do so. If `T` does not store an STL-compliant structure that uses
329 * `Stateless_allocator`, then this is harmless albeit a small perf hit (also skipped for all
330 * trivially-destructible `T`). If `T` does do so, then it is a convenience.
331 *
332 * Arguably more importantly: The returned `shared_ptr` is such that when garbage-collection of the created
333 * data structure does occur -- which may occur in this process, but via lend_object() and borrow_object()
334 * may well occur in another process -- the `T::~T()` *dtor* call shall also be bracketed by the aforementioned
335 * context. Again: If `T` does not rely on `Stateless_allocator`, then it's harmless; but if it *does*, then
336 * doing this is quite essential. That is because the user cannot, typically (or at least sufficiently easily),
337 * control the per-thread allocator context at the time of dtor call -- simply because who knows who or what
338 * will be running when the cross-process ref-count reaches 0.
339 *
340 * Lifetime versus `*this` arena
341 * -----------------------------
342 * Please read "Interrelated lifetimes" in class doc header.
343 *
344 * Errors
345 * ------
346 * ### On `allocate(sizeof(T))` failing ###
347 * The first step in this method is to allocate the outer-layer buffer sized for the new `T` itself. If this
348 * fails: the method throws as allocate(); namely it throws `std::bad_alloc`.
349 *
350 * @see allocate() doc header which describes the relevant throwing semantics. In short: the known
351 * (all non-mainstream) causes are environmental limits -- chiefly the per-process open-file-descriptor
352 * limit, as SHM-jemalloc keeps one descriptor open per SHM-pool -- and an absurdly large `sizeof(T)`.
353 * Contrast with, say, classic::Pool_arena::allocate() which can fail simply because the user-decided
354 * and unchangeable (for a given arena) overall pool capacity is exceeded.
355 *
356 * ### What else can fail? ###
357 * construct() in SHM-jemalloc, following the initial `allocate(sizeof(T))` and the ctor `T{...}`,
358 * performs further setup that assures the aforementioned cross-process GC. A problem can occur. In all
359 * cases, as a result, an exception is thrown upon undoing preceding successful steps.
360 *
361 * As with allocate() essentially all problems are of a non-mainstream nature/environmental limits. There are
362 * however a couple that *could* be of specific interest.
363 *
364 * - Internally the GC system can only handle up to a certain large # of live `construct()`ed objects *per thread*
365 * (per arena). As of this writing it is about 1 million. This is not a problem for most applications, but it
366 * is possible.
367 * - Result: throws `std::bad_alloc` after logging a WARNING. Note this is the same result,
368 * exception-type-wise, as allocate() failing. Both do indicate, usually, some kind of capacity problem.
369 * - Internally the GC system will need to create a (typically small, in terms of actual RAM use) auxiliary
370 * named SHM-pool. This can fail, though again it is unlikely in a setup that is basically working.
371 * - Result: throws `flow::error::Runtime_error` (itself an `std::runtime_error`) after logging a warning.
372 * An `Error_code` and an error string are available through the exception object.
373 * - Any other issue: Throws an exception.
374 *
375 * Last, and in fact not least:
376 *
377 * ### If `T` constructor throws ###
378 * The thrown exception propagates to our caller upon undoing the `allocate(sizeof(T))` preceding the ctor call.
379 *
380 * Corollary + context: A particular sub-case of this is that, while executing `T` ctor, a subordinate --
381 * typically/recommendedly via allocator-furnished container-containing type `T` -- `allocate()` threw `bad_alloc`.
382 * We guarantee that our `allocate(sizeof(T))` is undone. In addition: A properly coded (at all nesting-layers)
383 * container-containing type `T`, using (at all nesting-layers) a proper SHM-supporting allocator shall undo all
384 * `allocate()`s that had succeeded up to the one that failed. This method itself can only take care of its
385 * own `allocate()`, which as just noted it does.
386 *
387 * @tparam T
388 * The object type to be created.
389 * @tparam Ctor_args
390 * The parameter types that are passed to the constructor of T.
391 * @param ctor_args
392 * The arguments passed to the constructor of T.
393 *
394 * @return A shared pointer to an object created in shared memory. Not null.
395 */
396 template<typename T, typename... Ctor_args>
397 Handle<T> construct(Ctor_args&&... ctor_args);

399 /**
400 * Performs a non-garbage-collected allocation of a buffer in SHM.
401 *
402 * @warning It is irregular, though not formally disallowed, for the end user to invoke this except inside
403 * STL-allocator code. We provide shm::stl::Stateless_allocator (#Allocator) which shall do so for
404 * you, and we recommend you use that instead of rolling your own.
405 *
406 * On failure to allocate
407 * ----------------------
408 * The topic of how this acts on "failure to allocate" is arguably subtler than one might assume, mainly in
409 * that it's not so simple to define what "failure to allocate" means. We discuss that lower-down; but first
410 * the actual semantic:
411 *
412 * ### What allocate() does on failure to allocate ###
413 * If it is impossible to allocate the `n` bytes: Throws exception `std::bad_alloc`.
414 *
415 * @note This is intended to be consistent across
416 * SHM-providers like SHM-jemalloc and SHM-classic (classic::Pool_arena::allocate()).
417 *
418 * It is salient that an allocator's (e.g., our #Allocator) `allocate()` may forward to us and is
419 * allowed to "throw exceptions" (no particular exception type is mandated or recommended). So we are
420 * behaving consistently with letting an allocator's `allocate()` simply forward to this method (of some `*this`)
421 * and let it throw. There is no need to check for null return.
422 *
423 * ### What is failure to allocate? ###
424 * OK, so what should one do if this allocate() (or, e.g., `construct<T>()` that calls it 1+ times) in fact
425 * throws `bad_alloc`? Could one simply let the `bad_alloc` (if any) be thrown uncaught? That depends,
426 * naturally, on what occurred to result in this reported "failure to allocate."
427 *
428 * The meat-and-potatoes facts, presented for concreteness at the risk of describing some impl details, are as
429 * follows:
430 * - To allocate N bytes, here, is to ask jemalloc (a-la `malloc()`) to allocate an N-buffer in a particular
431 * segregated *jemalloc-arena* A. Basically the `malloc()`-like API returns null <=> failure to allocate.
432 * (We detect this internally and throw as advertised.)
433 * - This arena A does not have any total size that can be exceeded (cf.: classic::Pool_arena). As with
434 * vanilla `malloc()`, extents (vaddr areas) -- mapped (potentially sparsely) to actual RAM blocks -- are used
435 * in some fashion, and when none is sufficient for a given allocate-request, a new extent (vaddr area) is
436 * created by jemalloc corresponding to more RAM blocks (potentially sparsely).
437 * - We internally configure arena A so as to run some tricky Flow-IPC (SHM-jemalloc) code, via *extent hooks*,
438 * so when a new extent is needed (prev bullet) we'll map it to SHM as opposed to regular heap (+ more
439 * activities). If such a hook is invoked, it executes synchronously within allocate() here.
440 *
441 * That's the happy path; so how can it fail? Black-boxily speaking:
442 * - jemalloc code itself might fail in some way.
443 * - The known (non-mainstream) causes are environmental limits -- chiefly the per-process open-file-descriptor
444 * limit, as SHM-jemalloc keeps one descriptor open per SHM-pool -- and a too-large N. The latter
445 * specifically: N approaching or exceeding ~2GiB (at which point the needed SHM-pool would exceed the
446 * max size addressable by our fancy-pointer type) always fails.
447 * - Flow-IPC code itself might fail in some way (and would, potentially, log WARNING(s) as to what that was).
448 *
449 * That said:
450 * - *We do not know of a mainstream situation where this happens*. Unlike with `Pool_arena` in SHM-classic
451 * there is no arena max-size. Moreover, at least in Linux, running out of SHM (<=> tmpfs max-use limit reached)
452 * in a sparse setup like ours means a brutal, unavoidable crash (SIGBUS); so jemalloc-allocate is unlikely
453 * to be the thing that fails. Instead a subsequent touching of an in-extent page, possibly long after
454 * allocate() returns, is typically that thing: Something tries to write into a page's area (4Ki bytes wide
455 * usually); the page is not backed by RAM yet; OS tried to commit page; cannot (limit reached) => crash.
456 * - *We internally nevertheless treat it, defensively, as possible*. So we throw `bad_alloc` as noted.
457 * - Informally: Because of the first bullet above, we suggest that user code *may* treat the possibility
458 * of allocate() (or construct(), or other container-driven allocations) failing as being only as serious
459 * as a heap-alloc failure (e.g., when heap `new` throws `bad_alloc`). That is often defensibly taken to mean,
460 * "it's environmental/an act of god; just let it throw; don't catch it."
461 * - However: If writing code that is generic irrespectively of which SHM-arena/SHM-provider is acting, then
462 * potentially take the opposite approach. E.g., classic::Pool_arena::allocate() and `construct<T>()`
463 * definitely can fail with `bad_alloc`, and often one wants to be defensive/ready for this. So generic
464 * code might want to treat the Ipc_arena counterpart APIs defensively as well.
465 *
466 * Perf notes
467 * ----------
468 * A jemalloc thread cache will be used with this allocation automatically. See deallocate() also.
469 * (As of this writing preprocessor symbol `IPC_SHM_ARENA_LEND_JEMALLOC_NO_TCACHE` can be defined
470 * to forego tcaching entirely.)
471 *
472 * @param size
473 * The allocation size, which must be greater than zero.
474 * @return A non-null pointer to the base address of the allocation.
475 */
476 void* allocate(size_t size);

496 /**
497 * Synchronously garbage-collects, in the calling thread, any objects `x = A.construct()`ed by this thread, for *all*
498 * `Ipc_arena`s `A` in existence. To be explicit: the garbage-collection involves only objects `x` such that (1)
499 * there are no *user references* to `x` anymore (see below), and (2) SHM-jemalloc has not yet had a chance to
500 * free `*x`. Freeing an (in-SHM) object involves calling its destructor if any (which may itself free more
501 * in-SHM buffers, typically through allocator #Allocator action) and then freeing its `sizeof(*x)` in-SHM buffer.
502 *
503 * What are *user references*? Answer: Firstly: `x` itself (from the given `A.construct()`) is a `shared_ptr` in a
504 * group; so all `shared_ptr`s in that group are references. Secondly: there is the `Shm_session::lend_object()` +
505 * `Shm_session::borrow_object()` (the latter of which returns a `shared_ptr` similar to `x`) mechanism. Without
506 * delving into exact formal details, essentially: `x2 = S2.borrow_object()`, usually invoked in another process
507 * on `Shm_session S2` in a procedure starting with `S.lend_object(x)` (in our process), returns a `shared_ptr`;
508 * so the `shared_ptr`s in that `shared_ptr` group are also references (albeit typically cross-process ones).
509 * (If the session to that other process is gone -- no more `S` -- then effectively any borrowed references
510 * lent through it are dropped.) To reiterate: Once both types of references are all dropped, condition (1)
511 * above is satisfied.
512 *
513 * ### When to call this ###
514 * Ideally you should not need to call this, and informally we recommend against doing so willy-nilly in the
515 * middle of your SHM-using algorithm(s); not because it is a costly call (it is not), but because it cuts
516 * against the (we humbly hope) easy-to-use design of SHM-jemalloc. In short: Most SHM-jemalloc activities --
517 * including *any* call to construct(), create(), `Shm_session::lend_object()`, `Shm_session::borrow_object()`,
518 * `construct()`ed-object disposer, ditto borrowed, at thread exit -- will already perform the necessary
519 * garbage-collection. Moreover, in many cases (depending on your use patterns), the specific object that has
520 * just reached cross-process ref-count-zero will be *immediately* disposed (no later GC needed).
521 *
522 * However: If a given object `*x` happens to reach cross-process ref-count-zero (meaning the last cross-process
523 * `shared_ptr` group's last `shared_ptr` releases its reference) *not* in the thread that constructed it but
524 * another thread or process, *and* (this is key) that thread stops doing **nearly all** SHM-jemalloc work as
525 * triggered by your code (see above list which may not be exhaustive), then no opportunistic GC shall occur, and
526 * `*x` will not be freed yet. (Eventually it will; worst-case on thread exit.)
527 *
528 * It is arguably a pathological use pattern, but it's certainly possible. So if your thread enters an idle
529 * or SHM-jemalloc-free time period, while arena(s) exist that could have this-thread-`construct()`ed objects
530 * (that are no longer used) extant, then calling this will ensure such things, if any, are freed.
531 *
532 * ### Is it cheap? ###
533 * Above we casually say "it is not" expensive. Informally speaking this is generally true. It *is* possible
534 * to contrive a scenario where so many no-longer-referenced but not-already-GCed (through direct or
535 * piggy-backed internal SHM-jemalloc algorithms alluded-to above) objects have built up, that a given call
536 * is relatively heavy, just by virtue of having to do the actual freeing many times. Even then, though, it
537 * would be a one-time thing. The point is: if there's little or nothing to GC, then it's cheap, because the
538 * check is very cheap.
539 *
540 * ### Thread safety ###
541 * Safe to call anytime. Asterisk: We have not contemplated corner-case scenarios of calling this from a given
542 * thread, when that thread is exiting (such as in some `thread_local`'s destructor). So we formally say:
543 * Do not do it (on pain of undefined behavior). In any case it would be pointless: GC occurs during thread
544 * shutdown already.
545 */
546 static void this_thread_gc();

1323 /**
1324 * Reads the raw jemalloc-sourced stat-members -- the `m_vaddr` and `m_alloc` sub-groups -- of each
1325 * `(*rows)[idx]`, where `idx` is the index of a native arena-ID within #m_arenas; all from one jemalloc stats
1326 * snapshot. Pre-conditions: detail::jemalloc_stats_mutex() locked; jemalloc-stats enabled within jemalloc.
1327 *
1328 * ### Design: Who else refreshes jemalloc stats? ###
1329 * jemalloc serves every `"stats.*"` read from one snapshot for the entire process, replaced by any refresh (see
1330 * detail::stat::epoch_refresh()). Flow-IPC's own stats operations are excluded by detail::jemalloc_stats_mutex()
1331 * (see its doc header, including for what a refresh in the middle of our reads would do). But other code in the
1332 * process may use jemalloc stats/dump APIs directly; nothing in Flow-IPC forbids this, nor should it. No mutex of
1333 * ours can exclude that.
1334 *
1335 * So for those we use jemalloc's epoch counter, which each refresh increments: refresh (noting the epoch); read
1336 * everything; then check the epoch again. It is a time stamp of sorts; the jemalloc `man` page names exactly this
1337 * purpose for it. So: if unchanged then all values came from one snapshot. Otherwise something refreshed
1338 * concurrently, possibly (not necessarily) between two of our reads: read everything again, this time from the
1339 * new snapshot (which is at least as new as ours; so no need to re-refresh). Such outside refreshes are
1340 * presumably rare, so it should take 1, maybe 2, attempts. (In theory outside code refreshing nonstop, more often
1341 * than one attempt takes, would keep us retrying indefinitely.)
1342 *
1343 * @param rows
1344 * `rows->size()` must equal `m_arenas.size()`. Only the `m_vaddr` and `m_alloc` sub-groups are written.
1345 */

1457 * @see Sharded_stats doc header for how this specifically applies to these particular stats.
1458 *
1459 * ### Thread safety ###
1460 * Similar to #m_mem_mgr_base_stats but simpler, as there is no map here, just a single `struct`.
1461 */
1462 Sharded_stats m_sharded_stats;
1463
1464 /**
1465 * Per-native-arena reset-state ("base") for memory_manager_stats() / memory_manager_stats_reset(): for each
1466 * arena in #m_arenas it holds the since-reset baseline (the ACCUMULATOR values as of the last reset; and the
1467 * running high-water marks). Populated once at start() (one zero-init entry per arena); the structure is fixed
1468 * thereafter (no runtime insert/erase). Its *values* are mutated during stat-consumption/reset; see "Thread
1469 * safety" below.
1470 *
1471 * @see memory_manager_stats(), stat::Memory_manager_stats.
1472 *
1473 * Why `map<>`? Answer: no big reason; as of this writing its `.size() == 1` anyway, because that's the case
1474 * for #m_arenas. Basically #m_arenas is a semi-placeholder (size=1), and the original author used `map<>` for
1475 * it -- in tests arenas were thus auto-sorted by arena-ID, and that was nice? -- so we did the same here;
1476 * that's all. These details will most likely be changed-around for perf (at least), when `.size()` of
1477 * this and of `m_arenas` grows.
1478 *
1479 * ### Thread safety ###
1480 * The public `memory_manager_stats*()` API is advertised as safe to call concurrently with any method on the same
1481 * `*this`, including each other. That is delivered by detail::jemalloc_stats_mutex(), which (for its own,
1482 * process-wide reasons; see its doc header) is held throughout each memory_manager_stats() and
1483 * memory_manager_stats_reset() -- jemalloc reads included, not merely the access to `*this`. It must be held that
1484 * long: otherwise a stat-consumption's raw values could predate a baseline that a concurrent reset installed in
1485 * the meantime, and its since-reset counters would underflow.
1486 *
1487 * Even if that mutex did not deliver this guarantee for free, we would maintain it. Why the contract? In short:
1488 * the various other stats (e.g., #m_pool_stats) have the same property advertised via their relevant API(s).
1489 * There is no black-box reason why this should be any different. To strengthen it further:
1490 *
1491 * Technically the following is not in our purview here but nevertheless --
1492 * `ipc::session::shm::arena_lend::jemalloc`, which is Flow-IPC's recommended method of setting up arenas
1493 * like `*this` (though it can be done standalone also), shall periodically stat-consume (spoiler: partially
1494 * to keep the HI_WMARKs decently useful by sampling regularly, partially perhaps to log) in the background.
1495 * So if this were not thread-safe, the user couldn't safely stat-consume on-demand, as it could be concurrent
1496 * to the background activity. One could argue this "just" demonstrates the usefulness of keeping this
1497 * thread-safe in the first place.
1498 */
1499 std::map<arena_id_t, Memory_manager_stats> m_mem_mgr_base_stats;

1504template<typename T, typename... Ctor_args>
1505Ipc_arena::Handle<T> Ipc_arena::construct(Ctor_args&&... ctor_args)
1506{
1507 using arena_lend::detail::Thread_lcl_obj_db_admin;
1508 using arena_lend::detail::use_ct_idx_t;
1509 using util::op_with_possible_bipc_exception;
1510 using Disposer = arena_lend::detail::Owner_obj_disposer_and_mdt<Ipc_arena>;
1511 using Bipc_bad_alloc = ::ipc::bipc::bad_alloc;
1512 using Std_bad_alloc = std::bad_alloc;
1513 // using flow::util::construct_at; // C++20 => can conflict with incidentally included std:: counterpart.
1514 constexpr bool HAS_TRIVIAL_DTOR = std::is_trivially_destructible_v<T>;
1515
1516 static_assert(alignof(T) <= flow::util::max_align_sz(),
1517 "allocate() guarantees only std::max_align_t alignment; over-aligned T is not supported.");
1518
1519 Thread_lcl_obj_db_admin<Ipc_arena>::this_thread_piggy_scan(); // Opportunistic!
1520
1521 // No space => throws Std_bad_alloc as advertised. Nothing else to clean up yet; let it rip.
1522 void* const addr = allocate(sizeof(T));
1523
1524 /* Construct the T itself. As advertised try to help out by setting selves as the current arena.
1525 * As in the disposer below we too try to get a perf boost by not unnecessarily using an arena-activator.
1526 * After all it involves a thread-local variable assignment at the start and then another at the end plus 1-2
1527 * more to remember the previous value; it's quick but not nothing. It's trickier than the dtor situation
1528 * below though. Ideally we'd determine something like "T would not use an allocator to allocate something on its
1529 * behalf." There are some ideas, like maybe checking for the presence of tell-tale STL stuff... but it's tricky and
1530 * might be imperfect and thus arguably not worth it (@todo perhaps revisit). However: using
1531 * is_trivially_destructible_v<T> here too is safe, even though it likely won't catch all the cases -- but
1532 * no false negatives, so it's safe. Basically if it's trivially destructible, it can never allocate things
1533 * on its behalf in any sane way; so that fits the bill. */
1534 const auto obj = static_cast<T*>(addr);
1535 try
1536 {
1537 if constexpr(HAS_TRIVIAL_DTOR)
1538 {
1539 flow::util::construct_at(obj, std::forward<Ctor_args>(ctor_args)...);
1540 }
1541 else
1542 {
1543 Activator ctx{this};
1544 flow::util::construct_at(obj, std::forward<Ctor_args>(ctor_args)...);
1545 }
1546 }
1547 catch (...)
1548 {
1549 /* T ctor threw: before letting it propagate might as well undo what preceded it above (same steps as in
1550 * gc_func() below, minus ~T(), as ctor never completed) -- so as not to leak the buffer in SHM. */
1551 deallocate(addr);
1552 throw;
1553 }
1554
1555 /* Lastly: Set up the (cross-process!!) ref-counted garbage-collection machinery. A global
1556 * ->constructing_obj() + a special shared_ptr disposer (see below) will do it.
1557 * gc_func() = the steps eventually executed at GC-time. Additionally on (yet another) rare
1558 * exception below -- that is while merely setting up GC in here -- we may want to give up and therefore
1559 * "GC" it immediately, before/without the user ever accessing it. Hence this local function (no captures): */
1560
1561 const auto gc_func = [](void* addr, Ipc_arena* arena)
1562 {
1563 if constexpr(!HAS_TRIVIAL_DTOR)
1564 {
1565 Activator ctx{arena};
1566
1567 /* Call object's destructor (works for primitives but might be a pointless perf cost; have seen it in un-good
1568 * STL impls before, though the context was a bit different... but can't hurt to just skip it).
1569 * Key context: an allocator-equipped T (usually STL-compliant container) here will (in T::~T())
1570 * call-through to `arena->deallocate()` for each buffer that T had allocated for itself
1571 * (e.g., for vector<> internal buffer; for list<> the various nodes). In the process more destructors
1572 * may be invoked which would quite possibly do more dtor calling and thus deallocate()ing. And so on.
1573 * Hence the present operator()() is called at just the outer layer, then the inner deallocations (if any)
1574 * happen, and then we call deallocate() on the outer object's memory, last-thing, just below. */
1575 static_cast<T*>(addr)->~T();
1576 }
1577 // else { Trivially destructible => no need to... you get the point. }
1578
1579 arena->deallocate(addr);
1580 }; // auto gc_func =
1581
1582 /* The steps where we set up the cross-process-ref-counted GC machinery are all inside the innermost try{}
1583 * just here. In there is the happy path, but parts can throw, and if one does, we handle the possibilities
1584 * in an intentional best-effort way (keep reading). To wit, assuming something inside the try{} threw:
1585 * -# Catch Bipc_bad_alloc; if that: rethrow as Std_bad_alloc. If not that:
1586 * -# Catch other `bipc::interprocess_exception`s; if that: op_with_possible_bipc_exception() will
1587 * rethrow as Runtime_error with various goodies. If not that:
1588 * -# <whatever other exception E> is just thrown, not caught yet. Intention: let user see E.
1589 * -# All paths there lead to some exception X being thrown.
1590 * So we: catch X (as type ...), cleanup (<= attn!), rethrow X. */
1591
1592 pool_id_t lend_tracker_pool_id;
1593 use_ct_idx_t use_ct_idx;
1594 try
1595 {
1596 op_with_possible_bipc_exception(get_logger(), nullptr, // nullptr => if lambda throws, throw as Runtime_error.
1597 arena_lend::error::Code::S_SHM_BIPC_MISC_LIBRARY_ERROR,
1598 "jemalloc::Ipc_arena::construct():->constructing_obj():likely-aux-pool-creation",
1599 [&]()
1600 {
1601 try
1602 {
1603 Thread_lcl_obj_db_admin<Ipc_arena>::this_thread_obj_db()
1604 ->constructing_obj(&lend_tracker_pool_id, &use_ct_idx, this, &m_pool_stats.m_obj_db_aux_pool, addr,
1605 gc_func);
1606 }
1607 catch (const Bipc_bad_alloc&) // First! Grab it if it's a Bipc_bad_alloc; throw as Std_bad_alloc.
1608 {
1609 /* Bipc_bad_alloc would come from our own mem-algo Use_count_registry::allocate() inside Lend_tracker_pool
1610 * as managed by this_thread_obj_db()->constructing_obj() et al. The log message hedges slightly,
1611 * but as of this writing it should be what it says it probably is.
1612 *
1613 * Subtlety: this must be caught first, as a Bipc_bad_alloc is also a bipc::interprocess_exception
1614 * which would be caught by our next (implied) `catch` inside op_with_possible_bipc_exception(). We want it
1615 * to not be caught by op_...(), once we throw our preferred replacement Std_bad_alloc. */
1616 FLOW_LOG_WARNING("In construct<T>() successfully allocated/constructed the T (type "
1617 "[" << typeid(T).name() << "]), but the cross-process-GC hookup step then "
1618 "threw bipc::bad_alloc (there may be a WARNING with details ahead of this message); "
1619 "throwing as std::bad_alloc. (Probably this thread's per-arena (collection/arena ID "
1620 "[" << get_id() << "]) aux-SHM-pool ran out of space which would indicate a massive "
1621 "number of live construct()ed objects; WARNING above may confirm.)");
1622
1623 throw Std_bad_alloc{};
1624 }
1625 }); /* op_with_possible_bipc_exception():
1626 * Second! Grab it if it's another bipc::interprocess_exception (i.e., not bad_alloc) from
1627 * ->constructing_obj(); op_...() instead WARNs and throws Runtime_error with various goodies. */
1628 // Third! Just let it through if it's something else.
1629 }
1630 catch (...) // If something originally threw, then either it or a replacement exception reaches here.
1631 {
1632 gc_func(addr, this);
1633 throw;
1634 }
1635
1636 /* Recommend reading Disposer a/k/a Owner_obj_disposer_and_mdt class doc header; it is quite instructive
1637 * about the handful of things going on in this disposer, and how it relates to subsequent local
1638 * Shm_session::lend_object() and opposing Shm_session::borrow_object().
1639 *
1640 * Relatedly: Can this throw? Answer: Yes but only in shared_ptr's heap work (std::bad_alloc).
1641 * Normally Flow-IPC code treats heap-alloc-fail as a throw-our-hands-up situation, but let's in this one case think
1642 * about it anyway. In short: by placing this here instead of inside the inner-try{} above, the right
1643 * stuff should happen: shared_ptr should execute our Disposer synchronously -- use-count (currently 1)
1644 * reaches 0 in this_thread_obj_db(), so gc_func() executes. Everything is cleaned up. std::bad_alloc
1645 * then gets propagated out of construct() (which is eminently reasonable on heap-alloc fail). */
1646 return Handle<T>{obj, Disposer{shared_from_this(), lend_tracker_pool_id, use_ct_idx}};
1647} // Ipc_arena::construct()
