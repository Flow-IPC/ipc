44/**
45 * Owning and wrapping a pre-connected transport::Channel peer (an endpoint of an established channel over which
46 * *unstructured* messages and optionally native handles can be transported), this template is the central pillar of the
47 * ipc::transport::struc (*structured layer*), capable of communicating structured capnp-schema-based messages (and
48 * native handles).
49 *
50 * @see See also sub-namespace ipc::transport::struc::shm::rpc: It provides an alternative to struc::Channel by
51 * letting one use standard capnp-RPC (Cap'n Proto Remote Procedure Calls) while enjoying Flow-IPC zero-copy
52 * performance. Briefly, pros/cons:
53 * (1) struc::Channel is considerably simpler to set up and slot-in to near any
54 * event loop, which means among other things you're under no obligation to code using
55 * a particular event loop paradigm (using capnp-RPC means using, or integrating with, the KJ promise-based
56 * single-threaded event loop). struc::Channel provides simple-to-understand capabilities including
57 * message-type-muxing and request/response. Representing essentially a stream of the user's verbatim
58 * capnp-encoded messages (and, optionally, native handles), it's simple to reason about including in terms
59 * of perf.
60 * (2) However capnp-RPC is semantically *far* more powerful, providing
61 * function-call-like semantics and "time travel" via
62 * *promise pipelining* -- and more (see https://capnproto.org/rpc.html, a very nice explainer). It is also
63 * an established, mature API; Flow-IPC "merely" provides the zero-copy plumbing underneath (plus some nice
64 * optional integration with ipc::session, much as for struc::Channel et al).
65 * YMMV; both approaches are viable!
66 *
67 * @see sync_io::Channel and util::sync_io doc headers. The latter describes a general pattern which
68 * the former implements. Which of the two to use depends on your needs, as summarized in the util::sync_io
69 * doc header. In short:
70 * struc::sync_io::Channel is the core engine; to have it take action you must make API calls into it;
71 * nothing happens in the background.
72 * struc::Channel adds a background thread that will take action itself, while invoking your supplied
73 * functions, such as response handlers, from that thread to let you react (typically by placing the "true"
74 * reaction back onto your own thread(s) of choice).
75 *
76 * ### Context (short version) ###
77 * struc::Channel (and its `sync_io` counterpart -- and, internally, its core -- #Sync_io_obj)
78 * along with Msg_out and Msg_in essentially *are* the ipc::transport structured layer. We also
79 * suspect that (and designed ipc::transport accordingly) many users of ipc::transport, or arguably even Flow-IPC
80 * at large, will mostly care about the work they can do with struc::Channel and nothing else. Users just
81 * want to send structured messages (and sometimes native handles) in some forward-compatible protocol. Everything
82 * else -- sessions, unstructured-layer channels, the queues and/or socket streams comprised by those channels --
83 * are the necessary but ideally-ignored-most-of-the-time *means* leading to the *ultimate end* of having a working
84 * struc::Channel over which to exchange that structured stuff with the peer's struc::Channel counterpart.
85 *
86 * For performance, with minimal coding effort, these messages can be *SHM-backed* and thus never themselves
87 * copied into/out of an IPC transport (e.g., local/Unix-domain socket); or they can be more classically heap-backed.
88 *
89 * @note It is also at times desirable to keep certain SHM-backed data as native data structures, perhaps
90 * STL-compliant ones. Integration with a struc::Channel is straightforward: (1) use a SHM-provider
91 * in ipc::shm (SHM-classic in ipc::shm::classic, SHM-jemalloc in ipc::shm::arena_lend::jemalloc) to
92 * construct/lend/borrow your data structure; (2) use free functions struc::capnp_set_lent_shm_handle()
93 * to place a `ShmHandle` into a capnp-`struct` leaf field and struc::capnp_get_shm_handle_to_borrow()
94 * to get it out on receipt.
95 *
96 * ### Context (more in-depth) ###
97 * This has certain broad implications. Suppose one first familiarizes themselves with the unstructured layer
98 * (concepts Blob_sender, Blob_receiver, Native_handle_sender, Native_handle_receiver; bundling class template
99 * transport::Channel; concept impls -- classes/class templates Native_socket_stream, Blob_stream_mq_sender,
100 * Blob_stream_mq_receiver; low-level details like the MQ-related API and optionally Native_socket_stream_acceptor).
101 * If one indeed is familiar with that unstructured API, they'll note: struc::Channel API is quite
102 * different. Particularly it's very different in terms of how one handles *in-messages* (receiving). To wit:
103 * - The unstructured APIs are roughly boost.asio-like (though in fact *not* requiring any integration with actual
104 * boost.asio). That is:
105 * - Each async operation is invoked via an `X.async_F(H)` method, to which one passes the handler `H` to invoke;
106 * and `H()` is called *exactly* once: when the async op completes (with or without error); or `X` is
107 * destroyed first (in which case an `operation_aborted`-like error code is emitted to `H()`).
108 * - If more than one `X.async_F()` is invoked, for a given `F` (e.g., 3 Blob_receiver::async_receive_blob()
109 * outstanding calls on one Blob_receiver), then they are queued inside X as needed, with each arriving result
110 * firing 1 handler, dequeuing it in FIFO order.
111 * - If a pipe-hosing error occurs, it is fed to all queued handlers (i.e., the internal queue is cleared)
112 * and any future-invoked-async-API-passed handlers also.
113 * - (If choosing to work with `"sync_io::"` variants of these classes, mostly the same description applies,
114 * except by definition, except at most one pending receive op is allowed at a time.)
115 * - By contrast: The structured (struc::Channel) API is not at all boost.asio-like.
116 * - One registers events handlers for each type of event in which one is interested. While it's possible
117 * to auto-unregister an event handler after it fires once (async_request(), expect_msg()), the general
118 * case is that an event handler registration is sticky until explicitly undone.
119 * - As a sub-case of this paradigm, the act of sending an out-message can be optionally paired with
120 * registering an event handler for when (and if) the other peer responds to that specific out-message
121 * with a response in-message. Thus request/response semantics (while optional) are built-in.
122 * - As a corollary of this paradigm, a single error handler is registered; if a pipe-hosing error occurs,
123 * then that handler is invoked just once -- as opposed to invoking all the other stored handlers with
124 * that same #Error_code.
125 *
126 * As for the *out-message* (sending) API: It is actually similar to the unstructured layer's
127 * already simple API. To recap:
128 * - If you want to send a message, you invoke send() or async_request(). Each is non-blocking *and* synchronous,
129 * *yet* it cannot fail due to a would-block condition. There is no asynchronous send op!
130 * - Alternatively use sync_request() which is a blocking, optionally subject to timeout, version of
131 * async_request(). It will block until a one-off response is received to the sent message
132 * (or timeout, or error) and return that response synchronously (if indeed successful).
133 * - Note that, while sync_request() is formally/generally blocking, it can be used for very quick request-response
134 * exchanges; indeed that is its main use case. For example, a memory-allocation op might contact the
135 * memory-allocating process and return once that process has acknowledged completing the alloc request.
136 * It is both allowed and encouraged to set up the receive end in such a way as to make your *particular*
137 * sync_request() invocations non-blocking.
138 * - Graceful closing is forwarded to the unstructured layer. The Blob_sender, Native_handle_sender,
139 * transport::Channel async_end_sending() API is mimicked by simply passing-through to the owned #Owned_channel.
140 * - This features an asynchronous component. Discussion omitted here; please see async_end_sending().
141 *
142 * However the out-message (sending) API adds an important (optional but highly encouraged) capability:
143 * - Every out-message can be allocated in SHM (shared memory) instead of heap; send() (et al) then transparently
144 * sends (copies into transport, on other side copies out of transport) a tiny *handle* to the message.
145 * - This is enabled, or disabled, for the entire `*this` via compile-time parameters and ctor args.
146 * After such setup the API is identical regardless of whether this full *zero-copy* mode is in use
147 * or not.
148 * - An out-message can be reused and sent again. It can be modified in-between. It would be practical to use
149 * this technique to store complex data structures integral to your application as opposed to a mere messaging
150 * focus. This does not *require* the SHM-backed (zero-copy) mode, but it greatly improves performance
151 * when sharing with another process, at least beyond a certain message size.
152 * - This is an alternative to storing a C++ data structure, such as a `vector` of `map`s of ..., in SHM
153 * manually and transmitting a handle manually. Discussion of details of this is outside the scope
154 * here, but you should be aware that it's the alternative approach for structured-data storage in SHM
155 * and its IPC. They each have their pros/cons.
156 * - A very brief recap is found in a note above, under "Context (short version)."
157 *
158 * To summarize:
159 * - Sending is simple as in the unstructured layer.
160 * - However zero-copy backing of the structured message's serialization in SHM allows for improved
161 * perf.
162 * - Receiving follows an event-handler-registration model, instead of the unstructured layer's preferred
163 * async-op-and-handler model (as inspired by boost.asio). However, you *can* make certain operations
164 * *one-off* (event handler is auto-un-registered after firing once).
165 *
166 * ### Overview: How to use it, why to use it ###
167 * How to use this thing? Broadly speaking:
168 * -# One first establishes a channel connection (obtains a transport::Channel in PEER state). See
169 * transport::Channel. Attention: You will need a `sync_io`-pattern-peer-bearing transport::Channel
170 * (which is enforced at compile-time); formally `Owned_channel::S_IS_SYNC_IO_OBJ == true` is required.
171 * ipc::session emits such `Channel`s.
172 * - *If* you are manually assembling a `Channel` (or alias or
173 * data-less sub-class), then attaining fresh PEER-state peer objects of the `sync_io`-pattern variety
174 * should be equally easy. In the case of Native_socket_stream specifically, you can perform
175 * `.sync_connect()` on a `sync_io`-pattern transport::sync_io::Native_socket_stream; on success bundle
176 * it into `Channel`.
177 * -# One selects the capnp message schema they wish to use. In other words, what kinds of messages does
178 * one want to send? This determines the choice of the #Msg_body template parameter.
179 * -# One selects a technique as to where/how out-messages (and consequently in-messages) will be stored in RAM:
180 * SHM (for full zero-copy performance) or heap (for zero-copy on either side of the low-level transport).
181 * (Details omitted here, but for the sake of this brief recap let's consider this a formality.)
182 * -# One then constructs the struc::Channel, passing the transport::Channel (and the config from previous bullet
183 * point) into ctor -- which is moved-into the resulting `*this`.
184 * -# One then exchanges messages (and, if desired, native handles) with the matching struc::Channel on the
185 * other side via the `*this` transmission API.
186 * -# When `*this` is destroyed, so is the owned transport::Channel (and no earlier).
187 *
188 * So struc::Channel "eats" (via `std::move()`) a presumably fresh (no traffic exchanged) transport::Channel and all
189 * further work on the transport::Channel is through struc::Channel.
190 *
191 * What does struc::Channel add, broadly speaking, that transport::Channel does not already have? Why even bother?
192 * Answer:
193 * - Firstly, each message no longer consists of an (optional unstructured binary blob, optional #Native_handle) pair.
194 * Instead if consists of a (structured capnp-schema-based -- #Msg_body -- message, optional #Native_handle) pair.
195 * In other words this class adds the (mandatory) ability to send *structured* data instead of mere
196 * binary blobs. The schema language of choice is Cap'n Proto (capnp), which allows for zero-copy perf
197 * *at least* until blobs enter the transport and after they exit the transport.
198 * - By choosing to use SHM-based serialization storage for out-messages, zero-copy perf can be extended
199 * end-to-end, meaning only a short handle is ever copied into the transport and out of it on the receiving
200 * side.
201 * - Secondly it establishes some convenient protocol notions on top of the basic message-boundary-respecting/reliable
202 * functionality of transport::Channel.
203 * - Message type (a/k/a #Msg_which): While #Msg_body can specify an essentially arbitrarily complex schema for
204 * what messages can be sent, with `*this` API being generally agnostic as to its details, it does establish
205 * one simple standard: The message schema #Msg_body *must* feature a top-level anonymous (capnp) *union*, with
206 * the "which" enumerator specifying the type of message that it is. E.g., something approximating HTTP might
207 * have the top-level union specifying either a GET, POST, or CONNECT message type, with each one then featuring
208 * its own arbitrary capnp `struct` sub-schema, specifying what data come along with that type of message.
209 * - *Message type demuxing*: Based on this, one sets separate handlers for each individual value for
210 * an in-message's #Msg_which.
211 * - One-off demuxing: One can register the expectation for at most 1 message of a particular #Msg_which type.
212 * Then, when it is received, the expectation registration for that #Msg_which is auto-removed, as the
213 * user-supplied handler fires.
214 * - Open-ended demuxing: Alternatively one can set a permanent (unless explicitly unregistered later)
215 * expectation for a given #Msg_which. Then the user-supplied handler will fire each time a matching
216 * in-message arrives.
217 * - (Queuing) Any messages that have no expect-this-`Msg_which` handler registered are queued inside `*this`.
218 * Registering a demux expectation later will immediately feed matching queued such in-messages, as-if
219 * they'd arrived right then.
220 * - *Request/response demuxing*: Any message one sends can optionally be specified to be expecting response
221 * in-message(s). This is the alternative to #Msg_which-based demuxing. This establishes a basic
222 * request/response paradigm.
223 * - One-off response demuxing: One can specify that the given out-message expects up to exactly 1 response.
224 * - Open-ended response demuxing: One can instead specify that any number of responses may arrive
225 * (until one explicitly unregisters this expectation).
226 * - (Note) If a response in-message arrives, while `*this` has no response expectation registered, it is
227 * an error. However it is not necessarily a fatal error: There is a mechanism allowing the user
228 * to deal with this situation should it arise. However a properly designed protocol would eliminate this
229 * possibility in practice (informally speaking).
230 * - A single full-duplex pipe: transport::Channel, one notes, can be a bundle of up to 2 full-duplex pipes (though
231 * at least 1 is of course required): one for blobs only; one for blob/`Native_handle` combos.
232 * The 2 do not interact; therefore if one were to use both in parallel, various questions arise as to how
233 * (and why!) to use this functionality. struc::Channel elides these details completely and deals with
234 * them internally. Bottom line:
235 * - struc::Channel API models a single full-duplex pipe capable of transmitting messages, each of which
236 * is *either* just a structured message *or* a structured message plus #Native_handle. (The latter capability,
237 * naturally, is removed, if #Owned_channel lacks a native-handles pipe.) Internally the transport::Channel
238 * pipes are leveraged in such a way as to maximize performance.
239 * - Messages arrive in the same order as they are sent (as determined by the order of send() (et al) calls on the
240 * sender `*this`).
241 * - If a message arrives that has no event handler registered, then it is queued inside `*this`, as explained
242 * above. They are queued, and therefore popped if/when a handler is registered, in the same order as
243 * they arrived.
244 * - Suppose message with sequence # 5 has arrived but had to be queued due to lacking a registered handler.
245 * Suppose message with sequence # 6 has arrived and *does* have a registered handler. Message 6 will
246 * then be emitted to the user; in other words the act of being queued does not preclude the emission of
247 * subsequent messages.
248 * - Thirdly, there are some (mandatory) safety features. These are almost completely hidden from the user in
249 * regular operation. To the extent they are not, it has to do with the *log-in* feature. This is discussed
250 * separately below. Typically one need not worry about it.
251 *
252 * ### How to use it (deep-dive) (log-in excluded) ###
253 * Naturally there are two directions of transmission, sending out-messages and receiving in-messages. About the
254 * former first:
255 *
256 * To transmit an out-message:
257 * - Call create_msg(); this yields a cheaply-`move()`able out-message:
258 * #Msg_out. (See Msg_out doc header for formal public API.) You may also construct this
259 * directly -- even without a struc::Channel in existence at all; create_msg() merely helps by
260 * supplying the serialize/deserialize parameters (a/k/a builder/reader config) for you.
261 * - Fill out its contents: `M->body_root()` is a `Msg_body::Builder*`, where #Msg_body is determined by your
262 * choice of schema (#Msg_body template param); and `Msg_body::Builder` is the capnp-generated
263 * mutating API. For example: `M->body_root()->initCoolRequest().setCoolField(57);`
264 * - sets the message type to `Msg_body::Which::COOL_REQUEST` and initializes a blank `CoolRequest` capnp-`struct`;
265 * - mutates the field `coolField` -- presumably an integer of some kind in this example -- to equal 57.
266 * - Send it: `send(&M)` or `async_request(&M)`. Each is non-blocking and synchronous and cannot would-block.
267 * - If `M` is a response to some in-message `I`, use `send/async_request(&M, I, ...)`. Otherwise use
268 * `send/async_request(&M, nullptr, ...)`.
269 * - If you expect *response* message(s) to `M`, use `async_request(&M, ..., &id, H)`, where:
270 * - Set `&id` to `nullptr` if one expects at most 1 response to `M`; otherwise non-null.
271 * - In the latter case optionally use `undo_expect_responses(id)` to indicate no further responses
272 * to the out-message instance sent by that async_request() call are expected.
273 * - `H` is the handler for the reponse(s); `H(I)` shall be invoked, where `I` is the response in-message.
274 * - Alternatively to async_request(): `sync_request(&M)`. This is similar, but instead of returning it
275 * awaits the response and returns that response once received. Thus your code is simpler: no separate
276 * response handler function, to fire who-knows-when, is involved. Note that by definition such a request is
277 * one-off (exactly 1 response is expected). sync_request() can optionally specify a timeout.
278 * - Also: See async_end_sending() doc header. In short: You should call this when done using `*this`; then destroy
279 * `*this` once the async-handler you passed to async_end_sending() has fired.
280 *
281 * As usual, the incoming direction is somewhat more complex. It is also different from lower-level APIs
282 * such as boost.asio sockets and our various `Blob_sender`s and the like.
283 *
284 * Internally, all in-messages that do arrive on the "wire" are received immediately; each in-message at that point
285 * is then handled in exactly one of the following ways. (Here we do not discuss pipe-hosing errors yet.)
286 * A given in-message `I` is handled thus:
287 * - If `I` is not a response to an earlier out-message `M`:
288 * - If `I` is being expected via an earlier expect_msg() or expect_msgs() call: *Emit* `I` to that user handler.
289 * - Else: queue it inside `*this` silently.
290 * - Else:
291 * - If `I` is being expected via a response-expectation, as registered in async_request() or
292 * sync_request() (see above):
293 * *Emit* `I` to that user handler, or return it via sync_request() synchronously (whichever applies).
294 * - Else: it is a non-pipe hosing error condition. While you should (informally speaking) avoid this, if
295 * it does occur, you can handle it as you see fit. See set_unexpected_response_handler().
296 * See also set_remote_unexpected_response_handler(). Spoiler alert: This condition is emitted on both
297 * sides: locally, indicating an unexpected response arrived; and remotely, indicating that side *issued*
298 * an unexpected response.
299 *
300 * Hence there are exactly 3 ways to register a handler for in-messages.
301 * - Call expect_msg() or expect_msgs() to expect a particular type of *unsolicited* (non-response) message.
302 * expect_msg() indicates up to 1 such message shall be expected; expect_msgs() indicates 0+ such messages,
303 * until undo_expect_msgs().
304 * - If expect_msg() or expect_msgs() is invoked, and matching message(s) are queued inside `*this` (per above)
305 * at that time, `*this` behaves as-if those messages had just arrived. I.e., they are immediately
306 * *emitted*.
307 * - Call async_request() to expect a response to a particular out-message.
308 * - (No handler per se) Call sync_request() to send request and synchronously await one-off response to that
309 * particular out-message.
310 *
311 * Example:
312 * - I am a server, and I expect GET and POST messages. I invoke `expect_msgs(Msg_which_in::GET_REQ, handle_get_req)`
313 * and `expect_msgs(Msg_which::POST_REQ, handle_post_req)`. `handle_get_req(x)` shall be invoked for each
314 * incoming GET_REQ `x` and similarly for the POSTs.
315 * - I am a client, and I issue GET and POST messages. I invoke `async_request(&x, ..., nullptr, handle_get_rsp)`
316 * for a GET and `async_request(&y, ..., nullptr, handle_post_rsp)`, where earlier one did:
317 * - `x = ....create_msg()`; `x->body_root()->initGetReq().set{Url|HostHeader}(...)`;
318 * - `y = ....create_msg()`; `y->body_root()->initPostReq().set{Url|HostHeader|PostBody}(...)`.
319 *
320 * Last but not least: How does one read the contents of an incoming message? Answer: a
321 * user-provided handler shall be of the form: `H(I&&)`, where `I` is a #Msg_in_ptr, a ref-counted handle to a new
322 * in-message. (See Msg_in doc header for the formal public API.) Note the `&&`: it is an rvalue reference
323 * to the `shared_ptr`, rather than a `const &`, in case you'd like to `move()` it somewhere for perf instead of
324 * ref-counting increment/decrement.
325 * - `I->body_root()` is a `const Msg_body::Reader&`, where #Msg_body is as explained earlier, and
326 * `Msg_body::Reader` is the capnp-generated accessor API.
327 * For example: `I->body_root().getCoolRequest().getCoolField()` shall equal 57 on the other end, following
328 * the earlier out-message example.
329 * - In the case of unsolicited messages: `I->body_root().which()` shall equal the #Msg_which_in passed
330 * to expect_msg() or expect_msgs(). Therefore one can perform `I->body_root().getCoolRequest()` without
331 * fear it's not actually a `COOL_REQUEST` (which would otherwise at best yield a capnp exception).
332 * - In the case of response messages: `I->body_root().which()` can be anything (i.e., `*this` will not enforce
333 * anything about it). It is up to you to design that protocol.
334 * - We considered enforcing a #Msg_which_in expectation for responses, to be supplied with
335 * async_request(). However it seemed unnecessarily restrictive.
336 *
337 * ### Thread safety; handler invocation semantics ###
338 * In-message handlers, and all other handlers (including those from start(), set_unexpected_response_handler(),
339 * set_remote_unexpected_response_handler(), async_end_sending()) are invoked from an unspecified background thread
340 * started by `*this`. No 2 such handlers shall be invoked concurrently to each other.
341 *
342 * @note sync_io::Channel starts no background thread. Any handlers are invoked synchronously. This is the
343 * usual dichotomy between an `Async_io_obj` (here, struc::Channel) and its `Sync_io_obj` counterpart
344 * (here, #Sync_io_obj, namely struc::sync_io::Channel).
345 *
346 * Messages are emitted in the order received, except reordered as required by the queueing of not-yet-expected
347 * unsolicited messages (as explained earlier).
348 *
349 * Attention! Regarding general thread safety: A given `*this` features stronger safety than most other APIs:
350 * - **It is safe** to invoke a method concurrently with another method call (to the same or other API)
351 * on the same `*this`.
352 *
353 * You *may* call `*this` APIs directly from any in-message handler or other handler.
354 * Exception: You may *not* invoke sync_request() (or any other `sync_*()` that may be added over time)
355 * from an in-message handler or other handler. Doing so can disrupt the timeliness of delivering
356 * other async results.
357 *
358 * Informal recommendation:
359 * You should off-load most or all handling of in-messages onto your own thread(s) (such as via boost.asio
360 * `post()` or the flow.async infrastructure). For example: suppose your program has some main worker thread U,
361 * implemented as a `flow::async::Single_thread_task_loop U`. Then, e.g.:
362 * - In thread U: `async_request(&M, false, H)`:
363 * sends `M`; async-calls `H(I)` when response `I` to `M` arrives.
364 * - In (unspecified thread): `H(I)` fires. Your `H()` body:
365 * `U.post([I = std::move(I)]() { handle_i(std::move(I)); })`.
366 * - Actual handling of `I` occurs in your `void handle_i(...::Msg_in_ptr&&) { ... }`.
367 * `handle_i(){}` can be written with the assumption execution is back in thread U, same as the async_request()
368 * call that triggered all this (asynchronously).
369 *
370 * This is *not* a requirement. It is entirely conceivable one would want to piggy-back onto our internal
371 * unspecified thread. However please be mindful:
372 * - If your handler code is "heavy," then you may slow down internal transport::Channel and struc::Channel
373 * processing on a number of layers (though, only relevant to `*this`).
374 *
375 * ### Pipe-hosing error semantics ###
376 * The underlying transport::Channel, which every struc::Channel takes over in the first place at construction,
377 * can fail -- encounter a pipe-hosing error. Briefly speaking, a transport::Channel out-pipe can -- depending
378 * on the actual low-level transport involved -- be hosed while the in-pipe(s) remain unaffected; and indeed when
379 * a transport::Channel internally consists of 2 bidirectional pipes, it is even possible for 1 out-pipe to be hosed,
380 * while the other is not. (The same holds of in-pipes.) However, these details strongly depend on the actual
381 * low-level transports involved. To simplify error handling, these details are hidden away and normalized to
382 * the following straightforward behavior.
383 *
384 * As noted before, struc::Channel models a single bidirectional full-duplex pipe of discrete messages.
385 * The out-pipe is controlled simply: call send(), async_request(), or sync_request() to send a message, synchronously,
386 * non-blockingly (if not sync_request()).
387 * The in-pipe takes in all messages as soon as they arrive on the transport::Channel "wire"; they may be queued inside
388 * or immediately (or later) emitted, but this is not relevant to error handling.
389 *
390 * The entire bidirectional pipe is either not-hosed, or it is hosed (forever). A pipe-hosing condition,
391 * indicated by a truthy #Error_code, occurs (if it occurs at all) exactly once. (Note: Receiving the
392 * `transport::Channel`-level graceful-close message -- transport::error::Code::S_RECEIVES_FINISHED_CANNOT_RECEIVE --
393 * is not "special" -- it is also a pipe-hosing error.) When it occurs, it is immediately emitted to the
394 * `*this` user. There are 2 possible ways this can occur (again: only 1 of these can occur per `*this`):
395 * - Triggered by send(), async_request(), or sync_request(): Then that method shall emit the truthy #Error_code
396 * directly/synchronously via out-arg or exception.
397 * - Triggered spuriously in the background via incoming-direction processing: Then it shall be emitted via
398 * the on-error handler registered by the user. (If this occurs during sync_request(), then it shall be
399 * emitted via sync_request(), not via on-error handler.)
400 * - To receive any in-messages, you must call start() which takes the mandatory on-error handler as arg.
401 * Until then, any lower-level in-traffic shall be safely queued inside the #Owned_channel. Still, it is
402 * best to call start() early, to avoid RAM backup and such (informally speaking).
403 *
404 * After the pipe-hosing error is emitted, via exactly 1 of the above methods, further API calls on `*this` shall
405 * no-op and return `false` or a null value.
406 *
407 * Lastly, there is async_end_sending(). See its doc header. In short: Although the pipe is hosed at the
408 * struc::Channel level once a pipe-hosing #Error_code is emitted, it is still a good idea to execute
409 * async_end_sending() and only destroy `*this` once the async-handler passed to it has fired. (Though, if
410 * send() (et al) emitted the truthy #Error_code, there is no point: async_end_sending() will no-op.)
411 *
412 * Recap: Informal recommendations:
413 * - Recall that we recommend any event handling, from within an in-message handler or any other handler,
414 * be immediately off-loaded onto a user worker thread. (In particular you may not call `*this` APIs from these
415 * handlers.)
416 * - When such a user-thread handler, or other user-thread function, detects the emitted truthy #Error_code
417 * (from on-error handler, or via send(), async_request(), or sync_request() emitting it synchronously), mark
418 * `*this`, somehow, as hosed (e.g., via a flag or saved truthy #Error_code).
419 * - When about to do work on `*this`, check that flag or mark, so as to be aware `*this` is hosed and shutting
420 * down -- and no-op instead of trying to call whatever API. Though, it may be viable to simply count on
421 * the fact `*this` APIs shall all (except async_end_sending()) no-op and return `false` or null in that case
422 * anyway.
423 * - Lastly, recommend then calling `async_end_sending(F)`; and in `F()` destroy `*this` finally.
424 * - If you have 1 thread (e.g., via `flow::async::Single_thread_task_loop`; or equivalently one thread with
425 * `boost::asio::io_context::run()` executing) dedicated to processing `*this`,
426 * then this is particularly straightforward; no need to synchronize on `*this` and/or the `*this`-is-hosed
427 * flag/mark.
428 *
429 * @note sync_io::Channel only acts when you call into its API. Hence in its case everything is straightforwardly
430 * sequential: The first operation to yield an error can cease to operate on `*this` (other than,
431 * potentially, async_end_sending()). Again: this is the usual dichotomy between an
432 * `Async_io_obj` and its `Sync_io_obj` counterpart.
433 *
434 * ### Lifecycle of an out-message ###
435 * A #Msg_out represents the message payload; *and* separately/independently
436 * it also represents a particular `send()`t (past/present/future) *instance* of that payload.
437 * Regardless of what it represents, it is a data structure instance -- nothing more. Its outer shell sits
438 * wherever it is instantiated; typically either on the stack or in regular heap. It allocates space for the
439 * the serialization mutated by its `.body_root()` capnp `Builder` based on the #Builder_config type
440 * chosen at compile-time. (Also included, for performance purposes, is an internally-used *metadata header*
441 * which is relevant *only* during send() and equivalent parts of async_request(), sync_request(). It is for
442 * this reason, and this reason only, that send(), async_request(), and sync_request() take a `Msg_out*`
443 * as opposed to a `const Msg_out&`; the payload is not touched at all, but the internally-used metadata is
444 * indeed set there before being transmitted via IPC-transport of choice.)
445 *
446 * If you use create_msg(), this light-weight object #Builder_config -- essentially a few scalars -- is
447 * supplied to the `Msg_out` ctor for you. Otherwise you have to construct one directly and pass-in a
448 * `Builder_config` or `Builder` of the same type.
449 *
450 * This builder *engine* determines where this internal bulk -- the serialization backing --
451 * lives. For the rest of this discussion let us assume it is
452 * `shm::classic::Builder::Config` (or SHM-jemalloc equivalent); meaning the engine is zero-copy-enabling,
453 * for high perf and other benefits, and therefore allocates backing buffer(s) in SHM.
454 *
455 * #Msg_out, therefore, is similar to a container backed by a SHM-allocating allocator. It continues to take RAM
456 * resources, and the serialization continues to be accessible, on all ends until *both* of the following occur:
457 * - The #Msg_out is destroyed.
458 * - Every #Msg_in_ptr obtained in *any* opposing struc::Channel to have received it (via expect_msg(),
459 * expect_msgs(), and response-accepting handlers), after it had been send()ed (et al) there, is destroyed --
460 * along with all derived `Msg_in_ptr`s. (#Msg_in_ptr is `shared_ptr<Msg_in>`.)
461 *
462 * Suppose you create a #Msg_out and send() it. At this point there is "virtual" #Msg_in in existence:
463 * the underlying serialization will not be destroyed yet, even if #Msg_out is. Normally the opposing
464 * struc::Channel will be used to receive the message, in a real #Msg_in, via an aforementioned in-message
465 * handler. If this does not occur, the message leaks until the containing SHM arena is cleaned-up.
466 * (If you use ipc::session to manage SHM arena(s), which is the normal scenario, then ipc::session will take
467 * care of this for you. See ipc::session documentation, starting with the namespace doc header.)
468 *
469 * Suppose in your application, at this point, you will never again write to the #Msg_out further (modify it).
470 * You may freely send() the same #Msg_out again. You may send it through a different struc::Channel or
471 * the same one. You may do so at will, though not concurrently: send() modifies the metadata header. You may
472 * receive it, obviously, at will as well. Note, however, that #Msg_in is not fully symmetrical to #Msg_out: It
473 * represents not the container but rather the in-message *instance*: that particular time you received a message,
474 * with a handle to the payload controlled by the original #Msg_out. So for one #Msg_out, there may be 2+ `Msg_in`s
475 * in existence, across various processes to have received it. If one process has received it 2x, then there are
476 * potentially 2 `Msg_in`s in existence in that process. The original #Msg_out and each #Msg_in each contributes 1
477 * to the cross-process ref-count.
478 *
479 * Lastly suppose all the same is true, except that you would like to continue modifying the #Msg_out post-`send()`.
480 * This is allowed. However, this must be done with care. Of course there is the matter of
481 * synchronization as usual: Behavior is undefined if one reads a message while the #Msg_out is being mutated
482 * in the original process. While it is conceivable one could use an outside synchronization mechanism for this --
483 * an interprocess mutex for example -- informally we expect the best way is to use your struc::Channel
484 * messaging protocol. In particular it make sense to avoid any modification of a #Msg_out until one has received
485 * a response to any async_request() of it, with the guarantee that the module receiving that *particular* #Msg_in
486 * in the opposing process shall not further read its contents after issuing the async_request() for that response.
487 *
488 * Lastly suppose #Builder_config is *not* SHM-based; e.g. Heap_fixed_builder::Config.
489 * In that case, simply, #Msg_out is the original message container backed by an in-local-heap serialization;
490 * and every #Msg_in emitted by a receive-handler is a *copy*, also backed by an in-local-to-receiver-heap
491 * serialization. While #Msg_out can certainly be `send()`t repeatedly, and modified in-between,
492 * this simply has no effect on any resulting `Msg_in`s, as they are copies.
493 *
494 * ### Log-in ###
495 * Internally, each out-message is supplied by `*this` with a *session token*. In regular operation, every
496 * out-message's session token is the same value through the lifetime of a `*this`. Every in-message must also
497 * contain that same session token value. If an in-message arrives with an unexpected session token value, it
498 * is a pipe-hosing error. (The rationale for this is beyond the scope of discussion here; it is a safety feature.)
499 * This all happens internally.
500 *
501 * In regular operation, at struc::Channel construction time, the constant session token value must be supplied
502 * as a ctor argument. This session token must not be nil. While, formally speaking, any non-nil value will do --
503 * provided the same one is given to the struc::Channel on the other end -- correct use (in terms of safety)
504 * is to provide a properly generated unique token -- on both sides. Where to get this value, though? Answer:
505 *
506 * Before constructing any regular-operation `struc::Channel`s, in a given session between two processes A and B,
507 * one shall first construct *one* special-purpose transport::Channel, called the *session master channel*, and wrap it
508 * in a special-purpose struc::Channel on each side. This is the 2nd ctor form, the one without a `session_token`
509 * arg; one side must pass the value `is_server = true`; the other conversely `is_server = false`.
510 *
511 * This special channel is not yet in logged-in phase; it is in logging-in-as-client phase on 1 side and
512 * logging-in-as-server phase on the other side. The two `struc::Channel`s must then undergo a rigid, but short,
513 * sequence of steps to get to the logged-in phase (at which point the session master channel enters its own
514 * regular-operation phase; the purpose of that channel from that point on is unspecified here -- but read on).
515 *
516 * Namely: the client peer must create a message as normal (create_msg() or #Msg_out construction),
517 * fill out the returned out-message as desired, and async_request() it.
518 * The server peer conversely must invoke expect_log_in_request(), exactly once, handle the incoming request
519 * by filling out a response out-message, and send() that (response-supplying form is mandatory).
520 * - The server peer `*this` enters logged-in (regular-operation) phase upon `send()`ing the log-in response.
521 * Did you invoke send() successfully? Congrats: you're in regular-operation.
522 * - The client peer `*this` enters logged-in (regular-operation) phase upon receiving that log-in response
523 * Did your handler for the response get fired? Congrats: you're in regular-operation.
524 *
525 * While this mechanism is fairly general, and hopefully reasonably easy to operate, in practice most users will
526 * not need to ever do so themselves. Instead: On the server side, establish a `Server_session` (see
527 * session::Session_server). On the client side, establish a `Client_session`. They will operate an adequate
528 * session master channel internally. `Server_session` and `Client_session` shall then each reach their PEER state,
529 * at which point they each satisfy the formal session::Session concept (see session::Session doc header). Now,
530 * session::Session::session_token() shall return the uniquely generated session token. This value shall be passed to
531 * all subsequent `struc::Channel`s in the session, into their ctors (possibly via internal delegation).
532 * These subsequent `struc::Channel`s do not need a log-in phase and are immediately in regular-operation.
533 *
534 * Therefore, the only time a user must worry about session tokens at all is when creating a regular-operation
535 * struc::Channel, and even then only if no tag-form struc::Channel ctor is applicable. In that case:
536 * - Access session::Session::session_token().
537 * - Pass the result into struc::Channel ctor on each side.
538 *
539 * Incidentally, `Session` (as implemented by `Server_session`, `Client_session`, and variants) can also easily open new
540 * `Channel`s. Internally they do so by leveraging various features of struc::Channel as applied to the *one*
541 * (per process A-B session) session master channel. Each `Channel` obtained this way can then be fed (upgraded) into
542 * a new struc::Channel, if indeed structured messaging is desired for that transport::Channel. The information in
543 * this paragraph is, formally speaking, outside the purview of struc::Channel API, but I mention it here
544 * for context. For more detail see session::Session (and its impls session::Server_session, session::Client_session
545 * and variants).

550 * the user to explicitly wrap this class in a `unique_ptr`. For example, imagine
551 * a `Session::Structured_channel Session::structured_channel_upgrade(Owned_channel_t&& channel, ...)` that

557 * ### Implementation overview (threads U, W) ###
558 * struc::Channel sits atop several layers of concepts and objects implementing them: from the raw
559 * transports (transport::asio_local_stream_socket namespace, Persistent_mq_handle concept and impls); to
560 * the component Blob_sender, Blob_receiver, Native_handle_sender, Native_handle_receiver impls; to the
561 * transport::Channel (#Owned_channel) bundling them together; and lastly -- and most immediately relevantly --
562 * to the struc::sync_io::Channel core. (The latter is aliased as struc::Channel::Sync_io_obj.)
563 *
564 * In implementing struc::Channel, then, we already rely on much logic that is abstracted-away; we only
565 * need to "decorate" their work by, essentially, some pre- and post-processing -- to provide, specifically,
566 * the features explicitly outlined above publicly ("What does struc::Channel add, broadly speaking, that
567 * transport::Channel does not already have?").
568 *
569 * Perf, in particular low latency, is essential for this work-horse class template. For performance -- or perhaps
570 * more accurately for most direct/deterministic flow control/thread structure --
571 * we use `sync_io` objects throughout; our #Sync_io_obj core (`m_sync_io`) and the #Owned_channel subsumed by it
572 * create no handler-invoking threads. We, however, are ourselves an async-I/O-pattern object, and therefore
573 * essentially by definition of how that pattern works we start a worker thread W in which to (1) perform all
574 * asynchronously-delayed (i.e., contingent on event async-waits) work of all the aforementioned layers below
575 * us (helpfully encapsulated in #Sync_io_obj `m_sync_io`); and (2) invoke user-supplied completion handlers.
576 *
577 * This thread W (`m_worker`) is the only async-worker thread. Everything else is (to reiterate) `sync_io`-pattern.
578 *
579 * Thread U is (as per usual) the term for the user's calling thread (as usual they may of course use 2+ threads if
580 * desired; but via #m_mutex and #m_sync_op_mutex we essentially make all
581 * such calls non-concurrent... so as usual we call it thread U,
582 * as if it is one thread). We do allow transmission APIs to be invoked from within completion handlers of our
583 * own other transmission APIs (e.g., `send()` or `expect_msg()` directly within `expect_msg()` handler).
584 * (sync_request(), being blocking, is the exception.)
585 *
586 * Since there are 2+ threads, U and W, with async-processing in the latter potentially occurring concurrently with
587 * API calls in the former -- and with our explicitly allowing concurrent calls on the same `*this` --
588 * there's a big fat mutex `m_mutex` locked around most code. That said thread contention
589 * is unlikely in most use cases, unless the user causes it in their own code. (Details omitted here.)
590 *
591 * ### Implementation ###
592 * Unlike in the past, when `*this` template was monolithic, now it is split into the core functionality
593 * in sync_io::Channel (#Sync_io_obj `m_sync_io`) and the (relatively limited) logic necessary on top
594 * of this to adapt that into the async-I/O pattern, wherein user handlers fire from thread W, and
595 * any necessary internal async ops occur automatically in thread W without user participation.
596 *
597 * Therefore the really complicated stuff is abstracted away in the #Sync_io_obj. The adapting logic is
598 * simple enough to be understandable by reading the code and inline comments, especially on the data members.
599 *

1126 * In the synchronous/non-blocking manner of Blob_sender::send_blob() or Native_handle_sender::send_native_handle()
1127 * sends the given message to the opposing peer, as a *notification* (without expecting response).
1128 * The message may contain a #Native_handle.
1129 *
1130 * send() shall no-op (and return `false`) if one of the following is true.
1131 * - Log-in phase, as a client, has not yet been completed.
1132 * Use async_request() or sync_request() instead, as a log-in response (to the log-in request `msg`) is required.
1133 * - Log-in phase, as a server, has not yet been completed, and `originating_msg_or_null` is null.
1134 * Use non-null instead.
1135 *
1136 * Further documentation of behavior shall assume this no-op condition is not the case.
1137 *
1138 * @note You may use this in logged-in phase; or in logging-in phase but only as a server.
1139 *
1140 * @see async_request() which sends a *request* (same thing as here but *with* expecting response(s));
1141 * or sync_request(), a variation.
1142 * @see async_end_sending() for properly flushing out-messages near the end of `*this` lifetime.
1143 *
1144 * ### Send mechanics (applies also to async_request() and sync_request()) ###
1145 * The purpose of this important method is hopefully clear. That it's, essentially, a wrapper for
1146 * one of the aforementioned transport::Channel methods is also probably obvious. However its error-reporting
1147 * semantics are somewhat different from transport::Channel and the `Blob_sender`/`Native_handle_sender` concept(s) it
1148 * implements. Long story short, it reports errors similarly to the core Blob_sender::send_blob() or
1149 * Native_handle_sender::send_native_handle() with the following differences:
1150 * - If `msg` contains a #Native_handle, but #Owned_channel has no native-handles pipe: no-op, return `false`.
1151 * - If called after async_end_sending(): no-op, return `false`.
1152 * - If called after a background receive or preceding send() / async_request() / sync_request() /
1153 * remote_peer_process_liveness_check() / etc. emitted error: no-op, return `false`.
1154 * - Otherwise it'll attempt the core `send_*()` and return `true`.
1155 * - If that is successful, send() is successful.
1156 * - If not -- if it emitted error E -- then send() emits error E.
1157 * - And `*this` shall be considered hosed for any subsequent transmission.
1158 *
1159 * ### In more detail (applies also to async_request() and sync_request()) ###
1160 * Here is what the method does, ignoring logged-in phase checks and potential change inside.
1161 * -# If `msg` contains a #Native_handle, but Channel::S_HAS_BLOB_PIPE_ONLY is `true`, then returns `false`
1162 * and otherwise no-ops. This is a misuse of the chosen #Owned_channel as configured: a handles pipe
1163 * is required to send handles. Else:
1164 * -# Checks whether the pipe is hosed by a preceding error (which would have been reported via the
1165 * on-error handler registered by user on `*this`; or by the previous `send()`/etc. synchronously, if that's what
1166 * discovered the pipe is hosed instead). If so returns `false` and otherwise no-ops. Else:
1167 * (Note the previously discovered/emitted #Error_code is not re-emitted this time.) Else:
1168 * -# If you've called async_end_sending() already: Returns `false` and otherwise no-ops. Else:
1169 * -# Invokes either `Owned_channel::send_blob()` or `Owned_channel::send_native_handle()` 1+ times.
1170 * This determines the possible #Error_code emitted; see doc header for the chosen
1171 * sender concept impls for #Owned_channel. However:
1172 * - Note: transport::error::Code::S_SENDS_FINISHED_CANNOT_SEND shall not be emitted; instead send() will return
1173 * `false` as noted above.
1174 * - Note: Since we are in charge, internally, of invoking the low-level `send_*()` method, we shall ensure
1175 * transport::error::Code::S_INVALID_ARGUMENT is not a possibility.
1176 * - Serialization errors are also possible (can be thought of similarly to `send_*()` failing).
1177 * -# If such a call emits an error, the present method shall forward (emit) that error (but return `true`).
1178 * Moreover the pipe shall be considered hosed:
1179 * - The triggering #Error_code will *not* be emitted to user via on-error handler registered on `*this`,
1180 * because it will be emitted to the caller synchronously here by send().
1181 * - No further on-in-message user handlers (such as from expect_msg()) shall fire.
1182 * - Any future transmission API calls will no-op indicating this in various ways:
1183 * - expect_msg(), expect_msgs(), `set_*_handler()` shall return `false`;
1184 * - send() shall return `false` (as noted above).
1185 * - (create_msg() is unaffected: it still yields a valid out-message -- which one cannot then send.)
1186 * -# Otherwise, cool. It shall return `true` and not emit a truthy #Error_code.
1187 *
1188 * ### Why is `msg` a pointer-to-mutable rather than a const-ref? ###
1189 * We forego refs-to-mutable by Flow style convention. So the question reduces to: why is the `Msg_out` mutable,
1190 * if we are merely sending it? The answer is due to the nature of Msg_out. See its doc header; but in short:
1191 * A Msg_out, for perf reasons, owns the user's actual message payload *and* the metadata (mdt) internally-describing
1192 * the *last time that it was sent*. (E.g., internally, it stores a message ID and potentially a message ID of
1193 * `*originating_msg_or_null`.) send() (also async_request() and sync_request()) treats the message-payload part
1194 * as `const` but fills out the mdt part; so in total the `Msg_out` is modified and cannot be `const`. Consequently
1195 * do not send a given `Msg_out` concurrently, even via different `Channel`s.
1196 *
1197 * @param msg
1198 * The out-message, which may or may not store a #Native_handle. The mdt-part of `*msg` (and only it) may
1199 * be modified. (See above discussion.)
1200 * @param originating_msg_or_null
1201 * Pointer to the in-message to which this is responding. If the in-message is from another
1202 * struc::Channel, behavior is undefined. Set to null if this message is unsolicited (not a response).
1203 * @param err_code
1204 * See `flow::Error_code` docs for error reporting semantics. #Error_code generated:
1205 * See above. Not `INVALID_ARGUMENT`, not `SENDS_FINISHED_CANNOT_SEND`.
1206 * @return `false` if no-op-ing due to one of the following conditions:
1207 * invoked in logging-in phase as client; invoked in logging-in phase as server but
1208 * `originating_msg_or_null` is null; `msg` with-handle, but #Owned_channel has no handles pipe;
1209 * an #Error_code was previously emitted via on-error handler or send() / async_request() / sync_request() /
1210 * remote_peer_process_liveness_check() / etc.; async_end_sending() has already been called.
1211 * `true` otherwise (but some #Error_code may be emitted due to send failure).
1212 */
1213 bool send(Msg_out* msg, const Msg_in* originating_msg_or_null = nullptr, Error_code* err_code = nullptr);

1292 /**
1293 * A blocking (subject to timeout) operation that first acts as-if async_request() was invoked
1294 * in one-off-request mode; then awaits the one-off response and synchronously returns that response
1295 * (or pipe-hosing error, or timeout error).
1296 *
1297 * Unlike send() and async_request(), you *may not* invoke this method directly from an in-message handler or other
1298 * handler. Doing so can disrupt the timeliness of delivering async results and formally results in undefined
1299 * behavior.
1300 *
1301 * sync_request() shall no-op (and return null without a truthy `Error_code` emitted) if:
1302 * - log-in phase has not yet been completed.
1303 *
1304 * Further documentation of behavior (except "Thread safety, concurrency") shall assume this no-op condition is
1305 * not the case.
1306 *
1307 * ### Thread safety, concurrency ###
1308 * Per class doc header: yes, you can invoke `this->sync_request()` concurrently to all other `*this` methods
1309 * including sync_request() itself. However beware that if you invoke 2 `sync_request()`s concurrently 1
1310 * will not proceed until the other finishes, even if it must block. (By setting up handlers appropriately
1311 * ahead of sync_request() invocations you can ensure in local IPC that these calls will be non-blocking.)
1312 *
1313 * Furthermore, during the potentially-blocking portion of sync_request(), wherein it awaits the response or timeout,
1314 * other API calls shall execute non-blockingly rather than potentially-block waiting for sync_request() to return.
1315 * For example, a send() or async_request() will execute immediately.
1316 *
1317 * @warning Cross-process deadlock danger!
1318 * Sync-requests in opposite directions: If your protocol/impl has *both* sides issue `sync_request()`s, do
1319 * not invoke sync_request() from the thread that services the opposing side's requests (i.e., the thread
1320 * onto which your in-message handler defers the work of responding). Otherwise, should both sides
1321 * sync_request() at about the same time, each one's thread is blocked awaiting a response that
1322 * only the other one's blocked thread can send; both wait until both time out. `*this` cannot
1323 * prevent this: it does let the responding send() through while a sync_request() is blocking, as
1324 * noted above, but only if something is free to invoke it. Either sync_request() from a thread
1325 * that never responds to the peer, or respond from a thread that never `sync_request()`s, or use
1326 * async_request() after all. Silver lining: Observe for the deadlock danger to manifest, *each*
1327 * side has to be using one thread for both responding and sync-requesting; hence to avoid the problem,
1328 * only *one* of the sides has to be changed.
1329 *
1330 * @todo Improve ipc::transport::struc::Channel::sync_request(), so that 2 such calls on the same `Channel`
1331 * can execute without one having to fully block the other. Note this may be seen as a *breaking change* of sorts
1332 * for the purposes of release notes (even though it would presumably be seen as an improvement).
1333 *
1334 * ### Send mechanics ###
1335 * As the first step this method invokes essentially async_request(). Hence the following notes apply as they do
1336 * for async_request():
1337 * Long story short, it reports errors similarly to the core Blob_sender::send_blob() or
1338 * Native_handle_sender::send_native_handle() with the following differences:
1339 * - If `msg` contains a #Native_handle, but #Owned_channel has no native-handles pipe: no-op, return null
1340 * with falsy `Error_code`.
1341 * - If called after async_end_sending(): no-op, return null with falsy `Error_code`.
1342 * - If called after a background receive or preceding send() / async_request() / sync_request()
1343 * emitted error: no-op, return null with falsy `Error_code`.
1344 * - Otherwise it'll attempt the core `send_*()`.
1345 * - If that yields a (pipe-hosing) error, then: return null with truthy `Error_code` emitted.
1346 * - And `*this` shall be considered hosed for any subsequent transmission.
1347 * - Otherwise the method moves on to the wait phase.
1348 *
1349 * The result of the wait phase shall be one of:
1350 * - non-null response returned, no truthy `Error_code` emitted (success);
1351 * - null response returned, truthy `Error_code` -- that is not transport::error::Code::S_TIMEOUT -- emitted
1352 * (pipe hosed);
1353 * - null response returned, `Error_code == S_TIMEOUT` (pipe is fine, but the wait timed out) emitted.
1354 *
1355 * ### Subtlety about error::Code::S_SYNC_OP_INTERRUPTED_BY_CONCURRENT_NB_ERROR ###
1356 * Suppose this method emits an error E that is neither `TIMEOUT` nor `SYNC_OP_INTERRUPTED_BY_CONCURRENT_NB_ERROR`.
1357 * Then, regardless of whether this was immediate or occurring sometime during the wait pre-timeout:
1358 * - `*this` is hosed;
1359 * - E is emitted, the first and only time as usual, by us synchronously.
1360 *
1361 * Now suppose E is indeed error::Code::S_SYNC_OP_INTERRUPTED_BY_CONCURRENT_NB_ERROR. Then:
1362 * - `*this` is hosed (so: same as above); but
1363 * - the true channel-hosing error E2 was actually just sync-emitted by a concurrent non-blocking method
1364 * (send(), async_request(), remote_peer_process_liveness_check() as of this writing); and
1365 * - E indicates that that is what happened.
1366 *
1367 * Informally: Usually this should not mean much to you; any code that first sees `*this` emit an error should
1368 * take measures to cease use of `*this` ASAP; and indeed `*this` shall not perform any useful role in any case.
1369 * Formally we did want you to be aware that the general rule, wherein the channel-hosing original error is
1370 * always emitted at most once, we continue to follow.
1371 *
1372 * As for `TIMEOUT`: it does *not* imply the channel is hosed; only that we didn't get the desired result of
1373 * a channel-hosing condition in time.
1374 *
1375 * ### Late-response semantics ###
1376 * If the response, or pipe-hosing error, occurs during this method's wait, then hopefully everything is clear.
1377 * Now suppose it does time out and hence emits `Error_code` transport::error::Code::S_TIMEOUT.
1378 * In the background `*this` continues to await the one-off response. (Moreover it is not possible to
1379 * "un-expect" it or expect a response some other way; as response expectation can only be specified
1380 * at async_request() or sync_request() time, and you've already done the latter for that out-message, and a one-off
1381 * request expectation by convention cannot be undone as of this writing.)
1382 *
1383 * If the response (after timeout) never arrives, there's nothing further to discuss.
1384 *
1385 * Now suppose it does arrive at some point (after the timeout). It is dropped: a WARNING is logged, and
1386 * stat::Channel_sync_req_stats::m_late_responses is incremented; but no handler fires locally, and the opposing
1387 * peer is not informed. In particular it is *not* treated as an unexpected response
1388 * (see set_unexpected_response_handler()), since formally it is still expected.
1389 *
1390 * @todo Consider treating a response to a timed-out struc::Channel::sync_request() as an unexpected response:
1391 * firing the set_unexpected_response_handler() handler locally (perhaps with an added flag indicating
1392 * expected-but-timed-out) and informing the opposing peer, so that its set_remote_unexpected_response_handler()
1393 * handler fires. As of this writing such a late response is simply dropped.

1395 * @param msg
1396 * See async_request().
1397 * @param originating_msg_or_null
1398 * See async_request().
1399 * @param timeout
1400 * If no appropriate response to `msg` occurs, nor does a pipe-hosing error, before this time elapses
1401 * sync_request() shall emit transport::error::Code::S_TIMEOUT. Note that the latter does *not* indicate
1402 * the pipe has been hosed. To disable timeout please use the special value
1403 * `util::Fine_duration::max()`.
1404 * @param err_code
1405 * See `flow::Error_code` docs for error reporting semantics. #Error_code generated:
1406 * See async_request().
1407 * If the initial non-blocking send succeeds then other #Error_code possibilities
1408 * include:
1409 * Any pipe-hosing error that might be otherwise emitted outside a `sync_*()` due to in-traffic;
1410 * error::Code::S_SYNC_OP_INTERRUPTED_BY_CONCURRENT_NB_ERROR; and
1411 * transport::error::Code::S_TIMEOUT. Note that the latter does *not* indicate the pipe has
1412 * been hosed.
1413 * @return Non-null response message on success within timeout; otherwise null.
1414 * If null, emitted `S_TIMEOUT` indicates non-fatal timeout; emitted other truthy `Error_code` indicates

1508 /**
1509 * Operating at the unstructured layer, executes a graceful-close send by forwarding to the async
1510 * transport::Channel::async_end_sending() on the owned #Owned_channel. Reminder: Assuming not called
1511 * after async_end_sending() again: it queues a graceful-close after any other messages sent previously;
1512 * and executes `on_done_func(E)` once that graceful-close is actually sent into the low-level transport
1513 * (then `E` is falsy), or a transport error is encountered at any point, including in the past (then `E`
1514 * is truthy). Because the owned channel's lifetime is equal to that of `*this`, if `on_done_func()` has
1515 * not executed when `*this` dtor runs, it will be executed at that time with the usual
1516 * transport::error::Code::S_OBJECT_SHUTDOWN_ABORTED_COMPLETION_HANDLER.
1517 *
1518 * `on_done_func()` shall, as usual, execute from an unspecified thread that is not among the user calling thread(s);
1519 * and it shall not execute concurrently to any other handler invoked by `*this`.
1520 *
1521 * Formally -- that is all it does, period. Informally it is important to understand the relationship between
1522 * this call and the rest of the API which operates at the structured layer, particularly insofar as it relates
1523 * to the error semantics on that layer. (Please read the class doc header first.)
1524 *
1525 * ### Why and when to use this ###
1526 * The short answer as to when and how to use it: While optional, the best practice is: If you are done using
1527 * the channel (for any reason, whether due to error -- as reported via the error handler -- but especially
1528 * *without* any error), you should call `async_end_sending(F)`, asynchronously wait for `F()` to execute, and in
1529 * or after `F()` destroy `*this` to free resources.
1530 *
1531 * The long answer which hopefully explains the short answer is as follows. It's long, but the short answer is
1532 * sufficient arguably. So read if curious.
1533 *
1534 * Let us first consider the case where no `*this` error has occurred so far, meaning the `start()`-passed error
1535 * handler has not been invoked, and you no longer need the channel. The immediate thought might be, simply,
1536 * this means a graceful-close is in order as a matter of decent behavior, which is fair enough; although it
1537 * would not be wrong to implement your own application-layer message exchange for this (by adding these into
1538 * your #Msg_body capnp schema and sending it like any other message). However that is *not*, I (ygoldfel)
1539 * contend, the main reason `async_end_sending(F)` is a good idea in this context. That real reason: send() (et al),
1540 * externally, behaves as-if it is both synchronous and non-blocking yet cannot yield a would-block condition.
1541 * However, per Native_handle_sender and Blob_sender concept model docs, `send*()` actually may (though this should be
1542 * rare in practice) be internally asynchronous, in that it may encounter a would-block low-level transport
1543 * condition (e.g., MQ full, or local-stream-socket would-block), save a copy of the payload, and only succeed in
1544 * passing it to the out-wire later. `async_end_sending(F)` can and should be viewed as the async *out-flush*: it
1545 * ensures all the queued sends have truly succeeded -- or a transport error triggered -- and only *then* executes
1546 * `F()` asynchronously. Hence by waiting until `F()` before destroying `*this` you will have ensured that
1547 * all those care-free synchronous non-blocking sends have truly gone out; therefore `*this` can be destroyed
1548 * without accidentally cutting off the end of the conversation.
1549 *
1550 * Next let's talk about the error cases. There are roughly 2 as of this writing. One, a "soft" non-channel-hosing
1551 * situation can occur, namely information about a local or remote application-protocol error might trigger
1552 * a handler like those set by set_unexpected_response_handler() and set_remote_unexpected_response_handler().
1553 * While this may well indicate a serious problem to the user, `*this` does not consider it that way. It is up
1554 * to the user to decide what to do when such a "soft" handler executes. They could do nothing: conceivably they
1555 * coded in a loose way and consider this not an issue. Or they could consider this worth ending the conversation.
1556 * In that case, the situation is not *too* different from the non-error case discussed above. Want to end `*this`?
1557 * Flush any sends via `async_end_sending(F)`, then after `F()` destroy `*this`. At least this features less
1558 * entropy and is better, or at least not worse, than abruptly destroying the transport::Channel peer (and possibly
1559 * whole channel).
1560 *
1561 * Lastly: Two, an actual fatal error may occur. This is where there is some subtlety, due to the subtle difference
1562 * between the unstructured layer (#Owned_channel operation) and structured layer (the protocol in struc::Channel
1563 * on top of that). Suppose a channel-hosing error occurs: the `start()`-passed error handler *has* been invoked; by
1564 * definition this means `*this` can transmit no more *structured* messages in either direction; and in fact all
1565 * further APIs, with the exception of async_end_sending(), will return `false` (or similar) and no-op. However:
1566 * a channel-hosing error is (this is the subtlety!) one of 2 rough types.
1567 * -# It might be an unstructured-layer error: the #Owned_channel was trying to send or receive some blob or handle,
1568 * on behalf of `*this` internal code, and it encountered a pipe-hosing error E. E was then immediately
1569 * emitted by `*this` via the `start()`-passed error handler. Most public APIs from that point will no-op
1570 * indicating prior pipe-hosing error.
1571 * -# It might be a structured-layer error: that is the #Owned_channel is transmitting stuff fine still, but
1572 * the logical contents of what has been received is corrupted or unexpected -- maybe the other side misbehaved,
1573 * or there's a bug somewhere, maybe auth failed for some reason. Blobs and handles could continue to be sent,
1574 * but `*this` considers that bad, because the logical consistency of its world cannot be guaranteed.
1575 * In this case `*this` internally generates an appropriate E (for example
1576 * error::Code::S_STRUCT_CHANNEL_INTERNAL_PROTOCOL_BAD_AUTH) and emits it via the `start()`-passed error handler.
1577 * Most public APIs from that point will no-op indicating prior pipe-hosing error.
1578 *
1579 * Type 1 is more straightforward to think about. If a prior send emitted E due to #Owned_channel layer error E,
1580 * then async_end_sending() will simply emit E as well. If a prior receive emitted E similarly, then
1581 * async_end_sending() may re-emit E as well or not; for Native_socket_stream (wherein internally there's a single
1582 * local-socket connection for both directions despite being full-duplex -- an error in one direction hoses the
1583 * other direction) yes; for the MQs (wherein the 2 pipes are fully decoupled) no. That's not all that
1584 * straightforward already.
1585 *
1586 * Type 2 is even less straightforward. In this case #Owned_channel is fine: so async_end_sending() will yield a
1587 * successful E most likely -- but meanwhile `*this` is generally behaving as if it's hosed; and indeed it is -- just
1588 * at the higher (structured) layer!
1589 *
1590 * The point of all this: It is pointless to worry about how async_end_sending()'s emitted #Error_code relates to
1591 * what was emitted to the `start()`-passed error handler. It may be the same thing; it may be different; and it may
1592 * well even be a falsy (success) #Error_code! `async_end_sending(F)` -- again -- accomplishes a lower-level task:
1593 * it waits until any unsent messages are flushed out and then informs user via `F()`; and if this is at any stage
1594 * impossible (including immediately, due to prior error) then it indicates it right then via `F(E)` as well.
1595 * *They operate at different layers, even though their error may overlap depending on the situation.*
1596 * Hence, you should indeed invoke `async_end_sending(F)` from or after the error handler is invoked, then destroy
1597 * `*this` after `F()`.
1598 * - If #Owned_channel out-pipe is hosed anyway, this will simply get to `*this` destruction stage immediately,
1599 * which is fine: it's what one would do if they decide to not mess with async_end_sending() at all.
1600 * - If #Owned_channel out-pipe is fine (despite something else -- possibly in-pipe, possibly structured protocol --
1601 * being not-at-all-fine), this will in civilized fashion flush anything that might still be pending for whatever
1602 * reason -- and gracefully inform the other side that, at any rate, this peer does not want to talk anymore.
1603 * This reduces entropy; and at worst does not help anything but does not hurt.
1604 *

1854 * ### Rationale/purpose ###
1855 * This is intended to be invoked as soon as it is certain (1) `*this` is hosed, as well as (2) we are about to

1857 * Recall that there are two mutually exclusive, at-most-once-per-`*this` occurring ways of emitting channel-hosing
1858 * to the user: via `on_err_func()` as passed to start() (if error occurs asynchronously in thread W #m_worker),

1868 * Plus sync_io::Channel core, #m_sync_io, itself owns a transport::Channel (unstructured channel, with 1-2
1869 * IPC full-duplex pipes, such as `Native_socket_stream` et al) which also has lots of stats; accessible
1870 * via `m_sync_io.owned_channel().{blob|native_handle}_{send|receive}_stats()`. Why not print those? Answer:
1871 * Short version: We could, but it would duplicate a ton of stuff that'd be logged already, already at the
1872 * right time(s). Long version (skippable but may reinforce understanding of the general design of
1873 * struc::Channel versus struc::sync_io::Channel):

1875 * Recap of our doc header's impl section: `m_sync_io` is the core of `*this`; the most interesting stat-stuff is thus
1876 * there; and a `*this` is structured as a wrapper around it, in most cases basically forwarding `X()` to
1877 * `m_sync_io.X()`. What we add is #m_worker a/k/a background thread W, with an event loop capable of doing
1878 * async-waits on behalf of the very-synchronous-in-nature (like a Unix socket FD + socket API) `m_sync_io`
1879 * and calling back into its API to inform it of satisfied async-waits (like doing a `select()` and then calling
1880 * `recv()`). Because of this setup, as long as `m_sync_io` logs its stats -- which does include
1881 * its `owned_channel()`'s stats incidentally -- close to when *we* want to log stats (or perhaps more like

1963 /**
1964 * The current state of the blocking sync-op mechanism; a `variant` that broadly describes the state as:
1965 * no sync-op in progress, sync-op in progress sans result, sync-op in progress with result that has not yet
1966 * been returned to user (sync-op almost over). Please read on.
1967 *
1968 * ### Design of blocking sync-op mechanism ###
1969 * A `sync_*()` operation is one that synchronously awaits in-traffic of some kind and ends the wait/returns some
1970 * result due to one of the following outcomes:
1971 * - The desired in-traffic received. =>
1972 * Return a result based on its contents.
1973 * - Pipe got hosed with error E due to in-direction processing in thread W by #m_sync_io. =>
1974 * Do *not* report E as-normal via on-error handler; instead end the `sync_*()` and have it emit E synchronously.
1975 * - Pipe got hosed with error E due to user invoking non-blocking, potentially-pipe-hosing method send()
1976 * or async_request() or remote_peer_process_liveness_check() (as of this writing; could be more)
1977 * concurrently with the wait. =>
1978 * Report E as-normal via the concurrent send()/async_request()/remote_peer_process_liveness_check()/...;
1979 * and also end the `sync_*()` and have it emit a special outcome indicating that is what happened (do not
1980 * emit E per se; we do not duplicately emit the pipe-hosing error generally, and this is no exception to that
1981 * rule of thumb).
1982 * - A user-specified (as arg to `sync_*()`) timeout was reached before any of the above occured. =>
1983 * Report a special income indicating that is what happened.
1984 *
1985 * As of this writing there is only one such op: sync_request(). In this discussion we discuss that one
1986 * specifically (while mentally considering how it might be generalized in the future; the mechanism is designed
1987 * hopefully in such a way as to make it not-too-tough to extend to other `sync_*()`s; but we don't want to
1988 * over-engineer this and/or confuse the reader needlessly).
1989 *
1990 * It is a specific documented requirement that sync_request() may be invoked concurrently with itself. (Also it
1991 * is explicitly *not* to be invoked from thread W (i.e., directly from an on-receive handler), as that would
1992 * delay other handlers' execution; so it is to be invoked from thread U only.) Hence we use a dedicated
1993 * #m_sync_op_mutex so that, at any point in time for `*this`, there is either no sync_request() running,
1994 * or there is exactly one running -- though other APIs might be -- and moreover `*this` is safe from being destroyed.
1995 *
1996 * @note There is a to-do as of this writing in the sync_request() doc header to allow for one
1997 * `sync_request()` to not have to block the initiation of another until it fully completes.
1998 * To achieve this we might have not one #m_sync_op_state (or zero, via `optional`) but a set of 0+ of them.
1999 * The algorithm for each one would remain essentially the same as now. #m_sync_op_mutex can then go away.
2000 *
2001 * sync_request() first performs essentially a normal non-blocking async_request(), and if that succeeds the blocking
2002 * part begins. `m_sync_op_state->m_op_done_signal` is initialized to a promise and a future-wait (with timeout)
2003 * begins in thread U. Meanwhile in the background `*this` is operating normally,
2004 * handling all in-traffic. If it gets a successful result (namely a response
2005 * to the particular message the nb-send sent -- not some other in-traffic, which is
2006 * handled normally) while such a wait is in progress in thread U, it loads the result into #m_sync_op_state and
2007 * tickles thread U to stop waiting via `m_op_done_signal`. If it gets any pipe-hosing error, it loads that
2008 * different result and similarly tickles the `promise`. If a concurrent (to the future-wait inside
2009 * sync_request()), thread-U-ish send()/async_request()/remote_peer_process_liveness_check() emits a (pipe-hosing)
2010 * error, it similarly loads that different result and similarly tickles the `promise`. If the timeout happens first,
2011 * the promise is destroyed, and more importantly #m_sync_op_state is reset to steady state.
2012 *
2013 * After this, an error in thread W is handled normally through on-error handler; an error via send() or
2014 * async_request() or remote_peer_process_liveness_check() or similar is
2015 * also handled normally by being synchronously emitted. More interestingly, suppose
2016 * a response to the formerly-expecting-response-but-now-timed-out out-message does arrive later.
2017 * That out-message ID is still registered in #m_sync_io as expecting a response due to
2018 * a sync-op; but our special internal handler for that response detects that there is no longer a sync-request in
2019 * progress, or if there is it is for a different out-message ID -- so it timed out. So it is just dropped.
2020 *
2021 * That's broadly how it works. Now specifically here are the states in the state machine. Note this machine is
2022 * protected by #m_mutex.
2023 * - Null (steady state, no sync-op in progress): #m_sync_op_state is empty/null. sync_request() is not executing,
2024 * or is running before or after the blocking part.
2025 * - In-progress, no result: #m_sync_op_state is non-null, and its Sync_op_state::m_result_if_any
2026 * holds `monostate`: sync_request() is waiting on the promise inside #m_sync_op_state, subject to a timeout,
2027 * and no result has yet been received. (Or it is just about to enter this wait having unlocked mutex,
2028 * or it had just exited it and is about to lock mutex.)
2029 * - sync_request() has permanently set Sync_op_state::m_id to equal a unique ID and captured this in the
2030 * internal response handler, so it can be checked against `m_id` later.
2031 * - In-progress, with result: #m_sync_op_state is non-null, and its Sync_op_state::m_result_if_any
2032 * holds *not* `monostate` (but rather either a truthy `Error_code` indicating error; or else the response):
2033 * sync_request() is as in the previous bullet. However, since the result is ready, the code
2034 * (in thread W) -- having detected the result condition -- will, just before unlocking the mutex
2035 * having set the result in Sync_op_state::m_result_if_any, tickle the promise, waking up the wait
2036 * in sync_request(). Alternatively, user invokes concurrent non-blocking
2037 * send()/async_request()/remote_peer_process_liveness_check()/..., which
2038 * emits an error; so it acts similarly (set `m_result_if_any`, tickle promise, unlock mutex) but not in thread W.
2039 * - Suppose sync_request() wins the race by timing out first. It will then set #m_sync_op_state to null
2040 * (and return timeout to caller, all in thread U).
2041 * - If an error occurs in thread W subsequently, we'll see there's no sync-op in progress and
2042 * report error normally via on-error handler.
2043 * - If an error occurs in thread U/similar subsequently (async_request(), send(),
2044 * remote_peer_process_liveness_check(), ...), we'll see there's no
2045 * sync-op in progress and report error normally via sync emission.
2046 * - If response to the ID arrives, we'll see there's no sync-op
2047 * in progress, or a new one is in progress but with different `m_id`, so it is
2048 * a late-arrival. Then we drop it.
2049 */

2448 * So, if not for a possible sync_request(), we'd literally just do: on_err_func(err_code). However suppose
2449 * a sync_request() is currently executing in thread U. (In the future we could add other sync_*(): E.g.,
2450 * sync_<wait for a particular message a-la expect_msg()>.) In that case we must emit the error to the sync_*()
2451 * waiting for a result instead of the on-error handler. That is our overall contract in *this: Report a
2452 * channel-hosing error exactly once (if ever): either through a send() or sync_request(); or through
2453 * this error reporting handler -- whichever one happens first.
2454 *
2455 * (Note! m_sync_op_state->* may similarly be tickled in this->send(), this->async_request(), ....
2456 * They all use helper emit_sync_io_nb_result() to handle the similar thing.
2457 * @todo Code reuse between that and the below is not out of the question but not a total slam-dunk either.
2458 * The context is similar but not identical. It *might* reduce lines-of-code; but as for reducing
2459 * expressiveness and maintainability -- maybe not, maybe even the reverse.) */
2460
2461 {
2462 Lock_guard lock{m_mutex};
2463
2464 /* Check that (obviously) there is a sync-op in progress; but also (carefully) ensure it does not have a result
2465 * stored already. To show this is technically possible imagine this scenario: sync_request() is waiting in
2466 * thread U; the expected response was received in time and thus placed into m_sync_op_state->m_result_if_any,
2467 * and promise m_sync_op_state->m_op_done_signal was tickled to wake up thread U's future.wait_for();
2468 * but thread U hasn't yet woken up and nullified m_sync_op_state. So now we let that sync_request() return
2469 * success; we then emit the error asynchronously. Basically it's almost as-if the error occurred just after
2470 * the successful sync_request(). */
2471 if (m_sync_op_state)
2472 {
2473 assert((!holds_alternative<Error_code>(m_sync_op_state->m_result_if_any))
2474 && "Only a previous error-handler or nb-op like send() would have set that to an Error_code; "
2475 "and m_sync_io shall not emit pipe-hosing error more than once.");
2476 if (holds_alternative<monostate>(m_sync_op_state->m_result_if_any))
2477 {
2478 FLOW_LOG_INFO("struc::Channel [" << *this << "]: Sync-IO core reported error (details above); "
2479 "this occurred while awaiting sync-op (ID [" << m_sync_op_state->m_id << "]) completion. "
2480 "Therefore we emit the error to that waiting guy, loading that result and waking the guy.");
2481
2482 m_sync_op_state->m_result_if_any = err_code;
2483 m_sync_op_state->m_op_done_signal.set_value();
2484 return;
2485 }
2486 // else { sync_*() already received a success result; so we let that happen. }
2487 } // if (m_sync_op_state)
2488 // else if (!m_sync_op_state) { No sync_*() in progress. }
2489
2490 /* See log_stats() doc header for basic background behind the logic here.
2491 * Note we put this ahead of any handler-call to avoid reentrant hellishness. */
2492 log_stats("m_sync_io.start_and_poll().on_err_func(): emitting hosing to user");
2493 } // Lock_guard lock(m_mutex)
2494
2495 FLOW_LOG_TRACE("struc::Channel [" << *this << "]: Calling error handler from async-worker thread.");
2496 on_err_func(err_code);
2497 FLOW_LOG_TRACE("Handler completed.");
2498 }); // m_worker.post()
2499 }); // m_sync_io.start_and_poll()
2500} // Channel::start()

2503typename Heap_fixed_builder::Config // Static.
2504 CLASS_STRUCTURED_CHANNEL::heap_fixed_builder_config(const Owned_channel& channel, size_t segment1_sz)
2505{
2506 /* This (and similar below) could have been in sync_io::Channel instead. Doesn't really matter.
2507 * I just figured one place for these special static guys is enough, and if we pick one it should be
2508 * in the higher namespace. */
2509
2510 assert(channel.initialized()
2511 && "Method contract is that the tested `channel` is .initialized().");
2512
2513 /* The assumption is they plan to create a Channel like us, passing `channel` into ctor,
2514 * with Builder_config being Heap_fixed_builder::Config or similar. They
2515 * want a Config they can pass to our ctor. So we need to know what to pass to its ctor.
2516 * We have logger_ptr in channel.get_logger(). So we also need:
2517 * - segment_sz_cap: The max size of each segment in the serialization of the structured message itself.
2518 * (If a too-large leaf is mutated-in, this can still be exceeded; in which case Msg_out and Msg_in
2519 * machinery will perform relatively-expensive split/join post/pre-processing steps to ultimately ensure
2520 * we're subject to this hard cap when performing IPC of the unstructured blobs.)
2521 * So this is basically how much will fit into an unstructured msg as transmitted via `channel`. We can
2522 * get this via `channel` itself.
2523 * - grow_seg_sz_else_constant: `true` for segments 2, 3, ... (if they are needed; hopefully not)
2524 * to grow ~exponentially in size; `false` to use fixed size each time. We shall use `true`, as the required
2525 * pre-zeroing of segments has a non-trivial cost; hence starting with a tight upper-bound for a typical
2526 * message is likely to save processor cycles. (Only the actually-used space of each segment is actually
2527 * transmitted, so this is only about the calloc()/memset() -- not about copying unnecessary bytes.)
2528 * - segment_sz_init: If grow_seg_sz_else_constant is `true` (and it is), this is the
2529 * size to use for segment 1. On one hand this should be as small as possible to minimize the aforementioned
2530 * calloc()/memset(). On the other hand if it is too small for a given message to fit entirely, then
2531 * more segments shall be required; that has various perf costs. Therefore we take this one as an arg
2532 * (albeit with a default available for use): segment1_sz. The user is the best estimator of this,
2533 * and there is no way to somehow glean it from `channel`.
2534 * - frame_prefix_sz: For seg 1 only, this is the header space reserved by the capnp-serializer, just ahead
2535 * of byte 1 of seg 1. We use it to stuff mdt (e.g., message ID) for the entire message (all segments).
2536 * The sufficiently tight upper bound for much space is necessary for mdt is
2537 * BUILDER_CONFIG_FRAME_PREFIX_SZ_VIA_STRUC_CHANNEL.
2538 *
2539 * For segment_sz_cap: This must fit into the max sendable blob (send_blob()) or meta-blob (send_native_handle()).
2540 * And if we might invoke either one, then formally speaking we must report the lower of the two. */

2542 size_t ipc_max_sz;
2543 if constexpr(Owned_channel::S_HAS_BLOB_PIPE_ONLY)
2544 {
2545 // Only send_native_handle() shall be used. See send().
2546 ipc_max_sz = channel.send_blob_max_size();
2547 }
2548 else if constexpr(Owned_channel::S_HAS_NATIVE_HANDLE_PIPE_ONLY)
2549 {
2550 // Only send_blob() shall be used. See send().
2551 ipc_max_sz = channel.send_meta_blob_max_size();
2552 }
2553 else
2554 {
2555 static_assert(Owned_channel::S_HAS_2_PIPES, "This code assumes 1 blobs pipe, 1 handles pipe, or both exactly.");
2556 // Either one may be used. See sync_io::Channel::send_core().
2557 ipc_max_sz = std::min(channel.send_meta_blob_max_size(), channel.send_blob_max_size());
2558 }
2559
2560 return Heap_fixed_builder::Config{ channel.get_logger(), ipc_max_sz, segment1_sz,

2628TEMPLATE_STRUCTURED_CHANNEL
2629template<bool MSG_ELSE_LOG_IN, typename On_msg_handler>
2630bool CLASS_STRUCTURED_CHANNEL::expect_msg_impl(Msg_which_in which, On_msg_handler&& on_msg_func)
2631{
2632 using boost::make_shared;
2633
2634 /* We are in thread U or thread W (if invoked from a user handler).
2635 * Nothing is locked either way due to how we actually invoke user-supplied handlers (which we are about
2636 * discuss). */
2637
2638 /* Wrap (a moved version of) their function object in a shared_ptr<Function<>>. (Perf-wise, ultimately
2639 * m_sync_io will do this anyway; we probably aren't adding much churn with this op alone.)
2640 * Why? Answer: Unfortunately we have to first pass on_msg_func to m_sync_io.expect_*(); and then possibly
2641 * also invoke it ourselves -- if message(s) immediately available synchronously. So we can't
2642 * std::move(on_msg_func), as it'll get blown away (its captures will at least) before we can use it
2643 * synchronously. We could capture a copy of on_msg_func, but that is slow: Capturing a copy of a shared_ptr<>
2644 * is muuuuuch faster. */
2645 auto on_msg_func_ptr = make_shared<On_msg_func>(std::move(on_msg_func));
2646
2647 // See below first regarding the purpose of this guy. Then come back here.
2648 auto real_on_msg_func = [this, on_msg_func_ptr](Msg_in_ptr&& msg_in) mutable
2649 {
2650 // We are in thread W. m_mutex is locked!
2651
2652 /* Now comes a key decision: We are in thread W. We must call user handler on_msg_func(). Thread W isn't
2653 * thread U: it isn't the user thread. So it would appear we could just straight-up synchronously
2654 * `on_msg_func(std::move(msg_in))`. Yet instead we post() onto thread W again -- and do it there. Why?
2655 * Answer:
2656 *
2657 * Firstly, just technically speaking, m_mutex is locked (we are right now down the call stack from
2658 * async_wait() handler inside start_ops() statement inside our ctor: it locks m_mutex before calling
2659 * (*on_active_ev_func)(). So, it being a non-recursive mutex, if they were to call expect_msg(), or
2660 * send(), or anything else like that -- which they are explicitly allowed to do -- inside such a call
2661 * we'd deadlock right inside the hypothetical synchronous on_msg_func().
2662 *
2663 * However if we post() that onto thread W, then everything is cool. So at least we know it's safe.
2664 * Is it performant? Before trying to answer that let's consider the alternative.
2665 *
2666 * Sure: we could make m_mutex recursive. Or we could not-lock it inside our various APIs (including the
2667 * expect_msg() you're reading now -- albeit the async-handler inside it), which would be sort-of a user-space
2668 * recursive mutex action. So why not? My (ygoldfel) answer is arguably hand-wavy, but it's 2-fold.
2669 * 1, in every instance of my career where I tried to or saw someone tried to solve a deadlocking algorithm
2670 * by making a recursive mutex, it was the wrong move that was reversed soon enough. Also generally designs
2671 * with recursive mutexes that at least appeared to work seemed to do so out of a desire to avoid a few lines
2672 * of boiler-plate (_impl() methods that had mutex-lock as a pre-condition), in code of quite limited size --
2673 * not a complex state machine like we have here. 2, while at this exact moment I cannot think of a way
2674 * that allowing recursive calls into m_sync_io.*() API could lead to algorithmic mayhem/bugs, it is even for me
2675 * exceedingly difficult to convince myself of that. It does seem like probably as of this writing Sync_io_obj
2676 * is pretty clean as far as its algorithm not breaking down due to a handler calling back into its own API -- but
2677 * will that always be the case? Will it be reasonable to have to maintain that logic? It's mind-breaking.
2678 *
2679 * So is the alternative a good idea? Probably not. I'd like to prove it beyond a doubt but at the moment can't.
2680 * At the very least it is quite difficult to prove that it's *safe*, as it's so tough to reason-about due to
2681 * the flow control layers involved.
2682 *
2683 * Okay, so then, back to post()ing it onto thread W. We know it's safe. Is it performant? The question really
2684 * applies to the (presumably common) case where the user, in fact, in on_msg_func() does *not* call back into
2685 * `*this` API -- they are after all encouraged in our class doc header to keep themselves sane by post()ing
2686 * their true handling onto their thread U (or whatever their equivalent of post()ing is). So suppose, indeed,
2687 * their on_msg_func = { <their loop>.post([msg_in = std::move(msg_in)]() { ...handle it...}); }.
2688 * Indeed we're adding another m_worker.post() between now and their "...handle it..." actually executing; whereas
2689 * in *this* particular scenario it would've been perfectly safe to just, like, not.
2690 *
2691 * So is that delay okay? In absolute terms I would say... for now at least... yes. It'll add a few usec of
2692 * latency, as boost.asio winds up the stack into Task_engine::run(), then re-enters the post()ed handler of ours
2693 * and "finally" runs on_msg_func(). It's boost.asio flow control: it is common in boost.asio/async algorithms
2694 * as the technique to combat "recursive mayhem."
2695 *
2696 * @todo It is worth revisiting; possibly profiling. */
2697
2698 m_worker.post([this, on_msg_func_ptr = std::move(on_msg_func_ptr), msg_in = std::move(msg_in)]() mutable
2699 {
2700 // We are in thread W. Nothing is locked.
2701 FLOW_LOG_TRACE("struc::Channel [" << *this << "]: Invoking user on-expect-msg handler (async path).");
2702 (*on_msg_func_ptr)(std::move(msg_in));
2703 FLOW_LOG_TRACE("Handler completed.");
2704 });
2705 }; // auto real_on_msg_func =
2706
2707 Msg_in_ptr qd_msg;
2708 bool ok;
2709
2710 // Reminder: we must protect against concurrent calls from user threads U1, U2, ...; and against access from W.
2711 Lock_guard lock{m_mutex};
2712
2713 if constexpr(MSG_ELSE_LOG_IN)
2714 {
2715 ok = m_sync_io.expect_msg(which, &qd_msg, std::move(real_on_msg_func));
2716 }
2717 else
2718 {
2719 ok = m_sync_io.expect_log_in_request(which, &qd_msg, std::move(real_on_msg_func));
2720 }
2721
2722 if (!ok)
2723 {
2724 return false;
2725 }
2726 // else:
2727
2728 if (qd_msg)
2729 {
2730 // Message expectation immediately met. Report it immediately via thread-W (as we always must).
2731 m_worker.post([this, on_msg_func_ptr = std::move(on_msg_func_ptr), msg_in = std::move(qd_msg)]() mutable
2732 {
2733 // We are in thread W. Nothing is locked.
2734 FLOW_LOG_TRACE("struc::Channel [" << *this << "]: Invoking user on-expect-msg handler (sync path).");
2735 (*on_msg_func_ptr)(std::move(msg_in));
2736 FLOW_LOG_TRACE("Handler completed.");
2737 });
2738 }
2739 // else { It'll fire, if ever, asynchronously. }
2740
2741 return true;
2742} // Channel::expect_msg_impl()

2745template<typename On_msg_handler>
2746bool CLASS_STRUCTURED_CHANNEL::expect_msgs(Msg_which_in which, On_msg_handler&& on_msg_func)
2747{
2748 using boost::make_shared;
2749
2750 /* We are in thread U; or thread W (if invoked from a user handler); always serially.
2751 * Nothing is locked either way due to how we actually invoke user-supplied handlers. */
2752
2753 // Wrap (a moved version of) their function object in a shared_ptr<Function<>>. See explanation in expect_msg_impl().
2754 auto on_msg_func_ptr = make_shared<On_msg_func>(std::move(on_msg_func));
2755
2756 auto real_on_msg_func = [this, on_msg_func_ptr](Msg_in_ptr&& msg_in)
2757 {
2758 // We are in thread W. m_mutex is locked!
2759
2760 /* *Please* see comment in expect_msg_impl() similar spot regarding why we post() here.
2761 *
2762 * Orthogonally: The function where this comment sits may be executed 2+ times, unlike expect_msg_impl() which
2763 * is a one-off message expectation. So we cannot move(on_msg_func_ptr) -- it'll get nullified the first time,
2764 * and you're screwed. In expect_msg() we can though for a bit of extra perf. */
2765 m_worker.post([this, on_msg_func_ptr, msg_in = std::move(msg_in)]() mutable
2766 {
2767 // We are in thread W. Nothing is locked.
2768 FLOW_LOG_TRACE("struc::Channel [" << *this << "]: Invoking user on-expect-msgs handler (async path).");
2769 (*on_msg_func_ptr)(std::move(msg_in));
2770 FLOW_LOG_TRACE("Handler completed.");
2771 });
2772 };
2773
2774 typename Sync_io_obj::Msgs_in qd_msgs;
2775
2776 // Reminder: we must protect against concurrent calls from user threads U1, U2, ...; and against access from W.
2777 Lock_guard lock{m_mutex};
2778
2779 if (!m_sync_io.expect_msgs(which, &qd_msgs, std::move(real_on_msg_func)))
2780 {
2781 return false;
2782 }
2783 // else:
2784
2785 if (qd_msgs.empty())
2786 {
2787 return true; // They may fire asynchronously. Nothing for now.
2788 }
2789 // else
2790
2791 // Message expectation immediately met. Report these immediately via thread-W (as we always must).
2792 m_worker.post([this, on_msg_func_ptr = std::move(on_msg_func_ptr), qd_msgs = std::move(qd_msgs)]() mutable
2793 {
2794 // We are in thread W. Nothing is locked.
2795
2796 size_t idx = 0;
2797 for (auto& msg_in : qd_msgs)
2798 {
2799 FLOW_LOG_TRACE("struc::Channel [" << *this << "]: Invoking user on-expect-msg handler (sync path): "
2800 "handler [" << idx << "] (0-based) of [" << qd_msgs.size() << "] (1-based).");
2801 (*on_msg_func_ptr)(std::move(msg_in));
2802
2803 ++idx;
2804 }
2805 FLOW_LOG_TRACE("Handlers completed.");
2806 });
2807
2808 // Plus more may fire asynchronously.
2809
2810 return true;
2811} // Channel::expect_msgs()

2829TEMPLATE_STRUCTURED_CHANNEL
2830bool CLASS_STRUCTURED_CHANNEL::emit_sync_io_nb_result(bool sync_io_op_returned_ok,
2831 const Error_code& sync_io_op_emitted_err_code,
2832 util::String_view op)
2833{
2834 using std::holds_alternative;
2835 using std::monostate;
2836 using flow::util::ostream_op_string;
2837
2838 /* We are a helper that equals the final step of the caller calling a synchronous, non-blocking,
2839 * possibly-channel-hosing-error-emitting m_sync_io API; or more precisely (with tiny tweaks for exposition):
2840 * bool Channel::some_op(some_args, Error_code& sync_io_op_emitted_err_code)
2841 * {
2842 * Lock_guard lock{m_mutex};
2843 * const bool sync_io_op_returned_ok = m_sync_io.some_op(some_args, &sync_io_op_emitted_err_code);
2844 * ...
2845 * return ...;
2846 * }
2847 * Our mission is to handle the last two lines inside {}. To wit:
2848 *
2849 * Reminder: sync_io_op_returned_ok either returns false, meaning channel was already hosed, or an API mis-use --
2850 * either way we are to simply also return false; or true, meaning it did try the op, and
2851 * sync_io_op_emitted_err_code out-arg indicates whether it succeeded (falsy) or failed m_sync_io-hosingly
2852 * truthy. In the latter case we, mainly, should simply do that same very thing. Except:
2853 *
2854 * We are explicitly allowed to be invoked concurrently to the wait in sync_...() (sync_request() as of this
2855 * writing) -- m_mutex is *not* locked during that wait. We are in thread U', and they are in thread U.
2856 * The promised behavior is that we're orthogonal to the sync_...(), unless we emit a (new) error.
2857 * In that case, we promise to (1) emit the error as normal but also (2) wake the sync_...() and cause it
2858 * to emit a special error (not our sync_io_op_emitted_err_code). This is similar to what our on-error handler
2859 * (see start()) does in thread W:
2860 *
2861 * (If indeed we are emitting an error) detect whether there's an ongoing sync-op; if so place the result
2862 * they should emit (not sync_io_op_emitted_err_code) into the ongoing-sync-op structure; and ping the
2863 * signaller-promise to cause the wake-up. Please see start()'s similar section; omitting redundant comment(s)
2864 * here. */
2865 if (sync_io_op_returned_ok && sync_io_op_emitted_err_code)
2866 {
2867 if (m_sync_op_state)
2868 {
2869 assert((!holds_alternative<Error_code>(m_sync_op_state->m_result_if_any))
2870 && "Only a previous error-handler or nb-op like send() would have set that to an Error_code; "
2871 "and m_sync_io shall not emit pipe-hosing error more than once.");
2872 if (holds_alternative<monostate>(m_sync_op_state->m_result_if_any))
2873 {
2874 FLOW_LOG_INFO("struc::Channel [" << *this << "]: Sync-IO core reported error (details above) "
2875 "synchronously in user thread when attempting nb-op [" << op << "]; "
2876 "this occurred while concurrently awaiting sync-op (ID [" << m_sync_op_state->m_id << "]) "
2877 "completion. We will emit the above error as normal synchronously, but we will emit a special "
2878 "error to that guy, loading that result and waking the guy.");
2879
2880 m_sync_op_state->m_result_if_any = error::Code::S_SYNC_OP_INTERRUPTED_BY_CONCURRENT_NB_ERROR;
2881 m_sync_op_state->m_op_done_signal.set_value();
2882
2883 /* We emit error. However, don't fall through: i.e: don't log_stats(). Thus the sync_...() must
2884 * do so instead (and we won't dupe-log it). Note: it's just a design choice, and formally this is what we
2885 * advertised in our contract; but we could've advertised/done the reverse -- log_stats() here, don't
2886 * log_stats() there (in sync_...() on being awakened by a concurrent error-emission). From the functional
2887 * point-of-view, it's ~identical: it's logged at the same time either way and only once. So it's a matter
2888 * of what's stylistically better/more maintainable. That's a toss-up, we think. */
2889 return true;
2890 }

2928
2929 /* We are in thread U; or thread W (if invoked from a user handler).
2930 * Nothing is locked either way due to how we actually invoke user-supplied handlers. */
2931
2932 /* This is one of the 2 interesting send methods (the other being sync_request() which is a whole other thing).
2933 * That is we can't just forward to m_sync_io.async_request() all the way, tempting as it is. The reason is the same
2934 * as in expect_msg_impl() and expects_msgs() (at least): if we just forward on_rsp_func, it will run in thread W

2936 * we post(), in expect_msg_impl(). Same deal here. (We should add: if for some reason we crazily decided to
2937 * post() in (e.g.) expect_msg_impl() but not here, then handlers could fire out of order (and did, in testing

2942 * would only occur if they actually tried to use a *this API from directly in on_rsp_func(). I digress though.)

2945 * either (as in expect_msgs()) we either have to make copies of on_rsp_func and all its captures (expensive) or

2951 * complex, there's no proof that doing 2 move(on_rsp_func)s is faster than 1 such move() + some shared_ptr

2956 (Msg_in_ptr&& msg_in)
2957 {

2959

2962 {

2966 FLOW_LOG_TRACE("Handler completed.");
2967 });
2968 }; // auto real_on_rsp_func()

2970 // Reminder: we must protect against concurrent calls from user threads U1, U2, ...; and against access from W.
2971 Lock_guard lock{m_mutex};
2972 return emit_sync_io_nb_result(m_sync_io.async_request(msg, originating_msg_or_null,
2973 id_unless_one_off, std::move(real_on_rsp_func), err_code),
2974 *err_code, "async_request()");
2975} // Channel::async_request()
