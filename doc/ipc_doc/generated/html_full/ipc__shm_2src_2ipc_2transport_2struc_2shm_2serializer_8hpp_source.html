53/**
54 * Implements Struct_builder concept with maximal zero-copy perf by (1) storing the actual user-schema-controlled
55 * message using the SHM-provider of choice, in SHM, and (2) straightforwardly allocating 1 segment in regular heap
56 * and placing the SHM handle there for transmission over IPC. That is, each mutation via payload_msg_builder()
57 * may, as needed, trigger a SHM allocation. In this algorithm, somewhat similarly to Heap_fixed_builder, the size of
58 * each (SHM-)allocated segment will be determined intelligently based on an exponential-growth algorithm,
59 * albeit not strictly capped in size as in Heap_fixed_builder (as these buffers need not be copied: the whole point of
60 * SHM).
61 *
62 * @todo In shm::Builder some comments and/or logging and/or identifiers refer to "top/bottom" serialization; in others
63 * to "outer/inner" serialization; we should consistently use the latter terminology there and all over Flow-IPC.
64 *
65 * ### Failure mode; reasonable uses ###
66 * As long as the SHM-provider is able to dole out RAM,
67 * there is no limit at all on the size/complexity of what one mutates over payload_msg_builder(). In fact `*this`
68 * provides the 2-layer approach explained in the concept Struct_builder doc header.
69 *
70 * There are two realistic failure modes in `*this`. The first is the following:
71 * -# User attempts to mutate via payload_msg_builder().
72 * -# capnp internals recognize the current segment is used up and asks for a new segment of at least N bytes.
73 * -# `*this` asks the SHM-provider (see template param docs below) to allocate >=N bytes.
74 * -# The SHM-provider determines it has run out of space according to its policies/algorithm/limitations and
75 * throws exception, in spirit similar to `std::bad_alloc`.
76 * -# This propagates to the user via their payload_msg_builder() mutation statement: it throws.
77 *
78 * The key here: This cannot be detected via `*this`. In spirit it is similar to `Heap_fixed_builder`-originated
79 * mutations by the user running out of regular-heap (even virtual disk heap, if enabled) and is outside our scope
80 * to control. The only remedy: choose a SHM-provider that does not run out of space beyond simply running out of
81 * RAM; e.g., by mapping more SHM pools, or whatever. Otherwise, all the user can do is catch the `bad_alloc`-like
82 * exception around their mutations on payload_msg_builder() and take whatever contingency steps.
83 *
84 * The second failure mode is emit_serialization() failing. See its doc header for more information.
85 * In a similar key, Reader::deserialization() can fail down the line. See its doc header for more information.
86 *
87 * @see shm::Reader
88 * Counterpart Struct_reader implementation that can deserialize data that this has serialized.
89 * @see Struct_builder: implemented concept.
90 *
91 * @tparam Shm_arena
92 * SHM-provider type with the ability to allocate STL-compliant data structures directly in SHM, returning
93 * a `shared_ptr` outer-SHM-handle that is possible to `lend_object()`/`borrow_object()` via
94 * shm::Builder::Session.
95 * `Shm_arena::Handle<T>` must equal `shared_ptr<T>` (meaning type with standard `shared_ptr<T>` semantics;
96 * in practice probably either `std::shared_ptr<T>` or `boost::shared_ptr<T>`).
97 * It must provide a `construct<T>()` method as exemplified by shm::classic::Pool_arena::construct().
98 * (This is an *example*; you do not have to use `Pool_arena` and indeed should choose a SHM-provider
99 * suitable to your needs, especially as regards to being able to allocate sufficiently large segments.)
100 * That is: `Handle<T> construct<T>(...ctor_args...)`, such that if it returned `p` then
101 * `session::shm::Arena_to_shm_session_t<Shm_arena>` pointee has method
102 * `flow::util::Blob_sans_log_context lend_object<T>(const Handle<T>& p)`. Next, if the returned blob `b`
103 * is bit-wise copied into an IPC transport and copied out of it and then given to
104 * counterpart shm::Reader, then `shm::Reader::Session` pointee has method `borrow_object<T>(b)` that shall
105 * return (in the receiving process) `Handle<T>` that points to the same SHM-stored data structure originally
106 * returned by `construct()`. In addition `Shm_arena` must be compatible with `Stateless_allocator`
107 * requirements as explained in "Additional formal requirements" below.
108 * Lastly, `lend_object()` and `borrow_object()` may return an empty blob/null respectively, indicating
109 * (assuming proper inputs) the session is permanently down (opposing process is likely down/closed session).
110 *
111 * ### Additional formal requirements w/r/t `Shm_arena` ###
112 * Information on `T` that `*this` shall use with `Shm_arena::construct<T>()`: As of this writing it is
113 * `list<Basic_blob>`, representing (internally) the capnp-requested 1+ segments in which the serialization
114 * mutated via payload_msg_builder() is stored in zero-copy fashion. In order for this to work, the `Allocator`
115 * template arg on both `list` and the inner `Blob`s shall be ipc::shm::stl::Stateless_allocator.
116 * Therefore, the requirement is: `Shm_arena` must formally meet the requirements for `Arena` from
117 * ipc::shm::stl::Stateless_allocator doc header. Briefly these are: `allocate(n) -> void*`,
118 * `deallocate(void*)`, `Pointer` fancy-pointer type that is SHM-storable.
119 *
120 * A simple (likely the simplest) example is ipc::shm::classic::Pool_arena, which satisfies both
121 * `Shm_arena` and `session::shm::Arena_to_shm_session_t<Shm_arena>`-pointee requirements. However, it has deficiencies
122 * w/r/t max pool size having to be specified and a non-industry-strength allocation algorithm. The Jemalloc-based SHM
123 * provider in ipc::shm::arena_lend::jemalloc is more complex -- with a separate
124 * `Arena_to_shm_session_t<Shm_arena>` pointee from `Shm_arena` -- but lacks these problems.
125 */

331/**
332 * Implements Struct_reader concept by interpreting a serialization by shm::Builder with the
333 * same template params. If one understands how to use shm::Builder (see its doc header in-depth),
334 * it should be straightforward to figure out how to create/use a `*this`. Please read that; then come
335 * back here.
336 *
337 * ### How `Shm_arena` is used by a `*this` ###
338 * It is a good question, as shm::Reader is conceptually read-only w/r/t the SHM-stored serialization
339 * accessed by payload_msg_builder(). So why does it need any #Arena? Answer: well, it does not need *an* #Arena;
340 * unlike with shm::Builder you don't need to pass-in any `Arena*` into the ctor or elsewhere. That makes sense:
341 * it never allocates anything in SHM, only reads it. It does however need an equal #Arena template param.
342 * Why? Answer: There are internal reasons having to do with STL-compliant internal storage by the counterpart
343 * shm::Builder; to decode its data structures properly it needs to have some type information at compile-time;
344 * this "supplies" code -- not data.
345 *
346 * Anyway, just supply an equal #Arena template param. Should be fine.
347 *
348 * ### How shm::Reader::Session (a/k/a `Shm_session`) is used by a `*this` ###
349 * shm::Builder, internally, performs `Shm_arena::construct<T>()` to allocate a STL-compliant data structure
350 * and yield a `Shm_session`-lendable outer SHM handle. It performs `Shm_session::lend_object<T>()` in
351 * shm::Builder::emit_serialization(), registering the recipient-to-be process as the 2nd owner process.
352 * Then the counterpart `*this` performs `Shm_session::borrow_object<T>()` to recover the equivalent
353 * outer SHM handle to the same STL-compliant data structure the user had built up via
354 * shm::Builder::payload_msg_builder().
355 *
356 * @see shm::Builder
357 * The counterpart Struct_builder implementation that can create compatible serializations.
358 * @see Struct_reader: implemented concept.
359 *
360 * @tparam Shm_arena
361 * Must be the same as the serializing Builder counterpart. Note that no object of this type
362 * is required to the ctor unlike with Builder. Only the type is necessary (see discussion above).
363 */

534template<typename Shm_arena>
535void Builder<Shm_arena>::emit_serialization(Segment_bufs* target_blobs, util::Blob_mutable* hdr_blob,
536 Split_segments* split_segs,
537 const Session& session, Error_code* err_code) const
538{
539 if (flow::error::exec_void_and_throw_on_error
540 ([&](Error_code* actual_err_code)
541 { emit_serialization(target_blobs, hdr_blob, split_segs, session, actual_err_code); },
542 err_code, "shm::Builder::emit_serialization()"))
543 {
544 return;
545 }
546 // ^-- Call ourselves and return if err_code is null. If got to present line, err_code is not null.
547
548 assert(m_btm_engine && "Are you operating on a moved-from `*this`?");
549
550 /* Key subtlety: It may seem correct here to do initRoot<>(), not getRoot<>(), but that would be wrong:
551 * they may be reusing `*this` (to send it out a 2nd, 3rd, ... time). Fortunately getRoot<>() does the right
552 * thing: the 1st time, it's identical to initRoot<>(); subsequently it's a no-op that returns the existing
553 * root ShmTopSerialization::Builder. (If getRoot<>() initially barfed instead, we'd have to keep a
554 * `bool m_initialized` and do initRoot first and set it to true, then getRoot once it's true.)
555 *
556 * Also we must either const_cast<>, or make m_top_engine mutable, for the following to compile.
557 * Of course that is to be questioned; we justify it as follows: getRoot<>() could be done in ctor, and we could
558 * cache the result there; instead we do it lazily on-demand -- a pattern that's a typical justification
559 * for `mutable` (and the following is essentially a smaller-scoped `mutable`). The first time it's done
560 * it creates the root (which would otherwise be done in ctor); next time it does nothing; then in either case
561 * `root` becomes the same value. */
562 auto root = const_cast<Heap_fixed_builder&>(m_top_engine)
563 .payload_msg_builder()->getRoot<schema::detail::ShmTopSerialization>();
564
565 /* We have the bottom serialization inside m_btm_engine; the data they'd mutated via this->payload_msg_builder()
566 * is stored in a bunch of SHM segments of whatever sizes was deemed sufficient, all in one STL-compliant
567 * data structure directly in SHM. This will finalize that data structure; *and* emit some scalar(s) that encode
568 * the outer SHM handle to it. These bits are emitted right into the top
569 * serialization which will be copied through to the recipient/reader. (Analogy: They could, instead,
570 * be emitted into a disk file which would be read by the reader. The file, like this top serialization,
571 * is small: just a few scalars. But by following where it points in SHM, we can access an arbitrarily huge
572 * and complex structure.) Also it ups the process-owner ref-count from 1 (us) to 2 (us + them), so that our
573 * dtor won't blow away the SHM-stored data structure unless Reader has already invoked its dtor too.
574 * (If this is emit_serialization() #2, then the ref-count grows potentially to 3, etc.) */
575 if (!m_btm_engine->lend(&root, session)) // Target *root; put the outer SHM handle's encoding there.
576 {
577 *err_code = error::Code::S_SERIALIZE_FAILED_SESSION_HOSED;
578 return; // It logged already.
579 }
580 // else
581
582 /* Secondly obtain that resulting top (local-heap) serialization. Due to the nature of what it is encoding in our
583 * case, we can assume certain simplifications (assertion trips otherwise):
584 * - m_top_engine always emits a quite-small, constant-sized serialization
585 * for its SHM handle thingie; it will easily fit into any reasonable first segment and not even require any
586 * further segments, let alone overflow any segment.
587 * - That is exactly 1 segment shall be generated. (So assert this.)
588 * - That one segment, being un-overflowingly small, shall not need to be split. So pass-in out-arg
589 * split_segs=nullptr which means...
590 * - ...that if a split *is* needed, m_top_engine.emit_serialization() shall emit
591 * error S_INTERNAL_ERROR_SERIALIZE_LEAF_TOO_BIG; and it is the *only* possible error.
592 * - So assert no error was emitted.
593 *
594 * If this is emit_serialization() #2, #3, ...: This value will always be the same, since it's just the SHM handle's
595 * encoding; at least for the 2 SHM-providers (SHM-classic, SHM-jemalloc) that's the case, and I (ygoldfel) can't
596 * conceive of anything different. @todo Considering simply no-op-ing here for any emit_serialization()s except the
597 * first one. It's not urgent, probably, as despite looking fancy, in this case the insides of the following call
598 * will barely do any work. */
599 if (split_segs)
600 {
601 split_segs->clear(); // We always leave it empty (and as noted don't even give it to m_top_engine).
602 }
603 m_top_engine.emit_serialization(target_blobs, hdr_blob, nullptr, NULL_SESSION, err_code);
604
605 assert((!*err_code) && "The top serialization consists of exactly 1 small segment (storing SHM handle), so no "
606 "error should be possible here.");
607 assert((target_blobs->size() == 1)
608 && "We guarantee the top serialization consists of exactly 1 un-split segment (storing SHM handle), no more.");
609} // Builder::emit_serialization()

658template<typename Shm_arena>
659template<typename Struct>
660typename Struct::Reader Reader<Shm_arena>::deserialization(const Split_segments* split_segs_always_null,
661 Error_code* err_code)
662{
663 using Capnp_struct_reader = typename Struct::Reader;
664
665 FLOW_ERROR_EXEC_AND_THROW_ON_ERROR(Capnp_struct_reader, deserialization<Struct>, split_segs_always_null, _1);
666 // ^-- Call ourselves and return if err_code is null. If got to present line, err_code is not null.
667
668 if (split_segs_always_null)
669 {
670 FLOW_LOG_WARNING("shm::Reader [" << *this << "]: The top serialization apparently involved capnp-segments so "
671 "large that they had to be split and would now be reassembled; but in our case that is "
672 "nonsensical, as the top serialization must consist of 1 small segment always. Emitting error. "
673 "Other side misbehaved?");
674 *err_code = struc::error::Code::S_DESERIALIZE_FAILED_REASSEMBLY_FAILED;
675 return {};
676 }
677 // else
678
679 // The top serialization is simply this (but what it encodes is a handle to the bottom serialization).
680 const auto top_serialization_root
681 = m_top_engine.deserialization<schema::detail::ShmTopSerialization>(nullptr, err_code);
682 // Either that threw (error), set *err_code to truthy (error), or succeeded. Check for that middle one.
683
684 if (*err_code)
685 {
686 return {};
687 }
688 // else
689
690 assert(m_btm_engine.empty() && "Did you call deserialization() more than once?");
691
692 // Now get the bottom serialization out of SHM.
693 m_btm_engine.borrow(top_serialization_root, m_session, err_code);
694 if (*err_code)
695 {
696 return {};
697 }
698 // else
699 assert((!m_btm_engine.empty()) && "borrow() should have emitted error then. Bug in Capnp_message_reader?");
700
701 // .borrow() succeeded, so this will work.
702 return m_btm_engine.template getRoot<Struct>();
703} // Reader::deserialization()
