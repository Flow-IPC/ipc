115/**
116 * `Thread_local_pool_lookup_rev<R>.s_registry`, where `R` is a distinct pool-repository type,
117 * enables high-perf reverse-lookup from a vaddr to the containing SHM-pool's ID and
118 * offset in bytes from the pool-base vaddr.
119 *
120 * As far as we know, if one needs multithreaded such lookup with high performance, then whether owner-side or
121 * borrower-side one should use Thread_local_pool_lookup_rev. Note that `Thread_local_pool_lookup_rev<R1>`
122 * and `Thread_local_pool_lookup_rev<R2>` are completely independent, if `R1` and `R2` are different types.
123 *
124 * @see This is a key building block for the rev-lookup operations of Owner_shm_pool_repository (and
125 * Shm_pool_offset_ptr_data -- for Shm_pool_offset_ptr -- operating against it, owner-side) and of
126 * session::shm::arena_lend::detail::Borrower_shm_pool_collection_repository (ditto but borrower-side).
127 * In both cases this is done indirectly via Shm_pool_repo_lookup_core_rev which uses us directly.
128 * The rationale of separating us (Thread_local_pool_lookup_rev) from Shm_pool_repo_lookup_core_rev is the
129 * analogous nature of us and our forward-lookup cousin Thread_local_pool_lookup_fwd.
130 *
131 * ### How to use ###
132 * To actually perform the reverse-lookup operation, whose performance we are optimizing, use:
133 * - `Thread_local_pool_lookup_rev<Repository>::s_registry.this_thread_state()->lookup(vaddr, ...)`.
134 *
135 * The user has a rigid responsibility for loading the canonical, and complete, set of SHM-pool base vaddrs and
136 * their respective #pool_id_t values. This consists of two operations, and you must help us perform each:
137 * - *Pull*: A `*this` is auto-created in new thread Ti the first time it is needed.
138 * Therefore the new `*this` *pulls* the current canonical state from somewhere that you have it.
139 * - *Push*: Your current canonical state is updated (e.g., memory-manager created new pool).
140 * Therefore you *push* that state, wherever you've got it, into *every* extant `*this`.
141 *
142 * ### How to use: pull ###
143 * During the per-thread creation of a `*this`, the following expression shall be invoked on-demand:
144 * - `Repository::get_instance().tl_copy_rev_pull_pools(&M)`, where
145 * - `M` is #Map (vaddr -> Pool_by_base), and
146 * - that expression shall load `M` with the complete current information about base-vaddrs and pool info.
147 * - A central (1-1 with the type #Repository) mutex `Mtx` shall be locked;
148 * and it is the same mutex that shall be locked during a push (see below).
149 *
150 * ### How to use: push ###
151 * When the canonical such structure is modified in repo #Repository (addition,
152 * removal, init), that thread must do the following (certainly before any relevant subsequent lookup() calls):
153 * - `Thread_local_pool_lookup_rev<Repository>::s_registry.while_locked() {...}`.
154 * - Inside the `{...}`, obtain and loop-through each thread's extant thread-local
155 * Thread_local_pool_lookup_rev cache: `state_per_thread` from `.while_locked()` is a map whose
156 * keys are each a `Thread_local_pool_lookup_rev<Repository>`. (The values are some metadata like thread ID
157 * or what-not.)
158 * - For each of those: `cache.push_pools(M)`, where `M` is the complete new mapping.
159 * - The mutex that shall be locked inside the `{...}` shall be the same mutex `Mtx` used during any pull
160 * (see above).
161 *
162 * ### Design / Impl ###
163 * The basic lookup algorithm, even in one thread only, is that one needs a sorted-by-base-vaddr map from
164 * base-vaddr to pool ID, and with logarithmic time complexity lookup() shall perform a binary-search
165 * (as in `std::map::upper_bound()`) lookup of a nearby (versus the input `void*`) base-vaddr plus an
166 * adjustment of the resulting iterator. (That gets the pool ID; the offset is just the address minus the
167 * located base-vaddr.)
168 *
169 * For multithreaded access, the naive approach (full synchronization via one central mutex) exhibits terrible
170 * lock contention under high load. Therefore we looked for something involving a thread-local lookup().
171 * Flow's `Thread_local_state_registry` provides TL semantics; we expose a global #s_registry of that type;
172 * so `s_registry::this_thread_state()->lookup()` is how one would perform the lookup.
173 *
174 * In short: a given `*this` shall contain an up-to-date copy of the canonical set of bases and corresponding pool info.
175 * Therefore one must copy-over the canonical such map into the thread-local #m_pools_sorted_by_base
176 * *for each thread*, whenever said canonical map is updated (in whatever *pusher thread* happens to be
177 * performing that update).
178 *
179 * Naturally this creates the need for locking -- whose perf characteristics require scrutiny. The main critical
180 * mutex is a *per-thread* mutex (hence a non-`static` member, #m_pools_sorted_by_base_mutex). It is to be locked:
181 * - (Frequent) In end-user thread: lookup() -- around the lookup of #m_pools_sorted_by_base.
182 * - (Rare) In pusher thread: push_pools() -- around the replacement of #m_pools_sorted_by_base.
183 * - Since, if one assumes for simplicity of exposition that there's only one update happening at a time,
184 * this implies *at most* 2 threads contending for the lock, and usually only 1, this is perf-acceptable.
185 *
186 * @note That says "creates the need for locking," but it is possible to eliminate the (frequently accessed)
187 * mutex as well which would get back some more perf. See "Potential design improvement."
188 *
189 * There is another important lock involved. Per `flow::util::Thread_local_state_registry`, when looping
190 * over extant thread-local objects (`*this`es in our case) -- a key service of that utility module -- one
191 * shall lock a built-in central mutex via `Thread_local_state_registry.while_locked(F)`, where `F()` contains
192 * the code to copy-over the canonical map into individual `*this`es. Hence the directive to use
193 * `state_per_thread` in `F(state_per_thread)` to obtain the `*this`es.
194 *
195 * @note Tip: Since it is likely that the user code wants to protect against concurrent updates to the canonical map,
196 * it can take advantage of the mutex mentioned in the previous paragraph. That is `F()` given to
197 * `while_locked()` can perform the update of the canonical map first as well.
198 *
199 * Thus, during an update push_pools() code-flow, for a given `*this`, the central lock is locked, then the per-thread
200 * lock, then #m_pools_sorted_by_base is updated, then the locks are unlocked (in opposite order).
201 *
202 * During a pull code-flow, only the central lock is locked, then #m_pools_sorted_by_base is initialized (before
203 * being available to the user).
204 *
205 * During the lookup() code-flow, only the per-thread lock is locked.
206 *
207 * There is no deadlock.
208 *
209 * ### Design / Impl: Potential design improvement ###
210 * This little section is basically a to-do:
211 *
212 * @todo The algorithm used in Thread_local_pool_lookup_rev (owner-side and borrower-side), and similarly
213 * Thread_local_pool_lookup_fwd (borrower-side only), that relies on a frequently locked, but ~never contended,
214 * mutex can be improved further by instead using some one-way atomic signaling. Please read the commentary
215 * after this to-do in the code.
216 *
217 * The existing algorithm is nice. Along the frequently-called fast-path, namely in lookup(), a mutex is
218 * [un]locked every single time, but there's almost never another thread contending for it (and even then at most 1).
219 * So the slightly annoying cost that's still there = the ~uncontended lock+unlock ops. That's quick but may well
220 * be comparable to the map-lookup itself. We do optimize the map-lookup, and it'd be nice to cut down the [un]lock
221 * latency too. That said, unlike w/r/t the overall larger problem -- where we had real-world evidence that, say,
222 * doing a straight fully contended central-mutex [un]lock caused massive perf problems -- this smaller deficit is
223 * reasoned from just the code, not any field observations. Even so the improvement might be simple enough to
224 * "just" apply preemptively. To wit, for a given thread that would lookup():
225 *
226 * Currently there is first the *push* (lock { update thread's map }), second the *use* in `lookup()`
227 * (lock { use map for lookup }). In short: This could be turned into a one-way
228 * hand-off/produce-consume type of thing. The product is the thread's *pending* map copy.
229 * The producer is the push code: make the copy and set (this thread's) *pending* pointer to point to it, using an
230 * atomic release-exchange op. The (lazy) consumer is `lookup()`: no more lock op; but atomically consume
231 * (acquire-load / possibly acquire-exchange) the *pending* pointer; typically no change; but otherwise free
232 * the *current* map (of which it is the only user) and update *current*. Then use the map which is the *current*
233 * pointee.
234 *
235 * One technicality about the above we have to zoom into, as we don't want to mislead the implementer:
236 * The `lookup()` operation on the *pending* pointer is tempting to write as simply an atomic exchange with null:
237 * if we pop null out then no change; otherwise what we've got should become *current*. Slick and simple,
238 * but the existing mutex-lock op is already itself a read-modify-write (granted, there's the unlock too later,
239 * adding more cycles still). We should do better: separate into 1-2 ops instead. First do an acquire-load (no
240 * potential write). If null (fast-path)... done (no update needed); cycles nicely saved! If not null, *then*
241 * do the acquire-exchange-with-null after all (but it's the infrequent/slow-path). The thing the exchange op spits
242 * out -- cannot be null but might be different from whatever the earlier acquire-load probe yielded -- is to
243 * become *current*.
244 *
245 * In general, if this per-thread *pending* pointer is only ever modified via atomic-exchange, a clean algorithm is
246 * natural and apparent. Whichever module (either the push-code or `lookup()`) pops out a non-null ptr value becomes
247 * responsible for, at some point subsequently, freeing the pointee map. Push-code would free immediately: it
248 * means another central update happened before this thread got to consuming the preceding one's map. `lookup()`
249 * module would free it once *current* map is itself replaced later.
250 *
251 * ### Stats -- If #S_LOOKUP_CAN_FAIL is `true` only ###
252 * The object at `static` Pool_lookup_global_stats<Shm_arena, true>::stats() -- a global, per-`decltype(*this)`
253 * arena_lend::stat::Owner_pool_lookup_global_stats -- contains some interesting stats as updated by every `*this`.
254 *
255 * To reset this stat-set, use Pool_lookup_global_stats<Shm_arena, true>::stats_reset().
256 *
257 * ### Stats -- If #S_LOOKUP_CAN_FAIL is `false` only ###
258 * The object at `static` Pool_lookup_global_stats<Shm_arena, false>::stats() -- a global, per-`decltype(*this)`
259 * arena_lend::stat::Borrower_pool_lookup_global_stats -- contains some interesting stats as updated by every `*this`.
260 *
261 * To reset this stat-set, use Pool_lookup_global_stats<Shm_arena, false>::stats_reset().
262 *
263 * @tparam Repository_t
264 * See above. Formally(ish) there are two requirements/properties. 1, if and only if
265 * `is_same_v<R1, R2> == false` then `Thread_local_pool_lookup_rev<R1, ...>` and
266 * `Thread_local_pool_lookup_rev<R2, ...>` are independent registries; otherwise they are the same registry.
267 * 2, `Repository_t::get_instance().tl_copy_rev_pull_pools()` must exist and do what is
268 * explained above.
269 * @tparam LOOKUP_CAN_FAIL
270 * If `true`, lookup() may fail to find an address in any pool (yields `pool_id = 0` in that case).
271 * This is needed on the owner side, where an `Shm_pool_offset_ptr` with `CAN_STORE_RAW_PTR == true`
272 * may call `from_address()` on a non-SHM (stack/heap) address.
273 * If `false`, every address is assumed to reside in some known pool (borrower side), and lookup()
274 * has undefined behavior on a miss; pool sizes are not stored.
275 * @tparam Shm_arena_t
276 * See Pool_lookup_global_stats.
277 */

293 /**
294 * Reverse-lookup map type (base vaddr -> Pool_by_base). Used internally but exposed to our direct user via
295 * the push and pull APIs.
296 *
297 * ### Internally: Rationale for chosen type ###
298 * Used for #m_pools_sorted_by_base; is a `flat_map` (internally: sorted contiguous vector) rather than `std::map`
299 * (red-black tree). This is ideal here: lookup() -- the perf-critical hot path -- performs `upper_bound()` on
300 * contiguous memory (cache-friendly binary search) instead of pointer-chasing through scattered tree nodes.
301 *
302 * The downside of `flat_map` -- O(n) insertion -- is low-impact: the thread-local copy is never incrementally
303 * modified; it is only replaced wholesale in push_pools() (centrally when pool added/removed) and initialized
304 * wholesale in the pull path (once per thread). Both are off the fast-path.
305 */
306 using Map = boost::container::flat_map<void*, Pool_by_base>;

380/**
381 * Analogous to Thread_local_pool_lookup_rev but for forward lookup: pool ID -> base vaddr. Used borrower-side
382 * only (read on as to why not owner-side).
383 *
384 * As far as we know, if one needs multithreaded such lookup with high performance, then
385 * borrower-side one should use Thread_local_pool_lookup_fwd. However owner-side one can use a
386 * straight `static thread_local` map from pool ID to `void*`, updating it lazily on-demand on cache miss (letting
387 * outdated pool entries negligibly leak). Such a solution is insufficient for borrower-side lookup, as
388 * it is possible a pool is mapped, unmapped, then mapped to a different base vaddr -- but a thread's cache
389 * might (forever) store the now-incorrect base-vaddr. Hence use Thread_local_pool_lookup_fwd.
390 *
391 * The API and impl are the same: thread-local caches in a global #s_registry, with the same pull/push
392 * protocol and the same per-thread locking strategy. See Thread_local_pool_lookup_rev class doc header for
393 * the full design discussion; only the differences are noted here:
394 * - The cached data structure, while still a map, is simply looked-up directly: pool ID in, base-vaddr out.
395 * The chosen type for #Map may be of interest (see `Map` doc header).
396 * - The pull callback is `Repository::get_instance().tl_copy_fwd_pull_pools()` (not `..._rev_...`).
397 *
398 * ### Stats ###
399 * The object at `static` Pool_lookup_global_stats<Shm_arena, false>::stats() -- a global, per-`decltype(*this)`
400 * arena_lend::stat::Borrower_pool_lookup_global_stats -- contains some interesting stats as updated by every `*this`.
401 *
402 * To reset this stat-set, use Pool_lookup_global_stats<Shm_arena, false>::stats_reset().
403 *
404 * @tparam Repository_t
405 * Same concept as for Thread_local_pool_lookup_rev.
406 * `Repository_t::get_instance().tl_copy_fwd_pull_pools()` must exist and behave analogously
407 * to the reverse counterpart.
408 * @tparam Shm_arena_t
409 * See Pool_lookup_global_stats.
410 */

536template<typename Repository_t, bool LOOKUP_CAN_FAIL, typename Shm_arena_t>
537void Thread_local_pool_lookup_rev<Repository_t, LOOKUP_CAN_FAIL, Shm_arena_t>::lookup(const void* address,
538 pool_id_t& pool_id,
539 pool_offset_t& pool_offset) const
540{
541 // Lock with minimal contention (see class doc header Impl section).
542 flow::util::Lock_guard<decltype(m_pools_sorted_by_base_mutex)> lock{m_pools_sorted_by_base_mutex};
543
544 /* It would be typical in the rest of the code base to add assert(s)/guards/things like that.
545 * However we choose to skip past anything that might take cycles in production -- where it is not all that uncommon
546 * to keep assertions enabled. We're playing a little chicken here on purpose; the perf here has been
547 * shown under load to be of high impact. */
548
549 /* upper_bound() returns the first element with base > address. The candidate pool (if any) is the one
550 * just before that. Unlike with lower_bound(), there is no exact-match special case: always `--it`. */
551 auto it = m_pools_sorted_by_base.upper_bound(const_cast<void*>(address));
552
553 if constexpr(S_LOOKUP_CAN_FAIL)
554 {
555 if (it == m_pools_sorted_by_base.begin())
556 {
557 pool_id = 0;
558 return;
559 }
560 }
561 // else: Cannot be begin() by contract (address is in some pool).
562
563 --it;
564
565 const auto& pool_data = it->second;
566 const auto addr_ptr = reinterpret_cast<uintptr_t>(address);
567 const auto pool_base = reinterpret_cast<uintptr_t>(it->first);
568
569 if constexpr(S_LOOKUP_CAN_FAIL)
570 {
571 /* Check that address actually falls within this pool's [base, base + size) range.
572 * If not, it's in the gap between pools (or past the last pool). */
573 if (addr_ptr >= (pool_base + pool_data.m_sz_or_0))
574 {
575 pool_id = 0;
576 return;
577 }
578 }
579
580 pool_id = pool_data.m_id;
581 pool_offset = addr_ptr - pool_base;
582} // Thread_local_pool_lookup_rev::lookup()
