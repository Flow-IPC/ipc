ipc::shm::arena_lend::detail::Use_count_registry::Header::Header ( )

Ctor that leaves all scalars uninitialized, optionals empty, and m_bitmap_words untouched (therefore non-resident but zero-filled per that property of in-SHM vaddr areas).

Rationale

Why ctor exists instead of just letting us be aggregate-initialized a-la { sz, extra_hdr_sz, ... }: See m_bitmap_words doc header. It'd be shorter and nicer if we could just use the aggregate-init but can't.

Why ctor does not take the init values for various scalars, which are going to be immediately set anyway by daddy Use_count_registry: It'd be pointless boiler-plate for a single-use struct type.

◆ m_bitmap_words

Bitmap_words ipc::shm::arena_lend::detail::Use_count_registry::Header::m_bitmap_words

The bitmap, where 0 represents a free slot; 1 a taken slot.

Starts all zeroes; first special allocate() sets a small (at least 1) number of words at the start to consist of only 1-bits – corresponding to the metadata area albeit rounded up to whole words for simplicity. These are never freed, as that allocate() cannot be deallocate()d. The rest of the bits are for the remaining (actual) [de]allocate() calls.

C++ technicalities mean that we have to take some special measures to avoid zero-filling it (which (1) is redundant, as the in-SHM bytes are initially pre-zeroed, and (2) would make them resident which we – see Use_count_registry ctor – specifically don't want, as we can save some decent RAM in this area by avoiding it). Hence the presence of Header ctor.

◆ m_bitmap_words_next_search_idx

size_t ipc::shm::arena_lend::detail::Use_count_registry::Header::m_bitmap_words_next_search_idx

In the range [0, m_bitmap_words_sz), this is the index into m_bitmap_words where the next search (in allocate()) will begin.

Simply, this is the same word that the last allocate() found the 0-bit in; unless that bit was the last bit of the words; in which case it is the next word; unless that word would equal m_bitmap_words_sz; then it is 0.

So it'll search the same word again if there are bits left at the time in it (yes, that means potentially searching through some bits we already have seen to be 1), or the next word (wrapping around the active quanta) if none left in that word.

Note for context: deallocate() could occur before the next allocate(); it could open up more 0 bits in the current word; so none of this is an exact science. It is a heuristic algorithm meant to keep moving forward/around so as to hopefully find 0-bits quickly each time.

◆ m_bitmap_words_sz

size_t ipc::shm::arena_lend::detail::Use_count_registry::Header::m_bitmap_words_sz

At all times a positive multiple of S_BITMAP_QUANTUM_SZ / sizeof(bit_word_t), and at most S_USE_COUNTS_CAPACITY / sizeof(bit_word_t) / 8, this equals the number of m_bitmap_words elements that represent the currently active quanta.

I.e., it is the number of bitmap words, starting from the m_bitmap_words.begin(), through which allocate() shall search (in the bitmap). Once it fails to find a single 0-bit in the entire area, this is incremented by S_BITMAP_QUANTUM_SZ / sizeof(bit_word_t) (number of words in 1 quantum). If it already equals m_bitmap_words.size() – i.e., S_USE_COUNTS_CAPACITY / sizeof(bit_word_t) / 8 (all the available quanta) – then allocate() fails (no slots available).
