77/**
78 * A type used by struc::Channel for internal safety/security/auth needs. See in particular
79 * struc::Channel constructors, both the regular-channel one and the session-master-channel one.
80 * That said: The user of ipc::transport (aided by ipc::session) structured layer shall generally be unconcerned
81 * with this, in practice, as ipc::session machinery will take care of:
82 * - setting up the session master struc::Channel which will generate this token during initial setup (log-in);
83 * and
84 * - setting up further `struc::Channel`s as requested by the user (the preceding bullet's token shall be
85 * passed to each new struc::Channel and expected internally in all messages).
86 *
87 * However, if one plans to *create* a struc::Channel directly (as ipc::session does), then one must have some
88 * limited understanding of this guy's existence (if not the internal details).
89 *
90 * @internal
91 * As you can see: internally it is a UUID (RFC 4122 Universally Unique IDentifier) which is 128 bits (16 bytes)
92 * in size. It's also a POD (Plain Old Data object), meaning it's ctor-free (direct-initialized) and can be
93 * `memcpy()`d around and such. See boost.uuid docs (which are simple).
94 *
95 * ### Use and rationale thereof ###
96 * A session master channel struc::Channel, operating in server mode during the log-in phase, will (as of
97 * this writing anyway) generate this using the boost.uuid random UUID generator. From that point on all
98 * channels spawned through that guy (by ipc::session) will be cted with that token value; and all messages both
99 * in those channels and the original master channel (after the log-in message exchange) will send this value
100 * and ensure any in-message has that value (or immediately hose the channel -- auth failure). This is a
101 * safety (not really security, due to the lack of token invalidation at least) measure. It will reduce chances
102 * that "wires get crossed," and a message goes into the wrong channel somehow.
103 *
104 * That's how it's used. Is the random-generator method of UUID generation acceptable for this use?
105 *
106 * A bit of research (starting in the RFC perhaps; or Wikipedia) shows that collisions are so cosmically rare as to
107 * make it, quite officially, a non-concern. Even if one does not accept that, however, suppose a collision does
108 * occur: two channels happen to generate the same UUID on the same machine around the same time. This (essentially
109 * impossible) scenario would not cause either channel to break; it would only allow (in theory) a token check
110 * to succeed where it shouldn't, if the fabled wires-crossed scenario occurred. This is an acceptable level of risk.
111 *
112 * Conversely, perhaps using UUIDs for this is overkill. 128 bits isn't heavy, but perhaps something smaller --
113 * maybe even much smaller, like 32 bits or even 16 -- would improve perf without really reducing effectiveness
114 * given the above rationale. Indeed that's worth considering but only in the phase where perf optimization is
115 * the explicit goal. Until then (if that even happens) the ability to use the nice boost.uuid library instead
116 * of rolling our own jankier/smaller UUID-like thing (or whatever) is well worth the alleged perf cost.
117 *
118 * @todo Look into whether something smaller than RFC 4122 UUIDs can and should be used for #Session_token.
119 * This would be for perf but may well be unnecessary. See discussion near this to-do.
120 */
121using Session_token = boost::uuids::uuid;

123/**
124 * Sequence of 1+ segment descriptions, each representing a live writable segment (of a capnp serialization of a
125 * capnp-`struct`) and optional header/prefix area immediately preceding it. As of this writing this is specifically
126 * 1+ `Basic_blob` *pointers* to blobs that directly represent those segments+header(s) which must stay alive while
127 * these pointers may be dereferenced. In each `Basic_blob` [`begin()`, `end()`)
128 * is the serialization segment itself; and space before `begin()` (of size `start()`) may
129 * be reserved for framing prefix/header to preserve zero-copy when transmitting such serializations over
130 * an IPC "wire." (Area after `end()` up to `capacity()` could represent a framing postfix, though as of this writing
131 * we assume only a header might exist, for simplicity. As long as possible we shall avoid adding a postfix into the
132 * design.)
133 *
134 * ### Rationale ###
135 * Why represent the segment+header as `Basic_blob` specifically? Answer: The relevant serialization engine(s) could
136 * internally represent data structures (namely segments and frame-prefix and such) however they want, and indeed by
137 * choosing `Basic_blob*` here essentially we force that impl to be specifically that. That is a very reasonable
138 * structure (and less-feature-filled, slightly-higher-performing than the derivative `Blob`),
139 * but why force it? Indeed, as regards a public API, something merely describing locations and sizes *inside*
140 * the data structure of choice would be stylistically more direct and therefore more flexible/better. To wit
141 * #Segment_bufs (sequence of pointer + size pairs essentially) is almost such a thing; just it's not *quite* enough,
142 * because it does not directly/intuitively represent the header/prefix areas that might precede segments (but
143 * instead merely the segments themselves). So we choose `Basic_blob*` simply
144 * because it is (1) a decent choice for all impls in practice and (2) sufficiently-well describes both
145 * segments and frame headers nearby. It is slightly inflexible but acceptable overall.
146 *
147 * @todo As per nearby Rationale comment, `Segment_ptrs` element type would ideally be a view *into* `Blob`-or-similar
148 * instead of actual `Basic_blob*`, to decouple impl from API more cleanly. One approach might be to develop a
149 * `flow::util` class/template, a peer of the `flow::util::Blob` hierarchy, that specifically represents a view into a
150 * `Blob`-type-thing (perhaps 1 variant for mutable, 1 variant for immutable), perhaps analogously to how
151 * `span<uint8_t>` + `span<const uint8_t>` is each a view into `vector<uint8_t>` (minus the latter's capacity).
152 * It would therefore store a pointer, a size, a capacity, and a start-index -- representing a main buffer (`size()`
153 * in size), N-byte header/prefix (N = `start()`), and M-byte postfix (M = `capacity() - start() - size()`).
154 * (A more economical buffer+header version -- directly applicable here -- might store all of those minus the
155 * capacity, meaning there is no postfix area.) Possible names might be `Blob_view_const` (read-only view
156 * into buffer plus header plus postfix), `Blob_view_mutable` (same plus writable access),
157 * `Prefixed_byte_span_const` (`Blob_view_const` minus postfix area), `Prefixed_byte_span_mutable` (`Blob_view_mutable`
158 * minus postfix area). #Segment_ptrs would likely be `vector<Prefixed_byte_span_mutable>`.
159 */
160using Segment_ptrs = std::vector<flow::util::Blob_sans_log_context*>;
161
162/**
163 * Simpler cousin of #Segment_ptrs, this represents the IPC-transmissible representation of a capnp serialization
164 * of a capnp-`struct` including any framing header(s), expressed as simply a sequence of N read-only views, each
165 * containing a pointer to header-if-any-followed-by-serialization-segment and the size in bytes thereof.
166 *
167 * Note that while #Segment_ptrs contains info on header size, this `Segment_bufs` does not: So to properly interpret
168 * the given `Blob_const` element, one must know the size of the header therein (if any; by convention we can say that
169 * no header => header size is 0 => segment = entire `Blob_const`).
170 */
171using Segment_bufs = std::vector<util::Blob_const>;
172
173/**
174 * A simple data structure describing the segments (if any) in a #Segment_bufs (or similar) structure which had to
175 * be split (presumably due to size constraints); by following the indices/sizes into a post-split #Segment_bufs one
176 * can join the appropriate elements so as to obtain the original pre-split segments.
177 *
178 * The order of `Split_segment`s is strictly from left to right. A reasonable join algorithm, therefore, would
179 * iterate over a `Split_segments` in *reverse* order; for each Split_segment join the 2+ segments in the post-split
180 * #Segment_bufs (or similar) described therein, in-place. By doing this in reverse order, handling Split_segment
181 * A before B will not invalidate the start-index member in B.
182 *
183 * By convention #Split_segments shall include a Split_segment only if a segment actually needed to be split.
184 */
185using Split_segments = std::vector<Split_segment>;

194/**
195 * Message ID uniquely identifying outgoing message (Msg_out, among all other `Msg_out`s), per channel; and
196 * similarly incoming message (Msg_in, among `Msg_in`s), per channel. 0 is a sentinel value and not a valid
197 * user message ID. A message ID pertains to a *sent* or *received* *instance* of a user-created Msg_out
198 * (and its in-message counterpart Msg_in). A given Msg_out can be sent 2+ times through a given
199 * struc::Channel and even a *different* struc::Channel; a different message ID will pertain to each
200 * of those times for a given struc::Channel. Therefore there is no #msg_id_t *inside* a user Msg_out.
201 *
202 * This type is in the public API, as the message ID is made available in certain contexts for:
203 * - referring to an earlier-sent message, such as in struc::Channel::undo_expect_responses(); and
204 * - logging/reporting.
205 *
206 * @internal
207 * It can also be used as a sequence number and is therefore assigned from sequence 1, 2, ... (0 is sentinel).
208 *
209 * ### Rationale for type used ###
210 * Needs to be big enough to where there's no chance it overflows in a given channel for a given direction.
211 * Assume 1 billion messages per second, or about 2^30 msg/s. That would take 2^(64-30), or 2^34, seconds,
212 * or over 500 years, to overflow. So this should be fine. Moreover overflow is fine in that case, in practice,
213 * if this is used only as a unique ID; it would however in theory present problems if used as a sequence number.
214 */
215using msg_id_t = uint64_t;
