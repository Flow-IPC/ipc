Detailed Description

template<typename Repository_t, typename Shm_arena_t>
class ipc::shm::arena_lend::detail::Thread_local_pool_lookup_fwd< Repository_t, Shm_arena_t >

Analogous to Thread_local_pool_lookup_rev but for forward lookup: pool ID -> base vaddr.

Used borrower-side only (read on as to why not owner-side).

As far as we know, if one needs multithreaded such lookup with high performance, then borrower-side one should use Thread_local_pool_lookup_fwd. However owner-side one can use a straight static thread_local map from pool ID to void*, updating it lazily on-demand on cache miss (letting outdated pool entries negligibly leak). Such a solution is insufficient for borrower-side lookup, as it is possible a pool is mapped, unmapped, then mapped to a different base vaddr – but a thread's cache might (forever) store the now-incorrect base-vaddr. Hence use Thread_local_pool_lookup_fwd.

The API and impl are the same: thread-local caches in a global s_registry, with the same pull/push protocol and the same per-thread locking strategy. See Thread_local_pool_lookup_rev class doc header for the full design discussion; only the differences are noted here:

  • The cached data structure, while still a map, is simply looked-up directly: pool ID in, base-vaddr out. The chosen type for Map may be of interest (see Map doc header).
  • The pull callback is Repository::get_instance().tl_copy_fwd_pull_pools() (not ..._rev_...).

Stats

The object at static Pool_lookup_global_stats<Shm_arena, false>::stats() – a global, per-decltype(*this) arena_lend::stat::Borrower_pool_lookup_global_stats – contains some interesting stats as updated by every *this.

To reset this stat-set, use Pool_lookup_global_stats<Shm_arena, false>::stats_reset().

Forward-lookup map type (pool ID -> base vaddr).

Used internally but exposed to our direct user via the push and pull APIs.

Internally: Rationale for chosen type

As the Thread_local_pool_lookup_rev::Map cousin uses flat_map (sorted contiguous vector) for cache-friendly upper_bound(), we analogously use unordered_flat_map (open-addressing hash table) for cache-friendly find(). Same rationale.
