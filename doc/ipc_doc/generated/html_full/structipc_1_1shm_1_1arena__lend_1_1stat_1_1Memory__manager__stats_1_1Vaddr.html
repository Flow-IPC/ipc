Detailed Description

Sub-group: the arena's virtual-address-space / page-state footprint – how much memory it currently holds from the OS and in what state.

All members are GAUGEs in bytes.

Approximate relationships (sizes are post size-class quantization; see jemalloc docs for precise meanings):

  • m_mapped_sz ~= m_active_sz + m_inactive_resident_sz + m_inactive_muzzy_sz + allocator-metadata.
  • m_resident_sz ~= m_active_sz + m_inactive_resident_sz + allocator-metadata (excludes muzzy + retained).
  • m_retained_sz is separate: space excluded from m_mapped_sz book-keeping yet deliberately kept mapped, saved for cheap reuse (see its doc header).

size_t ipc::shm::arena_lend::stat::Memory_manager_stats::Vaddr::m_active_sz = 0

(Gauge) Bytes in pages backing live (active) allocations: ~= live allocated bytes + unused space on those same pages, set aside for future allocations of the same size.

(jemalloc packs same-size small allocations together into pages; such a page counts in full while at least one of them is live.) Excludes allocator metadata.

◆ m_inactive_muzzy_sz

size_t ipc::shm::arena_lend::stat::Memory_manager_stats::Vaddr::m_inactive_muzzy_sz = 0

(Gauge) Not-active (see also m_inactive_resident_sz) bytes that the memory manager has returned to the OS lazily: the OS may reclaim them at its leisure, and until then they may remain resident.

For SHM-jemalloc: jemalloc's muzzy pages (pmuzzy x page-size). SHM-jemalloc has no lazy-return ability (it returns pages via SHM-object hole-punching; see m_retained_sz), so this is always zero.

◆ m_inactive_resident_sz

size_t ipc::shm::arena_lend::stat::Memory_manager_stats::Vaddr::m_inactive_resident_sz = 0

(Gauge) Not-active (so freed from/not yet used for allocated user-buffers; contrast with m_active_sz) bytes not yet returned to the OS; hence physically resident (not available for general use by OS) – to the extent they were ever touched.

This is cheaply reusable in-place (no syscall required; just read/write at vaddr).

For SHM-jemalloc: jemalloc's dirty pages (pdirty x page-size). (This "dirty" is jemalloc's term: unused but not yet purged. It is unrelated to the OS-kernel sense of "dirty page.")

◆ m_mapped_sz

size_t ipc::shm::arena_lend::stat::Memory_manager_stats::Vaddr::m_mapped_sz = 0

(Gauge) Total bytes currently mapped from the OS into the arena's address space.

See sub-group doc header.

Reminder: This is not RAM in use (taken from general OS use); a page becomes resident only once accessed. E.g.: it is entirely possible and not even unusual for a particular vaddr area (in our case backed by a SHM pool) to be, say, mapped for 100 megabytes – but only 500 kilobytes of it correspond to actual RAM use (at most m_resident_sz).

◆ m_retained_sz

size_t ipc::shm::arena_lend::stat::Memory_manager_stats::Vaddr::m_retained_sz = 0

(Gauge) Bytes of once-used vaddr space the memory-manager has excluded from m_mapped_sz book-keeping yet deliberately keeps mapped – not returned to the OS – saved for cheap reuse (no memory-map op needed; the range is simply handed back out on a suitable future allocation).

For SHM-jemalloc this state is entered when jemalloc asks to remove unused extent (SHM-pool) space, and policy declines (as of this writing in our impl we indeed always decline): the backing physical pages are then released via SHM-object hole-punching – fallocate(FALLOC_FL_PUNCH_HOLE) et al in Linux – while the vaddr range and its SHM-pool remain intact.

SHM-jemalloc: See jemalloc::Ipc_arena::optional_remove_shm_pool().
