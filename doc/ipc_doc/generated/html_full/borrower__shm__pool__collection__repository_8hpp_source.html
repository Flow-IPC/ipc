51/**
52 * Singleton repository for borrowed SHM-pool data. All sessions (jemalloc::Shm_session) in this
53 * process funnel their borrowed pool info here, enabling offset-pointer resolution (to_address(), from_address())
54 * and pool-handle lifecycle management (ref-counted open/close).
55 *
56 * @note We mention #Uniq_collection_id below... though as of this writing it is not used in the actual public
57 * API. When we do this, we just mean an (`owner_id_t`, `collection_id_t`) pair. Such a pair ultra-uniquely
58 * identifies an arena a/k/a owner-pool-collection.
59 *
60 * ### Responsibility: Pool (+arena) lifecycle ###
61 * To summarize: First registration of a globally-unique `pool_id` opens the pool-handle/maps the vaddr area
62 * (stores a `Shm_pool`); last deregistration undoes both. That is the bottom line. To make that work you
63 * must register and deregister SHM-pools (and arenas a/k/a collections containing them).
64 *
65 * - register_collection() upon an opposing process lending its arena, via a `Shm_session`, to us.
66 * - deregister_collection() for each arena that had been lent, when that arena is un-lent.
67 * (As of this writing one does not un-lend an arena without closing session, which unlends *all*
68 * lent-through-it arenas; but we support the former here no problem.)
69 * - The same (meaning, same #Uniq_collection_id) arena being lent to us, via a different `Shm_session`, at
70 * the same time is possible; call it again then. Thus a given arena may be registered 1+ times
71 * concurrently.
72 * - Nothing spectacular happens once a particular arena goes from not-registered to 1x-registered, or vice versa.
73 * We track them at all, really, only because we need certain info on a per-arena (collection) basis
74 * (the `pool_name_base` at least).
75 * - register_shm_pool() and deregister_shm_pool() w/r/t SHM-pools being lent via `Shm_session`s works just the
76 * same... but know the following:
77 * - If pool P in arena C was lent through session S, then by definition first S notes the lending of C, then
78 * the lending of P. Therefore you shall call, for session S, `register_collection(C)` and
79 * `register_shm_pool(P)` in that order. (The same order of things, for the same P and therefore C may
80 * happen at any time including overlapping chronologically... but only for a different session than S.)
81 * This is all vanilla `Shm_session` stuff; we are restating it for context/exposition purposes.
82 * - When a given pool P goes from not-registered to 1x-registered, a `Shm_pool` is created and saved which means
83 * (as noted already) open SHM-pool-handle, map it into SHM.... Fairly spectacular!
84 * - When the reverse occurs, it is released: unmap from SHM, close SHM-pool-handle. Also spectacular!
85 * In fact this is required for the underlying RAM to be returned to the system for general use. (It is
86 * required but not sufficient: There may be SHM-pool-handles open in owner, and the pool-name
87 * may be registered in the file-system; owner side handles all that including undoing it, even after crash.)
88 *
89 * ### Responsibility: Offset-pointer resolution for Shm_pool_offset_ptr ###
90 * One uses to_address() for forward lookup (`pool_id` + offset -> vaddr).
91 * One uses from_address() for the reverse lookup (vaddr -> `pool_id` + offset).
92 *
93 * @see ipc::shm::arena_lend::Shm_pool_offset_ptr
94 *
95 * The `register_*()` stuff above provides the necessary inputs to make these work.
96 *
97 * ### Impl ###
98 * We could pontificate here about this and that impl detail, but it would probably not be helpful didactically,
99 * as it's all about various details, and those are documented closer to the fact. So we'd just be redundant.
100 * In this case it's best to just start with the data members and see how things interact.
101 *
102 * That said, we have found that the biggest hurdle is just grasping the 2 responsibilities in some depth. So
103 * to (re-)emphasize:
104 * - We need to keep *all* SHM-pools (`shared_ptr<Shm_pool>`) open, each one if and only if at least 1 -- possibly
105 * more -- session is borrowing it. Grasp how a pool ID is globally unique forever; but it does pertain to
106 * a particular arena (ID = #Uniq_collection_id = owner-PID + ordinal collection-ID for that PID), and (from
107 * both a `Shm_session`'s PoV *and* (to some extent) our PoV) this is significant. In our case that's so, b/c
108 * a `pool_name_base` `Shared_name`-fragment (prefix) is per-arena and determines the pool name, which is how
109 * we can even open the `Shm_pool`.
110 * - We need to *also* funnel that info into a global repository of *borrower* pool base-vaddrs and IDs.
111 * This enables high-performance computations for `Shm_pool_offset_ptr`s... which will absolutely litter
112 * any STL-compliant-container-stored-in-SHM. We provide the relevant output of this info: to_address() and
113 * from_address().
114 *
115 * Having grasped all that, go forth to the data members and the methods' insides. OK, no, one more thing....
116 *
117 * ### Impl: forward/reverse lookup and the 2 mutexes ###
118 * While the register/deregister calls feed the info needed for the following topic, that topic is otherwise
119 * essentially its own thing. That thing is: We are the top-level of the impl for:
120 * - Forward-lookup (to_address()) whose complexity reduces to: lookup from #pool_id_t to `void*` base-vaddr
121 * of that SHM-pool.
122 * - Reverse-lookup (from_address()) which is: lookup from vaddr `void*` within a SHM-pool to: #pool_id_t
123 * (of containing pool) and #pool_offset_t (integer byte offset from that pool's base-vaddr).
124 *
125 * Updates to, and lookup from, the relevant data structures we treat as essentially mutually independent
126 * in the sense of Fwd lookup versus Rev lookup. That is: We allow, say, 2
127 * `[de]register_shm_pool()` ops to be somewhat interleaved. More specifically: there are 2 mutexes, and
128 * in `[de]register_shm_pool()` we always lock/unlock one, then the other. E.g., there could be 1 `Shm_session`
129 * registering a pool while another is shutting down and deregistering a pool, so the update order of the
130 * Fwd and Rev structures might look chronologically like F1R1F2R2 or F1F2R1R2 or F2F1R1R2 or....
131 * If there is some danger to this, we don't see it (v). The benefit is that we can place the relevant blocks of
132 * code to be next to each other but independent -- no shared mutex, basically. This helps impl simplicity, as the
133 * primitives we use for each task (Fwd data update, Rev data update) are separate modules, and at least in one
134 * case a primitive (detail::Shm_pool_repo_lookup_core_rev) is reused in owner-land (detail::Owner_shm_pool_repository).
135 * Having to link the 2 things together code-wise by sharing a mutex would have been very annoying.
136 *
137 * (v): Footnote: There is one racy danger, in fact, having to do with pool-address reuse by the OS.
138 * deregister_shm_pool() avoids this while explaining the specifics inside.
139 *
140 * So now we can talk about how each of those is implemented, separately.
141 *
142 * ### Impl: Forward-lookup ###
143 * We use detail::Thread_local_pool_lookup_fwd (alias #Tl_copy_fwd). See its doc header first; then come back here.
144 * Welcome back:
145 * - #m_rc_pools_by_id is the canonical map from which we push/it pulls into the thread-local copies.
146 * - The "pull" impl is, as required by #Tl_copy_fwd, named tl_copy_fwd_pull_pools().
147 * - The "push" behavior is performed, in the manner required by #Tl_copy_fwd, within register_shm_pool() and
148 * deregister_shm_pool().
149 * - As recommended by #Tl_copy_fwd docs, we use its built-in central mutex as our overall Fwd-update mutex
150 * (1 of the 2 mutexes introduced above, thus synchronizing simultaneous SHM-pool-set updates) as well as
151 * to guard the push-op (as required by #Tl_copy_fwd formally). Nice to use just one mutex for Fwd.
152 *
153 * ### Impl: Reverse-lookup ###
154 * We simply use detail::Shm_pool_repo_lookup_core_rev, notably with
155 * Shm_pool_repo_lookup_core_rev::S_LOOKUP_CAN_FAIL at `false` (only in-SHM addresses are supported on borrower side).
156 * See its doc header. It has its own mutex inside the simple-looking ops we invoke (`.insert()`, `.erase()`).
157 * That's mutex 2 of 2.
158 *
159 * If you're wondering why Rev is so simple and encapsulated, while Fwd required a bunch of bullet points and
160 * code: It's just because we are the only place in Flow-IPC that needs to do what we do for Fwd lookup.
161 * (Owner-side Fwd lookup is algorithmically far simpler. The reason for that is, as of this writing, briefly explained
162 * in detail::Thread_local_pool_lookup_fwd doc header.) However Rev lookup is ~identical
163 * for us and in owner-land; hence it is encapsulated in `Shm_pool_repo_lookup_core_rev` and used here and ~identically
164 * in detail::Owner_shm_pool_repository.
165 *
166 * @tparam Shm_arena_t
167 * SHM-arena type (e.g., `jemalloc::Ipc_arena`). Not accessed API-wise; serves as a compile-time
168 * discriminator so that `Borrower_shm_pool_collection_repository<A1>` and
169 * `Borrower_shm_pool_collection_repository<A2>` are fully independent singleton registries
170 * if `A1 != A2`.
171 */

226 /**
227 * Key high-performance API: Given an in-SHM location as the pool and in-pool offset (values that remain constant
228 * between the lending process and us, the borrowing process) returns the process-local (local process being us,
229 * the borrower) vaddr pointing to that in-SHM location.
230 *
231 * Context: In particular, when processing fancy-pointers `Shm_pool_offset_ptr` (in STL-compliant structures
232 * stored in SHM and borrowed by this process) and top-level borrowed (by us) objects, this shall be called.
233 * E.g., when traversing some in-SHM borrowed STL-container, such lookups may be quite frequent.
234 *
235 * Perf: as of this writing this is a ~no-contention mutex-lock and a hash-map lookup of vaddr by integer;
236 * plus an offset addition.
237 *
238 * ### Corner cases ###
239 * If `pool_id` is that of a no-longer-borrowed, or never-borrowed, SHM-pool: undefined behavior.
240 *
241 * Otherwise, the returned address is non-null; however it shall simply equal the pool's base-vaddr plus
242 * `pool_offset`. If it is negative or beyond the pool's size, then the returned address shall be outside
243 * the specified pool; we shall not bounds-check it.
244 *
245 * @see to_address_safe() for a variation that avoids the aforementioned undefined behavior.
246 *
247 * @param pool_id
248 * The identifier of the SHM-pool.
249 * @param pool_offset
250 * The offset in bytes off the pool `pool_id` base vaddr.
251 * @return Non-null vaddr.
252 */
253 static void* to_address(pool_id_t pool_id, pool_offset_t pool_offset);
254
255 /**
256 * Identical to to_address() except returns null on invalid (no-longer borrowed or never-borrowed) pool ID.
257 *
258 * ### Rationale ###
259 * The precipitating use-case is `Shm_session::borrow_object()` that makes a best-effort safety check on
260 * the values ostensibly IPCed-over from the lending process. Even so, we can only do so much due to certain
261 * perf-based internal decisions made as of this writing: In particular `pool_offset` can still point outside
262 * the (valid) pool; this will not cause us to return null, even though for that particular use-case at least
263 * that would be preferable.
264 *
265 * @param pool_id
266 * See above.
267 * @param pool_offset
268 * See above.
269 * @return Non-null vaddr; or null if `pool_id` not found.
270 */
271 static void* to_address_safe(pool_id_t pool_id, pool_offset_t pool_offset);
272
273 /**
274 * Key high-performance API: Essentially the reverse of to_address().
275 *
276 * Context: A reverse-lookup should be much less frequent than forward-lookup to_address(); but typical STL-container
277 * code at times must figure out a `pointer` (in our case `Shm_pool_offset_ptr`) from a vaddr. (In heap-land
278 * the two are the same, but in SHM-land they are not.)
279 *
280 * Perf: similar to to_address() in terms of mutexes and maps involved; however the actual map lookup is essentially
281 * a binary search through a sorted array.
282 *
283 * If `address` param is invalid (not in any borrowed pool), behavior is undefined.
284 *
285 * @param address
286 * Vaddr to within a SHM-pool.
287 * @param pool_id
288 * Out-arg where the identifier of the pool containing `address` shall be placed.
289 * @param pool_offset
290 * Out-arg where the offset of a byte within pool `pool_id` at which `address` points shall
291 * be placed.
292 */
293 static void from_address(const void* address, pool_id_t& pool_id, pool_offset_t& pool_offset);

475 * The maximum `.size()` of #m_per_arena_borrower_pool_stats; once reached, and a `Stat_set` is to be
476 * inserted, the LRU `Stat_set` is erased from that map.
477 *
478 * @see #m_per_arena_borrower_pool_stats doc header for discussion of the LRU-eviction algorithm.
479 *
480 * ### Value ###
481 * We ran some experiments indicating how long stats()/stats_reset()/pretty-print of stats() takes and chose
482 * a value well below the point where those times stopped being reasonable. Since the value is still pretty high
483 * (e.g., a user is likely to pass a much lower, nonzero `per_arena_stats_sz_limit_or_0` to stats()),
484 * subjectively speaking, we feel this worked out OK.
485 */
486 static constexpr size_t S_N_PER_ARENA_BORROWER_POOL_STATS_SZ_LIMIT = 1000;

505 // Data.
506
507 /**
508 * Flat pools map: pool-ID -> ref-counted pool data. Pool IDs are globally unique across all owners/collections.
509 * Mutex: provided by `Tl_copy_fwd::s_registry.while_locked()`; see register_shm_pool(),
510 * deregister_shm_pool().
511 *
512 * @see Class doc header section "Impl: forward/reverse lookup and the 2 mutexes" and on.
513 */
514 boost::unordered_flat_map<pool_id_t, Pool_rc_data> m_rc_pools_by_id;
515
516 /// Map: (owner-ID, collection-ID) -> ref-counted collection data. Same mutex as #m_rc_pools_by_id.
517 boost::unordered_flat_map<Uniq_collection_id, Collection_data> m_collection_data_map;
518
519 /**
520 * Generally similar to `Shm_session::m_borrower_pool_stats` but across *all* `Shm_session`s (for the
521 * same SHM-provider <=> #Shm_arena type). Read that guy's doc header first. Then continue here:
522 *
523 * Regarding perf: basically same thing; there shall be potentially multiple `Shm_session`s around, but
524 * not so many that the frequency-of-stat-updates picture is fundamentally changed.
525 *
526 * Regarding concurrency/locking: basically same thing; no locking required. (Watch out, though,
527 * as #m_per_arena_borrower_pool_stats has a different story due to maintaining a key-set, being a map.)
528 * Regarding semantics: this PoV for a Borrower_pool_stats is fully non-degenerate. That should be clear
529 * having read the aforementioned doc header, but we emphasize: A first-registering of a SHM-pool here
530 * (its Pool_rc_data::m_use_count goes 0=>1 <=> new Pool_rc_data is created/inserted) means
531 * SHM-pool is opened/mapped; but 1=>2, 2=>3, etc., shall reuse the already-opened pool. Hence
532 * stat::Borrower_pool_stats::m_pool_open_count + `m_n_open_pools` are touched only in the 0=>1 case
533 * (w/r/t register_shm_pool() API). (Same deal with deregister_shm_pool() + unmap/close, etc. Same deal
534 * with arena/collection [de]registering.)
535 */
536 Borrower_pool_stats m_borrower_pool_stats;
537
538 /**
539 * Carries the totals from #m_borrower_pool_stats but broken-down by arena/collection *ever* borrowed (modulo
540 * the LRU eviction below), each as identified by #Uniq_collection_id.
541 *
542 * LRU eviction: To avoid unbounded growth evicts the LRU (least recently touched
543 * stats-wise arena, identified by `Uniq_collection_id`) entry on insertion having reached a certain max
544 * size. "Touching stats-wise" is defined as any of the 4 APIs `[de]register_{collection|shm_pool}()` invoked
545 * for that `Uniq_collection_id`.
546 *
547 * @note Key semantic point: (Assume no eviction has occurred.)
548 * A particular Uniq_collection_id X being in m_collection_data_map does imply
549 * it is in `m_per_arena_borrower_pool_stats`; but the reverse is not necessarily the case:
550 * The key-set here is historical; an arena being borrowed, then unborrowed, does not delete it from
551 * this map. Its then being borrowed again would, for example, increment its
552 * Borrower_pool_stats::m_arena_register_count by a total of 2 (1 at the first borrowing, 1 at the second).
553 * (Among other things that implies we cannot just shove a Borrower_pool_stats into Collection_data
554 * and therefore into #m_collection_data_map.)
555 * The only vaguely degenerate semantic thing is that here Borrower_pool_stats::m_n_borrowed_arenas
556 * cannot exceed 1: an arena is either currently being borrowed by 1+ `Shm_session`s, or it is not.
557 *
558 * @note Usually the entries in #m_per_arena_borrower_pool_stats combined match the totals
559 * in #m_borrower_pool_stats. This stops being fully true, *if* and (past) when the former grows
560 * large enough to require the LRU-removal of entries from then on, on subsequent insertions.
561 *
562 * ### Thread safety ###
563 * While at the level of an individual Borrower_pool_stats there are no particular worries -- it is all `atomic`s
564 * already -- here we also have the key-set of this map; it can be modified on behalf of, e.g., 2+
565 * `Shm_session`s concurrently. In short:
566 *
567 * Use the same mutex + lock-sections as #m_rc_pools_by_id and/or #m_collection_data_map when reading or
568 * modifying #m_per_arena_borrower_pool_stats.
569 *
570 * Reasons:
571 * - LRU-eviction (discussed some more below) means keys are sometimes removed from the map. Hence it's
572 * not safe to lock, get key set, unlock, do things to entries in the key set; use-after-free could occur.
573 * Even if that were not true (no removal ever):
574 * - It's, in subtle fashion, still wrong, even though we store `Own<>` wrappers which gives pointer stability.
575 * Details omitted, but it means semantically at least temporarily unpleasant values could be saved for
576 * some GAUGEs (and therefore even possibly permanently unpleasant results in derived
577 * HI_WMARKs could be saved), particularly if arena X is un-borrowed through one session while being borrowed
578 * through another right then. If locking in-tandem with #m_rc_pools_by_id et al, though, we always
579 * save the actual statistical picture.
580 *
581 * ### The LRU eviction: Rationale ###
582 * This is pretty straightforward, meaning the above explanation pretty much covers it; as usual minutiae are
583 * at least explained in methods. One thing to add: What are we trying to avoid, exactly, when eventually
584 * evicting old entries? We said it's about unbounded growth, which is true by definition, but it's really
585 * about two things:
586 * - The obvious one: RAM use on account of the global `*this`.
587 * - The less obvious one: In stats() (and stats_reset() for that matter), it is necessary to iterate
588 * through all of `m_per_arena_borrower_pool_stats`. If it can get huge, then that'll take a while.
589 * Also stats() copies stuff from there onto a user container. (There's also then a lengthy, if rare, lock
590 * involved.)
591 *
592 * So that's why we do it at all.
593 *
594 * Another question concerns the choice of what determines the LRU/MRU order. To restate, touching arena =
595 * register_collection(), deregister_collection() of a given arena +
596 * register_shm_pool(), deregister_shm_pool() of a pool pertaining to a given arena. In other words:
597 * touched/LRU/MRU = "the stats for it changed." So if we're forced to forget an arena, then its stats have
598 * been unchanged for the longest.
599 *
600 * We chose this ultimately because it's simple to understand and, hopefully, within reason as to what
601 * is useful to a user. Taking these 1 at a time:
602 * - Simple? Yes: A `Stat_set` is modified <=> touched. Hard to be simpler.
603 * - It also exactly matches the order in which stats() optionally emits these stats up to a
604 * (presumably lower) readability limit of `per_arena_stats_sz_limit_or_0` per-arena `Stat_set`s.
605 * - Usable? More or less, but it's arguable. An uptime/use-case resulting in (as of this writing)
606 * 1,000 borrowed arenas since process start means we are justified in throwing some away. At that point
607 * as long as the eviction-criterion is not plainly silly, I as a user am probably OK. "It hasn't changed,
608 * so it's less active, so let's get rid of that one, if we must" feels not-plainly-silly. It's definitely
609 * not a slam dunk either though: it ignores whether an arena is *currently* being borrowed or not; so
610 * arena A that was recently unborrowed (<=> session closed as of this writing) would stay in, while arena
611 * B that is still borrowed, but with zero further activity (these stats-wise... the SHM objects in the
612 * pools may well be being read, borrowed, etc.) for a longer time, would be evicted.
613 *
614 * That was written before deploying this in the field for the first time, so we may get field feedback to
615 * modify this policy.
616 *
617 * @todo Consider adding a public `stats_forget_by_arena()` which would lock, clear
618 * Borrower_shm_pool_collection_repository::m_per_arena_borrower_pool_stats, unlock; this would be available
619 * for tests that would like to start with/leave a clean slate for this set of stat; possibly even
620 * available via forward (like stats_reset()) by a public-facing API like `Shm_session`. The impl is
621 * simple and correct (won't create imbalanced stats or anything like that). For tests it may be quite helpful
622 * (as of this writing has not been needed though). Would tentatively avoid making a public-facing forwarder,
623 * though, as it feels fussy; the whole mechanism should already just work, when it comes to production use.
624 */
625 flow::util::Linked_hash_map<Uniq_collection_id, Own<Borrower_pool_stats>> m_per_arena_borrower_pool_stats;
626}; // class Borrower_shm_pool_collection_repository

686template<typename Shm_arena_t>
687void Borrower_shm_pool_collection_repository<Shm_arena_t>::register_collection(owner_id_t owner_id,
688 collection_id_t collection_id,
689 Shared_name&& pool_name_base)
690{
691 using flow::util::stat::fetch_add;
692 using flow::util::stat::update_hi_wmark;
693 using std::make_shared;
694
695 // Locks and unlocks central mutex 1.
696 Tl_copy_fwd::s_registry.while_locked([&](auto&&...)
697 {
698 const Uniq_collection_id key{owner_id, collection_id};
699 const auto iter = m_collection_data_map.find(key);
700
701 bool novel;
702
703 if (iter == m_collection_data_map.end())
704 {
705 // New collection.
706 novel = true;
707 /* Pass nullptr logger: this borrower-side collection only opens/maps + unmaps/closes pools; we log all of
708 * that here in `*this` (which has a thread-safe Log_context_mt), around the calls. So the collection itself
709 * need not -- and does not -- log; this sidesteps having to give it a concurrently-valid logger. */
710 m_collection_data_map.emplace(key,
711 Collection_data{ make_shared<Borrower_shm_pool_collection>
712 (nullptr, collection_id, std::move(pool_name_base)),
713 1 });
714 FLOW_LOG_TRACE_LOCKED("Registered new collection [" << collection_id << "], owner [" << owner_id << "].");
715 }
716 else
717 {
718 // Existing collection.
719 novel = false;
720 auto& coll = iter->second;
721 ++coll.m_use_count;
722 assert((coll.m_collection->get_pool_name_base() == pool_name_base)
723 && "Registered same owner/collection (allowed) but with different pool-name-base? Bug.");
724 FLOW_LOG_TRACE_LOCKED("Incremented use of collection [" << collection_id << "], owner [" << owner_id << "] to "
725 "[" << coll.m_use_count << "].");
726 }
727
728 { // Stats.
729 Borrower_pool_stats* per_arena_stats_ptr = nullptr; // There is a case where this stays as-is.
730 const auto iter = m_per_arena_borrower_pool_stats.find(key);
731 if (iter == m_per_arena_borrower_pool_stats.end())
732 {
733 if (novel)
734 {
735 m_per_arena_borrower_pool_stats[key].reset(per_arena_stats_ptr = new Borrower_pool_stats);
736 per_arena_stats_ptr->m_uniq_arena_id.m_id1 = uint64_t(owner_id);
737 per_arena_stats_ptr->m_uniq_arena_id.m_id2 = uint64_t(collection_id);
738
739 // That new per-arena stat-set is MRU... but have we reached the size where we'll need to evict LRU?
740 if (m_per_arena_borrower_pool_stats.size() > S_N_PER_ARENA_BORROWER_POOL_STATS_SZ_LIMIT)
741 {
742 m_per_arena_borrower_pool_stats.erase(--m_per_arena_borrower_pool_stats.past_oldest());
743 assert((m_per_arena_borrower_pool_stats.size() == S_N_PER_ARENA_BORROWER_POOL_STATS_SZ_LIMIT)
744 && "Some bug in the simple LRU/MRU algorithm?");
745 }
746
747 /* Note: That (combined with the 4 touch() calls throughout this class) = our LRU-eviction policy;
748 * but it's not the only possible policy. See m_per_arena_borrower_pool_stats doc header for discussion
749 * of this choice/possible alternative. */
750 }
751 /* else if (!novel): // && (key not in m_per_arena_borrower_pool_stats)
752 * Do not insert `key` yet; and leave `per_arena_stats_ptr == nullptr` for below. The reason is
753 * a bit subtle. Firstly, !novel here wouldn't even be possible normally; it can only happen if
754 * the LRU-ejection seen above happened for this `key` earlier (so m_per_arena_borrower_pool_stats got too
755 * big, etc.). So if that did happen, and since then `key`-arena did get unborrowed/deregistered the
756 * same # of times that it had been registered, and now that `key`-arena is being borrowed/registered
757 * again (hence `novel == false` now), suppose we allowed m_per_arena...[key] to be inserted now.
758 * Seems fine, but now suppose later it gets deregistered. ACCUMULATORs will be fine as always, more or
759 * less, but take a GAUGE -- say, m_n_borrowed_arenas -- which is (naturally) unsigned. We wouldn't
760 * ++ it below during this register_collection(); but the later deregister_collection() would `--` it.
761 * So it would become -1 (underflow). We could make it signed, but then it would be a weird-looking
762 * result. We just don't want any of that junk, not to even reason about it further; in other places
763 * too (like we can't claim it's always either 1 or 0 anymore, which as of this writing is assert()ed
764 * and stated in docs). Essentially: we were forced to junk that arena's data by the LRU considerations --
765 * we didn't want to (all else being equal), but we had to so as to avoid unbounded growth of the map.
766 * So continuing that, we are applying that junk-it policy for that arena... until things "even out."
767 * Once the # of register_collection()s and deregister_collection()s for it become equal -- `novel`
768 * becomes true for it -- then there's no reason not to keep those stats. (In any case, if novel=true
769 * then we don't even know if `key` was junked in the past, so we have to insert it, even if we didn't
770 * want to for some reason.) */
771 } // if (key not in m_per_arena_borrower_pool_stats)
772 else // if (key in m_per_arena_borrower_pool_stats)
773 {
774 per_arena_stats_ptr = iter->second.get();
775 m_per_arena_borrower_pool_stats.touch(iter);
776 /* It is now MRU again. Perf: touch() is a constant-time few ptr assignments. Plus there aren't typically
777 * so many arenas being juggled at a given time as to make this a frequent non-no-op anyway. */
778 }
779
780 /* This next part could -- one could say -- be outside of the lock-section. It is not. Why?
781 * - m_per_arena_borrower_pool_stats: See its doc header for why this is inside the lock-section.
782 * (In short: perf-wise does not matter. Correctness-wise: it could matter due to our fairly-unique
783 * semantic situation w/r/t an arena being potentially borrowed and un-borrowed concurrently through
784 * different sessions. So keep it simple and definitely-correct by mirroring m_collection_data_map.)
785 * - m_borrower_pool_stats: Keep it here as well to avoid having to worry about it (and perf-wise still
786 * does not matter) and for consistency. */
787
788 if (per_arena_stats_ptr)
789 {
790 fetch_add(&per_arena_stats_ptr->m_arena_register_count, 1);
791 if (novel)
792 {
793 fetch_add(&per_arena_stats_ptr->m_arena_first_register_count, 1);
794 update_hi_wmark(&per_arena_stats_ptr->m_n_borrowed_arenas_hi_wmark,
795 fetch_add(&per_arena_stats_ptr->m_n_borrowed_arenas, 1) + 1);
796 }
797 }
798 { // Same deal, for the total-stats guy.
799 fetch_add(&m_borrower_pool_stats.m_arena_register_count, 1);
800 if (novel)
801 {
802 fetch_add(&m_borrower_pool_stats.m_arena_first_register_count, 1);
803 update_hi_wmark(&m_borrower_pool_stats.m_n_borrowed_arenas_hi_wmark,
804 fetch_add(&m_borrower_pool_stats.m_n_borrowed_arenas, 1) + 1);
805 }
806 }
807 } // Stats.
808 }); // Tl_copy_fwd::s_registry.while_locked() // Locks and unlocks central mutex 1.
809} // Borrower_shm_pool_collection_repository::register_collection()

811template<typename Shm_arena_t>
812void Borrower_shm_pool_collection_repository<Shm_arena_t>::deregister_collection(owner_id_t owner_id,
813 collection_id_t collection_id)
814{
815 using flow::util::stat::fetch_add;
816 using flow::util::stat::fetch_sub;
817
818 // Locks and unlocks central mutex 1.
819 Tl_copy_fwd::s_registry.while_locked([&](auto&&...)
820 {
821 const Uniq_collection_id key{owner_id, collection_id};
822 const auto iter = m_collection_data_map.find(key);
823 assert((iter != m_collection_data_map.end()) && "Deregistering unknown collection; bug?");
824 bool novel;
825
826 auto& coll = iter->second;
827 if (coll.m_use_count == 1)
828 {
829 novel = true;
830 m_collection_data_map.erase(iter);
831 FLOW_LOG_TRACE_LOCKED("Removed collection [" << collection_id << "], owner [" << owner_id << "].");
832 }
833 else
834 {
835 novel = false;
836 --coll.m_use_count;
837 FLOW_LOG_TRACE_LOCKED("Decremented use of collection [" << collection_id << "], owner [" << owner_id << "] "
838 "to [" << coll.m_use_count << "].");
839 }
840
841 { // Stats.
842 const auto iter = m_per_arena_borrower_pool_stats.find(key);
843 if (iter != m_per_arena_borrower_pool_stats.end())
844 {
845 const auto per_arena_stats_ptr = iter->second.get();
846
847 // See note in register_collection() w/r/t why the following is inside lock-section instead of outside.
848
849 fetch_add(&per_arena_stats_ptr->m_arena_deregister_count, 1);
850 if (novel)
851 {
852 fetch_add(&per_arena_stats_ptr->m_arena_last_deregister_count, 1);
853#ifndef NDEBUG
854 const auto prev_val =
855#endif
856 fetch_sub(&per_arena_stats_ptr->m_n_borrowed_arenas, 1);
857 assert((prev_val == 1)
858 && "Per-arena m_n_borrowed_arenas should only ever be 0 or 1. Bug in register_collection()?");
859 } // if (novel)
860
861 m_per_arena_borrower_pool_stats.touch(iter);
862 // It is now MRU again. Perf: same comment as in register_collection().
863 } // if (key in m_per_arena_borrower_pool_stats)
864 /* else if (key not in m_per_arena_borrower_pool_stats):
865 * Normally this won't happen, as a thing must be registered before it can be deregistered, and the former
866 * would have inserted `key`, but there is a corner case: an, apparently, incredibly long-lived
867 * session/arena, such that a massive # of others have been more recently messed-with than the last time
868 * this one was touched stats-wise. It would then get evicted; and it is conceivable that the
869 * borrowing finally ended now... but too late: no per-arena stats to update. There isn't a great way
870 * to deal with it without producing some odd-looking values in the individual `Borrower_pool_stats`. This
871 * case is basically pathological, so they'll just have to make do without this particular arena's stats.
872 * (It is even conceivable that *another* session would be opened to borrow that same arena -- hence
873 * register_collection(), in the !novel case, will insert it and even make it MRU anew. Why only if !novel?
874 * See register_collection() itself; but in short: it also helps avoid odd-looking values due to imbalance
875 * of [de]register_collection() calls.)
876 *
877 * (By "odd-looking" we mean potentially documented-invariant- (possibly assert()-) breaking. E.g.
878 * m_n_borrowed_arenas, per arena, should be in [0, 1] according to docs and an assert() as of this writing.) */
879
880 { // Same deal, for the total-stats guy.
881 fetch_add(&m_borrower_pool_stats.m_arena_deregister_count, 1);
882 if (novel)
883 {
884 fetch_add(&m_borrower_pool_stats.m_arena_last_deregister_count, 1);
885 fetch_sub(&m_borrower_pool_stats.m_n_borrowed_arenas, 1);
886 }
887 }
888 } // Stats.
889 }); // Tl_copy_fwd::s_registry.while_locked() // Locks and unlocks central mutex 1.
890} // Borrower_shm_pool_collection_repository::deregister_collection()

892template<typename Shm_arena_t>
893void Borrower_shm_pool_collection_repository<Shm_arena_t>::register_shm_pool(owner_id_t owner_id,
894 collection_id_t collection_id,
895 pool_id_t pool_id,
896 std::size_t pool_size)
897{
898 using ipc::shm::arena_lend::Shm_pool;
899 using Shm_pool_ptr = std::shared_ptr<Shm_pool>;
900 using flow::util::stat::fetch_add;
901 using flow::util::stat::update_hi_wmark;
902
903 Shm_pool_ptr new_shm_pool;
904
905 // Locks and unlocks central mutex 1.
906 Tl_copy_fwd::s_registry.while_locked([&](const auto& state_per_thread)
907 {
908 const Uniq_collection_id key{owner_id, collection_id};
909 const auto rc_iter = m_rc_pools_by_id.find(pool_id);
910 if (rc_iter == m_rc_pools_by_id.end())
911 {

1023 assert((rc_iter != m_rc_pools_by_id.end()) && "Deregistering unknown pool; bug?");

1037 // *removed_pool still alive (via removed_pool shared_ptr); we'll eliminate it last-thing below.

1061 fetch_sub(&per_arena_stats_ptr->m_n_open_pools, 1);
1062 fetch_sub(&per_arena_stats_ptr->m_mapped_sz, removed_pool_size);

1066 // It is now MRU again. Perf: same comment as in register_collection().
1067 } // if (key in m_per_arena_borrower_pool_stats)
1068 /* else if (key not in m_per_arena_borrower_pool_stats):
1069 * Normally this won't happen, as... <see comment similar spot in register_shm_pool()>.
1070 * So in this case some arena gets registered and then not touched for ages stats-wise, and then
1071 * perhaps a relevant session ends; each pool in the arena gets deregistered.
1072 * We'll just have to not record that stats-event for it either. */
1073
1074 { // Same deal, for the total-stats guy.
1075 fetch_add(&m_borrower_pool_stats.m_pool_deregister_count, 1);
1076 if (removed_pool)
1077 {
1078 fetch_add(&m_borrower_pool_stats.m_pool_close_count, 1);
1079 fetch_sub(&m_borrower_pool_stats.m_n_open_pools, 1);
1080 fetch_sub(&m_borrower_pool_stats.m_mapped_sz, removed_pool_size);
1081 }
1082 }
1083 } // Stats.
1084 }); // Tl_copy_fwd::s_registry.while_locked() // Locks and unlocks central mutex 1.
1085
1086 if (removed_pool)
1087 {
1088 Core_rev::get_instance().erase(removed_pool->get_address()); // Locks and unlocks central mutex 2.
1089
1090 /* We saved removed_pool[_containing_collection] until this point to avoid a race between us
1091 * (deregister_shm_pool() of pool A=removed_pool) and another Shm_session performing register_shm_pool() of pool B.
1092 * Pools A and B are unrelated, but OS can (and, in Linux, very well might in practice) choose to map B
1093 * (hence B->get_address()) to an available vaddr including any used in the past (and not currently mapped).
1094 * That reuse (in itself) is absolutely fine, but for our data structures there could be trouble. The class
1095 * doc header impl section mentions this in a Footnote. So now we get into the specifics of it:
1096 *
1097 * We've got, in threads TA and TB:
1098 * TA: lock M1 { Aaddr = A->get_address() }; lock M2 { Core_rev::map.erase(Aaddr) }; { release (unmap) Aaddr }
1099 * TB: lock M1 { Baddr = <map new pool> }; lock M2 { Core_rev::map.insert(Baddr) }
1100 * The danger, in short, is that map.insert(Baddr), where Baddr=Aaddr due to address reuse by OS, would
1101 * happen-before map.erase(Addr) -- at which point everything about Baddr=Addr in Core_rev::map is messed up.
1102 * As written above (which represents how it's actually coded), though, that cannot happen: Aaddr=Baddr =>
1103 * unmap-Aaddr happened => map.erase(Aaddr) happened => map.insert(Baddr); all perfectly fine.
1104 *
1105 * How would it not be fine? An answer: Of these sections, since M1 and M2 are locked separately, the order
1106 * TA-M1/TB-M1/TB-M2/TA-M2/unmap-Aaddr is possible. Let's consider that order.
1107 * As written: No problems here. In particular notice Baddr=/=Aaddr in that scenario: TB-M1 happens-before
1108 * unmap-Aaddr, so OS cannot reuse Aaddr (yet).
1109 *
1110 * Now consider the counterfactual; suppose the `release (unmap) Aaddr` part were instead done earlier.
1111 * (This is tempting; just do it greedily in there and just save Aaddr alone for the `lock M2` part.)
1112 * TA: lock M1 { Aaddr = A->get_address(); release (unmap) Aaddr }; lock M2 { Core_rev::map.erase(Aaddr) }
1113 * TB: lock M1 { Baddr = <map new pool> }; lock M2 { Core_rev::map.insert(Baddr) }
1114 * Consider again the order TA-M1/TB-M1/TB-M2/TA-M2 (with unmap-Aaddr now folded into TA-M1).
1115 * The chaos, of one kind or another, begins in TB-M2: Core_rev::map.insert(Baddr), with Baddr=Aaddr,
1116 * is an attempt to insert at key that already exists; then TA-M2 erases at that same key. The various ways
1117 * that's bad should be clear. (Depends on what the double-insert would do. Either it loudly fails in
1118 * some way, or it doesn't -- but then the subsequent map.erase() removes the Aaddr=Baddr entry;
1119 * reverse-lookups for this SHM-pool don't work, etc. etc.) */
1120
1121 if (!removed_pool_containing_collection->release_shm_pool(removed_pool))
1122 {
1123 FLOW_LOG_FATAL_LOCKED("Failed to fully close/unmap (as borrower) SHM pool [" << pool_id << "], "
1124 "size [" << removed_pool_size << "], in collection [" << collection_id << "], "
1125 "owner [" << owner_id << "]. Something is likely borked about the machine now. "
1126 "Bailing out.");
1127 assert(false && "Failed to fully close/unmap (as borrower) SHM pool. "
1128 "Something is likely borked about the machine now.");
1129 std::abort();
1130 }
1131 // else
1132 FLOW_LOG_TRACE_LOCKED("Successfully closed, deregistered SHM pool [" << pool_id << "], "
1133 "size [" << removed_pool_size << "], in collection [" << collection_id << "], "
1134 "owner [" << owner_id << "].");
1135 }
1136 /* else { Pool structure unchanged; no rev-lookup (or fwd-lookup for that matter) update needed; no pool
1137 * to release. } */
1138} // Borrower_shm_pool_collection_repository::deregister_shm_pool()

1231 Borrower_shm_pool_collection_repository<Shm_arena_t>::stats

1236 using boost::adaptors::transformed;
1237 using boost::range::sort;
1238 using std::vector;

1294void Borrower_shm_pool_collection_repository<Shm_arena_t>::stats_reset()

1297 using boost::adaptors::map_values;
1298 using boost::adaptors::transformed;
1299
1300 stats_reset(&m_borrower_pool_stats, Borrower_pool_stats{}); // The across-all-arenas totals.

1303 * under central mutex 1, and ptrs are stable, but entries are sometimes LRU-erased; so do everything under
1304 * the lock. (Orthogonally: The resets write live `atomic`s -- standard under-concurrency stat behavior.) */
1305 Tl_copy_fwd::s_registry.while_locked([&](auto&&...)
1306 {
1307 const auto rng = m_per_arena_borrower_pool_stats | map_values
1308 | transformed([](const auto& own) -> auto { return own.get(); });
1309 for (auto* const stats_ptr : rng)
1310 {
1311 stats_reset(stats_ptr, Borrower_pool_stats{});
1312 }
1313 });

1315 /* One might wonder, here, why not "just" m_per_arena_borrower_pool_stats.clear() here instead of the
1316 * range-fu + stats_reset() dance above? It might be particularly tempting knowing how we have that LRU-eviction
1317 * mechanism in register_collection(), trying to keep this thing at most a certain size. A reset opportunistically
1318 * making that size=0 sounds pretty nice!
1319 *
1320 * It would be wrong, just because of how flow::util::stat stats work. Only ACCUMULATORs get zeroed by resets,
1321 * so if that's all we had, then it would be fine (if brittle, as ACCs-only now doesn't mean ACCs only forever).
1322 * GAUGEs in particular are untouched by proper stat-resets, so blowing them away (effectively zeroing them)
1323 * would be wrong. (Why do we blow them away in the LRU-eviction case anyway? Answer: We're forced to do it,
1324 * and we give up those stat-chunks willingly to avoid unbounded growth of m_per_arena_borrower_pool_stats.) */
