45/**
46 * This is to vanilla Session_server what shm::arena_lend::jemalloc::Server_session is to vanilla #Server_session:
47 * it is the session-server type that starts SHM-enabled sessions with SHM-jemalloc provider
48 * (ipc::shm::arena_lend::jemalloc). Its API is identical to that of Session_server, except that it emits
49 * #Server_session_obj that are shm::arena_lend::jemalloc::Server_session and not vanilla #Server_session.
50 *
51 * @note Lifetime recommendations and requirements -- the destruction order among `*this`, its sessions and their
52 * channels; how long the app_shm() arenas live -- are in the same-named section of session::Session_server
53 * doc header.
54 *
55 * @internal
56 *
57 * ### Implementation ###
58 * See similar section of session::Session_server. It explains why we sub-class Session_server_impl and even how
59 * that's used for this SHM-jemalloc scenario. To reiterate:
60 *
61 * We use 2 of 2 available customization points of `private` super-class Session_server_impl. We:
62 * - pass-up a `per_app_setup_func()` that, given the new session's desired Client_app, creates-if-needed the per-app
63 * SHM-arena and keeps it open as well as available via `this->app_shm(app)`; and
64 * - parameterize Session_server_impl on shm::arena_lend::jemalloc::Server_session which, during log-in, creates
65 * the per-session SHM-arena and keeps it open; saves `this->app_shm_ptr(app)`;
66 * and partners with Client_session_impl to set up the lend/borrowing capability between us.
67 *
68 * shm::arena_lend::jemalloc::Server_session doc header delves deeply into the entire impl strategy for setting up
69 * these arenas. If you read/grok that, then the present class's impl should be straightforward to follow.
70 *
71 * @endinternal
72 *
73 * @tparam MQ_TYPE_OR_NONE
74 * See vanilla #Session_server.
75 * @tparam TRANSMIT_NATIVE_HANDLES
76 * See vanilla #Session_server.
77 * @tparam Mdt_payload
78 * See vanilla #Session_server.
79 */

217 /**
218 * Returns pointer to the per-`app` SHM-arena, whose lifetime extends until `*this`, and every
219 * shm::arena_lend::jemalloc::Server_session of `app` from `*this`, are destroyed;
220 * or null if that arena has not yet been successfully created (which is attempted during the log-in of the
221 * first client of `app` to reach `*this` via async_accept()). Alternatively you may use
222 * shm::arena_lend::jemalloc::Server_session::app_shm() off any session object filled-out by `*this`
223 * async_accept(), as long as its Server_session_mv::client_app() equals `app` (by App::m_name equality).
224 *
225 * If non-null is returned, then the same pointer value shall be returned for all subsequent calls
226 * with the same (by App::m_name equality) `app`. The non-null pointers returned for any 2 calls, where `app`
227 * is different (by App::m_name equality) among them, shall always differ.
228 *
229 * See shm::arena_lend::jemalloc::Session_mv::Arena doc header for useful instructions on working with #Arena,
230 * `lend_object()`, and `borrow_object()`.
231 *
232 * ### Perf ###
233 * Given the choice between Server_session::app_shm() and the present method, the latter is somewhat
234 * slower; internally it involves a mutex-protected map lookup, while the former simply returns a cached
235 * pointer as of this writing.
236 *
237 * Generally it is also fine, and fastest, for the user to save any non-null value returned by either `app_shm()`;
238 * the pointer returned shall always be the same after all.
239 *
240 * @internal
241 *
242 * ### Thread safety ###
243 * For internal use, namely by shm::arena_lend::jemalloc::Server_session_impl::async_accept_log_in() at least,
244 * it is guaranteed that app_shm() and app_shm_ptr() may be called on the same `*this` concurrently to each other,
245 * themselves, and init_app_shm_as_needed(). Formally speaking this isn't publicly documented, as I (ygoldfel)
246 * didn't want to get users into any bad habit, but internally it does have this property -- as it is required.
247 *
248 * @endinternal
249 *
250 * @param app
251 * Client_app whose segregated SHM-arena to return, if a session for a client of the app has been
252 * opened prior to this call.
253 * @return Pointer to `*this`-held per-`app` SHM-arena, if it has been created; null otherwise.
254 * See above.
255 */
256 Arena* app_shm(const Client_app& app);

333 /**
334 * Performs `A->sample_hi_wmarks()`, where `A = m_app_shm_by_name[app_name]` is looked-up based on the
335 * caller-supplied `app_name`; and schedules for this to occur again in some regular period
336 * of time. Call this upon adding `app_name` to #m_app_shm_by_name; it will then self-perpetuate.
337 *
338 * Pre-condition: #m_app_shm_mutex must be locked (it will remain locked throughout).
339 *
340 * ### Rationale / Background ###
341 * See Session_impl::session_shm_stats_tickle_and_schedule() doc header. See how it mentions that `app_shm()`
342 * is `Session_server`'s responsibility, since `app_shm()` arena lifetime is orthogonal to individual session?
343 * This is our handling that responsibility.
344 *
345 * ### Corner case / defensive behavior / maintenance notes ###
346 * Method does not tickle/stops ticklings if `app_name` is not in #m_app_shm_by_name
347 * (or that entry is null; same treatment). We are not saying that removal of non-null entry is
348 * even possible... in fact as of this writing it is not; we are being defensive here. So: if it were possible
349 * and happened, then the stat-tickling and scheduling thereof would stop. In that case, if there is such a
350 * thing as re-adding it to #m_app_shm_by_name, one can invoke the method to start the ticklings again.
351 * That said: As currently written, it is not really totally robust: If, in particular, `app_name` were
352 * erased and then re-added during the "rest" period of this method's last invocation with `app_name`, then
353 * it would just keep going with the ticklings, which would probably be wrong -- as one would re-invoke it
354 * upon re-adding `m_app_shm_by_name[app_name]`; so there would now be two in-phase periodic ticklings going
355 * instead of the appropriate one tickling.
356 *
357 * To avoid this silliness: Add a mechanism for canceling the currently-scheduled tickling of `app_name`, whenever
358 * `app_name` is erased from `m_app_shm_by_name`. Would just need to save a handle from `.schedule_from_now()`
359 * and do the flow.async cancel op on that.
360 *
361 * Reminder: This whole premise is currently not a thing; the above is in case it becomes true in the future.
362 * Oh, also, be sure in that case to not mess-up the thing where `app_name` is in the map but the "arena"
363 * is a null handle. (As of this writing a failed init_app_shm_as_needed() leaves null in the map for simplicity,
364 * so just make sure all that is properly handled still, if conceptual remove from `m_app_shm_by_name` becomes
365 * possible.)
366 *
367 * @param app_name
368 * App::m_name, a key into #m_app_shm_by_name. If not present there, then there is no arena to tickle,
369 * and scheduling thereof stops. (See above discussion of that corner case. We could take a
370 * `shared_ptr<Arena>`, or at least a `const Client_app&`, instead; but again we're trying to keep this
371 * little mechanism as simple and self-contained/resilient as possible.)
372 */
373 void app_shm_stats_tickle_and_schedule(const std::string& app_name);

409 const Client_app::Master_set& cli_app_master_set_ref,
410 Error_code* err_code) :

440

453TEMPLATE_JEM_SESSION_SRV
454Error_code CLASS_JEM_SESSION_SRV::init_app_shm_as_needed(const Client_app& app)
455{
456 using ipc::shm::arena_lend::jemalloc::Memory_manager;
457 using std::make_shared;
458
459 /* We are in some unspecified thread; actually *a* Session_server_impl thread Ws (a Server_session_impl thread W).
460 * Gotta lock at least to protect from concurrent calls to ourselves on behalf of other async_accept()s. */
461
462 Lock_guard app_shm_lock{m_app_shm_mutex};
463
464 auto& app_shm = m_app_shm_by_name[app.m_name]; // Find; insert if needed.
465 if (app_shm)
466 {
467 // Cool; already exists, as app.m_name seen already (and successfully set-up, as seen below) by us.
468 return {};
469 }
470 // else
471
472 // Below should INFO-log already; let's not litter logs explaining why this is being created; context = sufficient.
473
474 /* Arena needs a pool name prefix it will use each time the memory manager decides it wants a new mmap()ped vaddr
475 * space (in the SHM context, <-> SHM-pool). We use our standard semantics for per-session items. Arena will
476 * append whatever pool ID stuff after this prefix.
477 *
478 * This is the same as Session_impl::init_shm() but simpler due to being a server-side thing (as opposed to possibly
479 * client-side) and thus not needing to add any client-PID for cleanup purposes (server-PID is already
480 * the srv_namespace baked into every Shared_name). Also it's per-app, not per-session, hence cli_namespace is
481 * not needed. */
482 auto shm_pool_name_prefix = build_conventional_shared_name(Shared_name::S_RESOURCE_TYPE_ID_SHM,
483 Shared_name::ct(m_srv_app_ref.m_name), m_srv_namespace,
484 Shared_name::ct(app.m_name));
485 shm_pool_name_prefix /= SHM_SUBTYPE_PREFIX;
486
487 /* Arena::create() throws on failure (it does not return null). We must catch it: same reasoning as in
488 * Session_impl::init_shm() (in short: we are in a flow::async thread, where an uncaught exception would exit() the
489 * process). Emit the exception's own Error_code, if it has one; else a general one of our own. */
490 Error_code create_err_code;
491 try
492 {
493 app_shm
494 = Arena::create(get_logger(),
495 // See equally-relevant note/@todo in Session_impl::init_shm().
496 make_shared<Memory_manager>(),
497 std::move(shm_pool_name_prefix),
498 util::shared_resource_permissions(m_srv_app_ref.m_permissions_level_for_client_apps));
499 }
500 catch (const boost::system::system_error& exc) // Including flow::error::Runtime_error.
501 {
502 create_err_code = exc.code() ? exc.code() : Error_code{error::Code::S_SHM_ARENA_CREATION_FAILED};
503 FLOW_LOG_WARNING("Session_server [" << *this << "]: Failed to create app-scope Arena; exception "
504 "[" << exc.what() << "]; emitting [" << create_err_code << "] "
505 "[" << create_err_code.message() << "]. Session will not open.");
506 }
507 catch (const std::exception& exc)
508 {
509 create_err_code = error::Code::S_SHM_ARENA_CREATION_FAILED;
510 FLOW_LOG_WARNING("Session_server [" << *this << "]: Failed to create app-scope Arena; exception "
511 "[" << exc.what() << "]; emitting [" << create_err_code << "] "
512 "[" << create_err_code.message() << "]. Session will not open.");
513 }
514
515 if (create_err_code)
516 {
517 /* app_shm, which is in the map directly, is null. Just leave null in the map; meh.
518 * .erase()ing it from there is just pedantic at best. (The [] lookup above will do the right thing next time.) */
519 assert(!app_shm);
520 return create_err_code;
521 }
522 // else: Cool!
523 assert(app_shm && "Arena::create() throws on failure, else returns non-null.");
524
525 // Its doc header explains things. Mutex is locked as required.

527

529 // Lock_guard app_shm_lock{m_app_shm_mutex}: unlocks here.
530} // Session_server::init_app_shm_as_needed()

532TEMPLATE_JEM_SESSION_SRV
533void CLASS_JEM_SESSION_SRV::app_shm_stats_tickle_and_schedule(const std::string& app_name)
534{
535 using boost::chrono::seconds;
536 using std::shared_ptr;
537
538 /* If you read our doc header and possibly consult Session_impl::session_shm_stats_tickle_and_schedule() -- our
539 * cousin -- then the below should be quite straightforward.
540 *
541 * A question might arise: the Session_impl guy is still simple, but it is worried about session-hosings
542 * and "thread W" -- whereas we really don't care; why not? Answer: That's just the nature of these app-scope
543 * arenas. They outlive any particular Session(s), potentially, and are available for use through any of
544 * them (well, ones w/r/t the same Client_app::m_name). Even if some session fails to start-up -- maybe even
545 * if it is the first one for this Client_app and hence the one that made m_app_shm_by_name[app_name] appear
546 * in the first place -- the *arena* is totally fine and cool to keep existing. Lastly: there is no such
547 * thing as *this Session_server (cf. various `Session`s) being "down": while `*this` exists, it's "up." So
548 * even if we wanted to stop these (harmless) ticklings due to *this no longer operating, it just isn't a
549 * thing as of this writing. Though even if it were... meh. Tickle away.
550 *
551 * Secondly let's discuss the appropriate (default at least) period for this tickling. ...See
552 * Session_impl::session_shm_stats_tickle_and_schedule(). We use a similar period here. Do realize:
553 * that one is per-session; this one is per-distinct Client_app that has connected to *this session-server
554 * at least once. Realistically: there might 1 or 2 or maybe 5 of these; like assuming it is 5, it means
555 * this application is capable of doing IPC (opening IPC sessions -- contexts basically) with 5 different
556 * applications (like, distinct executables... not processes/instances thereof); that's quite ambitious.
557 * That is to say... it's not going to be, like, 100 of these timers here. */
558 constexpr util::Fine_duration TICKLE_PERIOD = seconds{10}; // @todo Provide a knob including ability to turn off?
559
560 /* We are in thread <whichever one calls init_app_shm_as_needed()> or, after that, m_async_periodic_worker's.
561 * Does not matter: arena->sample_hi_wmarks() is safe from any thread by its contract.
562 *
563 * Mutex is locked by contract. */
564
565 const auto map_it = m_app_shm_by_name.find(app_name);
566 /* Subtlety: Due to an intentional quirk of init_app_shm_as_needed(), if it's in the map, the ptr may still be null:
567 * init_app_shm_as_needed() failed for app.m_name but does not erase in that case and just leaves null. */
568 const auto arena = (map_it == m_app_shm_by_name.end()) ? shared_ptr<Arena>{} : map_it->second;
569
570 if (!arena)
571 {
572 return; // As promised in contract: no tickle, no further tickles.
573 }
574 // else:
575
576 arena->sample_hi_wmarks();
577
578 m_async_periodic_worker.schedule_from_now(TICKLE_PERIOD, [this, app_name](auto&&) mutable
579 {
580 Lock_guard app_shm_lock{m_app_shm_mutex}; // Required by our contract.
581 app_shm_stats_tickle_and_schedule(app_name);
582 });
583} // Session_server::app_shm_stats_tickle_and_schedule()

671TEMPLATE_JEM_SESSION_SRV
672void CLASS_JEM_SESSION_SRV::cleanup()
673{
674 // `classic`? Pool_arena?! But this is jemalloc!?!?! Worry not. See remove_each_persistent_if() doc header.
675 using ipc::shm::classic::Pool_arena;
676 using util::String_view;
677 using util::process_id_t;
678 using boost::chrono::seconds;
679 using boost::lexical_cast;
680
681 constexpr util::Fine_duration CLEANUP_PERIOD = seconds{30};
682
683 FLOW_LOG_TRACE("Session server [" << *this << "]: Periodic (or initial) cleanup starting.");
684
685 /* This is just like Client_session_impl::cleanup(), except for some small differences explained therein; but
686 * the main explanation is right here. Read on.
687 *
688 * As with SHM-classic, cleanup of SHM-pools = 2 tasks; graceful cleanup, when objects are destroyed normally
689 * on process exit() or earlier; and cleanup after a process dies or zombifies/later dies and thus the
690 * regular destructors don't run. Graceful cleanup for SHM-jemalloc is accomplished in each Arena's dtor
691 * and is, to us, a black box; the point is it takes care of it, so we need not do anything further.
692 * (This is in contrast to SHM-classic which centers on classic::Pool_arena which is so minimalistic that it leaves
693 * that task to the user of Pool_arena; in our case ipc::session::shm::classic code is that user and takes care of it.
694 * Point is, with SHM-jemalloc we need not.) So that leaves ungraceful cleanup. In point of fact, SHM-jemalloc
695 * explicitly leaves the task of handling that to its user (that's us). So:
696 *
697 * In short, SHM-jemalloc at its core is symmetric in the sense that in an A-B session, where (say) A happens
698 * to be the Session_server side (SHM-jemalloc is not aware of that, but you and I are here), A maintains
699 * SHM-arena(s); and B maintains its own SHM-arena(s) (and the two cross-borrow objects from each other).
700 * If A aborts before destructor(s) completely run, then its arena(s) shall leak, and it's up to us to
701 * remove_persistent() (really, SHM-unlink) them; and just the same for B. While it is conceivable to try to
702 * impose the ipc::session ethos, where session-server is responsible for cleaning up everything -- including
703 * stuff leaked by session-client(s) -- in this (rare) case that's not really natural. It is difficult to make
704 * any assumptions about what state some creator-process of a given SHM-pool may be in: SHM-jemalloc is a (complex)
705 * black box. Instead it is better to treat each side as similarly as possible, mirroring SHM-jemalloc's own
706 * design (even though it left this task to us).
707 *
708 * Exact rationale aside, here's the deal. If a given creator (owner) process of a SHM-jemalloc-managed pool
709 * is not running, then it is correct and safe to remove_persistent() that pool: any existing handles to that
710 * pool in other processes that may be alive will continue to be valid; and no more such processes shall arise.
711 * Why? Answer: because they only *can* arise through the Shm_session::lend_arena(Arena*) operation within the
712 * creator (owner) of that Arena (which = pool collection = all SHM pools in arena)... but that process is dead.
713 * Nor does SHM-jemalloc support an owner re-opening (in the owner capacity) a previously created SHM-pool.
714 * Therefore, logically, *if* we can determine that a given pool's owner is dead, *then* we can/should SHM-unlink
715 * that pool. We'll discuss how to do that next. First, though, is it ever safe/correct to SHM-unlink a pool,
716 * while its creator (owner) is *not* dead? The answer is no, except if that process is zombified (not "really"
717 * active). We have no good way of determining that, as of this writing anyway. There are some exceptions to
718 * this within ipc::session, and we are indeed in ipc::session right now. Namely:
719 * - If the owner of a pool was a Session_server (or Server_session borne of one), then in our paradigm there
720 * must be at most one active Session_server; so if we are alive, then the owner of the pool must be inactive,
721 * assuming things are working properly. (SHM-classic cleanup relies on that in its cleanup algorithm.)
722 * - However no such inference can be on Client_session side: Multiple `Client_session`s of one Client_app
723 * may live concurrently.
724 * Since we can't really rely on that stuff, we elect to instead go with the simple aforementioned rule:
725 * - A SHM-pool was created by this app's SHM-jemalloc; and its owner (creator) process is now dead
726 * <=> remove_persistent() that SHM-pool.
727 *
728 * That leaves only the following challenges:
729 * - List all SHM-pools created by this app's SHM-jemalloc. Solution: Pool_arena::for_each_persistent(), etc.,
730 * which can scan /dev/shm (in Linux anyway) and find the pools with a certain name pattern; our Shared_name
731 * ipc::session semantics (formally implemented in session_shared_name.hpp and described in Shared_name doc
732 * header) name things in such a way as to make this pretty simple.
733 * - Determine PID of creator of given pool. Solution: Our PID is encoded into the Shared_name due to the
734 * aforementioned ipc::session Shared_name semantics.
735 * - Determine whether process with a certain PID is alive. Solution: util::process_running().
736 *
737 * A note on stats: Stats support for this sweep (scanned/removed/skipped counts and such) has been considered
738 * and deliberately omitted. Rationale: These events are rare by construction (crash aftermath); and the sweep
739 * is fully log-observable -- each removal is INFO-logged with the pool name and reasoning, anomalies are
740 * WARNING-logged, and the removed-count is logged at the end. For rare events those logs are strictly richer
741 * than counters would be; nor is this a hot path where instrumentation would come along ~free. Revisit only
742 * if a monitoring consumer materializes that needs queryable counts. (A cross-process SHM-resident stats
743 * store has also been considered and rejected: it would itself be a persistent resource requiring
744 * crash-cleanup -- the very problem class this algorithm handles -- plus versioning/consistency headaches.)
745 * (End of note on stats.)
746 *
747 * Let's do it. */
748
749 const auto n_removed
750 = util::remove_each_persistent_if<Pool_arena>(get_logger(),
751 [&](const Shared_name& shm_pool_name)
752 {
753 Shared_name resource_type;
754 Shared_name srv_app_name;
755 Shared_name srv_namespace_aka_pid;
756 Shared_name the_rest;
757
758 if (!(decompose_conventional_shared_name(shm_pool_name,
759 // We always identify resource type even though redundant in this case.
760 &resource_type,
761 &srv_app_name, // This must be us, not some other app.
762 &srv_namespace_aka_pid, // This is what must be dead.
763 nullptr, // cli_app_name: Needs to be there, but we don't care what it is.
764 nullptr, // cli_namespace_or_sentinel: Ditto.
765 &the_rest)
766 && (resource_type == Shared_name::S_RESOURCE_TYPE_ID_SHM)
767 && (srv_app_name == m_srv_app_ref.m_name)
768 && String_view{the_rest.str()}.starts_with((SHM_SUBTYPE_PREFIX + Shared_name::S_SEPARATOR).str())))
769 {
770 /* Not our pool to possibly delete. Misnamed; or not from a split with our Server_app;
771 * or not from this SHM-provider. */
772 return false;
773 }
774 // else
775
776 /* We could actually skip this next check -- then we'd be deleting client-created stuff too. It doesn't seem
777 * like there's any practical downside. Just... I (ygoldfel) have really convinced myself by that text
778 * in the big comment above regarding arena-lending SHM-providers being symmetrical in how each side deals
779 * with the resources they owned. So going out of our way to clean server stuff by server, client stuff
780 * by client. @todo Reconsider maybe. It's also not of huge import, this question: If it gets cleaned, cool. */
781 if (String_view{the_rest.str()}.find_first_of(Shared_name::S_SEPARATOR,
782 SHM_SUBTYPE_PREFIX.size() + 1) != String_view::npos)
783 {
784 return false; // Not our pool to possibly delete. From a split with our Server_app but created by client side.
785 }
786 // else
787
788 process_id_t pid = 0;
789 try
790 {
791 pid = lexical_cast<process_id_t>(srv_namespace_aka_pid.str());
792 }
793 catch (...) {}
794 if (pid <= 0)
795 {
796 FLOW_LOG_WARNING("Session server [" << *this << "]: During periodic cleanup found seemingly relevant "
797 "(based on prefix/form) SHM-pool named [" << shm_pool_name << "]; but server-PID (a/k/a "
798 "server-namespace) term [" << srv_namespace_aka_pid << "] is not a valid-looking PID. "
799 "Ignoring; but this warrants investigation.");
800 return false;
801 }
802 // else
803
804 if (util::process_running(pid))
805 {
806 return false;
807 }
808 // else
809
810 FLOW_LOG_INFO("Session server [" << *this << "]: During periodic cleanup found SHM-pool "
811 "named [" << shm_pool_name << "]; appears to have been created by a process of this application "
812 "that is no longer running, even as a zombie; perhaps it exited without graceful cleanup. Will "
813 "attempt to remove it. Competing cleanup(s) may be occurring concurrently; that is fine.");
814 return true;
815 }); // remove_each_persistent_if()
816 if (n_removed == 0)
817 {
818 FLOW_LOG_TRACE("Session server [" << *this << "]: Cleanup finished: removed none.");
819 }
820 else
821 {
822 FLOW_LOG_INFO("Session server [" << *this << "]: Cleanup finished: Removed [" << n_removed << "] pools "
823 "successfully.");
824 }
825
826 m_async_periodic_worker.schedule_from_now(CLEANUP_PERIOD, [this](auto&&) { cleanup(); });
827} // Session_server::cleanup()
