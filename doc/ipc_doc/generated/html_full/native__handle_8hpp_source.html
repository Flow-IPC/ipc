40/**
41 * A monolayer-thin wrapper around a native handle, a/k/a descriptor a/k/a FD.
42 * It would have been acceptable to simply use an alias to the native handle type (in POSIX, `int`),
43 * but this way is better stylistically with exactly zero performance overhead. Initialize it, e.g.,
44 * `Native_handle hndl{some_fd};`, where `some_fd` might be some POSIX-y FD (network socket, Unix domain socket,
45 * file descriptor, etc.). Or initialize via no-arg construction which results in a `null() == true` object.
46 * Copy construction, assignment, equality, total ordering, and hashing all work as one would expect and
47 * essentially the same as on the underlying native handles.
48 *
49 * It is either null() or stores a native handle. In the former case, null() being `true` means explicitly
50 * that `m_native_handle == Native_handle::S_NULL_HANDLE`.
51 *
52 * ### Ownership ###
53 * Native_handle is extremely simple. Other than providing move semantics, where the moved-from guy becomes `.null()`,
54 * and an always-manual close() API, it does not add ownership semantics. You're free to, e.g., assign a non-null
55 * socket value, then make a copy, then (e.g.) `.close()` them both -- the second one being an erroneous
56 * double-close. However, if you need added cleverness to avoid such things:
57 *
58 * @see Helper type #Own_native_handle: It adds auto-`close()` behavior, on destruction and being moved-to.
59 * (To get at the Native_handle itself, given an `Own_native_handle x`: Call `x.get()`. The full API
60 * is similar to `unique_ptr`'s basic API: `.reset()`, `.release()`, and so on.)
61 * This can be quite useful when one is juggling `Native_handle`s in some operation and, e.g., does not
62 * want to leak the OS-handles (descriptors) on early `return` due to error conditions. If ultimately
63 * a raw `Native_handle` is required, one can always get it out via `.release()`.
64 */

162 /**
163 * Little utility that returns #m_native_handle to the OS.
164 *
165 * This is helpful to close, without invoking a native API (`"::close()"` really), a value returned by
166 * `transport::asio_local_stream_socket::Peer_socket::release()` or, perhaps, received over a
167 * `transport::Native_socket_stream`.
168 *
169 * `*this` is nullified (null() shall return `true`). No-op if already so at entry.
170 *
171 * Nothing is logged; no errors are emitted. This is intended for no-questions-asked cleanup.
172 *
173 * @note The Native_handle destructor, such as it is, absolutely does not close() or anything similar.
174 * Similarly move ctor/assignment does not either. In fact nothing else in Native_handle does.
175 * If you want to do it, you must call close() yourself. It is a utility; and Native_handle as a whole
176 * intentionally features minimal intelligence; it is merely an object wrapper around a raw handle.
177 * Move ctor/assignment nullifying the source object is as "intelligent" as we get.
178 *
179 * @see However: #Own_native_handle adds auto-`close()` behavior, on destruction and being moved-to.
180 * This can be quite useful when one is juggling `Native_handle`s and, e.g., does not want to leak
181 * the OS-handle (descriptor) on early `return` due to error conditions.

185 /**
186 * Returns whether #m_native_handle is currently an open descriptor in this process; `false` if null().
187 *
188 * @warning Caveats due to the nature of what Native_handle stores:
189 * 1, is_open() is a point-in-time answer (nothing prevents a close immediately after).
190 * 2, returning `true` means *some* descriptor identified by #m_native_handle is open -- a stale value
191 * whose value has since been recycled answers `true`.
192 * So, watch out, particularly when there is asynchronicity and/or concurrency.
193 *
194 * Nothing is logged; no errors are emitted.
195 *
196 * @return See above.

200 /**
201 * Returns a new handle referring to the same underlying OS-level open resource as `*this`, a-la POSIX `"::dup()"`
202 * (in POSIX parlance: a new descript*or* to the same open file descript*ion*). The result is independent
203 * of `*this`: closing either leaves the other valid.
204 *
205 * @see duped_native_handle() to obtain the same in the auto-closing #Own_native_handle form.
206 *
207 * An error is possible but generally indicates a truly exceptional situation, probably classifiable in one of these:
208 * - User error: null() is `true`.
209 * - User error: The stored #m_native_handle is invalid/corrupt.
210 * - Environment is hosed: Ran out of descriptors in the OS table/reached a configured limit/etc.
211 *
212 * @note For all applicable OS: close-on-exec is set on the returned handle.
213 *
214 * @param err_code
215 * See `flow::Error_code` docs for error reporting semantics. #Error_code generated:
216 * transport::error::Code::S_INVALID_ARGUMENT if `*this` is `.null()`,
217 * system error (likely culprits estimated above).
218 * @return On success a non-`.null()` Native_handle; on failure a `.null() == true` one.
219 * (Per usual Flow semantics: on failure: if `!err_code`, exception is thrown instead.)
220 */
221 Native_handle dup(Error_code* err_code = nullptr) const;

243/**
244 * A `unique_resource` wrapper for Native_handle useful to avoid descriptor leaks and double-closing; can be thought
245 * of as a `unique_ptr<Native_handle>` except involves no heap allocation, and nullness is determined by
246 * Native_handle::null().
247 *
248 * For a bit more background on rationale and usage: see Native_handle doc header Ownership section.
249 *
250 * Reminder: if/when ready to get a raw, non-auto-closing Native_handle back: use `.release()`.
251 *
252 * @internal
253 *
254 * ### Impl notes ###
255 * `unique_resource` is almost perfect for what we want here. Just a couple subtleties:
256 * - `boost.scope` itself threw in a `unique_fd` which, in POSIX-land at least, is very similar or identical
257 * to `Own_native_handle`; it uses `unique_resource` too, naturally, but around `int` a/k/a Native_handle::handle_t
258 * as opposed to some wrapper like our `Native_handle`. We contemplated reusing it anyway, for that
259 * particular purpose, but decided that the Native_handle abstraction works for us, so we'd rather re-wrap
260 * it ourselves. As you can see it is not hard: one line here plus the traits functions
261 * Native_handle::make_default() and Native_handle::is_allocated().
262 * - The resulting thing, due to our use of traits, is quite tight perf-wise: Its size is that of `handle_t` --
263 * an `int` in POSIX at least -- and, combining `constexpr`ness and `unique_resource`'s design, all the
264 * basic operations (assign, compare, construct...) should be trivially fast.
265 * - There is one *little* asterisk on that front: Given a *non-null object*: the close operation (through
266 * `.reset()`, dtor, being assigned-onto or -from) will check for `m_native_handle == S_NULL_HANDLE`
267 * twice: 1, `unique_resource` through Native_handle::is_allocated() (traits); 2,
268 * in Native_handle::close() again. It'll be `false` both times, so then `"::close(m_native_handle)"`
269 * will occur. The 2nd equality check is redundant. (If it's a null object, then the initial check
270 * returns `true` => GTFO; no problem there.)
271 * - The reason: `.close()` is defensive, as it should be; and Native_handle::Closer inherits that -- why
272 * shouldn't it, in and of itself? -- and then it is convenient to use `Closer` for
273 * our `unique_resource` setup. Could we "defeat" it by using a, like, `Closer_unchecked` as the deleter?
274 * Yes; but pragmatically speaking that's over-engineering. A redundant `int` compare -- probably optimized
275 * away at some point anyway -- only when the close OS-call will be invoked? Not a real problem.
276 */
277using Own_native_handle = boost::scope::unique_resource<Native_handle, Native_handle::Closer, Native_handle>;

457constexpr bool operator<(Native_handle val1, Native_handle val2) noexcept
458{
459 /* In POSIX and Windows this is valid. So don't worry about #ifdef'ing for OS, static_assert(false), etc.
460 * I did check that even in Windows they are formally integers still. Update: Actually... not sure... depends
461 * on what's a Native_handle; if it's SOCKET then sure, but otherwise -- who knows? There's probably a ticket
462 * about that whole topic (porting for Windows, that is; a big part would be figuring out what Native_handle might
463 * even be... if anything). */
