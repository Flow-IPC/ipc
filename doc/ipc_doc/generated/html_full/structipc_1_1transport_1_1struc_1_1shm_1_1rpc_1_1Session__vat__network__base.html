Todo:
Session_vat_network::S_N_MAX_INCOMING_FDS is set to 10 as a reasonable default... so is it reasonable? I (ygoldfel) just picked something that felt like it would probably be more than enough in most conceivable uses of capnp-RPC's native handle (a/k/a FD in Unix a/k/a capability in capnp-RPC parlances) passing feature: really a capnp-interface impl can only feature a single handle via getFd(), and one guesses that even with all the promise-pipelining ever, a single internal rpc::Message is unlikely to combine more than 10 of these... probably? On the other hand, why not just make this, like, 250-ish? Answer: Comments in capnp suggest this whole thing is a "security" thing, but I personally lack the background as to the concerns discussed there. The to-do is to reach and document a greater level certainty about this value (and change it if appropriate).
