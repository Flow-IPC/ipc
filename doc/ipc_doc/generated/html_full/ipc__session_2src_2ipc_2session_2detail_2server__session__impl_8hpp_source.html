36/**
37 * Internal, non-movable pImpl-lite implementation of Server_session_mv class template.
38 * In and of itself it would have been directly and publicly usable; however Server_session_mv adds move semantics.
39 *
40 * @see All discussion of the public (and `private`, to be exposed `public`ly by Server_session_dtl) API is in
41 * Server_session_mv doc header; that class template forwards to this
42 * one. All discussion of pImpl-lite-related notions is also there. See that doc header first please. Then come
43 * back here.
44 *
45 * Impl design
46 * -----------
47 * Generally, I (ygoldfel) recommend looking through and understanding Client_session_impl first. It is similar but
48 * somewhat more complex, and once it is understood, you'll be able to understand Server_session_impl easily. Plus
49 * its logic is complementary to a `*this`, as the two directly interoperate via a couple of IPC forms. The below
50 * discussion does assume one has read/understood Client_session_impl doc header.
51 *
52 * Thread U represents all threads other than thread W: since the relevant methods are to be called by the user
53 * sans concurrency, those threads as a collection can be thought of as one thread.
54 *
55 * Thread W is the async worker thread where most work is done; this helps us entirely avoid mutexes.
56 * async_accept_log_in() is called exactly once, internally by Session_server; and subsequently
57 * open_channel() is fairly infrequently called. So it's not necessary to avoid
58 * latency by doing work concurrently in threads U and W. So we keep it simple by posting most stuff onto thread W.
59 *
60 * The state machine of Server_session_impl is simpler than Client_session_impl. The asymmetry is, firstly, due to the
61 * client-server setup: Session_server is the one, on the server end, that awaits the initial
62 * transport::Native_socket_stream connection. Once a PEER-state `Native_socket_stream` is ready, only then
63 * does Session_server create a Server_session_mv (which
64 * is a movable `unique_ptr` wrapper around this Server_session_impl). So `*this`, unlike a Client_session_impl,
65 * does not need to connect a socket. Next, Server_session_impl just needs to complete one async step, which is
66 * in practice immediately (and, by contract, only once) invoked: async_accept_log_in(). At this stage user does
67 * not have the Server_session_mv yet, so we're still in internal-code land. (By contrast Client_session is
68 * created directly by the user and is immediately publicly available as a stand-alone object.) async_accept_log_in()
69 * immediately upgrades the `Native_socket_stream` to a transport::Channel and then immediately upgrades that
70 * to a transport::struc::Channel, saving it to #m_master_channel (all synchronously). Lastly is the actual async work:
71 * awaiting the log-in request from Client_session. Once that is received, we respond via #m_master_channel,
72 * either with log-in success or failure. Assuming success, we invoke the (internal) async_accept_log_in()
73 * handler; on failure same thing but with a failure #Error_code.
74 *
75 * ### Sidebar: Init-channels ###
76 * Update (init-channels feature has been added): The preceding paragraph holds fully if and only if:
77 * - client (in its log-in request message, `LogInReq`) requested 0 init-channels to be opened on its behalf; and
78 * - server (via the user args from Session_server::async_accept() forwarded to async_accept_log_in()) requested
79 * 0 init-channels to be opened on local user's behalf.
80 *
81 * However, if the sum of these 2 numbers (as determined upon successful receipt of `LogInReq`, and assuming
82 * everything else was also successful, up-to-and-including sending successful `LogInRsp`) is N=1+, then before
83 * async_accept_log_in() can reach almost-PEER state (and fire completion handler), there is 1 more async-step:
84 * - (send `LogInRsp` as explained);
85 * - (prep) synchronously prepare the N=1+ init-channels (exactly as would occur
86 * if user invoked open_channel() N times in PEER state);
87 * - (prep) sync-send N `OpenChannelToClientReq` messages with names/handles for each of the N init-channels
88 * (exactly as would occur on N open_channel() calls in PEER state);
89 * - async: await a *single* `OpenChannelToClientRsp` response, indicating the last of the N channels has been
90 * accepted, and client is now in PEER state and ready for passive-opens (i.e., we can enter PEER-state
91 * which enables open_channel() by the local user).
92 *
93 * Why this last async step? Couldn't we just do the `send()`s and go to almost-PEER state immediately?
94 * Almost: but if we did that, then if the user immediately issued init_handlers() and an open_channel(),
95 * then the opposing Client_session_impl might not, technically, be quick enough to have moved to its own PEER state;
96 * then its `OpenChannelToClientReq` handler from the pre-PEER state (CONNECTING state) might be triggered;
97 * this would cause... nothing good. However the ACK from Client_session_impl is sent only just before
98 * entering PEER state, at which point it is safe for us to issue open_channel()s.
99 *
100 * ### Back to general impl discussion ###
101 * Our async_accept_log_in() is analogous/complementary to Client_session_impl::async_connect(), but the diff is that
102 * the user only gets access to a `*this` upon success of this async op; and never gets access upon failure
103 * at all. So that's another source of asymmetry versus Client_session_impl. Thus:
104 * - No need to guard against async_accept_log_in() call while the log-in is outstanding.
105 * - (As of *this* writing Client_session_impl only uses async_connect() internally and does not expose it,
106 * so it's not an issue there either; but that would change, if it became network-enabled at some level.)
107 * - No need to guard against other API calls, notably open_channel(), before (almost-)PEER state is achieved.
108 * (User only gets access to `*this`, once `*this` is in (almost-)PEER state.)
109 *
110 * Therefore there's no need to track an `m_state` the way Client_session_impl does. If #m_log_in_on_done_func
111 * is non-empty, then async_accept_log_in() is outstanding (analogous to Client_session_impl CONNECTING state).
112 * Otherwise see the "almost-PEER" section just below.
113 *
114 * ### Almost-PEER state impl ###
115 * There is a minor wrinkle in Server_session_mv (and thus Server_session_impl). Once the user obtains
116 * the Server_session_mv, it is in the so-called *almost-PEER* state. That is because it needs 1-2 more pieces of
117 * info to be set before it is formally in PEER state as specified by Session concept. Namely its
118 * on-error handler must be set (mandatory), as must its on-passive-open handler (optional; in that leaving it
119 * unspecified is allowed and means passive-opens are disabled on this side). To do so the *user*
120 * shall call init_handlers(). Until this is done, open_channel() and other public PEER-state APIs shall
121 * no-op and return sentinel/`false`.
122 *
123 * There is a subtlety in how this are-handlers-set check is performed. The crux of it is that #m_master_channel
124 * can report an error at any time starting with async_accept_log_in() (where it is first created), and what to
125 * do is quite different in each case:
126 * - Before public availability to user (async log-in ongoing).
127 * - Contingency: report failure of async_accept_log_in(), via its on-done handler.
128 * - After that but in almost-PEER state (on-error handler not yet set by user).
129 * - Contingency: well, we *want* to report it via on-error handler... but it's not set yet.
130 * So memorize it in special member #m_pre_init_err_code. Then in init_handlers() immediately fire off
131 * the freshly-available on-error handler with that #Error_code.
132 * - In PEER state (the handler has been set).
133 * - Contingency: yay, forward the #m_master_channel-reported #Error_code to the on-error
134 * handler.
135 *
136 * Because the #m_master_channel error handler is relevant across all of the above, and it is executed in thread W
137 * for reasons explained above (avoiding mutexes, etc.), to avoid concurrency difficulties the are-handlers-set
138 * check, and the assignment of the handlers, is also done in thread W. Hence, like most code in Server_session_impl,
139 * init_handlers() posts all its work onto thread W. All public APIs, even simple ones like session_token(),
140 * do the same, and that thread-W work always begins by ensuring handlers_are_set().
141 *
142 * Once PEER state is achieved, to the user `*this` is (just like Client_session_impl) an impl of Session concept.
143 * Internally it's somewhat different.
144 *
145 * ### PEER state impl ###
146 * Here our algorithm is complementary to the PEER state algorithm in Client_session_impl. Namely we expect
147 * passive-opens via an appropriate transport::struc::Channel::expect_msgs(); and we allow active-opens via
148 * open_channel(). The details of how these work are best understood just by reading that code inline. All in
149 * all, publicly it's just like Client_session_impl; but internally it is its complement and in fact has
150 * different (complementary) responsibilities. Most notably, regarding active-opens and passive-opens:
151 * - Server_session_impl is the one always internally responsible for acquiring the resources needed to
152 * establish the channel. Namely:
153 * - If #S_MQS_ENABLED: it *creates* the underlying MQs. This involves choosing a distinct-enough name for
154 * each of the 2 MQs (one in each direction, client->server, server->client). These names shall be
155 * sent-over, via #m_master_channel, to the Client_session_impl.
156 * - If #S_SOCKET_STREAM_ENABLED: it *creates* the pre-connected socket-pair, 1/2 of which (a `Native_handle`)
157 * shall be sent-over, via #m_master_channel, to the Client_session_impl.
158 * - Hence:
159 * - An active-open (open_channel()) sends over the references/handles to the above resource(s) in the
160 * open-channel-to-client request out-message via #m_master_channel. It then ensures the client
161 * replies with an OK (or failure) response in-message. open_channel() thus succeeds or fails.
162 * - A passive-open (on_master_channel_open_channel_req()) involves receiving an
163 * open-channel-to-server request in-message via #m_master_channel. It then acquires the above resource(s)
164 * and sends over the refs/handles to said resource(s) in our OK response to that request and invokes
165 * the on-passive-open handler locally.
166 *
167 * Client_session_impl active-opens and passive-opens act in a complementary fashion, never acquiring these resources
168 * but knowing what to expect.
169 *
170 * Otherwise open_channel() is set up similarly to Client_session_impl::open_channel(), namely the
171 * non-blocking/synchronous facade with async-with-timeout internals. See Client_session_impl doc header for
172 * brief discussion. In addition, the way work is distributed across threads U (user thread(s)) and thread W
173 * (#m_async_worker) inside open_channel() is deliberately asymmetric between open_channel() here and
174 * Client_session_impl::open_channel(); this avoids a certain cross-process deadlock situation. This is explained
175 * inside open_channel().

820TEMPLATE_SRV_SESSION_IMPL
821void CLASS_SRV_SESSION_IMPL::dtor_async_worker_stop()
822{
823 using flow::async::Synchronicity;
824 using boost::promise;
825
826 // We are in thread U (from either our own dtor or subclass dtor).
827
828 assert((!m_async_worker.task_engine()->stopped()) && "This shall be called at most once.");
829
830 /* The following is quite similar to Client_session_impl::dtor_async_worker_stop(), so keeping comments
831 * light here (@todo code reuse?). */
832
833 FLOW_LOG_INFO("Server session [" << *this << "]: Shutting down. Worker thread will be joined, but first "
834 "we perform session master channel end-sending op (flush outgoing data) until completion. "
835 "This is generally recommended at EOL of any struc::Channel, on error or otherwise. "
836 "This is technically blocking but unlikely to take long. Also a Graceful_finisher phase may "
837 "precede the above steps (it will log if so).");
838
839 /* First things first: no later than now -- in thread W terms -- stop emitting session-hosing errors to
840 * the user's on-error handler. See Session_base::m_dtor_started doc header (rationale et al). Posting order
841 * matters: this precedes any Graceful_finisher tasks below, and thread W executes in-order.
842 *
843 * Reiterating here though: Nothing can -- and this won't -- prevent handler firing during dtor altogether; it
844 * might be happening already. Said doc header explains why we still prevent it from this point on. */
845 m_async_worker.post([this]() { Base::set_dtor_started(); });
846
847 if constexpr(S_GRACEFUL_FINISH_REQUIRED)
848 {
849 typename Base::Graceful_finisher* graceful_finisher_or_null = {};
850 m_async_worker.post([&]() // Have to access m_graceful_finisher (the optional<>) in thread W only.
851 {
852 // We are in thread W.
853 if (m_graceful_finisher)
854 {
855 graceful_finisher_or_null = &(m_graceful_finisher.value());
856 }
857 }, Synchronicity::S_ASYNC_AND_AWAIT_CONCURRENT_COMPLETION); // m_async_worker.post()
858
859 /* If graceful_finisher_or_null is not null, then we're definitely in PEER state, and this is irreversible;
860 * so it's cool to ->on_dtor_start() on it. It'll block as needed, etc.
861 *
862 * If it *is* null:
863 * - If between the assignment above to null and the next statement, m_graceful_finisher did not become
864 * non-empty, then there's no controversy: It's still not in PEER state; and there's no reason to
865 * block dtor still. So no need to do anything, and that's correct. Can just continue.
866 * - If however in the last few microseconds (or w/e) indeed m_graceful_finisher
867 * has become non-empty, then now *this is in PEER state. ...NOPE! The only way that can happen
868 * for us -- unlike Client_session_impl as of this writing -- is via init_handlers(), which the user
869 * themselves must execute. So actually graceful_finisher_or_null remains accurate from up above
870 * to the next statement. */
871 if (graceful_finisher_or_null)
872 {
873 graceful_finisher_or_null->on_dtor_start();
874 // OK, now safe (or as safe as we can guarantee) to blow *this's various parts away.
875 }
876 } // if constexpr(S_GRACEFUL_FINISH_REQUIRED)
877
878 m_async_worker.post([&]()
879 {
880 // We are in thread W.
881
882 if (!m_master_channel)
883 {
884 return; // Destroyed at early juncture (as of this writing). Whatever; cool; nothing to flush anyway.
885 }
886 // else
887
888 promise<void> done_promise;
889 const bool did_it = m_master_channel->async_end_sending([&](const Error_code&)
890 {
891 // We are in thread Wc (unspecified, really struc::Channel async callback thread).
892 FLOW_LOG_TRACE("Server session [" << *this << "]: Shutdown: master channel outgoing-direction flush finished.");
893 done_promise.set_value();
894 });
895 // Back here in thread W:
896 if (did_it)
897 {
898 done_promise.get_future().wait();
899 }
900 /* else
901 * { Don't care it returned false and did nothing: cool then; did our best.
902 * Really it shouldn't happen: we don't call it twice, and channel was up for sure. So @todo assert(). } */
903 }, Synchronicity::S_ASYNC_AND_AWAIT_CONCURRENT_COMPLETION); // m_async_worker.post()
904 // Back here in thread U: done; yay.
905
906 m_async_worker.stop();
907 // Thread W has been joined.
908} // Server_session_impl::dtor_async_worker_stop()

915 using flow::util::ostream_op_string;

917 // We are in thread U. By contract in doc header, they must not call us from a completion handler (thread W).

944 }); // one_thread.start()

956 }

1020 "Success. Will emit any cached master-channel error ([" << m_pre_init_err_code << "] "
1021 "[" << m_pre_init_err_code.message() << "]).");

1024 Base::set_on_passive_open_channel_func(std::move(on_passive_open_channel_func_or_empty_arg));
1025 assert(handlers_are_set() && "We just set them....");

1028 {
1029 assert((!Base::hosed()) && "We only just entered PEER state.");
1030

1032 * and therefore thread U caller's, return. */

1034 {
1035 // We are in thread W.
1036

1038 {
1039 FLOW_LOG_INFO("Server session [" << *this << "]: We were about to fire cached error observed earlier "
1040 "during the almost-PEER phase; but somehow *yet another* error condition hosed us during "
1041 "the async-gap between that recent decision and this task executing in worker thread. "
1042 "It is hard to imagine what it could be, but it is not known to be a bug or problem. "

1047 Base::hose(m_pre_init_err_code);
1048 }
1049 /* else if (dtor_started()): The dtor has begun in the async-gap since init_handlers(); the user
1050 * no longer benefits from any notification. See Session_base::m_dtor_started doc header. */
1051 });
1052 return true;
1053 }

1055

1065 });

1149TEMPLATE_SRV_SESSION_IMPL
1150typename CLASS_SRV_SESSION_IMPL::Mdt_builder_ptr CLASS_SRV_SESSION_IMPL::mdt_builder()
1151{
1152 using util::Native_handle;
1153 using flow::async::Synchronicity;
1154 namespace asio_local = transport::asio_local_stream_socket;
1155
1156 // We are in thread U.
1157
1158 Channel_obj opened_channel;
1159 Native_handle remote_hndl_or_null;
1160 Shared_name mq_name_c2s_or_none;
1161 Shared_name mq_name_s2c_or_none;
1162 bool resources_acquired_ok = false;
1163
1164 typename Master_structured_channel::Msg_out open_channel_req_msg;
1165 bool open_channel_req_msg_inited = false;
1166 m_async_worker.post([&]()
1167 {
1168 // We are in thread W: need to be to access m_master_channel and to call create_channel_and_resources().
1169
1170 if (!handlers_are_set())
1171 {
1172 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open active request: Invoked before PEER state. "
1173 "Ignoring.");
1174 assert((!open_channel_req_msg_inited) && "Should have remained false as initialized.");
1175 assert((remote_hndl_or_null.null()) && "Should have remained .null() as initialized.");
1176 return;
1177 }
1178 // else
1179
1180 resources_acquired_ok
1181 = (!Base::hosed())
1182 && create_channel_and_resources(&mq_name_c2s_or_none, &mq_name_s2c_or_none, &remote_hndl_or_null,
1183 &opened_channel, true); // true => active-open, not passive-open.
1184
1185 assert(resources_acquired_ok || remote_hndl_or_null.null());
1186 open_channel_req_msg = m_master_channel->create_msg(std::move(remote_hndl_or_null));
1187 open_channel_req_msg_inited = true;
1188 // (Might be sending them this Native_handle too. ---^)
1189 }, Synchronicity::S_ASYNC_AND_AWAIT_CONCURRENT_COMPLETION);
1190
1191 // The rest we can do back in thread U again.
1192
1193 if (!open_channel_req_msg_inited)
1194 {
1195 // As advertised: Not PEER state => return null.
1196 return {};
1197 }
1198 // else
1199
1200 auto open_channel_root = open_channel_req_msg.body_root()->initOpenChannelToClientReq();
1201 if (resources_acquired_ok)
1202 {
1203 open_channel_root.setClientToServerMqAbsNameOrEmpty(mq_name_c2s_or_none.str());
1204 open_channel_root.setServerToClientMqAbsNameOrEmpty(mq_name_s2c_or_none.str());
1205 }
1206 /* else if (!resources_acquired_ok):
1207 * Possibility 1: When about to grab resources, detected Base::hosed(), so did not grab them: no point.
1208 * In any case we are not to return null (that is only if called pre-PEER, user error); but open_channel()
1209 * will not even check *<return value>'s contents; precondition hosed() is irreversible and leads it to
1210 * just return false and no-op otherwise. (We'll save the discussion of whether our behavior here is a
1211 * reasonable contract until a few lines down, where possibility 2 is discussed. More or less same logic here.)
1212 *
1213 * Possibility 2: Everything is otherwise fine, as far as we know, but tried to grab resource and:
1214 * Resource unavailable. Now, we know this already, even though we haven't even sent any request to the
1215 * client -- because we *are* the server and thus immediately can and must acquire the channel resources.
1216 * Our contract is to report such a problem via the later open_channel() though. So we save this fact
1217 * and will report it quickly from open_channel(), right at its start.
1218 *
1219 * By saving a default-cted Channel_obj in this event, we indicate this fact.
1220 *
1221 * Rationale: Well, we promised this behavior. But why? We could report it now. Answer: It would be a clumsy
1222 * API contract. Either we must return null, in which case they cannot easily distinguish between
1223 * "called pre-PEER => null, nothing more to it" and
1224 * "resource unavailable error => null, your decision whether to blow everything up or what.";
1225 * or we'd need to add an Error_code* out-arg, which means complicating the Session concept API, which means
1226 * changing Client_session too. Anyway, it is weird, from user's PoV, to even deal with the idea that
1227 * in a Server_session the metadata-builder-returning method somehow can already fail -- they have no reason
1228 * to think resource acquisition occurs at that stage. So at the expense of a short delay we just delegate
1229 * new-error reporting to open_channel() instead of making it an odd 2-step thing.
1230 *
1231 * That said, open_channel() contract still has to specifically note that the particular resource-unavailable
1232 * error -- not fatal to the Session -- is a possibility, unlike other `Error_code`s which are fatal.
1233 * However (1) that's open_channel()'s problem; and (2) it is manageable (and is mandated by Session concept). */
1234
1235 Open_channel_req_ptr open_channel_req_ptr{new Open_channel_req
1236 { open_channel_root.initMetadata(),
1237 std::move(open_channel_req_msg),
1238 // If this is empty: indicates resource-unavail eventuality.
1239 resources_acquired_ok
1240 ? std::move(opened_channel)
1241 : Channel_obj{} }};
1242 assert((static_cast<const void*>(open_channel_req_ptr.get())
1243 == static_cast<const void*>(&open_channel_req_ptr->m_mdt_builder))
1244 && "open_channel() recovers the struct from this member; it must sit at offset 0.");
1245
1246 return Mdt_builder_ptr{std::move(open_channel_req_ptr), &open_channel_req_ptr->m_mdt_builder};
1247} // Server_session_impl::mdt_builder()

1249TEMPLATE_SRV_SESSION_IMPL
1250bool CLASS_SRV_SESSION_IMPL::open_channel(Channel_obj* target_channel, const Mdt_builder_ptr& mdt,
1251 Error_code* err_code)
1252{
1253 using schema::detail::OpenChannelResult;
1254 using flow::async::Synchronicity;
1255 using boost::chrono::milliseconds;
1256 using boost::chrono::round;
1257
1258 // We are in thread U.
1259
1260 FLOW_ERROR_EXEC_AND_THROW_ON_ERROR(bool, open_channel, target_channel, mdt, _1);
1261 // ^-- Call ourselves and return if err_code is null. If got to present line, err_code is not null.
1262
1263 /* Whether or not we promised this when returning false, this overall avoids some headaches/maintenance pain and
1264 * allows us to, e.g., assert(!*err_code) up to a point. Just remember that if *err_code becomes truthy,
1265 * and *then* we decide to return false, it has to be ->cleared() again; otherwise we can mess up
1266 * the operation of FLOW_ERROR_EXEC_AND_THROW_ON_ERROR(). */
1267 err_code->clear();
1268
1269 if (!mdt)
1270 {
1271 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open active request: "
1272 "null metadata-builder passed-in; presumably user error. "
1273 "Emitting code-less failure in this synchronous path.");
1274 return false;
1275 }
1276 // else
1277
1278 /* The plan:
1279 *
1280 * As usual we want to do all the work in thread W, where we can access m_master_channel among
1281 * other things. We do need to return the results of the operation here in thread U though.
1282 * Client_session_impl::open_channel() is structured that way as well.
1283 *
1284 * Not so fast though. There is a cross-process deadlock possibility that arises if we implement both
1285 * Client_ and this Server_ open_channel()s in symmetrical fashion. The deadlock is particularly nasty, as
1286 * it would not typically manifest, but with coincidental timing it will:
1287 *
1288 * It requires both sides to execute open_channel() concurrently (and therefore to have registered a passive-open
1289 * handler on each side). So there's thread Ws (our thread W) and thread Wc (theirs).
1290 * (Those names apply within this comment only; elsewhere in this file Wc denotes the struc::Channel callback
1291 * thread.) In a symmetrical setup this could happen:
1292 * - [srv] thread Ws: SMC.sync_request() begins; awaits response (blocks).
1293 * - [cli] thread Wc: SMC.sync_request() begins; awaits response (blocks).
1294 * - [srv] thread SMCs: got request, invoke Server_session_impl handler;
1295 * that handler does Ws.post(Server_session_impl::on_master_channel_open_channel_req);
1296 * so Server_session_impl::on_master_channel_open_channel_req is *queued* on Ws
1297 * (Ws currently inside sync_request())
1298 * - [cli] thread SMCc: got request, invoke Client_session_impl handler;
1299 * that handler does Wc.post(Client_session_impl::on_master_channel_open_channel_req);
1300 * so Client_session_impl::on_master_channel_open_channel_req is *queued* on Wc
1301 * (Wc currently inside sync_request())
1302 * And that's it. on_master_channel_open_channel_req() queued on W, on each side; can't run; thread W
1303 * has SMC.sync_request() waiting for *opposing* on_master_channel_open_channel_req() to reply to
1304 * the request with an SMC.send(); both timeout after a long time; both receive the response, but it's past
1305 * timeout, so it's dropped. Incidentally this deadlock pattern is warned-about in Channel::sync_request()'s docs.
1306 *
1307 * To solve this: just changing one thing is sufficient: One side (not necessarily both), doesn't matter that
1308 * much which (we choose srv-side -- that's here -- as we vaguely suspect it would more commonly passive-open
1309 * and thus will be made somewhat more responsive), shall avoid executing SMC.sync_request() from thread W
1310 * and do it in thread U instead.
1311 *
1312 * This is slightly annoying for two reasons. 1, it means jumping back and forth between U and W. 2, some
1313 * state has to be accessed from not-W (something we avoid otherwise -- even in something as innocuous looking
1314 * as session_token()). 1: oh well. 2: that "some state" is precisely the SMC m_master_channel. See its
1315 * doc header... but in short struc::Channel's API (unlike most others) is thread-safe.
1316 *
1317 * OK: so the naive plan would've been: U->W*->U->return, with `*` being the core SMC.sync_request().
1318 * Instead this becomes: U->W->U*->W->U->return. A few reminders, since this is somewhat unusual:
1319 * - open_channel() itself is not allowed to be called concurrently to itself (nor to any other APIs).
1320 * So there's no need to worry about concurrency in that sense.
1321 * - Our entire operation happens synchronously in this function. So the lambdas involved capture [&], etc.
1322 * Keeps it relatively simple.
1323 * - (Related point: A different approach, which would have kept everything in thread W and therefore
1324 * more "normal" w/r/t Client_ and Server_ impl ways of doing things, would have been to use
1325 * SMC.async_request() instead of sync_request(). That'd be reasonable, but then there's more
1326 * asynchronicity which makes other things more complex. On balance the sync_request() way is easier,
1327 * we stipulate.)
1328 * - Whenever we enter thread W, we must check hosed(). This is done all-over, but in this case
1329 * W is entered not once but twice; so even the 2nd time it has to be checked: It is possible some SMC
1330 * in-traffic hosed the SMC (*m_master_channel) and therefore *this, while perhaps near the tail end
1331 * of `U*`.
1332 * Let's go. */
1333
1334 bool sync_error_but_do_not_emit = false; // If this ends up true, err_code is ignored and clear()ed ultimately.
1335 // If it -^- ends up false, *err_code will indicate either success or non-fatal error.
1336 Open_channel_req* open_channel_req = {}; // (Init to avoid overzealous warnings.)
1337
1338 m_async_worker.post([&]()
1339 {
1340 // We are in thread W.
1341
1342 assert(handlers_are_set()
1343 && "mdt is non-null, yet state is not PEER, even though PEER is an end state? Bug.");
1344
1345 if (Base::hosed())
1346 {
1347 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open request send-request stage preempted "
1348 "by earlier session-hosed error. No-op.");
1349 sync_error_but_do_not_emit = true;
1350 return;
1351 }
1352 /* else if (!Base::hosed()): We can attempt sync_request() (which could hose us itself)... but first....
1353 *
1354 * See mdt_builder(): It may be indicating to us the resource-unavailable error. Check for this. */
1355
1356 open_channel_req = reinterpret_cast<Open_channel_req*>(mdt.get());
1357 if (!open_channel_req->m_opened_channel.initialized())
1358 {
1359 // @todo Maybe save the original Error_code responsible for this instead of emitting this catch-all thingie?
1360 *err_code = error::Code::S_SESSION_OPEN_CHANNEL_SERVER_CANNOT_PROCEED_RESOURCE_UNAVAILABLE;
1361 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open active request: "
1362 "metadata-builder indicates resources-unavailable error (not fatal to session). Emitting "
1363 "(non-session-hosing) error [" << *err_code << "] [" << err_code->message() << "] "
1364 "without attempting any request to client.");
1365 return;
1366 }
1367 // else
1368
1369 /* Now simply issue the open-channel request prepared already via `mdt` and synchronously
1370 * await response, or error, or timeout. struc::Channel::sync_request() is tailor-made for this. */
1371 FLOW_LOG_INFO("Server session [" << *this << "]: Channel open active request: The blocking, but presumed "
1372 "sufficiently quick to be considered non-blocking, request-response exchange initiating; timeout set "
1373 "to a generous [" << round<milliseconds>(Base::S_OPEN_CHANNEL_TIMEOUT) << "]. The channel is "
1374 "already opened on our side: [" << open_channel_req->m_opened_channel << "].");
1375 }, Synchronicity::S_ASYNC_AND_AWAIT_CONCURRENT_COMPLETION); // m_async_worker.post()
1376
1377 // Thread U again.
1378
1379 if (sync_error_but_do_not_emit)
1380 {
1381 assert(!*err_code);
1382 return false;
1383 }
1384 // else
1385 if (*err_code)
1386 {
1387 return true;
1388 }
1389 /* else: All good for now.
1390 *
1391 * As planned in the big comment up-top: This part (and basically this part only) in thread U
1392 * (m_master_channel-> potentially-concurrent (versus thread W) calls are allowed by struc::Channel): */
1393 const auto open_channel_rsp = m_master_channel->sync_request(&open_channel_req->m_req_msg, nullptr,
1394 Base::S_OPEN_CHANNEL_TIMEOUT, err_code);
1395
1396 m_async_worker.post([&]()
1397 {
1398 // We are in thread W.
1399
1400 if (Base::hosed())
1401 {
1402 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open request send-request stage proceeded, but "
1403 "upon re-entering the main worker thread, we discovered we've just been preempted "
1404 "by earlier session-hosed error. "
1405 "No-op after all; forgetting any response from opposing side.");
1406 sync_error_but_do_not_emit = true; // *err_code is cleared/ignored.
1407 return;
1408 }
1409 /* else: Still good (no incoming-direction, or any other non-thread-U-originating, hosing has occurred).
1410 * (As usual: m_master_channel can get hosed at any time though (but we will be informed after this task
1411 * finishes, if that happens, at which point hose()ing of *this session-obj will execute).) */
1412
1413 if ((!open_channel_rsp) && (!*err_code))
1414 {
1415 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open request failed at the send-request stage "
1416 "(due to incoming-direction error which shall hose session around this time). No-op.");
1417 // (Wouldn't we be hosed() during the check above then? Well, no reason not to be defensive even if so.)
1418 sync_error_but_do_not_emit = true;
1419 return;
1420 }
1421 // else if (*err_code || open_channel_rsp)
1422
1423 if (*err_code) // && !open_channel_rsp)
1424 {
1425 assert((!open_channel_rsp) && "struc::Channel::sync_request() must emit no Error_code if it gets response.");
1426
1427 if (*err_code == transport::error::Code::S_TIMEOUT)
1428 {
1429 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open active request: It timed out. It may "
1430 "complete in the background still, but when it does any result shall be ignored. "
1431 "Emitting (non-session-hosing) error.");
1432
1433 *err_code = error::Code::S_SESSION_OPEN_CHANNEL_ACTIVE_TIMEOUT;
1434 // Non-session-hosing error will be synchronously emitted; *this will continue (as promised).
1435 return;
1436 }
1437 // else if (*err_code truthy but not timeout): Session got hosed.
1438
1439 /* As promised, open_channel() hosing the session shall be reported asynchronously like all errors;
1440 * while we will merely return false. */
1441 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open request failed at the sync-request stage, "
1442 "meaning either the nb-send failed, or in-error detected on channel while waiting for "
1443 "response (new error: [" << *err_code << "] [" << err_code->message() << "]). Hosing "
1444 "session (emit to session on-error handler); will synchronously return failure to "
1445 "open channel.");
1446 Base::hose(*err_code);
1447 sync_error_but_do_not_emit = true; // *err_code is cleared/ignored.
1448 return;
1449 }
1450 // else if (!*err_code): sync_request() succeeded all the way.
1451 assert(open_channel_rsp);
1452
1453 FLOW_LOG_TRACE("Server session [" << *this << "]: Channel open request: Request message sent to client "
1454 "sans error, and response received in time.");
1455
1456 const auto root = open_channel_rsp->body_root().getOpenChannelToClientRsp();
1457 /* The value comes from the (trusted) opposing peer; but as usual we handle its misbehavior on a best-effort basis:
1458 * a value it should never send (as of this writing only the server grabs channel resources, so
1459 * REJECTED_RESOURCE_UNAVAILABLE cannot legitimately come in the server-active-open path; the sentinel; or an
1460 * out-of-range value) is treated as a refusal -- never as success. */
1461 const auto open_channel_result = root.getOpenChannelResult();
1462 bool result_expected = false;
1463 switch (open_channel_result)
1464 {
1465 case OpenChannelResult::ACCEPTED:
1466 assert(!*err_code);
1467 result_expected = true;
1468 break;
1469 case OpenChannelResult::REJECTED_PASSIVE_OPEN:
1470 *err_code = error::Code::S_SESSION_OPEN_CHANNEL_REMOTE_PEER_REJECTED_PASSIVE_OPEN;
1471 result_expected = true;
1472 break;
1473 case OpenChannelResult::REJECTED_RESOURCE_UNAVAILABLE:
1474 case OpenChannelResult::END_SENTINEL:
1475 break;
1476 } // Compiler should catch missing enum value. (Out-of-range raw values skip all cases.)
1477
1478 if (!result_expected)
1479 {
1480 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open active request: Response received but "
1481 "contains unexpected result value [" << int(open_channel_result) << "] -- opposing peer "
1482 "(client) misbehaved? Treating it as refusal of the passive-open.");
1483 *err_code = error::Code::S_SESSION_OPEN_CHANNEL_REMOTE_PEER_REJECTED_PASSIVE_OPEN;
1484 }
1485
1486 if (*err_code)
1487 {
1488 FLOW_LOG_WARNING("Server session [" << *this << "]: Channel open active request: Response received but "
1489 "indicates opposing peer (client) refused; emitting "
1490 "[" << *err_code << "] [" << err_code->message() << "] with explanation from opposing "
1491 "peer. This will not hose session on our end.");
1492 // Note: all of the above are advertised as non-session-hosing.
1493 return;
1494 }
1495 // else: Cool! We already have our side of the channel too.
1496 assert(open_channel_req->m_opened_channel.initialized());
1497
1498 *target_channel = std::move(open_channel_req->m_opened_channel);
1499
1500 FLOW_LOG_INFO("Server session [" << *this << "]: Channel open active request: Succeeded in time yielding "
1501 "new channel [" << *target_channel << "].");
1502 }, Synchronicity::S_ASYNC_AND_AWAIT_CONCURRENT_COMPLETION); // m_async_worker.post()
1503
1504 // It all logged sufficiently. Just return the results.
1505

1640 Channel_obj* opened_channel_ptr,
1641 bool active_else_passive)

1643 using util::Native_handle;
1644 using transport::sync_io::Native_socket_stream;
1645 using transport::Socket_stream_channel;
1646 using transport::Mqs_channel;
1647 using transport::Mqs_socket_stream_channel;
1648 using transport::Socket_stream_channel_of_blobs;

1654 /* @todo It did not exist in the past, but now it does: the auto-closing Native_handle variant, Own_native_handle.
1655 * Use it, locally in here or more widely in *this, to ensure leaking of naked handles (FDs in *nix) does not
1656 * happen. As I write this, it looks solid, but the logic is unnecessarily brittle and easy for maintainers

1659 * it should be in an Own_native_handle. Lots of words here... but it's pretty straightforward really. */

1715 "must have just been hosed: [" << err_code << "] [" << err_code.message() << "]. "

1718 remote_hndl_or_null.close();

1720 }
1721 // else
1722 local_sock_stm_or_null.remote_peer_process_credentials(creds);
1723
1724 return true;
1725 }; // make_sock_stm_func =
1726
1727 if constexpr(S_MQS_ENABLED)
1728 {
1729 Persistent_mq_handle_from_cfg mq_c2s;

1746 std::move(local_sock_stm_or_null), &err_code};
1747 }
1748 else
1749 {
1750 assert(err_code); // Handled a bit lower down.
1751 }
1752 // Fall through.
1753 }
1754 else // if constexpr(!S_SOCKET_STREAM_ENABLED)
1755 {
1756 static_assert(std::is_same_v<Channel_obj,
1757 Mqs_channel<true, Persistent_mq_handle_from_cfg>>, "Sanity check.");

1808TEMPLATE_SRV_SESSION_IMPL
1809bool CLASS_SRV_SESSION_IMPL::make_channel_mqs(Persistent_mq_handle_from_cfg* mq_c2s,
1810 Persistent_mq_handle_from_cfg* mq_s2c,
1811 Shared_name* mq_name_c2s, Shared_name* mq_name_s2c,
1812 Error_code* err_code)
1813{
1814 using std::to_string;
1815
1816 assert(mq_c2s && mq_s2c);
1817 assert(err_code);
1818
1819 /* By default in Linux POSIX MQs this happens to be the actual limit for # of unread messages --
1820 * visible in /proc/sys/fs/mqueue/msg_max -- so we cannot go higher typically. However that file can be modified.
1821 * For now let's assume a typical environment.
1822 * @todo Persistent_mq_handle_from_cfg might be actually bipc MQ, with no such limit, though. So we're (1)
1823 * assuming a certain default and (2) taking POSIX MQs as the lowest common denominator (metaphorically speaking).
1824 * So really this could be something else in that case. Reconsider / make configurable / etc. Might also use the
1825 * default /proc/sys/fs/mqueue/msg_default which is possible using a certain mq_ API. Likely such niceties would
1826 * be factored out into Persistent_mq_handle concept API as opposed to litigated here.
1827 *
1828 * To be clear: the transport:: MQ stuff above the lowest (Persistent_mq_handle) level will seamlessly handle
1829 * any would-block situation due to reaching this limit. In theory it could affect perf. */
1830 constexpr size_t MAX_N_MSG = 10;
1831
1832 size_t max_msg_sz;
1833 const auto cfg_limit_or_zero = m_mq_msg_size_limit;
1834 if (cfg_limit_or_zero == 0) // Means pick a value ourselves.
1835 {
1836 /* We must also decide the max message of each size. If SHM-backing is disabled, then there's no question:
1837 * we have to use Base::S_MQS_MAX_MSG_SZ which (see its doc header) respects both the need to be as large
1838 * as possible to support the widest variety of user payloads; and the (POSIX-MQ-relevant) system limit(s) as
1839 * to the message size. If SHM-backing is enabled, it is tempting to simply use the same value... why not,
1840 * right? Good enough for the heap-backed case; why not the SHM-backed case? At worst it only wastes some
1841 * RAM, since each message transmitted over MQ contains merely a tiny SHM handle, right? Yes and no:
1842 * For bipc MQs, yes; but POSIX MQs impose yet another limit: A given process trying to maintain a *total*
1843 * of X bytes of MQs at a given time (the "total" roughly meaning the sum of `MAX_N_MSG x max_msg_sz` for
1844 * all then-opened MQs) will yield too-many-files (Linux errno=EMFILE) once X is exceeded. A typical value
1845 * for this is 819,200 -- or up to only *ten* such MQs of size MAX_N_MSG x S_MQS_MAX_MSG_SZ opened simultaneously.
1846 * This is in practice easily exceeded. On the other hand, suppose we instead use SHM_MAX_HNDL_SZ
1847 * instead of MQS_MAX_MSG_SZ -- which is sufficient, since we'll only be sending SHM handles, not the actual
1848 * data. As of this writing it's 512; so that's 8,192/512=16 *times* the number of MQs creatable this way;
1849 * errno=EMFILE occurs not after 10 MQs now but after 160 such MQs. Much more reasonable.
1850 * Trust me (ygoldfel): the ~10-MQ limit can be quite annoying.
1851 *
1852 * Update/correction: We say there, "we'll only be sending SHM handles, not the actual data." However that
1853 * assumes that (1) any channel opened will in fact be upgraded to a struc::Channel; and (2) that struc::Channel
1854 * will use the SHM-backed serializer for its `Msg_out`s. Neither is certain at all. So that's why
1855 * the user can override our chosen default here (hence m_mq_msg_size_limit). The chosen default
1856 * does make those assumptions (and we documented this in Session_server::mq_msg_size_limit() doc header). */
1857 if constexpr(S_SHM_ENABLED)
1858 {
1859 max_msg_sz = SHM_MAX_HNDL_SZ;
1860 }
1861 else
1862 {
1863 max_msg_sz = Base::S_MQS_MAX_MSG_SZ;
1864 }
1865 }
1866 else
1867 {
1868 max_msg_sz = cfg_limit_or_zero;
1869 }
1870
1871 ++m_last_channel_mq_id;
1872
1873 const auto mq_name_func = [&](bool c2s) -> Shared_name
1874 {
1875 // Session scope.
1876 auto mq_name = build_conventional_shared_name(Persistent_mq_handle_from_cfg::S_RESOURCE_TYPE_ID,
1877 Shared_name::ct(Base::m_srv_app_ref.m_name),
1878 Base::srv_namespace(),
1879 Shared_name::ct(Base::cli_app_ptr()->m_name),
1880 Base::cli_namespace());
1881 // That was the standard stuff. Now the us-specific stuff:
1882 mq_name /= c2s ? "c2s" : "s2c";
1883 mq_name /= to_string(m_last_channel_mq_id);
1884 return mq_name;
1885 }; // mq_name_func =
1886
1887 // These ctors should log in any case.
1888
1889 const auto perms = util::shared_resource_permissions(Base::m_srv_app_ref.m_permissions_level_for_client_apps);
1890
1891 *mq_c2s = Persistent_mq_handle_from_cfg{get_logger(), mq_name_func(true), util::CREATE_ONLY,
1892 MAX_N_MSG, max_msg_sz, perms, err_code};
1893 if (*err_code)
1894 {
1895 --m_last_channel_mq_id; // Might as well.
1896 return false;
1897 }
1898 // else
1899 *mq_s2c = Persistent_mq_handle_from_cfg{get_logger(), mq_name_func(false), util::CREATE_ONLY,
1900 MAX_N_MSG, max_msg_sz, perms, err_code};
1901 if (*err_code)
1902 {
1903 --m_last_channel_mq_id; // Might as well.
1904 const auto name = mq_c2s->absolute_name();
1905 *mq_c2s = {}; // Close the first guy; won't be used.
1906 Error_code ignored; // Don't forget to remove underlying MQ we'd successfully created.
1907 Persistent_mq_handle_from_cfg::remove_persistent(get_logger(), name, &ignored);
1908 return false;
1909 }
1910 // else
1911 *mq_name_c2s = mq_c2s->absolute_name();
1912 *mq_name_s2c = mq_s2c->absolute_name();
1913 return true;
1914} // Server_session_impl::make_channel_mqs()

1958 * first-thing (before traffic if possible) so let's. */

2376 * `ok` = <it returned non-null>).

2379 * thread, before any user code runs); and one that is entirely unresponsive stops auto-pinging, so our
2380 * idle timer would hose the channel and end the wait anyway. So without a timeout the wait could be
2381 * unbounded only if the peer's pinging continued while its reply never came -- i.e., a bug over there.

2383 * basis: the timeout merely bounds the wait (making any user-facing stall finite -- e.g., our dtor and
2384 * Session_server's, which joins incomplete sessions like *this); it does not make it prompt. Hanging
2385 * for tens of seconds, *formally* speaking, may or may not break some contract, but practically speaking
2386 * it could mean, e.g., that Session_server would stall for that time -- it's informally speaking broken
2387 * behavior anyway. We're just putting a cap on it at least because why not. Even that said: reiterating:
2388 * sync_request() would likely early-return due to auto-pinging (if not due to socket error or built-in
2389 * liveness check/PEER_PROCESS_NO_LONGER_EXISTS); so in the unlikely hypothetical this shouldn't hang.
2390 * This comment is arguably too long, but just we don't want this timeout arg's
2391 * centrality to be overestimated by the reader/maintainer.

2394 * asynchrony though. */

2397 Base::S_OPEN_CHANNEL_TIMEOUT, &err_code))
2398 : (m_master_channel->send(&open_channel_req_msg, nullptr, &err_code)

2436 * invoke handler. */
2437

2440 *mdt_from_cli_or_null = std::move(mdt_from_cli);
2441 }

2443 assert(!err_code);

2446 * info_collector() must work from now on. */

2449 else // if (!ok)

2476 }); // const bool result = m_master_channel->expect_log_in_request()

2494
2495 /* (If you are comparing this to Client_session_impl::on_master_channel_error(), you might notice this is a lot
2496 * simpler (at least in the log-in phase); that is because Client_session supports multiple async_connect()s in series
2497 * (if 1 or more fail), so m_master_channel can be nullified and then again constructed. In our case
2498 * async_accept_log_in() is a private API, made public via Server_session_dtl to Session_server
2499 * only, and therefore (due to having a limited internal use case) can be only called 1x, by contract.

2502 * for instance).) */

2508 "from opposing client, and it was invalid, so the channel was destroyed by our log-in request "
2509 "handler; but coincidentally before that destruction could occur an incoming-direction "
2510 "channel error occurred. The error does not matter anymore. Ignoring.");
2511 return;
2512 }
2513 // else
2514
2515 // Might want to read our class doc header impl section regarding error handling. Then come back here.
2516
2517 if (!m_log_in_on_done_func.empty())
2518 {
2519 // We are in logging-in phase still.
2520 FLOW_LOG_WARNING("Server session [" << *this << "]: Log-in: Session master channel reported error "
2521 "[" << err_code << "] [" << err_code.message() << "]. Will go back to NULL "
2522 "state and report to user via on-accept-log-in handler.");
2523
2524 /* Channel incoming-direction error while awaiting log-in request. Might as well clean this up; though
2525 * it would be cleaned up presumably pretty soon, as Session_server will destroy *this. */
2526 m_master_channel.reset();
2527
2528 m_log_in_on_done_func(err_code);
2529 FLOW_LOG_TRACE("Handler finished.");
2530 m_log_in_on_done_func.clear();
2531 return;
2532 } // if (!m_log_in_on_done_func.empty()): We are in logged-in phase: almost-PEER state or PEER state.
2533
2534 if (!handlers_are_set())
2535 {
2536 FLOW_LOG_WARNING("Server session [" << *this << "]: Almost-PEER state: Session master channel reported error "
2537 "[" << err_code << "] [" << err_code.message() << "]. Recording it to emit once "
2538 "user advances us to PEER state by setting handlers.");
2539
2540 assert((!m_pre_init_err_code) && "struc::Channel should emit no more than one fatal error.");
2541 m_pre_init_err_code = err_code;
2542 return;
2543 }
2544 // else if (handlers_are_set()): We are in PEER state. Here the logic is similar to Client_session_impl again:
2545
2546 if ((!Base::dtor_started()) && (!Base::hosed()))
2547 {
2548 Base::hose(err_code);
2549 }
2550 /* else if (dtor_started()): Session is already being destroyed of the user's volition; don't bug them.
2551 * else if (hosed()): No need to hose if already hosed (the usual pre-condition for hose()). */
2552

2554 {
2555 m_graceful_finisher->on_master_channel_hosed();
2556 }
2557} // Server_session_impl::on_master_channel_error()
