35/**
36 * A `capnp::MessageBuilder` used by Heap_fixed_builder: similar to a `capnp::MallocMessageBuilder` (albeit with
37 * somewhat different accounting/knobs) and with framing/header space around the allocated segment(s).
38 *
39 * It can also be used as a #Capnp_msg_builder_interface (`capnp::MessageBuilder`) independently of the rest
40 * of ipc::transport or even ::ipc, although that was not the impetus for its development originally.
41 *
42 * ### Move-ctible and move-assignable? ###
43 * As of capnp-1.0.0 at the latest, but sometime after capnp-0.10, the super-class #Capnp_msg_builder_interface
44 * a/k/a/ `capnp::MessageBuilder` -- which is not a pure interface but includes some impl -- is no longer
45 * move-ctible or move-assignable. Therefore we aren't either.
46 *
47 * (Historically: When it was movable, we were too, but we still advised that the super-class size is such that
48 * using its move facilities instead of e.g. `unique_ptr` wrapping might have been a bit slow.)
49 *
50 * ### Rationale ###
51 * Why we'd use a `MallocMessageBuilder`-like approach is explained within Heap_fixed_builder doc header.
52 * So why not just use that actual class? Answer: We send the resulting serialization segments over IPC pipes
53 * (Blob_sender, Native_handle_sender), and in some cases struc::Channel needs to surround the serialization
54 * with a bit of metadata. `MallocMessageBuilder` will, for each segment, allocate X bytes -- and then potentially
55 * fill all of them. The only way for struc::Channel to work with this is to allocate another buffer of
56 * X + (frame size) bytes and then copy the X bytes into it -- losing the adherence to the zero-copy-when-possible
57 * paradigm. Hence this class which will use `flow::util::Basic_blob` machinery to maintain the frame space.
58 *
59 * Note that in order to make use of the added feature (frame space) one should *not* access the serialization result
60 * via the usual `MessageBuilder::getSegmentsForOutput()`. That still works, and that method is essential in
61 * the impl of this class; but it returns only the actual serialization segments (each one's start and size,
62 * not including for example the allocated-but-unused data probably at the tail of the allocated buffer).
63 * Technically it would indeed be correct/safe to simply write frame prefix data by subtracting `frame_prefix_sz`
64 * from the segment's start pointer and writing there. However that is error-prone and inconvenient. Call
65 * emit_segment_blobs() instead: it will return the `flow::util::Basic_blob`s which will have set `start()` and `size()`
66 * appropriately (see emit_segment_blobs() doc header).
67 */

76 /**
77 * Constructs the message-builder, with the policy to allocate the segments in a particular way.
78 * See the doc headers for invidiuals args for details.
79 *
80 * For a given segment, emit_segment_blobs() shall emit it in the form of a sequence
81 * of `Basic_blob` pointers, 1-1 with the segments, where for a given `Basic_blob B` that capnp-serialization segment
82 * itself is in range [`B.begin()`, `B.end()`) (indices within internal buffer [`B.start()`, `B.start() + B.size()`));
83 * and the header if any lives in area [`B.begin() - B.start()`, `B.begin()`).
84 *
85 * Also/instead `getSegmentsForOutput()` can be used to obtain the same (well, very-related) information. The form
86 * is somewhat different; as only memory area descriptions are returned; are in `word`s instead of bytes; and
87 * any header location/size would have to be calculated by the caller. E.g., no equivalent of `B.start()` is
88 * communicated, so the caller would have to have memorized it.
89 *
90 * @param seg_and_frame_sz_cap
91 * Say `allocateSegment(M)` is being called; we shall now select the size N of the buffer to allocate;
92 * though if `M * sizeof(word)` exceeds this size, then N shall be ignored in favor of the `M`-derived size.
93 * N shall be chosen based on `grow_seg_sz_else_constant` and `segment_sz_init_pre_growth` as well as
94 * the value(s) chosen in preceding `allocateSegment()` calls if any; and then it shall be capped at
95 * `seg_and_frame_sz_cap`. Note that the buffer being described shall hold both the segment being requested;
96 * and header space just ahead of it (if so configured).
97 * @param frame_prefix_sz1
98 * For the first allocateSegment(): The allocated buffer shall have `.start() ==` this value. Hence
99 * the reserved header area for seg 1 is of this size and is immediately followed by the segment itself.
100 * Can be zero. Must be a multiple of `sizeof(capnp::word)`.
101 * @param frame_prefix_sz_cont
102 * Same as `frame_prefix_sz1` but applied to each subsequent allocateSegment() if any.
103 * @param grow_seg_sz_else_constant
104 * `true` means mimic capnp's `GROW_HEURISTICALLY` (preferred seg sizes grow ~exponentially) but capping
105 * preferred seg-size (including header if any) to `seg_and_frame_sz_cap` and starting at
106 * `segment_sz_init_pre_growth` (plus header if any).
107 * `false` means mimic `FIXED_SIZE` with preferred seg-size (including header if any) equal to
108 * `seg_and_frame_sz_cap`. (In the latter case `segment_sz_init_pre_growth` is ignored.)
109 * Note: "Preferred" here communicates the capnp mechanics described in the doc header for
110 * arg `seg_and_frame_sz_cap` (where if `M` is large enough, it overrides our calculated "preferred" seg-size).
111 * @param segment_sz_init_pre_growth
112 * See above. Relevant only if `grow_seg_sz_else_constant == true`, this is chosen
113 * as the size of the segment (not counting header if any) for the first allocateSegment().
114 * (Due to capnp mechanics, `allocateSegment()` 1 is always called with arg equal to ~0; hence seg 1's
115 * size, unlike the others', is simply known ahead of time.) If `grow_seg_sz_else_constant == false`, that
116 * seg 1 size (sans header) is instead chosen as `seg_and_frame_sz_cap - frame_prefix_sz1`.
117 * If it can be estimated, reasonably tightly, to be large enough for the entire message, then
118 * this can lead to significant perf wins: fewer zero-filling cycles spent and the entire message
119 * being in 1 segment.
120 * @param stats
121 * Optional pointer to the cumulative stats to update. If not null, pointee must outlive `*this`.
122 */
123 explicit Heap_fixed_builder_capnp_message_builder
124 (size_t seg_and_frame_sz_cap, size_t frame_prefix_sz1, size_t frame_prefix_sz_cont,
125 bool grow_seg_sz_else_constant,
126 size_t segment_sz_init_pre_growth = sizeof(::capnp::word) * ::capnp::SUGGESTED_FIRST_SEGMENT_WORDS,
127 stat::Serializer_stats::Snd* stats = nullptr);

134 ~Heap_fixed_builder_capnp_message_builder() override;

138 /**
139 * Returns pointers to `Basic_blob`s which are the serialization segments at this time. They are as follows:
140 * - Each `Basic_blob` holds a serialization segment, in order. There shall be at least 1.
141 * - For each `Basic_blob B` (see ctor):
142 * - `B.start() == frame_prefix_sz`.
143 * - [`B.begin()`, `B.end()`) is the serialization segment. Recall that `B.begin()` starts at position
144 * `B.start()`, while `B.end()` is at position `B.start() + B.size()`.
145 * - See ctor doc header for how `frame_prefix_sz` is determined.
146 *
147 * This method can be invoked more than once; however the emitted result is meaningless once any mutation occurs
148 * subsequently.
149 *
150 * @warning For a given emitted blob `B`: You'll note it is mutable. However, behavior is undefined if you
151 * modify anything about it or it-described memory area except the contents of the header memory area
152 * [`B.begin() - B.start()`, `B.begin()`). Hence, things you are disallowed to do include (but may not
153 * be limited to): modifying any other `B`-owned memory area (anything in
154 * [`B.begin()`, `B.begin() - B.start() + B.capacity()`); modifying any metadata of `B`
155 * itself (no `B.resize()` or derivatives thereof; no `B.make_zero()` or derivatives thereof).
156 *
157 * It is mutable expressly for the purpose of potentially modifying the header area -- that is it!
158 *
159 * ### Rationale ###
160 * This API is, on reflection, a bit funky. And, really, one could get by with just `getSegmentsForOutput()`
161 * (and memorizing the header policy, as passed to our ctor). It evolved this way, and to be fair it's nice
162 * to emit information that's stored anyway, namely `flow::util::Basic_blob::start()` being the header size (et al).
163 * On the other hand it's somewhat odd to emit mutable `Basic_blob`s but only formally allow modifying the header
164 * areas they describe. It's not language-enforced which is... well... it's okay but not ideal.
165 *
166 * At this time I (ygoldfel) think it's fine in the context of how Flow-IPC uses it but would've been probably
167 * too funky if its main or only use-case were direct calls by the user. So maintainers should keep that in mind.
168 *
169 * @param target_blob_ptrs
170 * It is appended-to. Recall these are mere pointers (into `*this`-managed heap memory, with each pointee
171 * `Blob_sans_log_context` describing a header + segment memory area).
172 */
173 void emit_segment_blobs(Segment_ptrs* target_blob_ptrs);
174
175 /**
176 * Returns what `target_blob_ptrs.size()` would return after calling `emit_segment_blobs(&target_blob_ptrs)` (with
177 * an empty `target_blob_ptrs` going-in), right now. In other words it is the number of times capnp has invoked
178 * allocateSegment().
179 *
180 * @return See above.
181 */
182 size_t n_segments() const;
183
184 /**
185 * Implements `MessageBuilder` API. Invoked by capnp, as the user mutates via `Builder`s. Do not invoke directly.
186 *
187 * @note The strange capitalization (that goes against standard Flow-IPC style) is because we are implementing
188 * a capnp API.
189 *
190 * For details as to how this will behave in context of `*this` see Heap_fixed_builder_capnp_message_builder()
191 * ctor doc header.
192 *
193 * @param min_sz_words
194 * See `MessageBuilder` API.
195 * The allocated segment will allow for a serialization of at most
196 * `min(min_sz_words * sizeof(word), segment_sz)` bytes, where `segment_sz` is determined according to the
197 * algorithm described in our ctor doc header (plus adjusted to the ceiling-nearest word).
198 * @return See `MessageBuilder` API.
199 * The ptr and size of the area for capnp to serialize-to.
200 * (As noted in ctor doc header: `frame_prefix_sz` bytes will precede this area; the value is determined as
201 * described in our ctor doc header.)
202 */
203 kj::ArrayPtr<::capnp::word> allocateSegment(unsigned int min_sz_words) override;

214 /**
215 * See ctor; this is set to `true` if we will grow #m_segment_sz; otherwise keep it constant.
216 * In addition we set it to `false` upon reaching #m_seg_and_frame_sz_cap -- no need to keep increasing it, once
217 * we have hit the limit.
218 */
219 bool m_grow_seg_sz_else_constant;

221 /**
222 * Preferred, capped size of the next segment returned (and allocated) by allocateSegment() -- if indeed
223 * `allocateSegment()` will again be called; a word-multiple. `allocateSegment()` will be called at least 1x;
224 * so before that happens the initial value is either `segment_sz_init_pre_growth` (if
225 * #m_grow_seg_sz_else_constant is `true`) or `m_seg_and_frame_sz_cap - m_frame_prefix_sz1` (otherwise).
226 * In the latter case it is also the final/forever value. Also, once the cap is reached in the former case,
227 * `m_segment_sz` similarly stops changing (in fact we then modify `m_grow_seg_sz_else_constant = false`).
228 *
229 * Explanation of "capped": `m_segment_sz` shall not exceed `m_seg_and_frame_sz_cap - F`, where `F` is one
230 * of `m_frame_prefix_sz1` (before first allocateSegment() call) or `m_frame_prefix_sz_cont` (after it).
231 * This is guaranteed initially in ctor; and subsequently in allocateSegment(), when (and if) it grows
232 * `m_segment_sz` therein.
233 *
234 * Explanation of "preferred": When selecting the actual segment size to return from allocateSegment(),
235 * the value chosen will be the *higher* of `min_sz` words or `m_segment_sz` (with cap already applied); where
236 * `min_sz` is the value passed by capnp into allocateSegment(). In other words `m_segment_sz` is
237 * what we'd "prefer" to size the segment, but if user demands more space, we will follow that demand.
238 * That typically occurs when the user tries to create a big leaf (list/blob/string).
239 *
240 * Explanation of how `m_segment_sz` grows while `m_grow_seg_sz_else_constant == true`:
241 * Vaguely speaking, it follows exponential growth with each allocateSegment() call. More specifically,
242 * we rip off `MallocMessageBuilder`: `m_segment_sz` is increased by the size of the segment actually chosen.
243 * So for example, supposing allocateSegment() is called always with `min_sz == 1` (not realistic... but it models
244 * well-enough needing more space for a small leaf, once the existing segment is too full, so the "preferred" size
245 * is never exceeded by `min_sz`), and the init size is 8Ki, with a huge cap and no headers for simplicity:
246 * `m_segment_sz` shall start at 8Ki; seg 1 shall be 8Ki, `m_segment_sz` shall increase to 16Ki; seg 2 shall be
247 * 16Ki, `m_segment_sz` shall increase to 32Ki (and so on, until no `allocateSegment()` is forthcoming, and
248 * the last-computed `m_segment_sz` is left unused). (Now, if a too-big `min_sz` is involved, then `m_segment_sz`
249 * wouldn't double but grow even more than that, that time. The header and cap if any affect the growth a
250 * bit... etc. The general pattern is roughly as shown though.)
251 */
252 size_t m_segment_sz;
253
254 /**
255 * Before emit_segment_blobs() emits a given segment, stores each segment allocated as requested by capnp via
256 * allocateSegment() `virtual` API, with `.size()` equal to `.capacity()` and >= `min_sz` words (arg to that method);
257 * immediately after emit_segment_blobs() each `.size()` has been adjusted to indicate the # of bytes actually used in
258 * that segment in the final serialization (so far). emit_segment_blobs() yields an equally sized list of pointers
259 * to the `.size()`-adjusted per-segment `Basic_blob`s.
260 *
261 * Note that `*this` itself does not rely on each guy's `.size()` which depends on whether allocateSegment() of that
262 * guy, or emit_segment_blobs() of that guy, was last called; it is used purely as an out-arg (of sorts) via
263 * emit_segment_blobs(). In *that* case `.size()` is set (by emit_segment_blobs()) to the above specific meaning.
264 *
265 * How does `*this` know the size of the serialization then? Answer: via `getSegmentsForOutput()`. How does
266 * capnp know the size of the allocated buffer then? Answer: we give it to it via allocateSegment() return value,
267 * and it memorizes it in `MessageBuilder` super-object somewhere (and `getSegmentsForOutput()` grabs that).
268 */
269 std::vector<flow::util::Blob_sans_log_context> m_serialization_segments_plus_frame_space;
270
271 /// Cumulative stats target, or null if no stats recording is configured.
272 stat::Serializer_stats::Snd* const m_stats;
273
274 /**
275 * Running tally: sum of `seg_sz` chosen for each allocateSegment() call. Sampled

277 * It is only used for stats, so it's untouched if null #m_stats.
278 */
279 uint64_t m_alloc_sz;
