39/**
40 * Type that adapts a given PEER-state sync_io::Native_handle_receiver or sync_io::Blob_receiver *core*
41 * into the async-I/O-pattern Native_handle_receiver or Blob_receiver. State-mutating logic of the latter is forwarded
42 * to a `*this`; while trivial `const` (in PEER state) things like `.receive_blob_max_size()` are forwarded directly to
43 * the core `sync_io::X`.
44 *
45 * Flow-IPC uses a `*this` to implement each of transport::Native_socket_stream (in-direction) and
46 * transport::Blob_stream_mq_receiver; but this is a public API, as one can implement any custom
47 * transport::Blob_receiver (et al) in terms of the corresponding custom sync_io::Blob_receiver (et al) impl.
48 * It would be an advanced task but nevertheless fully supported/intended.
49 *
50 * @internal
51 * @see transport::Native_socket_stream_impl uses this for 99% of its incoming-direction
52 * (PEER-state by definition) logic.
53 * @see transport::Blob_stream_mq_receiver_impl uses this for 99% of its logic.
54 * @endinternal
55 *
56 * @see Async_adapter_sender for the opposite-direction thing. E.g., transport::Native_socket_stream_impl
57 * uses that for 99% of its outgoing-direction logic.
58 *
59 * @internal
60 * Impl
61 * ----
62 * ### Threads and thread nomenclature; locking ###
63 * Thread U, thread W... locking... just see those sections in transport::Native_socket_stream_impl class doc header.
64 * We adopt that nomenclature and logic. However, as we are concerned with only one direction (op-type),
65 * we only deal with code in either thread U or W concerned with that. The other-direction code -- if applicable
66 * (e.g., applicable for `Native_socket_stream` which deals with both over 1 socket connection; N/A
67 * for `Blob_stream_mq_*` which uses separate objects entirely) -- simply co-exists in the same thread W and "thread"
68 * U. (If `Native_socket_stream` wanted to, it could even parallelize stuff in thread W by using separate worker
69 * threads Ws and Wr. As of this writing it does not, but it could -- nothing in `*this` would change.)
70 *
71 * Note, again, that we have our own `m_mutex`. If there is an opposing-direction counterpart Async_adapter_sender,
72 * then it has its own `m_mutex`; hence things can proceed concurrently.
73 *
74 * ### Impl design ###
75 * This is almost entirely subsumed by our `sync_io` core, Async_adapter_receiver::Core, an instance of
76 * sync_io::Native_handle_receiver or sync_io::Blob_receiver. It has a receive op-type (possibly among others), so we
77 * invoke its `"sync_io::*_receiver::start_receive_blob_ops()"` during our initialization. After that:
78 *
79 * For idle_timer_run(), we can again just forward it to `m_sync_io`. There's no completion
80 * handler either, unlike with `.async_end_sending()`, so it's even simpler -- just straight forwarding to
81 * the `sync_io` core.
82 *
83 * For async_receive_native_handle() (and its degenerate version async_receive_blob()) the `*_receiver` concept
84 * we implement has an extra feature on top of sync_io::Native_handle_receiver (and degenerate version,
85 * sync_io::Blob_receiver): when 1 async_receive_native_handle() is in progress asynchronously, it is allowed
86 * to invoke it again an arbitrary number of times, and they are to be served in the order they were called.
87 * Therefore:
88 * - We maintain a "deficit" queue of these requests. The currently-served request is stored in
89 * `User_request m_user_request`. The queued-up subsequent ones are stored in queue with that
90 * same element type, `m_pending_user_requests_q`.
91 * - When the ongoing (single) `m_sync_io.async_receive_*()` does complete -- which occurs in thread W --
92 * we emit the result (`Error_code`, `sz`) to the `User_request`-stored `m_on_done_func` (the completion
93 * handler from the user). Then we pop `m_pending_user_requests_q` (unless empty -- no further "deficit")
94 * into `m_user_request` and service *that* one via `m_sync_io.async_receive_*()`. Rinse/repeat.
95 *
96 * If the destructor is invoked before `m_user_request` can get serviced, then in the dtor
97 * we execute `on_done_func(E)`, where E is operation-aborted. Once that's done the dtor can finish.
98 *
99 * Update: The above remains quite accurate; but we added batch-receiving APIs to the `*_receiver` concepts and
100 * therefore impls and therefore `*this`. These are async_receive_native_handle_batch() and
101 * async_receive_blob_batch(). All that changes is that a given user-request can now be either a single-message
102 * receive request, or a batch receive request. So #User_request can encode one or the other; so it is a
103 * `variant` to that effect. Hence when processing a #User_request in #m_user_request (or the queue, if we need
104 * to look in there directly), we check which one it is and then invoke the appropriate #Core API
105 * (e.g., `async_receive_blob()` versus `async_receive_blob_batch()`).
106 * @endinternal
107 *
108 * @tparam Core_t
109 * The `sync_io::X` type being adapted into async-I/O-pattern `X`.
110 */

267 /**
268 * Analogous to User_request_one but for a batch async-receive request as opposed to single-message request.
269 *
270 * Essentially this stores args to async_receive_native_handle_batch() or async_receive_blob_batch().
271 * We store them in queue via #User_req_ptr.
272 *
273 * ### Impl design ###
274 * Conceptually this is straightforward; much like User_request_one this basically stores the args from the user
275 * to `async_receive_*_batch()`. The impl, however, is somewhat less straightforward than in User_request_one.
276 * Specifically, consider these bits of info:
277 * - (Easy) Whether it was `async_receive_native_handle_batch()` or `async_receive_blob_batch()`; determines
278 * which of the two eponymous methods of #m_sync_io we shall forward-to (call).
279 * - (Harder) The `batch` argument.
280 *
281 * The latter is really the crux (the former we save using the same mechanism opportunistically; but in and of itself
282 * it could have just been a `bool` flag or similar; e.g., User_request_one encodes it in `bool(m_target_hndl_ptr)`.)
283 * The problem with `batch` is its type is template-parameterized `Batch*`, where
284 * `Batch` is a `typename` template parameter. We have to save this info in #m_user_request and/or
285 * #m_pending_user_requests_q, and when forwarding-to `m_sync_io.async_receive_*_batch()` we must
286 * give it a value of type `Batch*`. So it's a standard type-erasure
287 * situation. As such we use a typical technique in solving it: use `Function<T>`,
288 * where `T` is a signature spec that is parameterized on `Batch`. That is we
289 * have #m_sync_rcv_batch_func which captures `batch` of whichever type (code generated at compile-time) and invokes
290 * the appropriate method, either the `_native_handle_` one or the `_blob_` one, thus compactly (code-wise anyway)
291 * encoding both the would-be flag (bullet point 1) and the `batch` value of the proper type (bullet point 2).
292 *
293 * The code is fairly slick, but there's a cost which is to some extent performance; `Function<>` does the
294 * type erasure leg-work for us, but it is *somewhat* heavyweight, and calling it involves some `virtual` overhead.
295 * The RAM weight doesn't much matter (overall it is small, and we move these around via `User_req_ptr`),
296 * and we consider the `virtual` overhead to be acceptable. (If profiling shows otherwise, we can revisit.)
297 */

391 /**
392 * Invoked via active-event API, handles the async completion
393 * of `m_sync_io.async_receive_*()` operation. Can be invoked from thread W only, and #m_mutex must be
394 * locked. #m_user_request must not be null.
395 *
396 * This method iteratively, synchronously leverages #m_sync_io to read as many in-messages available
397 * in the transport as possible, until: the request deficit is met (either by reading enough messages
398 * to satisfy #m_user_request and #m_pending_user_requests_q; or by encountering pipe-hosing error)
399 * or would-block. In the latter case another async-wait is initiated by this method synchronously.
400 *
401 * The first action, before those potential further reads, is to process_msg_or_error() the just-received
402 * (or pipe-hosing would-be) single-message or batch (sized 1+ messages). Then for each further
403 * in-message/in-batch process_msg_or_error() is again invoked.
404 *
405 * For each request satisfied, a separate user handler is posted onto thread W to execute in order.
406 *

460 */

484template<typename Core_t>
485Async_adapter_receiver<Core_t>::Async_adapter_receiver(flow::log::Logger* logger_ptr,
486 util::String_view log_pfx,
487 flow::async::Single_thread_task_loop* worker,
488 Core* sync_io) :
489 flow::log::Log_context(logger_ptr, Log_component::S_TRANSPORT),
490 m_log_pfx(log_pfx),

492 m_sync_io(*sync_io)
493{
494 using util::sync_io::Asio_waitable_native_handle;
495 using util::sync_io::Task_ptr;
496 using flow::util::Lock_guard;
497
498 // We've just entered PEER state, so set up the receive-ops.
499
500 /* Hook up the m_sync_io=>*this interaction. m_sync_io will use these callbacks to ask
501 * us to ->async_wait() on `Asio_waitable_native_handle`s for it.
502 *
503 * The *this=>m_sync_io interaction shall be our APIs, like async_receive_native_handle(),
504 * simply invoking the same API in m_sync_io (m_sync_io.async_receive_native_handle() for that example). */
505
506 /* (.start_receive_native_handle_ops() would do the same thing, if it exists. If it exists, that's because it has
507 * both to satisfy two concepts -- for when the user uses the sync_io::X directly -- but we don't care about that;
508 * we know they are the same in this case; so just use the one we know exists for any X.) */
509#ifndef NDEBUG
510 const bool ok =
511#endif
512 m_sync_io.start_receive_blob_ops([this](Asio_waitable_native_handle* hndl_of_interest,
513 bool ev_of_interest_snd_else_rcv,
514 Task_ptr&& on_active_ev_func)

637template<typename Core_t>
638void Async_adapter_receiver<Core_t>::async_receive_impl(Native_handle* target_hndl_or_null,
639 const util::Blob_mutable& target_meta_blob,
640 flow::async::Task_asio_err_sz&& on_done_func)
641{
642 using flow::util::Lock_guard;
643 using std::in_place_type;
644 using std::get;
645
646 // We are in thread U (or thread W in a completion handler, but not concurrently).
647
648 /* This is essentially the only place in *this where we're more than a mere forwarder of the core m_sync_io
649 * sync_io::*_receiver (which is synchronous) into an async *_receiver. I.e., in this
650 * case we add a feature on top; namely more than 1 async_receive_*() can be pending for us, whereas only
651 * 1 async_receive_*() is allowed in the sync_io one. We call this is a *deficit*, meaning there are more
652 * user requests than available messages (there's only ever 1 message "available" -- once the
653 * m_sync_io.async_receive_*() succeeds -- and only momentarily, as it's immediately fed to the
654 * completion handler of our async_receive_*() that precipitated it.
655 *
656 * Thus, if there is no deficit, and async_receive_*() comes in, we trigger m_sync_io.async_receive_*()
657 * and save the associated request info (basically our 3 args above) into m_user_request.
658 * Once it succeeds we feed the result to the completion handler saved among those 3 args and nullify
659 * m_user_request. Meanwhile, if another one comes in while there's already a deficit (m_user_request
660 * is not null), we queue it in m_pending_user_requests_q. Lastly, having nullified
661 * m_user_request as noted a couple sentences ago, we pop the _q (if not empty) into m_user_request
662 * and trigger another m_sync_io.async_receive_*(), continuing the chain this way until _q is empty
663 * and m_user_request is null (at which point there's no deficit and not reason to
664 * m_sync_io.async_receive_*()).
665 *
666 * Oh, also, if an m_sync_io.async_receive_*() yields a socket-hosing error, then it is fed to the entire
667 * deficit queue's handlers; as in any case any subsequent attempted m_sync_io.async_receive_*() would fail.
668 *
669 * Note that there can be a deficit (pending user requests) but no surplus (pending messages): we don't
670 * make unnecessary m_sync_io.async_receive_*() calls and thus don't need to save surplus messages.
671 * If we did, we'd need to copy any such surplus message (into user buffer) once this->async_receive_*() does
672 * come in. This is discussed and rationalized elsewhere, but for convenience, recap: The reason is, basically,
673 * the send-side concept is obligated to internally copy-and-queue messages on encountering would-block.
674 * Since the system will thus not lose messages (if the receiver side is being slow in popping them from the pipe),
675 * the complexity of queuing stuff -- and the perf loss due to copying -- is kept to one side. */
676
677 FLOW_LOG_TRACE(m_log_pfx << ": Incoming user async-receive request for "
678 "possible native handle and meta-blob (located @ [" << target_meta_blob.data() << "] of "
679 "max size [" << target_meta_blob.size() << "]). In worker now? = [" << m_worker.in_thread() << "].");
680
681 auto new_user_request = boost::movelib::make_unique<User_request>(in_place_type<User_request_one>);
682 auto& req1 = get<User_request_one>(*new_user_request);
683
684 req1.m_target_hndl_ptr = target_hndl_or_null;
685 req1.m_target_meta_blob = target_meta_blob;
686 req1.m_on_done_func = std::move(on_done_func);
687
688 /* We will be accessing m_user_request, m_pending_user_requests_q, and possibly m_sync_io receive-ops
689 * sub-API -- while ctor's ev-wait function's async_wait() handler will be accessing them too from thread W -- so: */
690
691 Lock_guard<decltype(m_mutex)> lock{m_mutex};
692
693 if (m_user_request)
694 {
695 m_pending_user_requests_q.emplace(std::move(new_user_request));
696 FLOW_LOG_TRACE("At least 1 async-receive request is already in progress. "
697 "After registering the new async-receive request: Head slot is non-empty; and "
698 "subsequently-pending deficit queue has size [" << m_pending_user_requests_q.size() << "]. "
699 "Will sync-IO-receive to handle this request once it reaches the front of that queue.");
700 return; // Lock_guard<decltype(m_mutex)> lock{m_mutex}: unlocks here.
701 }
702 // else if (!m_user_request):
703
704 FLOW_LOG_TRACE("No async-receive request is currently in progress. Starting sync-IO-receive chain to service the "
705 "new request and any further-queued requests that might appear in the meantime.");
706 m_user_request = std::move(new_user_request);
707 // new_user_request is now hosed.
708
709 /* If receive completes synchronously (there are data pending on the "wire"), these will reflect that.
710 * If not then sync_err_code will indicate would-block. */
711 Error_code sync_err_code;
712 size_t sync_sz;
713
714 sync_receive(req1, &sync_err_code, &sync_sz);
715
716 if (sync_err_code == error::Code::S_SYNC_IO_WOULD_BLOCK)
717 {
718 // Async-wait started by m_sync_io. It logged plenty. We live to fight another day.
719 return; // Lock_guard<decltype(m_mutex)> lock{m_mutex}: unlocks here.
720 }
721 // else:
722
723 /* Process the message and nullify m_user_request. (It would also promote any m_pending_user_requests_q head
724 * to m_user_request; but in our case that is not possible. We are still in the user async-receive API!) */
725 process_msg_or_error(sync_err_code, sync_sz);
726
727 FLOW_LOG_TRACE("Message was immediately available; synchronously returned to user; handler posted onto "
728 "async worker thread. Done until next request.");
729
730 // Lock_guard<decltype(m_mutex)> lock{m_mutex}: unlocks here.
731} // Async_adapter_receiver::async_receive_impl()

899template<typename Core_t>
900void Async_adapter_receiver<Core_t>::process_msg_or_error(const Error_code& err_code, size_t sz_if_applicable)
901{
902 using std::get_if;
903 using std::get;
904
905 // We are in thread U or W. m_mutex is locked.
906
907 assert(err_code != boost::asio::error::operation_aborted);
908 assert((err_code != error::Code::S_SYNC_IO_WOULD_BLOCK) && "By our contract.");
909
910 FLOW_LOG_TRACE(m_log_pfx << ": Earlier async-wait => event active => rcv-mutex lock => "
911 "on-active-event-func => sync_io module => on-rcv-done handler => here. "
912 "Or else: rcv-mutex lock => sync_io module => no async-wait needed => here.");
913
914 /* As noted in our doc header, we have roughly two items on the agenda.
915 *
916 * 1, we need to invoke m_user_request->m_on_done_func, passing it the results (which is/are our arg(s)).
917 *
918 * 2, we need to update our m_* structures, such as popping stuff off m_pending_user_requests_q
919 * and starting the next m_sync_io.async_receive_*() if any -- and so on.
920 *
921 * Oh and 2b: if err_code is truthy, we need to invoke all the pending handlers (if any) and nullify/empty
922 * all of that.
923 *
924 * The question is what thread to do that stuff in. There are a couple of approaches, at least, but the following
925 * seems the least latency-ridden:
926 * - For 1 and 2b, we must post() the handler(s) onto thread W.
927 * - If we are in thread U: It is plainly required, as we promised to invoke completion handlers
928 * from unspecified thread that isn't U.
929 * - If we are in thread W: To avoid recursive mayhem if they choose to call some other API
930 * inside an on_done_func(), we queue it onto thread W by itself. (But if it's 2b in addition to 1,
931 * then we can bundle them all together into one thread-W task; no need for the churn of post()ing
932 * each one individually.)
933 * - However for 2, there's no need to post() anything. The mutex is already locked, so even if we're in thread
934 * U (m_sync_io.async_receive_*() succeeded synchronously, and this->async_receive[_*]_impl()
935 * therefore invoked us synchronously, from thread U) we are within
936 * our rights to just finish the job here synchronously as well. In fact, that's great! It means
937 * data were waiting to be read right away, and we did everything we could synchronously in the
938 * original async_receive_*() call, post()ing onto thread W only 1 above -- the completion handler invoking (which
939 * we must do by contract). Yay! By the way, if that's the case (we are in thread U), then 2b doesn't apply;
940 * only 1 does. (The situation where there are items in m_pending_user_requests_q means we wouldn't have
941 * started an actual m_sync_io.async_receive_*() in the first place, as one was already in progress. So
942 * it couldn't have magically completed synchronously -- not having begun and all.) */
943
944 // Okay, so first deal with m_*, here and now as discussed. In so doing prepare the stuff to call in thread W.
945
946 assert(m_user_request);
947 User_req_ptr ex_user_request{std::move(m_user_request)};
948 assert(!m_user_request);
949
950 decltype(m_pending_user_requests_q) ex_pending_user_requests_q_or_none;
951 if (err_code)
952 {
953 FLOW_LOG_TRACE("Error emitted by sync-IO => all [" << m_pending_user_requests_q.size() << "] pending "
954 "handlers (may well be none) will be invoked with error in addition to the head handler.");
955
956 ex_pending_user_requests_q_or_none = std::move(m_pending_user_requests_q);
957 assert(m_pending_user_requests_q.empty());
958 }
959 else if (!m_pending_user_requests_q.empty()) // && (!err_code)
960 {
961 FLOW_LOG_TRACE("Success emitted by sync-IO => lead handler will be invoked; next pending request will "
962 "be serviced by sync-IO; pending request count has become (after popping from queue into lead "
963 "slot): [" << (m_pending_user_requests_q.size() - 1) << "].\n");
964
965 m_user_request = std::move(m_pending_user_requests_q.front());
966 // m_pending_user_requests_q.front() is now null; we're gonna pop that null ptr presently.
967 m_pending_user_requests_q.pop();
968 }
969 else // if (_q.empty() && (!err_code))
970 {
971 FLOW_LOG_TRACE("Success emitted by sync-IO => lead handler will be invoked; no pending requests queued up.\n");
972 }
973
974 // Second: Post the completion handlers as discussed.
975 m_worker.post([this, err_code, sz_if_applicable,
976 /* Have to upgrade to shared_ptr<>s due to capturing requiring copyability (even though copying is not
977 * actually invoked by us). unique_ptr and queue<unique_ptr> = not copyable. */
978 ex_user_request = boost::shared_ptr<User_request>{std::move(ex_user_request)},
979 ex_pending_user_requests_q_or_none
980 = boost::make_shared<decltype(ex_pending_user_requests_q_or_none)>
981 (std::move(ex_pending_user_requests_q_or_none))]()
982 mutable
983 {
984 // We are in thread W. Nothing is locked.
985
986 assert(ex_user_request);
987 FLOW_LOG_TRACE(m_log_pfx << ": Invoking head handler.");
988
989 auto& req = *ex_user_request;
990 if (auto req1 = get_if<User_request_one>(&req))
991 {
992 req1->m_on_done_func(err_code, sz_if_applicable);
993 }
994 else
995 {
996 assert((sz_if_applicable == 0) && "sz_if_applicable is not applicable to batches; should have been passed as 0.");
997 get<User_request_batch>(req).m_on_done_func(err_code);
998 }
999
1000 FLOW_LOG_TRACE("Handler completed.");
1001 if (!ex_pending_user_requests_q_or_none->empty())
1002 {
1003 assert(err_code);
1004 assert(sz_if_applicable == 0);
1005
1006 FLOW_LOG_TRACE(m_log_pfx << ": Invoking [" << ex_pending_user_requests_q_or_none->size() << "] "
1007 "pending handlers in one shot (due to error).");
1008 while (!ex_pending_user_requests_q_or_none->empty())
1009 {
1010 auto& req = *(ex_pending_user_requests_q_or_none->front());
1011 if (auto req1 = get_if<User_request_one>(&req))
1012 {
1013 req1->m_on_done_func(err_code, 0);
1014 }
1015 else

1049 * to process the ready message/batch first-thing. But let's say that's taken care of. After that: we can't just

1075 }

1085 * Success => m_user_request is null, m_pending_user_requests_q is null. No req to service. Loop end.
1086 * Success => m_user_request is NOT null, m_pending_user_requests_q is ???. Req needs service.

1090 } // while (m_user_request && (sync_err_code != error::Code::S_SYNC_IO_WOULD_BLOCK));
