35/**
36 * This is to vanilla Session_server what shm::classic::Server_session is to vanilla #Server_session: it is
37 * the session-server type that starts SHM-enabled sessions with SHM-classic provider
38 * (ipc::shm::classic::Pool_arena). Its API is identical to that of Session_server, except that it
39 * emits #Server_session_obj that are shm::classic::Server_session and not vanilla #Server_session. In addition:
40 *
41 * @note Lifetime recommendations and requirements -- the destruction order among `*this`, its sessions and their
42 * channels; how long the app_shm() arenas live -- are in the same-named section of session::Session_server
43 * doc header.
44 *
45 * ### Pool size and RAM use (optional configuration) ###
46 * Each session's SHM pool, and each Client_app's, is sized per pool_size_limit_mi(); see its doc header. The pools
47 * are *sparse*: a pool takes RAM only page by page, as it is used. If you would rather a given pool take all its
48 * RAM up-front, call `commit()` on the arena -- a shm::classic::Pool_arena (our #Arena) -- obtained via
49 * the appropriate session's session_shm() or app_shm() (or our app_shm()). See the RAM-use section of the
50 * shm::classic::Pool_arena doc header.
51 *
52 * In many cases none of this should need attention. Power users of potentially larger amounts of RAM per
53 * SHM-arena may need to look into this topic (again -- see `Pool_arena` in that case).
54 *
55 * @internal
56 *
57 * ### Implementation ###
58 * See similar section of session::Session_server. It explains why we sub-class Session_server_impl and even
59 * how that's used for this SHM-classic scenario. To reiterate:
60 *
61 * We use 2 of 2 available customization points of `private` super-class Session_server_impl. We:
62 * - pass-up a `per_app_setup_func()` that, given the new session's desired Client_app, creates-if-needed the per-app
63 * SHM-arena and keeps handle open as well as available via `this->app_shm(app)`; and
64 * - parameterize Session_server_impl on shm::classic::Server_session which, during log-in, creates
65 * the per-session SHM-arena and keeps handle open; and saves a shared handle to the former (via a `private`
66 * `app_shm_ptr(app)`).
67 *
68 * shm::classic::Server_session doc header delves deeply into the entire impl strategy for setting up these arenas.
69 * If you read/grok that, then the present class's impl should be straightforward to follow.
70 *
71 * @endinternal
72 *
73 * @tparam MQ_TYPE_OR_NONE
74 * See vanilla #Session_server.
75 * @tparam TRANSMIT_NATIVE_HANDLES
76 * See vanilla #Session_server.
77 * @tparam Mdt_payload
78 * See vanilla #Session_server.
79 */

147 /**
148 * Destructor: contract is identical to session::Session_server dtor.
149 *
150 * @internal
151 * In particular this dtor shall perform
152 * shm::classic::Pool_arena::remove_persistent() on *each* pool returnable by app_shm()
153 * (the per-Client_app pools). Reminder: like all kernel-persistent `remove_persistent()` methods this will not
154 * necessarily free the RAM held on behalf of a given pool; any currently opened `Pool_arena`s -- presumably
155 * ones still (possibly) held by counterpart `shm::classic::Client_session_impl`s -- will continue to function
156 * fine.
157 *
158 * ### Rationale for aforementioned `remove_persistent()` op ###
159 * Why do it? Answer: Naturally this should be freed sometime; otherwise the RAM will leak, even though the
160 * session pertaining to the per-session pool is gone.
161 *
162 * Why not do it earlier? Answer: It would be nice to do it super-early... like, say, just after creating the
163 * pool during the async portion of async_accept(), namely in init_app_shm_as_needed().
164 * The only reason *not* to do it is if a client handle (`Pool_arena`) to the pool has not yet had a chance to
165 * get opened by the name deleted via `remove_persistent()`. But this can occur an indefinite number of times
166 * after init_app_shm_as_needed() creates the pool: the whole idea is the pool is shared between different
167 * sessions with the same (by value equality) Client_app, across different client processes in fact.
168 *
169 * Hence we postpone it until this dtor: no further session can open; and any still-alive `Server_session` keeps
170 * its own handle to the pool, which survives the removal until every handle is gone.
171 *
172 * Why not do it later? Answer: Session-server is done-for, if we are being invoked; the counterpart
173 * `Client_session`s could not possibly hope to open the pool now, even if they somehow wanted to do so. So why wait?
174 *
175 * ### What if this dtor never runs? ###
176 * In any program that exits without aborting abruptly, it *will* run -- either proactively during user program
177 * de-init code or implicitly when it exits.
178 *
179 * It however may not run due to abrupt termination (a crash). In that case the `app_shm()` pools will indeed
180 * leak, in that this dtor won't execute, so the `remove_persistent()`s will not occur in that fashion.
181 * The shm::classic::Session_server has a contingency for this, which we don't describe here, wherein it has
182 * *cleanup points* at which it cleans up anything thus leaked during previous invocations of the same
183 * Server_app.
184 *
185 * ### What about the per-session pools? ###
186 * The above talks only of the app_shm()-returned pools; what about shm::classic::Session_impl::session_shm()?
187 * Shouldn't we clean it up here? Answer: Well, we could, but since it's a per-session thing,
188 * each shm::classic::Server_session_impl takes care of its own `session_shm()`.
189 */
190 ~Session_server();

194 /**
195 * The pool-size value, in mebibytes, which will be used to size the pool in subsequent
196 * `async_accept()`s. One can change this via the mutator overload.
197 *
198 * A large default value is used if one does not invoke that mutator.
199 *
200 * ### How it works ###
201 * Each time async_accept() succeeds, a SHM pool sized according to this value is created for the session;
202 * and potentially another SHM pool sized similarly is created for the Client_app (if and only if a session against
203 * the same Client_app has not yet been opened by `*this`). The *key point*: only a tiny amount of RAM
204 * is actually taken at that time for each pool; the pool size only counts against vaddr space which is
205 * essentially unlimited. Physical RAM is reserved only upon actual allocation for objects subsequently, with
206 * kernel-page-sized quantization. Therefore a huge value can be used here with no RAM-use penalty; on the
207 * other hand if this value is too small, and an allocation makes a pool run out of vaddr space, then
208 * a `bad_alloc` exception will be thrown, and you're pretty much kaput. So you should use a huge value!
209 * And indeed the default is quite large.
210 *
211 * There is, however, at least in Linux, a system-wide limit on the RAM taken by SHM-pools in this fashion (it
212 * is admin-configurable; it might default to half your physical RAM for example). Should a pool page be first
213 * touched while that limit is reached, there is no error to report: the process is killed (SIGBUS). If you
214 * would rather learn of such a shortage early and civilly, call `commit()` on the arena(s) in question; see the
215 * RAM-use section of the shm::classic::Pool_arena doc header. For power users of RAM-hungrier SHM-classic
216 * arenas, there may be a real trade-off there: commit() but have to be stingy with max pool size, or accept
217 * that total-SHM-used limit is potentially harshly enforced.
218 *
219 * For most use cases none of this will be a problem. If a fixed per-pool size is a problem, consider
220 * ipc::session::shm::arena_lend::jemalloc::Session_server (SHM-jemalloc) which is a multi-pool
221 * system that adjusts dynamically without your having to worry about it at all.
222 *
223 * @return See above.
224 */
225 size_t pool_size_limit_mi() const;

313 /**
314 * Returns pointer to the per-`app` SHM-arena, whose lifetime extends until `*this`, and every
315 * shm::classic::Server_session of `app` from `*this`, are destroyed;
316 * or null if that arena has not yet been successfully created (which is attempted during the log-in of the
317 * first client of `app` to reach `*this` via async_accept()). Alternatively you may use
318 * shm::classic::Session_mv::app_shm() off any session object filled-out by `*this` async_accept(), as long as its
319 * Server_session_mv::client_app() equals `app` (by App::m_name equality).
320 *
321 * If non-null is returned, then the same pointer value shall be returned for all subsequent calls
322 * with the same (by App::m_name equality) `app`. The non-null pointers returned for any 2 calls, where `app`
323 * is different (by App::m_name equality) among them, shall always differ.
324 *
325 * See shm::classic::Session_mv::Arena doc header for useful instructions on working with #Arena,
326 * `lend_object()`, and `borrow_object()`.
327 *
328 * ### Perf ###
329 * Given the choice between Session_mv::app_shm() and the present method, the latter is somewhat
330 * slower; internally it involves a mutex-protected map lookup, while the former simply returns a cached
331 * pointer as of this writing.
332 *
333 * Generally it is also fine, and fastest, for the user to save any non-null value returned by either `app_shm()`;
334 * the pointer returned shall always be the same after all.
335 *
336 * @internal
337 * ### Thread safety ###
338 * For internal use, namely by shm::classic::Server_session_impl::async_accept_log_in() at least,
339 * it is guaranteed that app_shm() may be called on the same `*this` concurrently to itself
340 * and init_app_shm_as_needed(). Formally speaking this isn't publicly documented, as I (ygoldfel) didn't want
341 * to get users into any bad habit, but internally it does have this property -- as it is required.
342 * @endinternal
343 *
344 * @param app
345 * Client_app whose segregated SHM-arena to return, if a session for a client of the app has been
346 * opened prior to this call.
347 * @return Pointer to `*this`-held per-`app` SHM-arena, if it has been created; null otherwise.
348 * See above.
349 */
350 Arena* app_shm(const Client_app& app);

429 /**
430 * Implementation of our `per_app_setup_func()` customization point used in the ctor impl:
431 * invoked from an unspecified thread, asynchronously, by async_accept() during log-in, it
432 * synchronously makes it so that `this->app_shm(app)` returns non-null from now on.
433 * What it returns is a pointer (always the same one) to the segregated SHM-arena pertaining to
434 * all sessions (current and future) pertaining to `app` in `*this` server. On success returns
435 * falsy #Error_code. Success means either `app_shm(app)` was already going to return non-null,
436 * or it wasn't, but we successfully made it so it will.
437 *
438 * On failure to set this up:
439 * - Truthy #Error_code reason for failure is returned.
440 * - `app_shm(app)` shall continue to return null.
441 * - `*this` is not hosed.
442 *
443 * This method is thread-safe to invoke on the same `*this` w/r/t concurrent calls to itself
444 * and app_shm().
445 *
446 * @param app
447 * The Client_app for which to set up, if needed, the per-app SHM-arena.
448 * @return See above; falsy if and only if `app_shm(app)` shall return non-null from now on.
449 */
450 Error_code init_app_shm_as_needed(const Client_app& app);
451
452 /**
453 * Identical to app_shm() but returns a shared handle: For shm::classic::Server_session_impl (via
454 * Session_server_dtl), so that its per-app arena lives as long as the session does, even if `*this` does not.
455 * Same thread safety as app_shm().
456 *
457 * @param app
458 * See app_shm().
459 * @return See app_shm().
460 */

484 * Set of names of every SHM-pool created w/r/t #m_app_shm_by_name. Each time an #Arena is added to
485 * #m_app_shm_by_name, its pool name is added to #m_shm_pool_names. A certain cleanup function, run

493 * instead; and the `vector` lives as long as it needs to to be scanned by the cleanup task.
494 */

516 m_pool_size_limit_mi(2048), // This is configurable; this is the default. @todo Maybe have constant for this magic #.
517 m_srv_app_ref(Impl::m_srv_app_ref),
518 // (m_srv_namespace: initialized just below.)
519 m_shm_pool_names(boost::make_shared<std::vector<Shared_name>>())
520{
521 using transport::sync_io::Native_socket_stream;
522
523 // Before we continue: handle that Impl ctor may have thrown (then we don't get here) or emitted error via *err_code.
524 if (err_code && *err_code)
525 {
526 return;
527 }
528 // else Impl ctor executed fine.
529
530 {
531 auto empty_session_public
532 = Server_session_dtl<Server_session_obj>::ct_base(nullptr, m_srv_app_ref, Native_socket_stream{});
533 m_srv_namespace = Server_session_dtl<Server_session_obj>{ empty_session_public }.base().srv_namespace();
534 }
535
536 /* This is a (as of this writing -- the) *cleanup point* for any pools previously created on behalf of this
537 * Server_app by previous active processes before us. The session_shm() pools are gracefully cleaned up
538 * in shm::classic::Server_session_impl dtor; while app_shm() pools are gracefully cleaned up by
539 * our own dtor, as set up a few lines down via Impl::sub_class_set_deinit_func(). This cleanup point is a
540 * best-effort attempt to clean up anything that was skipped due to one or more such destructors never getting
541 * to run (due to crash, abort, etc.).
542 *
543 * We simply delete everything with the Shared_name prefix used when setting up app_shm() pools
544 * (see init_app_shm_as_needed()) and session_shm() pools
545 * (see shm::classic::Server_session_impl::async_accept_log_in()). The prefix is everything up-to
546 * (not including) the PID (m_srv_namespace). Any pool found under it is old: per the documented lifetime
547 * requirements (session::Session_server doc header), no `Session` or channel from an earlier `Session_server` for
548 * this Server_app may still exist when we are constructed -- in any process, this one included (a
549 * `Session_server` following another in the same process has the same m_srv_namespace, our PID). So we remove
550 * them all, regardless of any liveness consideration.
551 *
552 * A note on stats: Stats support for this cleanup point has been considered and deliberately omitted;
553 * see similar note in session::Session_server_impl ctor (and a longer discussion in
554 * shm::arena_lend::jemalloc::Session_server::cleanup()). */
555 util::remove_each_persistent_with_name_prefix<Arena>
556 (get_logger(), build_conventional_shared_name_prefix(Shared_name::S_RESOURCE_TYPE_ID_SHM,
557 Shared_name::ct(m_srv_app_ref.m_name)));
558
559 // Set up the final-cleanup step via impl customization point. For explanation see init_app_shm_as_needed().
560 Impl::sub_class_set_deinit_func([this,
561 /* ^-- Careful: We only use this->get_logger() which is explicitly okay.
562 * *this is destroyed w/r/t shm::classic::Session_server_impl by the
563 * time this lambda is executed; so we do not use that.
564 *
565 * Copy-capture the shared_ptr (see rationale in m_shm_pool_names doc header).
566 * Basically this ensures the vector<Shared_name> lives, even after
567 * *this->m_shm_pool_names has been destroyed via our own dtor, before
568 * Session_server_impl dtor runs. */
569 shm_pool_names = m_shm_pool_names]()
570 {
571 // We are in thread U (in dtor chain).
572 Error_code sink; // We do not care about any error. This is our best effort; it'll WARN on (unlikely) error.
573 for (const auto& shm_pool_name : *shm_pool_names)
574 {
575 Arena::remove_persistent(this->get_logger(), shm_pool_name, &sink);
576 }
577 });
578} // Session_server::Session_server()

603TEMPLATE_CLSC_SESSION_SRV
604Error_code CLASS_CLSC_SESSION_SRV::init_app_shm_as_needed(const Client_app& app)
605{
606 using boost::make_shared;
607
608 /* We are in some unspecified thread; actually *a* Session_server_impl thread Ws (a Server_session_impl thread W).
609 * Gotta lock at least to protect from concurrent calls to ourselves on behalf of other async_accept()s. */
610
611 Lock_guard app_shm_lock{m_app_shm_mutex};
612
613 auto& app_shm = m_app_shm_by_name[app.m_name]; // Find; insert if needed.
614 if (app_shm)
615 {
616 // Cool; already exists, as app.m_name seen already (and successfully set-up, as seen below) by us.
617 return {};
618 }
619 // else
620
621 // Below should INFO-log already; let's not litter logs explaining why this is being created; context = sufficient.
622
623 auto shm_pool_name = build_conventional_shared_name(Shared_name::S_RESOURCE_TYPE_ID_SHM,
624 Shared_name::ct(m_srv_app_ref.m_name),
625 m_srv_namespace,
626 Shared_name::ct(app.m_name))
627 / SHM_SUBTYPE_PREFIX
628 / Shared_name::S_1ST_OR_ONLY;
629 /* As of this writing we only maintain the one --^-- per-Client_app SHM pool. (Of course the user can do whatever
630 * they want and make their own -- but within the ipc::session-maintained ones, this is it.)
631 * So use 1ST_OR_ONLY per its doc header; and as that suggests, if we want to maintain more in the future
632 * we can switch to a uint or atomic<uint> data member instead. */
633
634 Error_code err_code;
635 app_shm = make_shared<Arena>(get_logger(), shm_pool_name, util::CREATE_ONLY,
636 size_t(1024 * 1024) * pool_size_limit_mi(),
637 util::shared_resource_permissions(m_srv_app_ref.m_permissions_level_for_client_apps),
638 &err_code);
639 if (err_code)
640 {
641 /* Careful: a failed Pool_arena ctor still yields a (non-null) object in a failed state. Do not leave that in
642 * the map: app_shm(app) must keep returning null, and the next attempt for `app` must try again. So leave null
643 * in the map; meh. .erase()ing it from there is just pedantic at best. (The [] lookup above will do the right
644 * thing next time.) */
645 app_shm.reset();
646 }
647 // Now either err_code is truthy/app_shm is null; or vice versa.
648
649 /* Cool! Let's return (and continue the log-in async op!). ...Not so fast. Almost.
650 * Please now see the doc header for our dtor, where we promise -- on dtor invocation -- to remove all
651 * app_shm() pools. It explains why we do that, and what actual effect it has. The below is *how*
652 * we accomplish it: We have just added a pool to what app_shm() can return; and thus (and this is the only way it
653 * would need cleaning up) we now ensure that *in* the dtor, the pool removal shall execute.
654 *
655 * The technique we use, and the rationale for it, is very similar to that in
656 * shm::classic::Server_session_impl::async_accept_log_in() (in that case for the per-session pool). Nevertheless
657 * here is a full explanation tailored to our specific case.
658 *
659 * It's tempting to Just Do It in the dtor, but there are caveats. Vaguely, all we want to do is something like,
660 * right in the dtor, for all m_shm_pool_names N (each computed into shm_pool_name above):
661 * Arena::remove_persistent(N);
662 * This would work 99.999% of the time just fine... except for the annoying possibility that the user
663 * destroys *this while an async_accept() is outstanding still.
664 *
665 * In my mind this leaves two possible approaches.
666 *
667 * One is to operate in the various threads started by *this (really by super-class Session_server_impl).
668 * However this is entropy-laden and seems to involve a race against the potentially ongoing async_accept()s.
669 * Like, suppose we do that -- and some app_shm() returnee is not yet set-up -- so we don't clean its name;
670 * then while the super-class dtors are running (including the highly significant Session_server_impl dtor)
671 * the async-accept happens to advance a bit and adds an app_shm() returnee, before that dtor has a chance to
672 * stop/join the relevant thread(s). Now we've leaked the RAM. (Granted, the anti-crash contingency
673 * in shm::classic::Session_server should catch it when the next
674 * instance -- if any -- of this Server_app starts up. Relying on that outside a crash scenario is a misuse
675 * of that contingency logic; there is nothing un-graceful about our dtor being invoked before an async-accept
676 * completes.)
677 *
678 * The other approach is more orderly: We know the dtor chain is being invoked, so when ~Session_server_impl()
679 * does execute (very soon), it will indeed stop all relevant threads -- in whatever state they happen to be
680 * at the time. At *that* stage there is no more race involved: there's just what that super-class dtor executes
681 * (in caller thread U) after stopping all internal threads. Now the state is straightforward: Either
682 * the various internal threads worked together to add shm_pool_name-pool into app_shm() returnees --
683 * then shm_pool_name should be removed -- or it did not (then there is nothing to remove).
684 *
685 * So that is what we do. Session_server_impl supplies a `protected` API for any custom de-init code which
686 * we invoke elsewhere and which scans *m_shm_pool_names. We simply use that by adding to the latter;
687 * and we only do that right here, the one place we add a new app_shm() returnee. */
688 if (app_shm)
689 {
690 m_shm_pool_names->emplace_back(std::move(shm_pool_name));
691 }
692
693 return err_code;
694 // Lock_guard app_shm_lock{m_app_shm_mutex}: unlocks here.
695} // Session_server::init_app_shm_as_needed()
