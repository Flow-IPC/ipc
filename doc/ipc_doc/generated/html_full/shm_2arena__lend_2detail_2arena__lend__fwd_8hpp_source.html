123/**
124 * (Roughly) the borrower-side counterpart of Owner_obj_disposer_and_mdt, this returns a borrower-side
125 * handle `shared_ptr<T>` whose disposer is the borrower-side counterpart to Owner_obj_disposer_and_mdt.
126 *
127 * Also: keeps `shm_session_to_keep_alive` alive until disposer executes (~analogously to Owner_obj_disposer_and_mdt
128 * doing so w/r/t the constructing `Shm_arena`). (Rationale is similar; the machinery tracking borrowed objects
129 * via session so-and-so is maintained, at least partially, in so-and-so borrower-side `Shm_session`.)
130 *
131 * This is a key helper for `Shm_session::borrow_object()`, returning the very disposer-furnished handle
132 * that method must return. The caller must first obtain the borrower-side vaddr of the in-SHM object (`addr`)
133 * as well as certain values (all originating in the opposing process; see Owner_obj_disposer_and_mdt)
134 * required for the disposer we furnish to act properly. Namely that disposer will simply decrement a single
135 * in-SHM atomic ref-count via Lend_tracker_pool; the saved args like `use_ct_idx` are needed to identify the
136 * location of this atomic.
137 *
138 * @note One might assume that the `--` is in the disposer, so the `++` is inside this free function. Not so:
139 * The `++` occurred in fact in the *opposing* process's earlier `Shm_session::lend_object()` call which,
140 * incidentally, returned the blob that encoded the values that *our* side just decoded again into
141 * the args to our function here. Otherwise the object might be destroyed before lending process was
142 * able to transmit said blob to us and/or before this function call. The key point:
143 * Calling `blob_here = sess_here->lend_object(p_here)` in P1 is part of 3-part procedure; part 2 is
144 * IPC-transmitting `blob_here` to P2 as `blob_there`; part 3 is
145 * `auto p_there = sess_there->borrow_object(blob_there)` which calls us upon decoding `blob_there`.
146 *
147 * @tparam T
148 * In-SHM object type.
149 * @tparam Shm_session
150 * See above.
151 * @param addr
152 * Borrower-side vaddr of the in-SHM object.
153 * @param lend_tracker_pool_id
154 * See Owner_obj_disposer_and_mdt data member.
155 * @param use_ct_idx
156 * See Owner_obj_disposer_and_mdt data member.
157 * @param owner_id
158 * Globally unique ID (as of this writing simply PID) of *owner* process of `addr`-pointed in-SHM object.
159 * That process is the one that did `arena->construct<T>(...)` originally.
160 * As of this writing that isn't transmitted on a per-borrowed-handle basis but rather available
161 * in the `Shm_session` at large (we know the PID of the guy with whom we converse).
162 * @param collection_id
163 * Given `owner_id`, unique arena-ID of the *owner* `Shm_arena` (e.g., jemalloc::Ipc_arena).
164 * (Together `owner_id` + `collection_id`, sometimes known as #Uniq_collection_id, is a globally unique
165 * identifier of that `Shm_arena`.)
166 * @param shm_session_to_keep_alive
167 * As it says! The arg itself is consumed (nullified).
168 * As of this writing we merely keep it alive; we don't modify it (nor even need to query it).
169 * @return Borrower-side ref-counted handle to `addr`-pointed in-SHM object whose disposer shall participate in
170 * the *cross-process garbage collection* of that object.
171 */
172template<typename T, typename Shm_session>
173Obj_handle<T> construct_with_borrower_obj_disposer(T* addr,
174 pool_id_t lend_tracker_pool_id,
175 use_ct_idx_t use_ct_idx,
176 owner_id_t owner_id,
177 collection_id_t collection_id,
178 std::shared_ptr<const Shm_session>&& shm_session_to_keep_alive);

226/**
227 * Assembles and outputs the current stats tracked by the obj-DB module (as anchored by Thread_lcl_obj_db_admin).
228 * This is the main stat-consumption API for the obj-DB module, as required by the `Shm_arena`
229 * (e.g., jemalloc::Ipc_arena) stat-consumption API's impl. Since the obj-DB module (again, as anchored
230 * by Thread_lcl_obj_db_admin and further aided by Thread_lcl_obj_db_client) is a highly central engine
231 * to the functioning of an arena-lend-type SHM-provider (e.g., SHM-jemalloc), many important stats are
232 * tracked within the compiled-here `Stat_set`, namely Sharded_stats.
233 *
234 * @see Sharded_stats doc header (and relevant stat-member doc headers) to get a bird's-eye-view of
235 * the kinds of stats included here (and many details if desired).
236 *
237 * ### How to use this ###
238 * `Shm_arena` should store a Sharded_stats, initially default-cted.
239 * Suppose the `Shm_arena` user requests Sharded_stats (or some other grouping of stat-sets which
240 * includes the items in Sharded_stats; but let's assume not for exposition simplicity; it does not
241 * change the point). Call this free function, targeting the stored stat-set; then return it, probably, by value
242 * (`stats_assign()`).
243 *
244 * ### Impl notes for context ###
245 * Briefly: the obj-DB module is essentially thread-locally implemented (hence the names like
246 * Sharded_stats). As such, for stat-keeping performance, stats are TL-sharded (per
247 * design explained in `flow::util::stat` doc header). This free function:
248 * - locks the various sources of Sharded_stats shards, comprising as of this writing
249 * Thread_lcl_obj_db_admin, Thread_lcl_obj_db_client, and Finalized_shards;
250 * - aggregates all those shards via `flow::util::stat::stats_aggregate_shards()` onto
251 * `*target_stats`.
252 * - Reminder: The current values in `*target_stats` do -- in some specific cases -- matter; it is an out-arg, yes,
253 * but also partially an in-arg. The "some specific cases" are: any `HI_WMARK` stat-members.
254 * See `flow::util::stat::stats_aggregate_shards()` doc header for all the deets on that.
255 * Bottom line: caller shall remember to keep `*target_stats` for next time this free function
256 * is called for the same arena.
257 *
258 * @param shm_arena
259 * See, e.g., Thread_lcl_obj_db_admin::constructing_obj().
260 * @param target_stats
261 * See above.
262 */
263template<typename Shm_arena>
264void sharded_stats(const Shm_arena& shm_arena, Sharded_stats* target_stats);

298/**
299 * (Helper for sharded_stats_impl() and `Thread_lcl_obj_db_admin/client`) Process-global, immortal recursive mutex
300 * serializing obj-DB stat-consume/reset against `_admin` + `_client` thread exit. It eliminates The Gap during
301 * thread exit: the brief window in which a going-away `_admin` or `_client` has been removed
302 * from its `Thread_local_state_registry` but has not yet deposited its stat-shard into either Finalized_shards
303 * or a new drain-mode `_admin` in a replacement thread.
304 *
305 * ### Premise: The Gap ###
306 * This is best observed in ~Thread_lcl_obj_db_client() and ~Thread_lcl_obj_db_admin() dtors; the former is
307 * simpler as an intro to the topic. In either place, you'll see that each (per-arena) Sharded_stats still
308 * in the `TLODB...` does not simply disappear but rather needs to be saved elsewhere: either into Finalized_shards
309 * (`_client` case; `_admin` case where no degraded-mode `_admin` thread/object is required) or into
310 * a new `_admin` (`_admin` degraded-mode case). Before The Gap such a shard would be -- upon locking certain
311 * other central mutexes -- included in the sharded_stats_impl() range-walk through all extant TL-shards:
312 * After The Gap: same (either in an `_admin` or in Finalized_shards). *During* The Gap, however, the
313 * extant-TL-state registry (`Thread_local_state_registry<_admin>` or `Thread_local_state_registry<_client>`) has
314 * ejected the `_admin` or `_client` but either has not yet reinserted the replacement `_admin` therein, or has done
315 * so without the shard being transferred-over into that `_admin` yet; nor have we yet inserted it into
316 * Finalized_shards.
317 *
318 * Bad things about these stat-ops happening during The Gap:
319 * - sharded_stats() will yield incomplete `*target_stats` (each ACC and GAUGE may be missing 1+ addends),
320 * and HI_WMARKs might miss peaks.
321 * - If sharded_stats() was called merely to update HI_WMARKs (e.g.: Ipc_arena::sample_hi_wmarks()), then
322 * it may update them incorrectly.
323 * - sharded_stats_reset() may fail to reset ACCs, and HI_WMARKs might be wrong subsequently.
324 * - Explaining to the user what they must avoid in order to avoid such things is not that easy.
325 * User thread exit may be not too bad for them to control; but the degraded-mode (drain) `_admin` threads
326 * are an internal thing, so even having to mention it is a communication ordeal.
327 * - As of this writing SHM-jemalloc ipc::session machinery auto-tickles Ipc_arena::sample_hi_wmarks() regularly;
328 * if that were to happen during a relevant thread-exit (thus a Gap), then there can be HWM-correctness trouble.
329 *
330 * All in all, it is not the crime of the century, but it is not good. Better is to lack any such caveats.
331 *
332 * ### Basic solution ###
333 * Setting aside the mechanism we're about to describe, consider what ops are involved and when.
334 * - sharded_stats_impl() (stat-consume/reset/HWM-tickle). Bracketed by 3 mutex-locks: `_admin`-registry's,
335 * `_client`-registry's, Finalized_shards singleton's.
336 * - `_admin` thread-exit: `_admin`-registry lock (by `Thread_local_state_registry` code), removal from registry,
337 * unlock, `~_admin()` dtor. Inside there: either:
338 * - Finalized_shards lock, insert of Sharded_stats into it, unlock; exit dtor; or:
339 * - spawn drain-thread, `_admin`-registry lock, construct `_admin` and add to registry, unlock;
340 * shove the Sharded_stats into the new `_admin` in drain-thread; once signalled that is complete: exit dtor.
341 * - `_client` thread-exit: `_client`-registry lock (by `Thread_local_state_registry` code), removal from registry,
342 * unlock, `~_client()` dtor. Inside there:
343 * - Finalized_shards lock, insert of Sharded_stats into it, unlock; exit dtor.
344 *
345 * The "whens": sharded_stats_impl() -- anytime; the `_admin` teardown -- 1x per thread at most; `_client` ditto.
346 * (The latter two can *both* happen in a given thread; but actually fully in-series within that thread; there is
347 * no interleaving.)
348 *
349 * @note The "1x per thread" is per `Shm_arena` type. So generally speaking there can be more, if SHM-jemalloc were
350 * to be used simultaneously with another SHM-arena-lend provider.
351 *
352 * The trouble occurs with bullet 2 and bullet 3: after registry-unlock, before "exit dtor." (`~admin()` in the
353 * spawns-new-thread case happens to exit dtor specifically just after new-thread-`_admin` code has signalled
354 * it has moved all its state from dying-`_admin`. The other 2 "exit dtor" eventualities are simpler. In all cases,
355 * though, "exit dtor" is when The Gap has definitely passed.) So the challenge is to avoid bullet 1
356 * between the 1 `_admin`'s (A) registry-lock-at-thread-teardown and (B) its "exit dtor" point; and ditto
357 * for the 1 `_client`.
358 *
359 * So: Use a global mutex (that is us) around each bullet above. The existing locks "almost" do it but not actually:
360 * in bullets 2 and 3 they are active only at the start, but then by the time each dtor starts -- no longer so.
361 * As long as this mutex is locked before existing first lock and unlocked after existing last unlock: solved.
362 *
363 * ### Refinement: `at_thread_exit()` ###
364 * It would be easy-peasy, if each bullet above were a linear sequence of statements. That is not the case
365 * however: `Thread_local_state_registry` controls bullet 2 and bullet 3 and launches each dtor after
366 * lock/remove/unlock. (`sharded_stats_impl()` is all us though, so no problem there.) Locking this mutex
367 * in `Thread_local_state_registry<T>` cleanup would require some kind of hook API in addition to the existing
368 * straightforward execution of `~T()`. A possibility -- but we went another way. It is haxory, but we have
369 * a bespoke challenge which we resolve with a bespoke technique instead of modifying the TL-utility with an
370 * awkward hook.
371 *
372 * `Thread_local_state_registry` ultimately is explicitly executing all cleanup (our dtors in this case) off
373 * `boost::thread_specific_ptr` per-thread cleanup phase. `boost::this_thread::at_thread_exit(F)` specifically
374 * allows one to execute `F()` (and *all* such registered functions) during thread shutdown (yes, with or without
375 * a backing `boost::thread`; `std::thread` => still yes) and specifically before the TL-ptr cleanups.
376 *
377 * Call our mutex here `M`. Stipulate that when an `_admin` or `_client` is (per-thread) created, it registers
378 * the following to execute `at_thread_exit()`: `M.lock()`. Stipulate further that:
379 * - sharded_stats_impl() is bracketed with lock/unlock of `M`.
380 * - `~admin()` and `~client()` each does `M.unlock()` at "exit dtor" point.
381 *
382 * So the order is:
383 * - Sometime during thread-proper: Register `at_thread_exit(F)` (see above).
384 * - Thread exit begins.
385 * - `boost::thread` machinery executes the at-thread-exit `F()`s. So, in some arbitrary order:
386 * - 1 `M.lock()` for `_admin<Arena_type1>`.
387 * - 1 `M.lock()` for `_client<Arena_type1>`.
388 * - 1 `M.lock()` for `_admin<Arena_type2>`.
389 * - 1 `M.lock()` for `_client<Arena_type2>`.
390 * - ...
391 * - Boost machinery executes the `tsp` cleanups. For us: in some arbitrary order:
392 * - For `_admin<Arena_type1>`:
393 * - `Thread_local_state_registry<Arena_type1>` locks registry, removes, unlocks. Gap begins here.
394 * - It calls `~_admin()`. Gap continues, until the shards are saved where they must be during this dtor.
395 * - Last thing `~_admin()` does: `M.unlock()`. Gap ends here.
396 * - For `_client<Arena_type1>`: Ditto.
397 * - For `_admin<Arena_type2>`: Ditto.
398 * - For `_client<Arena_type2>`: Ditto.
399 * - ...
400 *
401 * The refinement we were building up to is this: By using `at_thread_exit()` we caused all the `M.lock()`s
402 * to happen first and the `M.unlock()`s second. So we aren't cleanly bracketing each Gap. That is OK:
403 * - Ensure `M` is recursive. Now `M` will be held from the first `M.lock()` to the last `M.unlock()`.
404 * - The Gaps, in a sense, merge into one MegaGap; and there's no deadlock at the 2nd `M.lock()`.
405 * - Ensure `M` spans *all* `Shm_arena` types, as opposed to maintaining an `M<Shm_arena>` per `Shm_arena`.
406 * Otherwise there can be trouble given the arbitrary order as noted above; 2 threads exiting concurrently may
407 * do M1-lock/M2-lock and M2-lock/M1-lock (standard deadlock).
408 *
409 * @warning Both of these, normally, would be red flags in my (ygoldfel) opinion/experience. First, recursive mutexes
410 * tend to paper-over some design corner-cutting. Second, every single other mechanism as of this writing
411 * segregates one SHM-provider from another -- but not here. Yet we do both things here, and both things
412 * have one original sin causing them: The `.lock()` is decoupled from `.unlock()`. Given that we've
413 * decided not to invade `Thread_local_state_registry` cleanup code/add hooks to it, instead using
414 * a more-global Boost hook, we have no choice but to deal with it accordingly.
415 *
416 * Okay: so given the above, if sharded_stats_impl() happens to execute during all this, it will either complete
417 * before the first `M.lock()` above or pause and actually-execute after the last `M.unlock()` above.
418 *
419 * @return Reference to the singleton mutex. The pointee will outlive all C++ code.
420 */
421flow::util::Mutex_recursive& thread_end_gap_mutex();
