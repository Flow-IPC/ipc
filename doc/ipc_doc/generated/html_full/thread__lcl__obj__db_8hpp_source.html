67/**
68 * (Internal-use) `Thread_lcl_obj_db_admin<A>::this_thread_obj_db()` is the current thread's module that tracks
69 * extant `a.construct<>()`ed (in this thread) objects in SHM, where `a` represents all SHM-arenas of type `A`.
70 *
71 * ### What to use ###
72 * In particular, in the case of SHM-jemalloc (the first example of an arena-lending SHM-provider):
73 * - `A` (#Shm_arena) is jemalloc::Ipc_arena.
74 * - `Thread_lcl_obj_db_admin<A>` represents all SHM-jemalloc arenas' stuff.
75 * - This would be fully independent of `Thread_lcl_obj_db_admin<B>`, where B is some other arena-type that isn't
76 * SHM-jemalloc's jemalloc::Ipc_arena.
77 * - In current thread U, `Thread_lcl_obj_db_admin<A>::this_thread_obj_db()` is the compendium of
78 * objects constructed via *all* `a.construct<T>(...)` calls (hence each object is a *first-class* or *high-level*
79 * or *outer* object, unlike, say, additional buffers allocated by the T ctor via STL-allocator-magic; these
80 * are *not* tracked by `Thread_lcl_obj_db_*`). Here `a` are *all* instances of `A` (of jemalloc::Ipc_arena)
81 * to have had `.construct<T>(...)` called on them from thread U.
82 * - So if in thread X no jemalloc::Ipc_arena has SHM-constructed a first-class object, then there has been
83 * no need to call this_thread_obj_db() from thread X, and no this_thread_obj_db() exists for that thread.
84 * The user hasn't, essentially, done SHM-jemalloc work from that thread.
85 * - While `auto x = this_thread_obj_db()` (for a given thread U) tracks *all* (type `A`) arenas to have
86 * SHM-constructed things, within `x` (conceptually speaking) what is relevant to arena `a1` is fully
87 * independent of what is relevant to arena `a2`. In terms of one's mental model, it's best to take a particular
88 * arena type (jemalloc::Ipc_arena in this case) and particular arena of that type as a given... then contemplate
89 * various (non-`static`) APIs.
90 *
91 * A particular `Shm_arena` is specified to our non-`static` APIs as either a `Shm_arena*` or a `collection_id_t`.
92 * Reminder: a collection ID, as pertains to SHM-arena owned by *this* process, uniquely identifies a `Shm_arena`.
93 * (A given `collection_id_t` value might equal some that of some other arena owned by/allocating in another process;
94 * but in the context of Thread_lcl_obj_db_admin -- as it is an *admin*, meaning owner-oriented, module -- we
95 * are always talking of the current process.)
96 *
97 * ### How to use it ###
98 * A `*this` supports the key ipc::shm::arena_lend (arena-lend-oriented) operations (a/k/a *events*):
99 * - `p = a.construct<T>(...)`: #Shm_arena `a` allocating `sizeof(T)` bytes in SHM managed by `a`; and executing
100 * ctor `T(...)`. (If `T` is STL-compliant container, with SHM-aware allocator set, then the ctor may further
101 * allocate in-SHM; e.g. `vector` would allocate a buffer. However such allocs do not, also, `.construct()`.
102 * Unlike `p` the resulting buffers are *inner*; `p` is *outer*`.) `p` is of this writing a `shared_ptr<T>`.
103 * - Invoke constructing_obj().
104 * - `session.lend_object<T>(p)`: Intent to transmit an encoding of handle `p` to opposing process, where an
105 * identically-behaving handle shall be created via `p2 = session2.borrow_object(encoding_of_p)`.
106 * - Invoke lending_obj() (in sending process, on `session.lend_object()`).
107 * - Do so *only* from the `p`-constructing thread U! If in another thread you must use Thread_lcl_obj_db_client
108 * instead.
109 * - The disposal of a given handle `p` (as of this writing, when the `shared_ptr` group of `p` reaches
110 * ref-count zero): I.e., in this process, the constructed (in original process) or borrowed (in opposing
111 * process) handle to the object is to be disposed. Once *all* processes' extant such handles have been disposed,
112 * the owner-process shall (internally to Thread_lcl_obj_db_admin machinery) garbage-collect the datum.
113 * - Invoke disposing_obj().
114 * - Again: do so only from `p`-constructing thread U! Else use Thread_lcl_obj_db_client.
115 *
116 * @see Thread_lcl_obj_db_client which handles each event (lend, dispose) such that that event pertains to an object
117 * originally constructed in another thread versus where said event occurred.
118 *
119 * You'll note mention of "garbage-collect[ing] the datum," once all handles for a particular `*this`-assigned
120 * thread's object have been disposed of (disposing_obj() or Thread_lcl_obj_db_client::disposing_obj()).
121 * Formally this is the purview of `*this`, but our user's help is required to make this work. By design we do *not*
122 * start background-threads to handle such things; we rely (much like most memory-allocator libs) on
123 * *piggy-backing*. That is:
124 * - you *must* frequently-enough invoke a so-called *piggy-scan*. In short this will dispose of any
125 * no-handles-remaining `*this`-thread-constructed objects. (For each guy this also invokes its destructor,
126 * so any *inner* buffers allocated throughout its lifetime would also get deallocated. Not our purview though.)
127 * - Invoke `static` this_thread_piggy_scan()...
128 * - ...but when is "frequently-enough"? Formally: not for us to say. In reality: recommend doing it
129 * opportunistically ahead of any related op such as construct, dispose, lend, borrow (for any object).
130 * Perf-wise: this_thread_piggy_scan() that has nothing to do (which is more typical than not) has
131 * very low cost. One that does have something to do (objects to dispose) costs ~as much as the actual
132 * disposing does (reasonable low overhead).
133 *
134 * A higher-scope event is
135 * - the decision to shut down a particular #Shm_arena `a`. That is, none of the objects constructed from `a`
136 * shall be touched by this process or, to the extent we can assume it, other process(es). Hence (1)
137 * we should dispose of any `a`-constructed objects (having stopped the regular-operation garbage-collection
138 * ops described above) that might remain (though ideally none should; but we cannot assume it; our user
139 * such as jemalloc::Ipc_arena can make a best effort at it); and (2) clean up any internal book-keeping
140 * relevant to `a`.
141 * - Invoke `static` forgetting_shm_arena() from any thread.
142 * - It is potentially an async op; hence caller is to give it a function to execute on completion.
143 * In particular that function might dispose of the lower-level arena `a`-related resources; this would not
144 * be safe to do until forgetting_shm_arena() disposes any remaining constructed-by-`a` objects.
145 * (In the case of SHM-jemalloc that would include at least destroying, via the raw jemalloc API, the relevant
146 * jemalloc-arena(s) associated with jemalloc::Ipc_arena `a`.)
147 *
148 * ### Impl: Across multiple `*this`es ###
149 * Firstly, per above, a `*this` <=> a particular thread that has performed at least one
150 * `construct()`. We use a `static flow::util::Thread_local_state_registry` (Static_state::m_obj_db_registry)
151 * to maintain such thread-local `*this`es with the ability to enumerate all extant ones. As ever, enumeration
152 * of thread-local items is unnatural and annoying; in our case we need it, as of this writing, for:
153 * - forgetting_shm_arena() (for: ping each `*this` to free objects et al w/r/t the specific shutting-down arena);
154 * - sharded_stats() et al (for: walk across each `*this`, summing its stat-shards into the current resulting
155 * stat-`struct`);
156 * - dbs_set_logger() (for: setting the `Logger*` of each `*this`).
157 *
158 * In general things are fairly elegant, except for the forgetting_shm_arena() flow, at which point we must contend
159 * with the aforementioned thread-local-item enumeration/looping and related yuckiness. Particularly yucky
160 * is the corner case wherein, at forgetting_shm_arena() time from thread X, threads which aren't X have extant
161 * `Thread_lcl_obj_db_admin`s with extant objects belonging to the #Shm_arena that's going away.
162 *
163 * Yuckier still is the case where a thread X is joined by the end user's application, but that thread has an
164 * extant Thread_lcl_obj_db_admin (it has `.construct()`ed objects) with extant objects (they have not all been
165 * disposed). This creates the basic issue: only thread X, in our design, can dispose of items constructed by
166 * thread X; but there is no thread X; but the rest of the processes -- and/or other (borrowing) process(es) --
167 * still hold handle(s) to 1+ objects. Well, it is okay for another thread to do it, as long as it doesn't
168 * intermix with other threads' activities in some bad way. Our answer to all this is, just before thread X is joined,
169 * create a *degraded* thread X-prime, whose purpose is to be <=> with death-row-inhabiting thread X; and to
170 * perform only the disposal of X's objects. New ones by definition cannot appear; and once the extant ones are all
171 * gone, X-prime can also end. Only problem is, when to do this disposal? There's no piggy-backing (it's our thread,
172 * unlike X, which is/was an end-user thread). Answer: we do it periodically. See degraded_admin_thread_body().
173 *
174 * Another tricky aspect concerns stat-collection (referenced above already). See Sharded_stats doc header for
175 * an intro to that design. In short: we use TL-sharding, wherein ongoing ops only make stat-updates to
176 * thread-local stat::Sharded_stat `struct`s; at stat-consume time (et al) the extant such `struct`s are basically
177 * summed member-by-member.
178 *
179 * ### Impl: For a given `*this` ###
180 * Back to the relatively-elegant design of a particular `*this`. The following gives the flavor of what to
181 * expect. The code itself should be reasonably easy to follow, but the following might help as an intro.
182 *
183 * The main building block is Lend_tracker_pool, which in our case is used in admin-mode;
184 * see its doc header. Lend_tracker_pool accesses (and in our -- admin -- case, creates, namely the first time
185 * a given thread `.construct()`s something in a given `Shm_arena`) a SHM-pool-stored high-perf resource with
186 * use-counts pertaining to all of a single `Shm_arena`'s objects (constructed by `*this`-assigned thread).
187 * Hence we store one of these per distinct #Shm_arena. constructing_obj() creates a use-count therein and
188 * sets it to 1; lending_obj() increments it; disposing_obj() decrements it and potentially (if that makes
189 * use-count reach zero) returns it for use by another future use-count.
190 *
191 * The other main thing stored = each live object's info including its address, disposing functor (invoked once
192 * a live object's use-count reaches zero), and #use_ct_idx_t (identifies a use-count slot within the relevant
193 * arena's Lend_tracker_pool). The key thing there is that Lend_tracker_pool is only aware of use-counts, not
194 * anything about what object each use-count pertains to; all of that is higher-level and hence up to us.
195 *
196 * ### Impl: cleanup ###
197 * We turn your attention to the place where a Lend_tracker_pool object is destroyed; actually two places:
198 * inactive_arenas_scan() (from dtor code-path) and forget_shm_arena() (from forgetting_shm_arena() code path).
199 * We won't recap what's said there; but it is of some importance.
200 *
201 * @tparam Shm_arena_t
202 * The arena type which an end user instantiates to then `.construct<T>()` things that we
203 * handle via `.constructing_obj()` and subsequent ops. As of this writing it's going to be a sub-class
204 * of arena_lend::Owner_shm_pool_collection (such as jemalloc::Ipc_arena in the case of SHM-jemalloc).
205 * `Thread_lcl_obj_db_admin<A1>` and `Thread_lcl_obj_db_admin<A2>` are fully independent singleton
206 * registries if `A1 != A2`.
207 */

355 /**
356 * Initiates the process of forgetting (cleaning up) a given #Shm_arena across all per-thread
357 * Thread_lcl_obj_db_admin instances. Any remaining live objects for that arena are destroyed
358 * (even if their use-counts are non-zero).
359 *
360 * This is potentially asynchronous: each per-thread admin must perform its share of the cleanup
361 * from its own thread. Once all per-thread admins have completed this procedure, that is to say
362 * the last per-thread admin to have done so realizes that was the case, it invokes
363 * `on_done_func` (giving it a safe `Log_context_mt` for logging); meanwhile this method returns `false`
364 * (indicating async work remains <=> `on_done_func()` shall be invoked from another thread). If all work
365 * completes synchronously, then `on_done_func` is forgotten and never invoked, and this method returns
366 * `true` (indicating no async work remains <=> `on_done_func()` shall never run).
367 *
368 * ### When can you call this? ###
369 * Since object disposal is asynchronous, take care to not bring down any resource required for
370 * object disposers (constructing_obj() `del_func` arg) to run, before `on_done_func()` runs, assuming
371 * this method returns `false` (if `true`: can proceed immediately).
372 * What the heck is "any resource" in this context? Answer in plainer language: e.g.: SHM-jemalloc
373 * (`Shm_arena` = jemalloc::Ipc_arena) requires the jemalloc-arena to exist; so you must ensure
374 * you don't invoke jemalloc::Memory_manager::destroy_arena() / jemalloc::Thread_cache::destroy_arena_safely()
375 * until entry to `on_done_func()` (if we return `false`). We mention this, since typically a call
376 * like that would be along the same code flow as forgetting_shm_arena(). It makes sense to use
377 * `on_done_func()` to perhaps execute those `destroy_arena...()` items.
378 *
379 * So let's assume that is not an issue. Are there more times when one must not call forgetting_shm_arena()?
380 * Yes:
381 *
382 * Firstly: do not call it concurrently to a *user* thread exiting such that that thread has ever
383 * `constructing_obj()`ed (<=> `Shm_arena::construct<T>()`ed) w/r/t the arena `collection_id`. This can
384 * result in undefined behavior. In practice *from the end user's PoV* (as of this writing): For SHM-jemalloc:
385 * "Calling this" equals calling jemalloc::Ipc_arena::destroy() which equals the last `Ipc_arena` ref-counted-ptr
386 * reference being dropped; we document this accordingly in public-facing `Ipc_arena` doc header(s). (For
387 * other #Shm_arena types -- probably same or similar.)
388 *
389 * It is however fine to call it concurrently with a degraded_admin_thread_body() replacement-`_admin` thread's
390 * teardown. Internal reasoning for this paragraph and the preceding is found inside ~Thread_lcl_obj_db_admin()
391 * dtor body.
392 *
393 * ### Impl discussion for context ###
394 * We cannot control when a different thread's admin-object cleans up: They are generally end user threads:
395 * we cannot schedule them to do things except opportunistically (this_thread_piggy_scan()). (There are also
396 * degraded-admin threads, but such a thread only enters existence, if a user-thread with extant live objects happens
397 * to be joined. This might happen, or it might not happen. So the general case is as noted.)
398 * If the calling thread has an admin, its portion is done synchronously within this call; other threads'
399 * portions are deferred (flagged for execution on their next piggy-scan or degraded-admin-thread wakeup).
400 *
401 * @tparam On_done_func
402 * Functor type compatible with `void (const flow::log::Log_context_mt*)`.
403 * @param collection_id
404 * Identifies the arena to forget.
405 * @param logger_ptr
406 * Logger to use for log messages during the synchronous part of the operation.
407 * @param on_done_func
408 * Completion handler: if `false` returned, then `on_done_func()` is invoked (from another thread) once
409 * all per-thread admins have forgotten this arena (or more precisely: by the last admin to have done

765 /**
766 * Per-arena tracking map: keyed by collection-ID, each value is the arena's Collection_db
767 * containing the Lend_tracker_pool and the set of live objects constructed from that arena
768 * in this thread. Entries are created on first constructing_obj() for a given arena and
769 * removed by forget_shm_arena(). In addition, inactive_arenas_scan() destroys Collection_db::m_lend_tracker_pool
770 * but does *not* remove that arena's entry. (The latter is because of stat-consumption; explained below.)
771 *
772 * ### Rationale: Choice of container ###
773 * It's a hash-map for standard reasons; but why specifically do we use `unordered_flat_map<K, Own<V>>`,
774 * (where `V` is Collection_db)? To answer: there are essentially 3 choices for the basic template:
775 * -# `unordered_map`, the classic.
776 * -# `unordered_node_map`, the classic modernized.
777 * -# `unordered_flat_map`, the standard for performance -- if certain behaviors of the other two are
778 * not required.
779 *
780 * Throw out (1), as in simple terms (2) is better. Details are out there for perusal, and there are some
781 * niggles, but all in all that sufficiently covers it. So that leaves (2) versus (3).
782 *
783 * In general these days (3) `unordered_flat_map` is the highest-performance hash-map (omitting details which
784 * are well publicized). However, `u_f_m<K, V>`, for us, would be insufficient: we need pointer stability
785 * of `V` in one form or another. (See Design below for the key explanations.) We don't need it consistently
786 * but really just one in one situation (again, see Design below); thus simply changing it to
787 * `u_f_m<K, Own<V>>` gives us what we need. In particular, in the one place where we need a `V`
788 * (Collection_db) to not move in memory, we save the `.get()` -- a raw pointer `V*` -- until we (quite soon)
789 * dereference it and do some work; and done. This is required for correctness, but we also get
790 * significant syntactic benefit: we can use `[]` for lookup and auto-insertion, plus there's no need
791 * to use `.emplace()`-and-friends (which would require a ctor for Collection_db -- cannot construct with
792 * member-by-member init). The perf cost is acceptable: an extra use of the heap, rarely (insertion is rare);
793 * and a single extra pointer deref per #Shm_arena in the fast-path (of this_thread_piggy_scan()) which
794 * fades into the background versus the rest of the required work.
795 *
796 * The alternative would have been (2); or really two sub-alternatives:
797 * - 2a: `unordered_node_map<K, V>.
798 * - 2b: `unordered_node_map<K, Own<V>>.
799 *
800 * (2b) is plainly worse; it still has the added cost of `Own`, while the base container performance is worse.
801 * So that leaves (2a). That one is at least worse syntactically (in the ways mentioned), but ignoring that:
802 * We come down to, what's the better trade-off: avoid heap/indirection of `Own<V>`, or get the significantly
803 * better base performance (for lookup especially) of `...flat_...` over `...node_...`? The answer is that
804 * the latter is better.
805 *
806 * Let's emphasize one key point about perf here: #m_collection_dbs is a perf-relevant data structure that
807 * figures in ~every this_thread_piggy_scan() which in turn is *the* perf-relevant part of
808 * Thread_lcl_obj_db_admin... one could even reasonably argue of SHM-jemalloc at large (probably jemalloc, or
809 * the memory manager of choice, is at least as important, but they're definitely mutually within the ballpark
810 * of perf-relevance). Consider: every this_thread_piggy_scan(), called on ~every SHM-jemalloc API,
811 * opportunistically, must:
812 * -# loop through #m_collection_dbs;
813 * -# for each arena (`collection_id_t` = integer = the key), grab the mapped Collection_db;
814 * -# then access its Lend_tracker_pool, grab the aux-pool base-vaddr, at a certain constant offset
815 * grab an integer (Lend_tracker_pool::n_unused());
816 * -# then based on the value of that integer, do a roughly proportional-to-it amount of further work.
817 *
818 * Now, the (reasonable) hope is that for most invocations of this algorithm, for most arenas touched
819 * by a thread-local `*this`, this `n_unused` integer will equal zero, meaning no further work is required
820 * (specifically: there are no first-class zombie-objects in SHM to destroy). However the steps up to that
821 * are mandatory per ever-having-`.construct()`ed `Shm_arena`! Therefore the speed of those steps is important.
822 * So choosing the proper container is important.
823 *
824 * @note constructing_obj(), disposing_obj(), lending_obj() are also frequent and also access `m_collection_dbs`.
825 *
826 * ### Design / Thread safety ###
827 * If one ignores the topic of stat-keeping (stat::Sharded_stats), the situation is straightforward.
828 * We need a Collection_db per arena for reasons that are hopefully clear (in short, we're serving the needs
829 * of owner-arenas like jemalloc::Ipc_arena). All access is thread-local; even forgetting_shm_arena(),
830 * invoked from one thread but charged with removing the given arena's node from #m_collection_dbs, uses
831 * a special tool (Flow's `Polled_shared_state`) to outsource this removal to thread-local code
832 * (forget_shm_arena()). Hence no locking is necessary, and there is no thread safety about which to worry.
833 *
834 * The situation somewhat complicates when adding `Sharded_stats` to the mix (namely into
835 * Collection_db). While the stats within that `struct` are being updated during regular work
836 * (e.g., constructing_obj(), this_thread_piggy_scan()), it's all simple (in terms of concurrency); they're
837 * `atomic`s so that during stat-consumption (from some other thread) no locking is needed -- this is
838 * standard (see `flow::util::stat` doc header for discussion of various stat-keeping techniques). The
839 * updating itself is all strictly thread-local. No problem.
840 *
841 * The problem: Consider stat-consumption from some thread U, while a thread-local `*this` corresponds to
842 * thread V. If we simply had a single stat::Sharded_stats in `*this`: no issue; but we have N of them:
843 * one per arena (per `collection_id_t`/Collection_db pair). In fact stat-consumption executes for a
844 * given #Shm_arena A of the stat-consumption API's caller's choice; so only a particular Collection_db C
845 * is of interest. Hence, in U, that code must grab V's (among others) Collection_db C from
846 * `this->m_collection_dbs`; that is if there even *is* a C (which is the case only if
847 * `this->constructing_obj()` has ever executed on behalf of arena A -- `A.construct<T>(...)`).
848 *
849 * So in U we must access the key-set of #m_collection_dbs; but in thread V, constructing_obj() may
850 * at any moment concurrently modify this key-set (occurs when a new-to-`*this` arena first constructs
851 * from V). Therefore, at least, both the thread-U key-set read and the thread-V key-set write must
852 * be mutex-protected. That's #m_collection_dbs_mutex.
853 *
854 * To continue: upon grabbing the value `&C` (address of the Collection_db for key A), in U we then
855 * access the `Stat_set` stat::Sharded_stats, aggregate it with those of other V-like threads' `*this`es,
856 * and return the assembled stat-values. Note that #m_collection_dbs_mutex need not be locked for that
857 * part; and not-locking it for that part is good for perf, since a concurrent thread-V activity can be
858 * blocked by longer lock (granted: not frequently, and still for a split-second). Such a lock-less access
859 * of `C->...` is safe as long as these hold:
860 * - Node A is not to be removed from the key-set of #m_collection_dbs during thread-U stat-consumption.
861 * (It won't be: If they're accessing A's stats, they are not allowed to let arena A disappear, which is
862 * the only thing that can cause the removal of that node: forgetting_shm_arena() path.)
863 * - `&C` -- the location of Collection_db -- cannot change. Stat-consumption will grab `&C` and then
864 * read `*&C` as part of aggregation. If `&C` became wrong during this short section => catastrophe.
865 * (This is the pointer-stability requirement which we have assured; see preceding doc header section.)
866 *
867 * @warning Restating for maintainers! Do not remove keys from #m_collection_dbs, except in forget_shm_arena().
868 * In particular that's why inactive_arenas_scan() only checks whether the map has only
869 * empty `Collection_db`s, as opposed to removing them and then checking for
870 * `m_collection_dbs.empty()`.
871 *
872 * ### When must we lock #m_collection_dbs_mutex? ###
873 * Above we explained why it is necessary to have it; and one situation in which it must be locked.
874 * The naive assumption would be that every access to the key-set of #m_collection_dbs requires a lock.
875 * This is not the case. (Though, if it were the case, it would still not be catastrophic for perf:
876 * Stat-consumption is rare, so there is almost never contention, so the locks/unlocks along the fast-paths
877 * of this_thread_piggy_scan() + `{construct|dispos|lend}ing_obj()` -- if one were always required -- would
878 * be quite quick. Nevertheless it would still be unpleasant: We go to all this trouble to TL-shard these
879 * damned stats and TL-distribute all the main work of the obj-DB, and yet still we have to lock some mutex
880 * every time? Just for stats at that? No worries though: we don't have to lock it. So back to that.)
881 *
882 * So far we've shown that (1) thread U at stat-consumption time (rare) must lock it when obtaining the
883 * arena's-of-interest Collection_db for its stats-`struct`; and (2) thread V must lock it when *inserting*
884 * a new (to `*this` thread) arena's new Collection_db (also rare). What other places must lock for safety?
885 * That question is equal to the question, "when am I reading X, while someone might concurrently write X; or
886 * when am I writing X, when someone might concurrently read X?" -- where X is `m_collection_dbs`'s key-set.
887 * The answer is, respectively, as follows.
888 * - Thread U during stat-consumption -- the *only* time `*this` is accessed by a thread other than V.
889 * Already discussed above.
890 * - Thread V when *adding* to the key-set. Already discussed above. It is constructing_obj().
891 * (Reading it -- the fast-path -- is fine; by design it's the only thread that accesses `*this`'s key
892 * set and writes to it; and it can't concurrently read and write.) Plus:
893 * - Thread V when *removing* from the key-set. That is, as of this writing, forget_shm_arena(),
894 * triggered by forgetting_shm_arena()s `static` API (and rare).
895 * - Again... removing it is fine, as long as stat-consumption isn't reading the thing being
896 * removed. In case of forget_shm_arena() it won't be. So it is fine.
897 *
898 * So, again: The fast-paths of this_thread_piggy_scan() + `{construct|dispos|lend}ing_obj()` never
899 * lock #m_collection_dbs_mutex.
900 */
901 boost::unordered_flat_map<collection_id_t, Own<Collection_db>> m_collection_dbs;
902}; // class Thread_lcl_obj_db_admin

905 * (Internal-use) Where a Thread_lcl_obj_db_admin cannot handle lend-object and dispose-object tracking, because
906 * the end user triggering those ops happens to be in a thread different from the one in which the object
907 * was `.construct()`ed, use Thread_lcl_obj_db_client: whether in the owner process (but not-constructing thread) or
908 * a borrower process (any thread).
909 *
910 * @see Thread_lcl_obj_db_admin first. Then come back here.
911 *
912 * We keep this doc header short: It is best to understand the doc header of Thread_lcl_obj_db_admin. This should
913 * make clear when that class template is not sufficient; at that point invoke the relevant method of
914 * Thread_lcl_obj_db_client. Namely:
915 * - this_thread_obj_db()->lending_obj(): From owner process but thread that is *not* the one where
916 * Thread_lcl_obj_db_admin::constructing_obj() was called. Otherwise similar trigger to eponymous admin-method
917 * (which can only be invoked from the constructing-thread).
918 * - this_thread_obj_db()->disposing_obj() (`Shm_arena`-taking overload): Ditto.
919 * - this_thread_obj_db()->disposing_obj() (non-`Shm_arena`-taking overload): From a borrower process.
920 * Otherwise similar trigger to eponymous admin-method (which can only be invoked from the constructing
921 * thread, necessarily in the owner process... not any borrower(s)).
922 *
923 * ### Impl notes ###
924 * The docs on the data members and on/inside methods should be sufficient. Generally Thread_lcl_obj_db_admin has
925 * to orchestrate book-keeping about a particular thread's constructed objects; plus certain tricky cleanup-y
926 * activities. Our task is much simpler; really the bottom line is, some other threads need to either `++` or `--`
927 * certain use-counts; so we need to maintain client-mode `Lend_tracker_pool`s; that's about it. The caller must,
928 * essentially, supply (1) the lend-tracker-pool's ID (recall that `pool_id_t`s are completely unique/1-1 across the
929 * system) and (2) a use-count slot index within that pool. We store nothing per-object; and all we need to do
930 * beyond forwarding the dispose/lend request to a Lend_tracker_pool is, the first time a given `pool_id_t` is
931 * mentioned to a `*this`, create/save a Lend_tracker_pool (client-mode: so it'll open a SHM-pool).
932 *
933 * There is one additional task a `*this` must handle: the cleanup of `Lend_tracker_pool`s that will never be used
934 * again; this is potentially important to prevent SHM-RAM leaks over time, as a Lend_tracker_pool existing means
935 * a SHM-pool handle being open, which prevents the underlying RAM (in-SHM) to be returned to the OS for general use.
936 *
937 * Such cleanup is handled, and explained, inside helper new_pool_data(). If interested in cleanup please read that;
938 * then come back here.
939 *
940 * Lastly w/r/t cleanup: new_pool_data() self-cleans as explained; that covers #m_lend_tracker_pools which is
941 * by far the bulkiest aspect of a `*this`. What about #m_per_arena_stats_shards? Indeed: per-arena stat-shards
942 * need cleanup albeit triggered *not* by a `*this` disappearing (user thread exiting); in fact `*this` dtor
943 * instead offloads any stat-shards into stat::Finalized_shards. Instead their cleanup is triggered only by
944 * respective arena(s) shutting down (which is controlled by the user). Therefore we have a `static`
945 * forgetting_shm_arena(), superficially similar to `_admin`'s. However we emphasize that both its impl and its
946 * importance (especially the latter) are far lesser than for `_admin`.

1404 * hook. First thing to realize is that -- for an original _admin per-thread object created in the *user* thread,

1406 * there are either exactly 1 or exactly 2 _admin objects to ever exist, and therefore ~_admin() dtors to ever

1408 * - Invocation/SCENARIO 1 (happens): When user thread exits (user application chose to do so). ~dtor() runs.
1409 * - Invocation/SCENARIO 2 (may happen): If SCENARIO-1 ~dtor() had to create a degraded-admin thread before
1410 * exiting, then this ~dtor() shall later run when *that* thread exits.
1411 *
1412 * If you're reading this linearly for the 1st time, the 2nd bullet might make no sense, since you haven't seen
1413 * the part that spawns that 2nd thread (which is *not* a user thread, but it is performing work for us on that

1419 *
1420 * The thread exiting can happen while the relevant cting arena(s) is/are still up.

1422 * to do with those arena(s) that have been destroyed, from like Ipc_arena dtor, before we can execute.
1423 * So we shall assume that if there is anything left, it's because some arena(s) are still up, and we must keep
1424 * doing our thing (more on that later, when we get to it).
1425 *
1426 * First things first though: Let's do a thorough scan (once isn't a big deal) and see if anything is in fact
1427 * left. An unused_obj_scan() now, in and of itself, is the right thing to do: this dtor would be invoked only
1428 * when thread is exiting, which the user cannot have triggered themselves, but it is an opportunity, and
1429 * we should take it while knowing it's not redundant or recursive or anything like that. So we should do it;
1430 * and it would not be wrong/surprising, if we indeed do find things to delete/clean. As for making it an
1431 * exhaustive scan, it's an anti-entropy measure; as if anything is left after, we're gonna perform a complex
1432 * maneuver involving spawning a new, semi-detached thread, and the less stuff to carry-over the better -- all else
1433 * being equal.
1434 *
1435 * As in this_thread_piggy_scan(), do a form of forgetting_shm_arena()-tail-end work before the scans; this
1436 * (bottom-line) may erase more stuff, so the scans don't even see it/worry about it.

1438 * Possibly we also need to do a thing about remaining stat-struct(s); but more on that below, when we do it.
1439 *
1440 * SCENARIO 2: This ~dtor() executing after degraded_admin_thread_body() exited, ending the replacement thread.
1441 *
1442 * That method ~is the thread body, so we fully control its behavior, and its purpose is to keep running

1444 * no new ones may appear: user thread is gone by now). So inactive_arenas_scan() *will* return true.
1445 * This ~dtor() is the very last thing (of ours) to execute w/r/t the original user thread. All that's left
1446 * is (potentially) the stats-transfer into _finalized_shards.
1447 *
1448 * Can we detect whether this is the active SCENARIO? We probably could by using a flag or something, but
1449 * no need: We are still an _admin, and this is still ~_admin(). So just let the same scans as in
1450 * SCENARIO 1 run; inactive_arenas_scan() shall return true; we'll save the stats -- which, incidentally,
1451 * did *not* happen in invocation 1 of ~_admin() earlier (which spawned the new thread/_admin) -- and that's it.

1534 * static forgetting_shm_arena() will *never* target `this` as part of its mission.

1537 *
1538 * However the caveat: During the short time period between when Thread_local_state_registry, during thread exit,
1539 * removed us from the registry (and then immediately invoked this dtor), and when the new thread
1540 * calls this_thread_obj_db() below, if user manages to get Shm_arena (Ipc_arena as of this writing) deletion
1541 * to start -- meaning static forgetting_shm_arena() is called during this short time period -- then there will
1542 * be trouble. Neither `this` nor the new this_thread_obj_db() were in the registry in that moment;
1543 * yet we (potentially) hold resources to-do with the Shm_arena being destroyed. Behavior is undefined in that
1544 * case -- and we advertised this in forget_shm_arena() doc header -- but, e.g.,
1545 * if an object later reaches ref-count 0, the degraded-admin guy replacing
1546 * *this will try to call ~T() and deallocate its backing memory (but the vaddr space belongs
1547 * to a potentially now-gone arena, its getting destroyed prematurely, because one of the stakeholders was not

1552 * the unused_obj_scan() might have found use-count=0 object(s) from A and tried to free them -- undefined behavior
1553 * again. However! We suggest not worrying about what exactly is OK, and what isn't; it is a waste of cognitive
1554 * resources. Instead we've made the just-mentioned sufficiently-conservative rule: forgetting_shm_arena(A)
1555 * is OK, unless thread shutdown is ongoing for a thread that has ever constructing_obj(A)ed. That includes
1556 * this entire destructor body, if it would have ever touched A-related resources-that-need-actual-arena-alive.
1557 * Disallowing that is (1) not too onerous on the end user and (2) avoids any issues.
1558 *
1559 * However: we are not disallowing forgetting_shm_arena() while a degraded/drain thread and replacement _admin --
1560 * which we're about to spawn and create respectively -- is shutting down. That is SCENARIO 2. So is it safe?
1561 * Answer: Yes. Let's see why. SCENARIO 2 means we've returned above already: inactive_arenas_scan()
1562 * returned true, meaning no live objects remained in any known-to-`*this` arena at that time. The question,
1563 * though, is again whether unused_obj_scan() preceding that could have touched A-related
1564 * resources-that-need-actual-arena-alive. The answer is no; the whole point is -- restating this --
1565 * degraded_admin_thread_body() returns (letting thread exit) only once inactive_arenas_scan() returns
1566 * `true` in the first place. (forgetting_shm_arena() during that time is perfect safe and good.)
1567 * So unused_obj_scan() will, at worst, note a bunch of m_collection_dbs per-arena entries each of which
1568 * lacks an m_lend_tracker_pool (inactive_arenas_scan() would have shut them all down upon detecting
1569 * no-live-objects left); so the scan short-circuits for each arena (if any), doing nothing: there's nothing
1570 * to do. Therefore it is safe.
1571 *
1572 * It is fortunate we need not disallow the thing in the preceding paragraph: It would be difficult for an
1573 * end-user to know when not to let `Shm_arena` shut down relatively to degraded_admin_thread_body() thread
1574 * shutdowns, whose lifetimes they do not directly control (and which even depend on timer schedules).
1575 *
1576 * Another potential problem that comes from the same source -- The Gap -- has to do with
1577 * m_collection_dbs[A]->m_stats_shard (which is kept around even past `inactive_arenas_scan() == true`).
1578 * I.e., a sharded_stats*(A) (stat consumption/similar) would right now not detect A's m_stats_shard, as
1579 * `this` is not in Thread_local_state_registry, and the replacement _admin is not either (plus later it
1580 * will be in-registry but not yet have move()d m_collection_dbs[A]->m_stats_shard into itself; same prob).
1581 * In short: No problem: That is why we do the thread_end_gap_mutex()-lock above. Again: see
1582 * thread_end_gap_mutex() doc header for all details about this. Bottom line is it's fine to do
1583 * sharded_stats*() even during this teardown.
1584 * (End of forgetting_shm_arena() caveats discussion.)
1585 *
1586 * --- OK. So:
1587 *
1588 * Gotta start thread; and since we must exit gotta detach from it. We can't *really* .detach() though;
1589 * or rather we can, but this creates a bad situation, if by the time the program is otherwise ready to
1590 * std::exit() normally (probably main() `return`s): Any detached threads will be forcibly killed at that point.
1591 * Just in and of itself that's uncool/entropy-laden; but also in actual reality the following is not-uncommon:
1592 * program is about to exit and starts sanely joining normal threads; *this dtor runs; an object or two remain live
1593 * at this time; we launch the thread below and detach; just then the program is able to free whatever it is that
1594 * was still live; and then immediately main() `return`s; in ~100msec (as of this writing; see
1595 * degraded_admin_thread_body()) it would've detected the live objects are unused; free them nicely; and exit
1596 * the thread peacefully. Instead OS murders the thread before it can do that.
1597 *
1598 * So we "semi-detach": Add it to a global/static vector of `Thread`s; and when program exits we use an
1599 * std::atexit() handler to join those threads. Unless there is some bug, at that point they'll either already
1600 * be stopped/joined (!<...>.joinable()); or will soon-enough wake up, clean up what's left, and become thus.
1601 * So the atexit() handler can .join() the .joinable() one(s) if any and itself return. By C++1x rules,
1602 * the atexit() handler will run fully-before any of this static stuff is destroyed, because it has been constructed
1603 * by the time we invoke std::exit() to register the handler.
1604 *
1605 * Lastly:
1606 * 99.999999% of the time when launching threads we use the delightful (if I do say so myself)
1607 * flow::async::Single_thread_task_loop; however that (as of this writing) does not support detaching thread
1608 * from the object, so this is the rare case where we'll make the Thread ourselves.
1609 * In doing so do copy a couple of (logging- and pinning-related) niceties that would have happened there. See
1610 * flow::async::Task_qing_thread for inspiration. */

1708template<typename Shm_arena_t>
1709template<typename Deleter_func_obj>
1710void Thread_lcl_obj_db_admin<Shm_arena_t>::constructing_obj(pool_id_t* lend_tracker_pool_id_ptr,
1711 use_ct_idx_t* use_ct_idx,
1712 Shm_arena* shm_arena,
1713 arena_lend::stat::Obj_db_aux_pool_stats*
1714 obj_db_aux_pool_stats,
1715 void* addr, Deleter_func_obj&& del_func)
1716{
1717 using flow::util::Lock_guard;
1718 using flow::util::stat::fetch_add;
1719 using std::optional;
1720 using std::in_place;
1721
1722 auto& lend_tracker_pool_id = *lend_tracker_pool_id_ptr;
1723 const auto collection_id = shm_arena->get_id();
1724
1725 /* Our core, fast-path task here is:
1726 * - Grab X = m_collection_dbs[collection_id], the Collection_db for the owner-side arena with ID collection_id.
1727 * - Register a new use-count slot in X->m_lend_tracker_pool (in-SHM aux pool storing use-counts per-object).
1728 * - Create an Object struct-instance, saving some basic info about the new object for later reference,
1729 * such as for wehn the object is to be destroyed; and add it to LRU-ordered x->m_objs.
1730 *
1731 * The first step, in the fast-path, is read-only. However, the first time constructing_obj() is called on
1732 * arena collection_id (that is the first time this thread does (that arena)->construct() in this thread),
1733 * X won't exist, so we must (1) create the fresh Collection_db (no objects in it yet) and (2) insert
1734 * it into m_collection_dbs. Now, if you read m_collection_dbs doc header, you'll see that due to
1735 * certain aspects to do with concurrency and stats, (2) has to be done in a very specific way.
1736 * Simply doing the syntactically-nice `X = m_collection_dbs[collection_id]` and checking for X being null
1737 * (just-inserted in our case) is tempting but would be wrong. Specifically, we have to write this out
1738 * the long way: if key=collection_id is there, great; if not, then add it. The reason is that the
1739 * "add it" part -- and that part only -- has to be protected by m_collection_dbs_mutex. */
1740
1741 Collection_db* collection_db;
1742 const auto it_collection_id_and_db = m_collection_dbs.find(collection_id);
1743 if (it_collection_id_and_db == m_collection_dbs.end())
1744 {
1745 // Slow-path. Create fresh Collection_db.
1746 lend_tracker_pool_id = Shm_pool_offset_ptr_data_base::generate_pool_id();
1747 FLOW_LOG_INFO_LOCKED("Tl_obj_db_admin: For arena/collection (collection-ID [" << collection_id << "]), "
1748 "first constructed-obj in this thread; will create this thread+arena's lend-tracker SHM-pool "
1749 "(pool-ID [" << lend_tracker_pool_id << "]) and related tracking structures in heap.");
1750 collection_db
1751 = new Collection_db{ shm_arena,
1752 lend_tracker_pool_id,
1753 optional<Lend_tracker_pool>
1754 {std::in_place,
1755 this, &m_skip_fast_path_verbose_logging, // For its logging needs.
1756 Owner_spc_impl<const Shm_arena>{*shm_arena}
1757 .generate_shm_object_name(lend_tracker_pool_id),
1758 util::CREATE_ONLY,
1759 obj_db_aux_pool_stats, // Saved here once. Ignored in future calls.
1760 shm_arena->get_permissions()},
1761 {}, {} };
1762 // ^-- Assumes any Shm_arena_t is an Owner_shm_pool_collection; true by arena-lend design.
1763
1764 // As noted above, insert under lock -- stat-consumption might be reading key-set under same lock right now.
1765 {
1766 Lock_guard<decltype(m_collection_dbs_mutex)> lock{m_collection_dbs_mutex};
1767 m_collection_dbs[collection_id].reset(collection_db);
1768 }
1769 } // if (m_collection_dbs[collection_id] not found)
1770 else // if (m_collection_dbs[collection_id] found)
1771 {
1772 // Fast-path.
1773 collection_db = it_collection_id_and_db->second.get();
1774 lend_tracker_pool_id = collection_db->m_lend_tracker_pool_id;
1775 }
1776 /* Either way, we can now do the rest of it: register use-count, save Object.
1777 *
1778 * Subtlety: constructing_obj() cannot be invoked once inactive_arenas_scan()s start (dtor or
1779 * degraded_admin_thread_body()), so inactive_arenas_scan() could not have nullified
1780 * collection_db->m_lend_tracker_pool; so it is safe to just deref it without a null check. */
1781 *use_ct_idx = collection_db->m_lend_tracker_pool->use_count_new(); // (Can throw bad_alloc.)
1782
1783 typename Collection_db::Object& obj = collection_db->m_objs[*use_ct_idx];
1784 assert((!obj.m_del_func) && "Double-used use_ct_idx somehow? Tracking bug? Investigate!");
1785
1786 obj.m_addr = addr;
1787 obj.m_del_func = std::move(del_func);
1788
1789 if (!skip_fast_path_verbose_logging())
1790 {
1791 FLOW_LOG_TRACE_LOCKED("Tl_obj_db_admin: For arena/collection (ID [" << collection_id << "]), constructed-obj "
1792 "registered in lend-tracker SHM-pool and related tracking structures in heap; use count = 1; "
1793 "addr = [" << addr << "]; use-count index in lend-tracker-pool = [" << *use_ct_idx << "]; "
1794 "lend-tracker-pool ID = [" << lend_tracker_pool_id << "].");
1795 }
1796 // else { Skip ~any cycle use on logging along fast-path. }
1797
1798 { // Stats.
1799 auto& stats_shard = collection_db->m_stats_shard;
1800 auto& owner_obj_stats = stats_shard.m_owner_obj;
1801 fetch_add(&owner_obj_stats.m_construct_count, 1);
1802 fetch_add(&owner_obj_stats.m_live_handle_groups, 1);
1803 fetch_add(&stats_shard.m_live_obj.m_live_objects, 1);
1804 // Reminder: HI_WMARKs, when sharding as we are, are computed at stat-consumption time. No update here.
1805 }
1806} // Thread_lcl_obj_db_admin::constructing_obj()

1895template<typename Shm_arena_t>
1896void Thread_lcl_obj_db_admin<Shm_arena_t>::unused_obj_scan(bool exhaustive, bool draining)
1897{
1898 using arena_lend::stat::Zombie_obj_reaper_stats;
1899 using flow::util::stat::fetch_add;
1900 using flow::util::stat::fetch_sub;
1901 using std::vector;
1902 using std::atomic;
1903
1904 // Reminder: This entire method is "fast-path"; we need to zealously conserve compute (unless `exhaustive`).
1905
1906 vector<use_ct_idx_t> unused_ct_idxs; // (Try to optimize a bit by declaring these non-ptrs/refs on the outside.)
1907 typename decltype(Collection_db::m_objs)::Iterator obj_it;
1908 typename decltype(Collection_db::m_objs)::Reverse_iterator obj_r_it;
1909 for (const auto& collection_id_and_db : m_collection_dbs)
1910 {
1911 /* Aliases: FLOW_LOG_..._LOCKED() messages below may not name structured bindings (C++17).
1912 * @todo Move to C++20 => Use bindings after all for pithiness. (Some C++17-mode compilers already OK; not all.)
1913 * Remove the @warning about this from doc header of FLOW_LOG_WARNING_LOCKED() (in Flow, not Flow-IPC). */
1914 const auto collection_id = collection_id_and_db.first;
1915 const auto& collection_db = collection_id_and_db.second;
1916
1917 auto& lend_tracker_pool_opt = collection_db->m_lend_tracker_pool;
1918 if (!lend_tracker_pool_opt) // inactive_arenas_scan() may have nullified it.
1919 {
1920 continue; // It's a dead Collection_db, kept-around only for m_stats_shard. Don't count the scan (as doc-ed).
1921 }
1922 // else
1923 auto& lend_tracker_pool = *lend_tracker_pool_opt;
1924
1925 auto& stats_shard = collection_db->m_stats_shard;
1926 auto& zombie_obj_reaper_stats = draining ? stats_shard.m_zombie_obj_reaper_drain
1927 : stats_shard.m_zombie_obj_reaper_main;
1928 { // Stats. Get this one out of the way before any short-circuiting.
1929 fetch_add(&zombie_obj_reaper_stats.m_scans, 1);
1930 exhaustive && fetch_add(&zombie_obj_reaper_stats.m_exhaustive_scans, 1);
1931 }
1932
1933 auto& objs = collection_db->m_objs;
1934
1935 /* n_unused() is signed (for subtle reasons that should be understood: see its doc header), so this must be too,
1936 * as initially this holds n_unused()'s ret-value. It can also go from positive to negative, as it gets
1937 * decremented with each obj-reaping; see near end of hint loop below for this "to negative" corner case. */
1938 signed int n_unused;
1939 if (exhaustive)
1940 {
1941 n_unused = std::numeric_limits<decltype(n_unused)>::max();
1942 }
1943 else
1944 {
1945 n_unused = lend_tracker_pool.n_unused();
1946 if (n_unused <= 0) // (Can be negative; as noted just above this is explained in n_unused() doc header.)
1947 {
1948 /* An optimization. Technically emit_unused_ct_idx_hints() can yield stuff nevertheless, and is a pretty
1949 * quick constant-time search through the hints array; but if right at this moment the count is <=0,
1950 * then don't waste a single cycle (that there is non-zero chance hints array will have something if we look
1951 * is true but unlikely/not worth it). */
1952 continue;
1953 }
1954 // else: There *must* be some unused live objs.
1955 }
1956 /* We check the hints array first for speed; then if n_unused still shows there shall be more,
1957 * do the FIFO-order search of objs. */
1958
1959 auto n_unused_saved = n_unused; // For logging/stats only.
1960 enum { HINTS_SUFFICIENT, FIFO_SUFFICIENT, EXHAUSTED } scan_outcome; // Ditto.
1961 /* Most members of zombie_obj_reaper_stats are not each ++ing 0-1 per-arena-per-scan but per-arena can each be
1962 * incremented any number of times or not at all, depending on n_unused, the hint array's contents, and what's
1963 * at the front of .m_objs. So instead of ++ing the actual `atomic`s each time, we cache the total here
1964 * and then += the non-zero totals onto the appropriate `atomic`s. This cache starts at all-zeroes. */
1965 Zombie_obj_reaper_stats::Events<false> batched_stats; // false => non-atomic members.
1966 unsigned int batched_destroy_count = 0;
1967
1968 lend_tracker_pool.emit_unused_ct_idx_hints(&unused_ct_idxs); // (It is cleared at start.)
1969 batched_stats.m_hints_checked += unused_ct_idxs.size();
1970 for (auto unused_ct_idx_possibly : unused_ct_idxs)
1971 {
1972 obj_it = objs.find(unused_ct_idx_possibly);
1973 if (obj_it == objs.end())
1974 {
1975 // Hint did not work out (perhaps we got it in an earlier pass). Anyway it is a hint; no harm done.
1976 if (!skip_fast_path_verbose_logging())
1977 {
1978 FLOW_LOG_TRACE_LOCKED("Tl_obj_db_admin: For arena/collection (ID [" << collection_id << "]), piggy-scan "
1979 "got hint about live object with use-count=0; but we'd already deleted it; it happens; "
1980 "(former) use-count index in lend-tracker-pool = [" << unused_ct_idx_possibly << "]; "
1981 "lend-tracker-pool ID = [" << collection_db->m_lend_tracker_pool_id << "].");
1982 }
1983 // else { Skip ~any cycle use on logging along fast-path. }
1984
1985 ++batched_stats.m_hints_stale;
1986 continue;
1987 }
1988 // else if: An object at that slot is live. Is its use-count zero right now though?
1989
1990 auto use_ct_idx_copy = unused_ct_idx_possibly;
1991 if (!lend_tracker_pool.use_count_return_if_unused(&use_ct_idx_copy))
1992 {
1993 /* Nope.
1994 *
1995 * It is rare but can happen. It takes 2+ scans (a scan collects the hints before its FIFO phase; and objects
1996 * are constructed only in this thread, hence not during a scan):
1997 * -# A client decrements the use-count to 0; it posts the hint a little later, but before it does:
1998 * -# Meanwhile a scan (the hints already collected, hence excluding that one) reaches the object in its
1999 * FIFO phase and reaps it; in particular n_unused() could have already been incremented.
2000 * -# The hint is placed into the hint-area (but the scan already did not see that).
2001 * It may stay unread for a while (and that's fine; it got reaped anyway): Non-exhaustive scans skip
2002 * this arena while n_unused() is 0, which it likely is after that reaping.
2003 * -# This thread constructs a new object -- constructing_obj() -- and that use-count slot is reused for
2004 * it, depending on Use_count_registry pattern of movement around the pool area.
2005 * -# n_unused() is non-zero again, and a later scan reads the hint, finds the new object at that index:
2006 * but it's live.
2007 * (Without step 4 this would have been a stale hint instead; see above.) */
2008
2009 if (!skip_fast_path_verbose_logging())
2010 {
2011 FLOW_LOG_TRACE_LOCKED("Tl_obj_db_admin: For arena/collection (ID [" << collection_id << "]), piggy-scan "
2012 "got hint about live object with use-count=0; and one is live at that index; but it "
2013 "must be another object by now, as its use-count is >0; "
2014 "(former) use-count index in lend-tracker-pool = [" << unused_ct_idx_possibly << "]; "
2015 "lend-tracker-pool ID = [" << collection_db->m_lend_tracker_pool_id << "].");
2016 }
2017 // else { Skip ~any cycle use on logging along fast-path. }
2018
2019 ++batched_stats.m_hints_stale_and_slots_reused;
2020 continue;
2021 }
2022 /* else: Found one! It reached 0 (end state), and it is live, and we are the only ones who can remove it, so
2023 * there's no danger of concurrent competition. */
2024
2025 auto& obj = obj_it->second;
2026
2027 if (!skip_fast_path_verbose_logging())
2028 {
2029 FLOW_LOG_TRACE_LOCKED("Tl_obj_db_admin: For arena/collection (ID [" << collection_id << "]), piggy-scan "
2030 "got hint about live object with use-count=0; and one is live at that index; and the "
2031 "use-count *is* zero; we shall immediately delete it from in-heap tracking/removed it "
2032 "from lend-tracker SHM-pool; addr = [" << obj.m_addr << "]; use-count index in "
2033 "lend-tracker-pool = [" << unused_ct_idx_possibly << "]; "
2034 "lend-tracker-pool ID = [" << collection_db->m_lend_tracker_pool_id << "].");
2035 }
2036 // else { Skip ~any cycle use on logging along fast-path. }
2037
2038 obj.m_del_func(obj.m_addr, collection_db->m_shm_arena);
2039 objs.erase(obj_it);
2040 ++batched_destroy_count;
2041
2042 --n_unused;
2043 // Might even become negative (hints array and N-unused metadata are not modified atomically in concert)!
2044 } // for (auto unused_ct_idx_possibly : unused_ct_idxs)
2045
2046 if (n_unused <= 0)
2047 {
2048 scan_outcome = HINTS_SUFFICIENT; // The search-avoiding hints phase was [more than] sufficient to be done.
2049 }
2050 else // if (n_unused > 0)
2051 {
2052 /* As explained in class doc header Impl section: search from oldest to newest to hopefully maximize
2053 * speed of getting n_unused down to 0 (though it might already be at 0 even!). */
2054 obj_r_it = objs.oldest();
2055
2056 /* scan_outcome shall end up either EXHAUSTED (unlikely/impossible unless `exhaustive`) or FIFO_SUFFICIENT.
2057 * We'll be pessimistic for tactical convenience and start with assuming the former; but if
2058 * (likely/guaranteed unless `exhaustive`) we see `n_unused == 0` (not the case right at the moment), then
2059 * we'll set scan_outcome otherwise. */
2060 scan_outcome = EXHAUSTED;
2061 bool done = obj_r_it == objs.past_newest();
2062 while (!done) // First time around, `done` can only be `true` due to EXHAUSTED. After that -- see below.
2063 {
2064 ++batched_stats.m_fifo_objs_checked;
2065
2066 auto unused_ct_idx_possibly = obj_r_it->first;
2067 auto use_ct_idx_copy = unused_ct_idx_possibly;
2068 if (!lend_tracker_pool.use_count_return_if_unused(&use_ct_idx_copy))
2069 {
2070 done = ((++obj_r_it) == objs.past_newest()); // n_unused unchanged, so `true` would be due to EXHAUSTED.
2071
2072 ++batched_stats.m_fifo_objs_live;
2073 continue; // Just a live object. Nothing to see here for now.
2074 }
2075 // else if (found and returned use-count=0): Much like in the above hints-array pass:
2076
2077 /* A reverse iterator actually stores an iterator at base, so we'll erase where the reverse iterator is
2078 * pointing. To do this, we need to convert to a regular iterator and go back one. The reverse iterator
2079 * obj_r_it will point to "next" automatically after erasure. */
2080 auto obj_it_to_erase = obj_r_it.base();
2081 --obj_it_to_erase;
2082
2083 auto& obj = obj_it_to_erase->second;
2084
2085 if (!skip_fast_path_verbose_logging())
2086 {
2087 FLOW_LOG_TRACE_LOCKED("Tl_obj_db_admin: For arena/collection (ID [" << collection_id << "]), piggy-scan "

2514 * we move-cted it into the Own<Collection_db> on the stack above.
2515 *
2516 * Note: Lend_tracker_pool (admin-type) dtor performs removal of pool name from file-system.
2517 *
2518 * This is the other location -- versus inactive_arenas_scan() (executed in our dtor or later within
2519 * degraded_admin_thread_body()) -- where this occurs. Please read the note in inactive_arenas_scan() in a similar
2520 * spot; it explains certain cleanup implications relevant to Thread_lcl_obj_db_client. */
2521} // Thread_lcl_obj_db_admin::forget_shm_arena()

2523template<typename Shm_arena_t>
2524void Thread_lcl_obj_db_admin<Shm_arena_t>::degraded_admin_thread_body(Thread_lcl_obj_db_admin* exiting_thread_obj_db,
2525 boost::promise<void>*
2526 done_with_exiting_thread_obj_db)
2527{
2528 using flow::Fine_clock;
2529 using boost::chrono::milliseconds;
2530 using boost::chrono::seconds;
2531 using boost::chrono::round;
2532 namespace this_thread = flow::util::this_thread;
2533
2534 constexpr util::Fine_duration PERIOD_BTWN_CHECKS = milliseconds{100};
2535 constexpr util::Fine_duration PERIOD_BTWN_INFO_LOGS = seconds{5}; // Don't spam.
2536
2537 const auto exiting_thread_token = exiting_thread_obj_db->m_thread_token;
2538 FLOW_LOG_INFO_LOCKED("Tl_obj_db_admin: Degraded-admin thread started to take over from thread with unique-token "
2539 "[" << exiting_thread_token << "] (and/or see the present thread's nickname) "
2540 "which is exiting and will exit shortly, but "
2541 "not all live objects constructed by that thread have become unused, so we must keep "
2542 "deleting them when possible in this new thread; once all gone: exit this thread too. "
2543 "This new thread-local object has moved all live-object data from the exiting thread's.");
2544
2545 {
2546 /* Key-set write to *this->m_collection_dbs. Per the #m_collection_dbs doc header, key-set writes must hold
2547 * #m_collection_dbs_mutex: *this (the replacement admin) is already registered in the TLSR-admin set, so
2548 * without this lock a concurrent stat::sharded_stats_impl() -- which reads the key-set under the same mutex --
2549 * could observe this map mid-move, i.e. a data race / UB. */
2550 flow::util::Lock_guard<decltype(m_collection_dbs_mutex)> lock{m_collection_dbs_mutex};
2551 m_collection_dbs = std::move(exiting_thread_obj_db->m_collection_dbs);
2552 }
2553 assert(exiting_thread_obj_db->m_collection_dbs.empty());
2554
2555 /* Gotta update each Lend_tracker_pool's logging resource pointers; essentially it has a couple pointers into
2556 * the dying/dead thread's _admin; needs to be to *this _admin. Only we can ever touch any of these
2557 * `Lend_tracker_pool`s, so there's no potential concurrency involved in this op. Also:
2558 *
2559 * Seed this (drain) thread's tcache for each arena whose objects we may be reap-destroying below: we
2560 * inherited the exiting thread's objects but have never allocate()d anything ourselves. In short this
2561 * ensures various deallocate()s can use Shm_arena memory-manager's (at least: SHM-jemalloc <=> jemalloc)
2562 * tcache mechanism. The precipitating use-case is specifically jemalloc::Ipc_arena::deallocate() (see inside it)
2563 * and jemalloc::Ipc_arena::this_thread_ensure_tcache_exists() (see its doc header). There's a somewhat-tricky
2564 * to-do in the former that might eliminate the impetus for this_thread_ensure_tcache_exists() existing/being
2565 * called. Probably the impl for that to-do would live in or around this _admin class.
2566 * (Here also skip dead collections: nothing left to destroy there.) */
2567 for (const auto& [nil, collection_db] : m_collection_dbs)
2568 {
2569 auto& lend_tracker_pool_opt = collection_db->m_lend_tracker_pool;
2570 if (lend_tracker_pool_opt) // inactive_arenas_scan() may have nullified it.
2571 {
2572 lend_tracker_pool_opt->update_log_context(this, &m_skip_fast_path_verbose_logging);
2573
2574 Owner_spc_impl<const Shm_arena>{*collection_db->m_shm_arena}.this_thread_ensure_tcache_exists();
2575 }
2576 }
2577
2578 exiting_thread_obj_db = nullptr; // Just to avoid temptation to dereference -- it won't exist after this:
2579 done_with_exiting_thread_obj_db->set_value();
2580
2581 auto last_info_log_when = Fine_clock::now();
2582 do // Don't check inactive_arenas_scan() now, since we wouldn't have been launched if it returned `true` now.
2583 {
2584 this_thread::sleep_for(PERIOD_BTWN_CHECKS);
2585
2586 const auto now = Fine_clock::now();
2587 if ((now - last_info_log_when) >= PERIOD_BTWN_INFO_LOGS)
2588 {
2589 last_info_log_when = now;
2590 FLOW_LOG_INFO_LOCKED("Tl_obj_db_admin: Informing you periodically: "
2591 "Degraded-admin thread still alive; # of arenas/collections with 1+ live objects: "
2592 "[" << m_collection_dbs.size() << "]. We scan this thread's obj-DB every "
2593 "[" << round<milliseconds>(PERIOD_BTWN_CHECKS) << "] which includes right now.");
2594 }
2595
2596 /* We're just gonna ignore the flag in degraded-admin mode and assume it's true. In for a penny, in for a pound.
2597 * forgetting_shm_arena() will arm it, and we just won't disarm it. It might arm it again which is harmless.
2598 * (And again, etc.) Note that it's not a lengthy operation -- too lengthy for any fast-path, but every
2599 * PERIOD_BTWN_CHECKS it is totally fine.
2600 *
2601 * P.S. Why ignore it? Answer: just seems simpler/less entropy-laden. Though to be honest it should be fine
2602 * to not-ignore it too. @todo Maybe revisit. */
2603 if_requested_forget_arena_related_resources(true);
2604
2605 unused_obj_scan(false, true); // Non-exhaustive; drain-mode (stats attribution).
2606 /* Note: I (ygoldfel) considered using unused_obj_scan(true, true) here but went with the non-exhaustive one
2607 * after all.
2608 * Reminder: non-exhaustive means it saves a copy of n_unused() -- count of live-but-unused objects at that
2609 * moment -- and only deletes at most that many; exhaustive means ignore that and go through *every* object.
2610 * There's only one drawback to non-exhaustiveness: n_unused() reads an atomic counter with relaxed-order, so
2611 * there could be some thread-cache-lag or ordering weirdness about its value. An exhaustive scan would defeat
2612 * it (but not using it), but in some kinda-random situations a non-exhaustive scan could basically leave
2613 * some live-unused objects around in this pass. We consider this acceptable:
2614 * - even every PERIOD_BTWN_CHECKS, we don't want to do some unnecessary huge scan, if possible; and
2615 * - worst-case, in another PERIOD_BTWN_CHECKS, we'll catch anything we missed; this delay is acceptable
2616 * by its very conception. */
2617
2618 /* Now check again for any arenas we track for which the above have eliminated all remaining live objects.
2619 * In addition to freeing the Lend_tracker_pool RAM, it returns true iff no live objects remain across *all*
2620 * of the arenas we track. In that case we can finally RIP.
2621 *
2622 * Too lengthy (also, stupid) for any fast-path; absolutely fine every PERIOD_BTWN_CHECKS. */
2623 }
2624 while (!inactive_arenas_scan());
2625
2626 FLOW_LOG_INFO_LOCKED("Tl_obj_db_admin: Degraded-admin thread started to take over from thread with unique-token "
2627 "[" << exiting_thread_token << "]: Done! Exiting thread.");
2628} // Thread_lcl_obj_db_admin::degraded_admin_thread_body()

2646template<typename Shm_arena_t>
2647stat::Sharded_stats*
2648 Thread_lcl_obj_db_admin<Shm_arena_t>::stats_update_pre_consumption(collection_id_t collection_id)
2649{
2650 using flow::util::stat::store;
2651 using flow::util::Lock_guard;
2652
2653 /* Caution! Any field updated here may need special care when doing Finalized_shards::insert() in our ~dtor().
2654 * Make sure they act in sync. */
2655
2656 // We are *not* necessarily in `*this` thread. Hence the lock (see m_collection_dbs doc header).
2657
2658 { // Lock protects *both* the key-set *and* pointer-thing in optional<Lend_tracker_pool> m_lend_tracker_pool.
2659 Lock_guard<decltype(m_collection_dbs_mutex)> lock{m_collection_dbs_mutex};
2660 const auto it_collection_id_and_db = m_collection_dbs.find(collection_id); // <-- Lock needed.
2661 if (it_collection_id_and_db == m_collection_dbs.end())
2662 {
2663 return nullptr; // As advertised. Reminder: this is not an error; just means no relevant constructing_obj() yet.
2664 }
2665 // else:
2666
2667 Collection_db& collection_db = *it_collection_id_and_db->second; // &collection_db is ptr-stable.
2668
2669 auto& stats_shard = collection_db.m_stats_shard;
2670 const auto& lend_tracker_pool_opt = collection_db.m_lend_tracker_pool; // <-- Lock needed.
2671 if (lend_tracker_pool_opt)
2672 {
2673 /* .n_unused() is a relaxed-atomic load.
2674 * Orthogonally: it can be (slightly) negative (see its doc header); hence clamp to 0. */
2675 const signed int n_unused = lend_tracker_pool_opt->n_unused();
2676 store(&stats_shard.m_live_obj.m_live_object_zombies, (n_unused < 0) ? 0 : n_unused);
2677 }
2678 else
2679 {
2680 // No pool => inactive_arenas_scan() nullified it: no live objects, and none can appear.
2681 store(&stats_shard.m_live_obj.m_live_object_zombies, 0);
2682 }
2683
2684 return &stats_shard;
2685 } // Lock_guard{m_collection_dbs_mutex}
2686
2687 /* Tactical design discussion: Consider Live_obj m_live_obj and its stat-members; which ones should we update
2688 * here and why or why not? Answers:
2689 * - The _hi_wmark x 2 fields are not to be updated, as we're doing TL-sharding (explained in flow::util::stat
2690 * doc header; we follow this logic in quite a few places). stats_aggregate_shards() will set them.
2691 * - That leaves m_live_objects (call it X) and m_live_object_zombies (call it Y).
2692 * - We update Y here; while X is live-updated regularly. Why though?
2693 *
2694 * Take Y first. There is only one source of it: m_collection_dbs[A]->m_lend_tracker_pool->n_unused(), or 0
2695 * if !...->m_lend_tracker_pool. All in all, we don't really have too much choice: Ignoring temporarily the
2696 * no-pool-due-to-inactive_arenas_scan() possibility: ->n_unused() loads an in-SHM atomic. To live-update a
2697 * stat-member based on that, we'd have to go inside Lend_tracker_pool and have it live-updating both the in-SHM
2698 * atomic (as it must already, for the unused_obj_scan() algorithm to work) *and* the stat-member. We want no
2699 * part of that, both due to perf concerns and due to the layer-penetration involved. It would be ugly and possibly
2700 * slow -- for zero user benefit (it's still a shard, so we can't get an accurate _hi_wmark out of it). So that's
2701 * why. (Now, unforget the no-pool-due-to-inactive_arenas_scan() possibility. We must therefore contend with
2702 * the possibility that the TL-state's thread will nullify the optional<> concurrently. Fortunately this is not
2703 * too difficult, nor it is perf-dangerous: The nullification is rare, as is stat-consumption; so as documented
2704 * on m_collection_dbs_mutex, we "merely" need to extend that mutex to cover also this optional<>'s modification;
2705 * and lock it just above (which we must anyway: key-set is accessed) + when .reset()ting the optional<>.)
2706 *
2707 * Now take X. At a first glance it seems like a good candidate for not-live-updating it as well. Its value
2708 * is "simply" m_collection_dbs[A]->m_objs.size(). Awesome! Actually it is not awesome: This value is not
2709 * atomic<>, and it can be updated anytime and *frequently* (disposing_obj(), unused_obj_scan()). So we'd have
2710 * to extend m_collection_dbs_mutex to protect it; but this would mean frequently locking it in the aforementioned
2711 * places. (Granted: contention would be nil, so it's pretty cheap; but we've taken some serious effort to avoid
2712 * doing that all over, particularly if it'd be just for stats, and we endeavour to do the same here.)
2713 * Therefore that means we need to live-update the stat-member; and indeed we do, wherever m_objs is modified.
2714 * Fortunately this is both easy (enough) and cheap; at least no more expensive than the various other
2715 * TL-sharded stat-member updates we perform. */
2716} // Thread_lcl_obj_db_admin::stats_update_pre_consumption()

2753template<typename Shm_arena_t>
2754Thread_lcl_obj_db_client<Shm_arena_t>::~Thread_lcl_obj_db_client()
2755{
2756 using flow::util::Lock_guard;
2757 using flow::util::Mutex_recursive;
2758 using std::optional;
2759
2760 const auto this_thread_unique_token = flow::util::this_thread_unique_token();
2761 if (this_thread_unique_token != m_thread_token)
2762 {
2763 FLOW_LOG_WARNING_LOCKED("Tl_obj_db_client: "
2764 "Shutting down from different thread (unique-token [" << this_thread_unique_token << "]) "
2765 "than the one (unique-token [" << m_thread_token << "]) that created us; "
2766 "bailing out. Honestly this is strange; we are a `static` TL-registry, and per-thread "
2767 "dtors should run before the central static object's. In any case this can conceivably -- "
2768 "in the absence of bugs -- only occur when program is exiting, at which "
2769 "point graceful shutdown of resources is arguably less essential.");
2770 assert((!m_locked_gap_mutex) && "Tl_obj_db_client: We have a misdesign/bug; something is off thread-wise.");
2771 // We "even" skip the stats-saving stuff below. Just don't feel like dealing with anything in this odd situation.
2772 return;
2773 }
2774 // else
2775
2776 /* See explanation of identical thing in ~_admin() at identical spot. This is part of that same technique. Though:
2777 * Our situation is simpler in that there is only one way out of this dtor + only one place for our stat-shards
2778 * from m_per_arena_stats_shards to end up: Finalized_shards. (_admin dtor may need to instead start a replacement
2779 * thread + new _admin; we lack anything like that.) So yes: last thing we do is insert our shards into
2780 * Finalized_shards; then we return, right after unlocking this lock. */
2781 optional<Lock_guard<Mutex_recursive>> gap_lock;
2782 if (m_locked_gap_mutex) // See this guy's doc header for explanation about this guard.
2783 {
2784 FLOW_LOG_TRACE_LOCKED("Tl_obj_db_client: The Gap mutex is locked: adopting until dtor returns.");
2785 gap_lock.emplace(stat::thread_end_gap_mutex(), boost::adopt_lock);
2786 }
2787 else
2788 {
2789 FLOW_LOG_INFO_LOCKED("Tl_obj_db_client: The Gap mutex is *not* locked; presumably this is the OS/main thread; "
2790 "probably application exit()ing/typically post-main(); no real danger of concurrent "
2791 "stat-touching.");
2792 }
2793
2794 /* Similarly to ~_admin() execute any pending arena-forgettings. new_pool_data() does it regularly, but by
2795 * its nature it might simply not be called even once after a forgetting_shm_arena(), before thread-exit ends
2796 * it all. So we hoover it up.
2797 *
2798 * Don't bother checking the flag -- just assume it is armed (thread exit is infrequent; the scan is cheap
2799 * when nothing is pending) -- and delete the state to do with arena(s) whose destruction is in-progress. */
2800 if_requested_forget_arena_related_resources(true);
2801
2802 /* *this exists specifically to execute this thread's SHM-pool use_ct++ and use_ct--, because the objects
2803 * involved were constructed in some other thread. So by definition our thread exiting means nothing we do
2804 * matters from this point on... except the stats-dumping. So just clean up all the resources; that's it...
2805 * aside from the stats-dumping. */
2806 FLOW_LOG_INFO_LOCKED("Tl_obj_db_client: Thread exiting; will simply close any lend-tracker SHM-pool client handles "
2807 "we've opened.");
2808
2809 // Note: Lend_tracker_pool (client-type) dtor does not perform removal of pool name from file-system.
2810
2811 if (!m_per_arena_stats_shards.empty()) // Don't even touch it, if all arenas already forgetting_shm_arena()ed away.
2812 { /* Stats.
2813 * Last thing is we have to do this stats-related procedure, so that the stats we've accumulated do not go *poof*.
2814 * Take a particular Shm_arena A and, say, stats_shard->m_lend_obj.m_lend_count we've counted in
2815 * m_per_arena_stats_shards[A]. That shard is merely a shard for the
2816 * thread that is now exiting; arena A may well still exist, and
2817 * our contribution to m_lend_count at stat-consumption that counted a split-second ago should equally count a
2818 * split-second after the dtor exits and thread exits. It should keep counting until that arena goes
2819 * away, at which point all such contributions would be thrown out (for cleanliness/leak avoidance).
2820 *
2821 * At any rate: Finalized_shards takes care of it; we just have to give it whatever
2822 * arena/stats pairs we've got still, before they go *poof*.
2823 *
2824 * There is one caveat, analogous to (though a bit simpler than) ~_admin() dtor's similar short time window:
2825 * Right now `this` has been removed from the Thread_local_state_registry<_client>, so our stats
2826 * won't participate in any aggregation. We'll fix that via _finalized_shards soon, but in the meantime
2827 * stat-consumption and stat-resetting will be incomplete if executed right now... but that is why
2828 * we're doing the thread_end_gap_mutex() thing above. So in fact if it's executing right now then it is waiting
2829 * for that lock to become available; all is cool.
2830 *
2831 * Lastly: There could be another caveat, again sorta-analogous to ~_admin()'s: During this time window
2832 * forgetting_shm_arena(), in looping through extant `_client`s, will not see `*this`. Is it an issue?
2833 * The answer is no-ish. There's no *this needing access to the arena itself, nor is there any
2834 * replacement _client possibility; _client::forgetting_shm_arena(A) is only about erasing each
2835 * m_per_arena_stats_shards[A], for cleanliness + avoiding small RAM-leak. So before this ongoing teardown,
2836 * [A] would be erased fine (at the latest by the if_requested_forget_arena_related_resources() above); after
2837 * it, Finalized_shards::stats_erase(A) will clean it out of Finalized_shards (where we would have put it just
2838 * below). During it -- The Gap -- though, it would leak into Finalized_shards where it would stay forever.
2839 * It's certainly a bit ugly and slightly leaky but not really a big deal practically speaking... as of this
2840 * writing. That said formally we disallow it. 1, ugly+leak = let's not. 2, in _admin() it is a *real*
2841 * problem, and for that one we disallow it... but _admin and _client teardowns are part of the same thing,
2842 * really: in practice _admin::f_s_a() and _client::f_s_a() are called one after the other in Shm_arena (e.g.,
2843 * jemalloc::Ipc_arena) shutdown. So let's just avoid all this entropy. No forgetting_shm_arena() during
2844 * _client teardown (now). */
2845
2846 // (No need to lock. As noted, stat-consumption TL-state walk won't see us by now.)
2847 for (const auto& [collection_id, stats_shard] : m_per_arena_stats_shards)
2848 {
2849 stat::Finalized_shards<Shm_arena>::get_instance().stats_insert(collection_id, *stats_shard);
2850 }
2851 } // Stats.
2852
2853 // stat::thread_end_gap_mutex() unlocks here.
2854 } // Thread_lcl_obj_db_client::~Thread_lcl_obj_db_client()

2885template<typename Shm_arena_t>
2886void Thread_lcl_obj_db_client<Shm_arena_t>::disposing_obj(const Shm_arena& shm_arena,
2887 pool_id_t lend_tracker_pool_id, use_ct_idx_t use_ct_idx)
2888{
2889 using flow::util::stat::fetch_add;
2890 using flow::util::stat::fetch_sub;
2891
2892 // This is the owner-side disposer action in non-admin (i.e., allocating, for the given object) thread.
2893
2894 const auto it = m_lend_tracker_pools.find(lend_tracker_pool_id);
2895 const auto pool_data = (it == m_lend_tracker_pools.end()) // ? slow-path : fast-path
2896 ? new_pool_data(lend_tracker_pool_id, util::Process_credentials::own_process_id(),
2897 shm_arena.get_id(),
2898 Owner_spc_impl<const Shm_arena>{shm_arena}
2899 .generate_shm_object_name(lend_tracker_pool_id))
2900 : it->second.get();
2901 pool_data->m_lend_tracker_pool.use_count_dec(use_ct_idx); // It logs enough.
2902 /* Even if it reached 0, it'll require ..._admin counterpart to complete the disposal of the object
2903 * in the proper thread. ->m_lend_tracker_pool did try to help it do so faster by writing some hint stuff. */
2904
2905 { // Stats.
2906 auto& owner_obj_stats = stats_shard(shm_arena)->m_owner_obj;
2907 fetch_add(&owner_obj_stats.m_disposer_count, 1);
2908 fetch_sub(&owner_obj_stats.m_live_handle_groups, 1);
2909 }
2910
2911 /* Slow-path only (new_pool_data() called above): Mini-discussion about error handling:
2912 * What if it threw, as (per contract) it can? The cause can be split into 2 categories; in all cases only

3329 * to _finalized_shards -- is our (and _admin's) own Shm_arena tparam. I.e., both the _admin and the _client
3330 * for the SHM-provider (SHM-jemalloc being one of them; Shm_arena = jemalloc::Ipc_arena) dump their

3332 * Where the stats come-from doesn't matter; they're all aggregated-together anyway as shards.
3333 *
3334 * So the stats_insert() just has to happen once, when the given arena is being forgotten. Since
3335 * _admin is the big daddy, if it has to be one of us, it should be _admin.
3336 * @todo Though (very) arguably, perhaps it would be safer maintenance-wise to do it in both places
3337 * anyway, since both *do* dump shards in there. Revisit maybe. */
3338 }

3341template<typename Shm_arena_t>
3342void Thread_lcl_obj_db_client<Shm_arena_t>::if_requested_forget_arena_related_resources(bool assume_requested)
3343{
3344 using flow::util::Lock_guard;
3345 using std::vector;
3346
3347 /* Avoid logging work, or any unneeded work of any kind, in our fast-path... though as of this writing
3348 * we are only invoked from new_pool_data() (which by definition is not the fast-path of lending_obj() or
3349 * disposing_obj() (owner-side)) and from our dtor. So we're already not called that often. */
3350
3351 if ((!assume_requested) && (!m_forget_resources_requested_poll_flag.poll_armed()))
3352 {
3353 return;
3354 }
3355 /* else if (it was requested) || assume_requested: We will do it.
3356 * Unless assume_requested: It is now re-marked as not-requested. */
3357
3358 // Non-fast-path is in effect (can log, etc.).
3359
3360 s_state.m_arenas_to_forget_map.while_locked([&](auto* arenas_to_forget_map_ptr)
3361 {
3362 auto& arenas_to_forget_map = *arenas_to_forget_map_ptr;
3363 vector<collection_id_t> finished_collection_ids;
3364
3365 for (auto& collection_id_and_db_set : arenas_to_forget_map)
3366 {
3367 // (See similar C++17/20 note higher up in similar situation.)
3368 const auto collection_id = collection_id_and_db_set.first;
3369 auto& db_set = collection_id_and_db_set.second;
3370
3371 if (db_set.erase(this) == 0)
3372 {
3373 continue; // This collection/arena being forgotten is (no longer?) dependent on our deleting it from *this.
3374 }
3375 // else
3376
3377 const bool last_one = db_set.empty();
3378 bool erased;
3379 {
3380 /* The goal of all this unpleasantness is in this block. To repeat our doc header Impl mini-section:
3381 * We change the key-set of m_per_arena_stats_shards; and therefore we must lock it; but the fact
3382 * we do so in the proper thread w/r/t *this -- and no other thread changes the key-set -- means
3383 * that when *reading* m_per_arena_stats_shards in the lending_obj()/disposing_obj() fast-paths we
3384 * don't need to lock said mutex.
3385 * @todo Honestly... locking that mutex there, under zero contention, is pretty damned cheap; and then
3386 * forgetting_shm_arena() would be just a few lines and synchronous at that; the present method
3387 * wouldn't exist at all. The gain in simplicity/maintainability might be worth it. Revisit. */
3388 Lock_guard<decltype(m_per_arena_stats_shards_mutex)> lock{m_per_arena_stats_shards_mutex};
3389 erased = (m_per_arena_stats_shards.erase(collection_id) == 1);
3390 }
3391 if (erased)
3392 {
3393 FLOW_LOG_INFO_LOCKED("Tl_obj_db_client: Local arena/collection [" << collection_id << "] is being "
3394 "forgotten; so will forget related tracking structures in heap; are we the last "
3395 "per-thread obj-DB that was remaining to do this? = [" << last_one << "].");
3396 }
3397 // else { For the arena-being-forgotten, we don't have any data anyway. }
3398
3399 if (last_one)
3400 {
3401 FLOW_LOG_INFO_LOCKED("Tl_obj_db_client: Local arena/collection [" << collection_id << "] is being "
3402 "forgotten; opportunistically scanned our per-thread in-heap structures, and this was "
3403 "the last such per-thread structure that needed handling; so this completes the "
3404 "forgetting of that arena/collection among the obj-DB per-thread clients.");
3405 finished_collection_ids.push_back(collection_id);
3406 }
3407 } // for ([collection_id, db_set] : arenas_to_forget_map)
3408
3409 // Clean out the entries we made empty (arena-IDs such that nothing left to do for it; arena forgotten).
3410 for (const auto collection_id : finished_collection_ids)
3411 {
3412 arenas_to_forget_map.erase(collection_id);
3413 }
3414 }); // s_state.m_arenas_to_forget_map.while_locked()
3415} // Thread_lcl_obj_db_client::if_requested_forget_arena_related_resources()
