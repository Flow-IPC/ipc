Detailed Description

Wrapper around jemalloc.

This is a thin wrapper around the jemalloc API: used by SHM-jemalloc for its internal impl purposes but available for direct end user calls as well.

Purpose

It is usable directly as a small jemalloc wrangler. That is, it can make easier some of the more advanced activities, like working with custom-made arenas, including the surprisingly tricky business of destroying one safely. The stats-dump helpers like stats_dump_to_string() and stats_dump_to_ostream() are potentially nice too. (However they're also available through Ipc_arena::info_dump().) Last but not least, using this wrangler instead of direct jemalloc-API calls can avoid certain jemalloc landmines not yet fixed as of jemalloc-5.4.0 (see below).

It won't block access to the actual jemalloc API.

That said, the main purpose of its existence is for the SHM-provider SHM-jemalloc (see ipc::shm for overall intro to Flow-IPC's SHM-providers) to implement its services. For example Ipc_arena::construct() and Ipc_arena::allocate() will use Memory_manager::allocate(), while Ipc_arena::create() will create_arena() while hooking up its SHM-wrangling extent hooks that would execute as part of allocate() at times.

The public access to these goodies seemed worthwhile as well, so we made it user-facing.

See also
also Thread_cache which provides a related, and fairly sophisticated, wrangler of the jemalloc tcache system. How to properly use the jemalloc tcache feature is not necessarily obvious, especially so if custom arenas with arbitrarily overlapping finite lifetimes are involved. Things are prone to crash – and not necessarily right when one does the wrong thing but, in some scenarios, later.

SHM-jemalloc versus direct use of jemalloc

Using jemalloc directly ("directly" in this case includes calls through Memory_manager) is possible with or without using SHM-jemalloc (centered on Ipc_arena) in parallel. As far as conflicts of using jemalloc directly versus SHM-jemalloc in parallel:

  • SHM-jemalloc [de]allocates() only through jemalloc-arenas it creates/destroys/manages by itself; never through the default arenas (i.e., it would not do a regular jemalloc-malloc() but rather always specifies some arena ID it itself maintains). This holds whether or not jemalloc is also your default malloc()/free()/new/delete for regular heap purposes.
  • Certain global (as opposed to per-arena) jemalloc config options are required for SHM-jemalloc to work properly. In some cases this is something we enforce programmatically: by emitting an error if something is set wrong (best-effort). Otherwise we assume the default/common setup is what is in effect and proceed under that assumption (see below todo). As of this writing the checking/emission occurs in Ipc_arena::create().
Todo:
While the current SHM-jemalloc impl is thought to play nicely with other parallel jemalloc use (such as for vanilla heap allocation) – with all allocation segregated into separately maintained jemalloc-arenas and with only very few enforced global option-setting requirements – we should methodically explore and document what exactly SHM-jemalloc requires of the jemalloc config (both compiled-in and dynamically settable options). Things are OK given a standard jemalloc build, within a fairly wide (calendar-wise) version range, and we check some (a small # of) global settings we know we require, but a methodical analysis in the guts of SHM-jemalloc might yield more and save users some pain.

Stats-dump versus arena creation/destruction

We offer a thin wrapper for jemalloc's stats-dump-to-string dump feature (malloc_stats_print()): stats_dump_to_ostream(), stats_dump_to_string(), log_stats_dump(). It turns out that malloc_stats_print() is likely to crash (abort with a message like <jemalloc>: Failure in xmallctlbymib() and variations), if concurrently an arena is being destroyed or (conservatively speaking) created. (This is not fixed, or counted as a bug, as of jemalloc-5.4.0 (9/2026).)

SHM-jemalloc works around it (internally by using a process-wide mutex), so as long as one uses our APIs (Flow-IPC generally for SHM-jemalloc arena control as needed, naturally; Ipc_arena::info_dump() or Memory_manager::*stats_dump*() for stats-dumping), one is safe from this problem. Just be warned that using these jemalloc APIs directly (for whatever reason) can lead to trouble, as direct calls will not know to collaborate with Flow-IPC's use of the internal mutex; and Flow-IPC may itself create/destroy arenas and dump stats at various times.

void ipc::shm::arena_lend::jemalloc::Memory_manager::stats_dump_to_ostream ( std::ostream &  os = std::cout,

Writes a broad, raw, process-wide jemalloc statistics dump (all arenas) to os.

Thin wrapper around jemalloc malloc_stats_print(). For curated, typed, per-Flow-IPC-arena stats use jemalloc::Ipc_arena::memory_manager_stats() instead; this dump is the complementary "everything jemalloc knows" firehose of information.

The output ends in a newline. No bracketing text is added by us: it all comes from jemalloc. (OK, fine, for Stat_format::S_JSON we add a newline at the end.)

If the linked jemalloc was built without statistics support (a configure-time option, --disable-stats, reported at runtime by the read-only config.stats option), the output is still well-formed and non-empty. Roughly, it'll include at least things like jemalloc version + build config + settings but will omit per-arena runtime statistics (alloc counts/bytes, bins/large/extents/mutex).

Note
Relatedly: our curated stats-accessor, Ipc_arena::memory_manager_stats(), will also produce nominally non-empty output, if jemalloc not built with stats support, but essentially it'll be zeroes all-over.
Parameters
osStream to which to write. Defaults to standard output.
formatFormat of the output. Defaults to human-readable text.
extra_optsIf not empty: appended verbatim to jemalloc's malloc_stats_print() options string (its flag letters toggle output sections – merged-vs-per-arena, bins/large/extents/mutex; see jemalloc docs).
