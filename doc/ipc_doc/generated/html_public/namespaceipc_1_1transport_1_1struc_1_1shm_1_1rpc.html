Detailed Description

Provides Flow-IPC's integration with Cap'n Proto's Remote Procedure Call (RPC) layer, wherein one can perform all the cool, promise-pipelined, interface-and-callback-happy RPC provided by capnp-RPC – while enjoying the zero-copy performance provided by Flow-IPC's SHM features.

Naturally this works for IPC-RPC local to one machine (as SHM is local to one machine) – not networked – but one should be able to slot-it-in painlessly whenever no network is involved; and revert to normal networked capnp-RPC otherwise; with only a handful lines of code different between the two.

Generally speaking, here is how this module relates to a few other key modules:

  • struc::shm::rpc implements capnp-RPC interfaces and concepts, so that one can use capnp-RPC as normal – but zero-copy-enabled (plus some added niceties, namely optional ipc::session support in peer-process discovery and session establishment/termination).
  • struc::shm::rpc layer sits on top of Flow-IPC's SHM-enabled structured-transport layer, ipc::transport::struc::shm. Notably, to zero-copyify vanilla capnp-RPC, internally it makes use of public APIs shm::Capnp_message_builder and shm::Capnp_message_reader (which themselves implement key interfaces capnp::MessageBuilder and capnp::MessageReader, respectively, in capnp's lower serialization layer).
  • struc::shm::rpc is a cousin of, and an alternative to, struc::Channel (+ struc::Msg_out, struc::Msg_in): both carry capnp-encoded data between processes with zero-copy performance; they differ in programming model. See just below.

capnp-RPC versus struc::Channel

struc::Channel transmits a stream of the user's own capnp-encoded messages (and, optionally, native handles), adding message-type demultiplexing and request/response. It is simple to set up, simple to reason about (including in terms of perf), and can be slotted into nearly any event loop.

capnp-RPC is semantically far more powerful: function-call-like semantics on remote objects (capabilities), callbacks, and promise pipelining ("time travel"). It is also an established, mature API in its own right; Flow-IPC "merely" provides the zero-copy plumbing underneath (plus optional ipc::session integration). The price is that one uses, or integrates with, the KJ promise-based single-threaded event loop.

Both are viable. (The struc::Channel doc header contains a similar comparison from its point of view.)

Map of this namespace

From highest-level (easiest to use) to lowest-level:

  • Ez_rpc_client, Ez_rpc_server: analogous to capnp's EzRpcClient, EzRpcServer. They set up everything, including the KJ event loop, in a few lines.
  • Client_context, Context_server (which yields Server_contexts): establish the Flow-IPC session (including SHM) with the opposing process and supply the VatNetwork; you create and drive the capnp::RpcSystem yourself.
  • Session_vat_network: the core: Flow-IPC's implementation of capnp::VatNetwork; essentially capnp::TwoPartyVatNetwork but with zero-copy. The above classes use it internally.

Learning capnp-RPC; examples

How to use capnp-RPC itself is outside our scope here. See https://capnproto.org/rpc.html and https://capnproto.org/cxxrpc.html; and capnp's Calculator sample (c++/samples/calculator-*). Flow-IPC's test/suite/rpc_demo program replicates that sample using the classes above.

The guided Manual chapter Zero-copy capnp-RPC covers these topics.

◆ Rpc_conn

using ipc::transport::struc::shm::rpc::Rpc_conn = typedef ::capnp::TwoPartyVatNetworkBase::Connection

Flow-IPC-styled alias for Session_vat_network and TwoPartyVatNetwork's "connection," which is an interface for essentially an RPC-oriented stream of capnp messages – a relatively thin layer on top of the capnp::MessageStream interface.

The latter is a general stream of capnp messages. Incidentally capnp::MessageStream is something like capnp's version of our transport::struc::Channel.

It is unlikely the typical RPC user needs to work with this; but if one extends the RPC system (such as we did with Session_vat_network et al), this might be helpful.

◆ Vat_id

using ipc::transport::struc::shm::rpc::Vat_id = typedef ::capnp::rpc::twoparty::VatId

Flow-IPC-styled alias for the node ID in a Session_vat_network or TwoPartyVatNetwork: namely an enumeration containing SERVER and CLIENT.

Incidentally we remind you: Much like in ipc::Session the server-vs-client dichotomy carries no meaning, once a session is established (is in PEER state), similarly by-and-large this ID is just a node ID. A server can do client-like things and vice versa... etc.

It is unlikely the typical RPC user needs to work with this; but if one extends the RPC system (such as we did with Session_vat_network et al), this might be helpful.
